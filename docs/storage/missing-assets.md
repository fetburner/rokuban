## 孤児回収の逆: 実体無し検出（§7 の一部）

実体ファイルが無いのに active な行は、記録して Warn ログとゲージで報告するだけで、自動では消さない。「ファイルが無い」は削除の必要条件であって十分条件ではないので、実削除の判断は人間に委ねる。

孤児回収は「ファイルはあるが、`storage.stores` の FS 置き場（FS 置き場は今 1 つだけ。[置き場の規則](../configuration/keys.md#置き場の規則)）の `media_asset_copies` に対応するパスが無い」を追う。逆方向の、`state = 'active'` なのに実体ファイルが無いコピーを検出する経路が無く、行の内容が実体と違っていても誰も気付かない穴があった。不変条件 3（コミット = DB 行）は行の内容が実体と一致することを要求するだけで、それを検証する経路までは要求しない。この穴は不変条件そのものの欠陥でなく、検出器の不在だった。

削除 reconcile パスが孤児回収と同じ 1 回のディレクトリ走査結果を使い、逆方向にも突き合わせる。その置き場の `media_asset_copies.state = 'active'` の行のうち、走査でファイルが観測されなかったものを `missing_media_assets` に記録する。パスと状態はコピー表から読み、録画 ID と種別は論理資産の `media_assets` から読む。

この表は `orphan_files` の鏡像で、行の存在 = 直前のパスで実体を観測できなかったという主張を表す。記録の主キーは物理コピーの ID である。同じ論理資産に複数の世代や置き場があっても、観測したファイルだけを個別に記録できる。記録は Warn ログと `rokuban_media_assets_missing{kind}` ゲージに出す。自動では一切消さない。孤児回収と同じ非対称で、手動削除・バックアップからの部分復元・FS の破損・別プロセスのトラブルのいずれでも「ファイルが無い」は起きるためである。

`orphan_files` は `(store, rel_path)` で置き場ごとの観測を分ける。移行前の行は `store` が空で、`storage adopt <store-name>` が割り当てる。`store` が空の行が残る間、worker は起動を拒む。

サーキットブレーカーは持たない。孤児回収・`until_encoded` の安全弁は「大量削除という不可逆な操作」を止めるためのものだが、この検出は削除を一切行わないので止める対象が無い。

### 検出の安全弁

実体無しの検出は、誤った置き場を見た「無い」の誤報を、置き場の目印とエイジングで抑える。

worker は media root の `.rokuban-store` の内容を、`storage.stores` の FS 置き場の名前と照合する（FS 置き場は今 1 つだけ。[置き場の規則](../configuration/keys.md#置き場の規則)）。目印が無い・読めない・名前が違うときは、その操作を見送り、`rokuban_store_marker_mismatch_total{store}` を増やす。目印は走査の対象から除く。

照合する場面は 2 つある。1 つは、パスを解決するファイルシステム操作（作成・mkdir・unlink・lock file の作成）の直前である。もう 1 つは、「無い」を観測した後に DB へ書く直前（実体無しの記録・削除済みの確定・孤児記録の削除）である。Stat・走査・既存ファイルの open は、誤った置き場に向いても何も書かないので、その前では照合しない。結果を使う決定が、それぞれ直後に照合を持つ。

開いた fd への write・Sync は、fd が別の置き場へ移らないので照合しない。rename の前後も、temp が照合済みの置き場にあるので照合しない。

目印が確認するのは media root だけである。一部だけを mount した構成でそのサブツリーが消えても、root の目印は残り、見送りは起きない。実体無しの検出は、死んだサブツリー配下の `active` 行を、エイジング後に確認済みとして報告する。ごみ箱などで削除の対象になった資産は、`ErrNotExist` から削除済みの確定まで進む。

エイジングでは、候補は `first_seen` を記録し、既定 24 時間連続で観測され続けたものだけを確認済みとして報告する（`missing_asset_age`）。これは単発の走査揺れを異常と区別するためである。孤児エイジングの 14 日と揃える必要はない。削除の猶予でなく通知の遅れを抑える値なので、短めにしている。

`storage.stores` に FS 置き場が無い構成では目印を照合せず、全損シグネチャで見送る。全損シグネチャは、「この 1 回の走査でファイルを 1 件も観測できなかったのに `active` な行が存在する」という形である。これは件数の閾値でなく、reconciler の `breaker.ReconcileTotalLoss` と同じ考え方である。検知したパスは記録を丸ごと見送り（`rokuban_missing_asset_scan_suspected_storage_failure_total` が進む）、既存の確認済み候補にも触れない。疑わしいパスの結果で前回までの状態を上書きしない。

この形が「マウントが落ちている」を捕まえられるのは、1 マウント = `media_dir` 全体という構成でだけである。判定に使うのは、走査が観測した全ファイル（`catalog/` 以外）の件数である。そのため `media_dir` 直下がローカルディスクで、その下のサブツリーだけがマウントされている場合（アーカイブ階層だけが落ちる部分マウント障害）は発動しない。`.DS_Store` / `lost+found` / mtime が新しくて孤児回収も消せない残骸が 1 個でもある場合も、`0 件` にならず発動しない。

その場合は、死んだサブツリー配下の active コピーが全部、エイジング後に確認済みとして報告される。報告は削除を伴わないので、この検出の被害は騒音のみである。一方、削除の対象になった資産は、旧構成でも `ErrNotExist` から削除済みの確定まで進む。マウント単位で判定する形にはしていない。`media_dir` 配下のどこにマウント境界があるかは設定にも `rel_path` にも現れず、Rokuban はそれを知らない。

### 走査が見ないパス

同じ走査を逆向きに使うと、走査の除外の誤りの向きが反転する。除外されたパスや、走査が辿らないシンボリックリンクの先の資産は、恒久的に「実体無し」と誤報される（シンボリックリンクの側は未検証）。削除はしないので被害は騒音のみで、走査の除外を足すときは、この誤報も確認する。

孤児方向では除外は安全側で、除外されたパスは孤児候補にならない＝削除されない。逆方向では、除外されたパスの資産が恒久的に「実体無し」と誤報される。

走査は root の `.rokuban-store` と `.rokuban-locks` も除く。`mediapath.Resolve` は root の `.rokuban-store` と `.rokuban-locks` 配下を `ErrReservedMediaPath` で拒む。ingest・encode・削除・in-place 登録・rescue はこの関数を通るので、これらを指す `rel_path` の行は作れず、操作の対象にもならない。ネストした `x/.rokuban-store` は拒まず、走査も除かない。

走査は `catalog/` を SkipDir する（[contract.md](contract.md) §5 のトップレベル予約ディレクトリ）。誤報は 15 分ごとの Warn とゲージが下がらない形で現れる。今日は該当する `rel_path` が存在しない。だがそれは「既存行が予約ディレクトリを先頭成分に持たない」という contract.md §5 自身が但し書きを付けている前提の上の断定である。走査の除外を足すときは、削除側だけでなくこちら側の誤報も確認する。

同型の穴が「走査が降りないディレクトリ」の側にもある。走査は symlink を辿らない。書き込み・読み出し側のパス解決は字句的である（`filepath.Join` + 接頭辞検証）。`media_dir` 配下のディレクトリ成分を symlink にして別ボリュームを合成する構成では、書けて読めるのに走査からは見えないサブツリーができる。その配下の資産が恒久的に誤報される（未検証。symlink を張った構成のテストは無い）。

走査側で辿る形にはしていない。循環と、`media_dir` の外を指す symlink（`rel_path` が契約上の名前空間の外のファイルを指すことになる）の扱いを先に決める必要があり、この検出器の範囲を超えるからである。合成が必要ならディレクトリ成分の symlink でなくマウントを使う。
