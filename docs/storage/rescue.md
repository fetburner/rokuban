## 8. catalog エクスポートと rescue（災害復旧）

### 保護対象の仕分け

失うと痛いデータを仕分けすると、EPG プロジェクションは mirakc から再構築可能、ジョブキューは一時的で、**保護対象は「ルール・録画履歴・media_assets・ドロップ統計・tombstone・手動オーバーライド」のみ（数 MB）**。

### catalog エクスポート

- worker の定期ジョブが、このコアデータを JSON で**メディアストレージ自身の `catalog/` 配下に書き出す**（日次 + 世代保持）。メディアが生き残る障害では catalog も一緒に生き残る
- pg_dump に依存しない（distroless イメージに postgres クライアント不要）アプリレベルのエクスポートで、後述 rescue の入力形式を兼ねる
- フル忠実度が欲しい場合の日次 pg_dump 構成例はドキュメントに記載（推奨・非必須）

### 世代の完成判定（rescue が読んでよい世代の定義）

通常の media asset は `media_assets` 行の INSERT を公開点にできる（§3 ルール 3）が、**DB 喪失時に使う catalog は DB を公開点にできない**。ファイルが `catalog/` に見えることは何の宣言でもない —— 書きかけ・停止途中・S3 の非アトミックな置き換えの途中が同じ見え方をする。そこで catalog は**ストレージの中だけで完結する公開点**を持つ。

**1 世代 = 1 ディレクトリ。**

```
catalog/
  catalog-20260801T030000Z/     ← 世代ディレクトリ（この名前は二度と再利用しない）
    catalog.json                ← 本体
    manifest.json               ← 完成宣言。世代データを全部書き終えた後に最後の一発書きで置く
  catalog-20260802T030000Z/
    ...
```

**完成世代 = 次を全部満たす世代**（1 つでも欠けたら不完全。rescue は選ばない）:

1. `manifest.json` が存在し、**JSON として最後まで parse できる**
2. `manifestVersion` がこのバイナリの理解する版以下
3. `schemaVersion`（世代が載せている catalog document の版）がこのバイナリの読める版以下
4. `generation` が世代ディレクトリ名と一致する
5. `document`（本体ファイル名）が `files[]` に載っている
6. `files[]` の**全項目**が存在し、**サイズと sha256 が両方一致する**

判断の根拠:

- **公開点は「manifest を書き終えたこと」であって rename ではない。** §2 の通り S3/FUSE にアトミック rename は無い（Mountpoint は rename 自体が無い）ので、`latest` を差し替える・一時名から最終名へ移す、はどちらも公開点に使えない。本体も manifest も**最初から最終名へ一発書きする**（§3 ルール 1）。順序（本体 → fsync → manifest）だけが公開のプロトコルになる
- **manifest を先に書くと完成宣言にならない。** 先に置いた manifest は「これから書く予定」しか主張できず、途中停止と区別が付かない
- **manifest 自身が途中で切れても安全側に倒れる。** 途中まで書かれた JSON は閉じ括弧を欠いて parse に失敗し（判定 1）、たとえ parse できても本体の sha256 検証（判定 6）を通らない限り完成扱いにならない。manifest 自身の checksum は自己参照になるので持たない —— **manifest の正しさは「本体を言い当てられているか」で測る**
- **parse 成功だけでは足りない。** JSON 文字列の中の 1 バイトが化けた本体は parse に成功する（`TestVerifyGeneration_RejectsSilentByteFlip` が実測: parse は通り、sha256 だけが不一致になる）。また複数ファイル世代になったとき、parse は「隣のファイルが無いこと」を検出できない。だから**サイズと sha256 と `files[]` の網羅**を判定に入れる
- **世代名は再利用しない。** 同じ秒に 2 回書くことになったら `-2`, `-3` と連番を足して別の世代を作る。既存の完成世代を上書きしに行かないので、「書き直しの途中で前の完成世代も壊れる」窓が無い

### rescue の世代選択とフォールバック

`rokuban rescue` は次の順で入力を選ぶ:

1. 世代ディレクトリを**新しい順**に完成判定に掛け、**最初に通った世代**の本体を読む。落ちた世代は理由付きで warn ログに出す（黙って古い世代に落ちない）
2. 完成世代が 1 つも無ければ、manifest を持たない**旧形式のフラットな `catalog-*.json`**（世代ディレクトリ導入前に書かれたもの）を新しい順に読めるだけ読む。これは**検証不能な最後の手段**で、選んだら warn ログに出す。旧形式のファイルを新たに書くことはない
3. それも無ければストレージスキャン（次節）

つまり**最新世代が不完全・checksum 不一致なら 1 つ前の完成世代から復元する**。「最新に見えるもの」ではなく「最新の**検証済み**」を選ぶ。

### 不完全世代の保持と掃除

- **完成世代（+ 旧形式ファイル）を新しい順に `keep` 件（既定 7）残す。** それより古いものは削除する
- **不完全な世代は「それより新しい使える世代がある」ときだけ削除する。** 最新側にある不完全世代は**進行中のエクスポートかもしれない**ので消さない。次のエクスポートが成功した時点で「より新しい完成世代」ができ、そこで掃除される
- **エクスポートが途中で失敗しても、書きかけの世代ディレクトリを消しに行かない。** プロセスが落ちる形の停止では後始末は走らないので、**後始末が走ることを正しさの前提にしない**（走るときだけ綺麗になる、では判定基準にならない）。掃除は上のルールに一本化する
- 不完全世代は容量を食うが、保護対象は数 MB 規模（本節冒頭）なので、進行中と区別できないものを消す危険と釣り合わない

### rescue --- ストレージスキャンからの再構築

`rokuban rescue`: ストレージを走査し、

- `catalog/` があれば照合してフルメタデータ（番組情報・ドロップ統計・保持ポリシー）ごと復元
- catalog が無ければ TS / M2TS を `original`、MP4 / MKV / WebM を `encoded`
  （`profile = rescue-<拡張子>`）として、現在位置のまま登録する。タイトルと時刻は
  ファイル名 / mtime、番組・サービス情報は「metadata unavailable」と明示した素の録画になる
- `catalog/` 自身、未知拡張子、symlink は走査対象にしない。ファイル本体はコピーも変更もしない
- 同じ相対パスは安定した合成番組 identity へ写し、再実行しても録画・asset が増殖しない

登録トランザクションは `internal/inplace` に置き、`rokuban import epgstation` も同じ
in-place 登録機構を使う。DB 行のコミットが公開であるというストレージ契約は通常 ingest と同じ。

### Postgres 運用

世帯スケールでは catalog（+ 任意で日次 pg_dump）で十分。WAL アーカイビングは過剰。

## 経緯と失敗事例

- 世代ディレクトリ + manifest による完成判定は issue #180。それ以前は `catalog/` 直下にフラットな `catalog-<時刻>.json` を「一時名 → rename」で置いており、**完成した世代と書きかけを区別する手段が無かった**（rename のアトミック性は §2 の通り S3/FUSE では成立しないので、最終名のファイルが途中の中身を持ちうる）。rescue はファイル名の辞書順で「最新」を選ぶだけだったので、**書きかけを選びうる**状態だった
