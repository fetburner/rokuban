# 不変条件 9〜14 の失敗の形

CLAUDE.md の不変条件 9〜14 は、チェックの一文だけを持つ。この文書は、そのチェックが何を止めているかを置く。いま同じ列・同じ JOIN・同じ表を足そうとしたときに先に浮かぶ案と、それが壊すものである。

間違えそうになったとき、あるいはルールの根拠を辿りたいときだけ読む。コードを書くときの判断は、CLAUDE.md のチェックで足りる。

番号は追加のみで、既存の 1〜8 は docs が番号で参照しているので振り直さない。

## 9. 導出値と不可逆な事実を同じ列に載せない

毎パス再計算される値と、二度と再取得できない事実を 1 つの列に同居させると、**導出側が事実を上書きする。** 混同は、列だけでなく identity・式・適用の瞬間にも起きる。

### 列

同じ列に載せたくなる組は 3 つあり、今でも先に浮かぶのは 3 つ目の形である。番組終了後に観測されなかったという事実と、ルールが供給しているかという導出値を、同じ列に載せる形である。同期の可否は実効値の skip で決める。

1 つ目は、「録る / 録るな」と「パラメータを上書きしたか」である。意図の列が NOT NULL なので「上書きだけ」を表現できず、掃除の判定が別表を見に行って誤答する。

2 つ目は、「ユーザーが手動予約したか」と「いまルールが base を供給しているか」である。導出器が前者を後者で不可逆に書き換え、永続資産（録画履歴の出自の列）に恒久的に漏れる。

3 つ目は、「番組終了後に schedule が観測されなかった」と「ルールが base を供給しているか」である。導出値（active / detached）が同期フィルタを兼ねるので、ルールが外れた手動予約が気づかないうちに録画されなくなる。

同期の可否を決めるのは effective.skip である。active / detached は同期の可否に使わない。

<details><summary>根拠</summary>

- 録画履歴の出自の列: `source`
- 同期の可否を決める値: `effective.skip`

- 導出値の状態: `active` / `detached`

</details>

### identity

API の宛先を導出物の id で指定すると、書ける意図が導出側の状態に依存し、導出し直しで id が変わると結合が切れ、除外やエンコード方針の参照が外れる。導出器が作るキーは使わず、外から与えられたキーで引く。

予約 id を宛先にすると、導出行が「無い」ときだけ作成 API が意図を書ける。逆に「ある」ときだけ削除 API が意図を書ける。そのため、base の skip を覆す「録れ」を立てる経路が存在しなくなる。

導出器が作るキーは、宛先にも、述語の結合キーにも、FK 経由の参照にも使わない。適用先は宛先だけではない。ここを「API のパスの話」と読んだために、録画行の予約 id への FK を経由するロジックが、同じ族のバグを繰り返し生んだ。壊れ方は 3 種ある。原因は共通で、**ruler の導出削除・再実体化で id が変わると結合が切れる**ことである。

- 「この予約に録画行があるか」の除外が引けなくなり、終了済み予約が毎パス desired に戻り続ける
- エンコード方針が NULL に落ちて、エラーを出さずにエンコードされない（ログにも出ない）
- 開始遅延検出器が「開始が観測済みか」を引けず、録画中ずっと誤検知する

チェックは、`WHERE a.x_id = b.id` を書くとき「この id は誰が作り、いつ変わるか」を問うことである。導出器が作るなら、放送イベント `(site, network_id, service_id, event_id)` や `(site, program_id)` のように、外から与えられたキーで引く。

同一サービス内の event_id は、イベント終了から 24 時間しか一意性を持たない（ARIB TR-B14 第四編 8.2.1）。そのため、録画の永続 identity は開始時刻を組にする。

読者を移設し終えても、その列は「便利な結合キー」の見た目を保ち続け、7 例目を書く手を止めるのはレビューの運になる。そこで、導出器が作るキーを保存する列は、読者を移設し終えたら DROP する。予約の id の列は DROP 済みである。チェックを「読むたびに問う」から「間違えられる列を無くす」へ一段強くした形である（不変条件 10）。

<details><summary>根拠</summary>

- 録画行から予約 id への FK: `recordings.reservation_id`
- 予約 id を宛先にしたときに覆せなくなる値: `base.skip`
- 一意性が 24 時間に限られるキー: `event_id`
- 結合に使うべきキー: `WHERE a.x_id = b.id`、`(site, network_id, service_id, event_id)`、`(site, program_id)`
- 永続 identity を持つ表: `recordings`
- DROP 済みの列: `reservations.id`

</details>

### 式

導出を docs に式で書いても、実装が列に遷移を保存すると、式の片側の分岐しか持たない。導出は読むたびに評価し、やむなく列に焼くなら両方向のテストを書く（CLAUDE.md「テスト規律」）。

式の例として、予約が detached になる条件を「ルールが無く、base がある」と書いても、実装が前パスの rule_id を見ていれば detached にならない。ルールを削除した経路（FK が先に rule_id を落とす）がその例である。

<details><summary>根拠</summary>

- 式の例: `detached ⟺ rule_id IS NULL AND base IS NOT NULL`

</details>

### 適用の瞬間

導出の判定をメモリに持って後で適用すると、その間に別の書き手が割り込む。**距離を作らざるを得ないなら、適用の側で判定条件を再評価する。**

ruler は削除対象を tx の外で計算してから tx 内で DELETE していたので、その窓に着地した手動予約（意図と予約行を 1 tx で書く）を消していた。読み順を入れ替えても窓は残る。対策は、削除文の WHERE に load-bearing 行の NOT EXISTS を置くことである。「1 つの表に書き手が 2 人いる」（不変条件 12）が見えたら、その 2 人の直列化契約も要る。

<details><summary>根拠</summary>

- 削除文の WHERE に置く条件: `NOT EXISTS`

</details>

## 10. 意味を持たない行を作らない

**行の存在そのものを主張として使う。** 「何も主張していない行」を作ると、それを掃除する規則が判断材料を別表に求めて壊れる。あってはいけない組み合わせは、禁止するより表現不可能にする方が強い。

実例は 4 つある。上書きの表は、空の上書きを行が無いことで表し、空の行を作らない。サーキットブレーカーの表は、行の存在が発動中を表し、「停止していない」を表す行は無い。再開は DELETE である。

エンコード方針と取り込み進捗の表は、行の存在が凍結済み・転送中を表す。列の既定値では、「まだ」と「空として確定した」が区別できない。即時削除の要求の表は、行の存在が「猶予を待たず今すぐ消してほしい」を表し、取り消し（復元）は DELETE である。時刻の列で持っていた頃は、書く値が常に現在時刻で、現在時刻以前でしか読まないのに、「未来の予約削除」に見えていた。

「あってはいけない組み合わせ」は、CHECK で禁止するより表現不可能にする方が強い。CHECK は覚えておくべき規則だが、表現不可能なら忘れようがない。

<details><summary>根拠</summary>

- 上書きの表: `program_overrides`（`{}` の行を作らない）
- サーキットブレーカーの表: `circuit_breakers`
- エンコード方針と取り込み進捗の表: `recording_encode_policy` / `recording_ingest_progress`
- 即時削除の要求の表: `recording_purge_requests`（時刻の列で持っていた頃の書く値は `now()`、読む条件は `<= now()`）

</details>

## 11. 形を固定する前に、その形を決める判定基準を書く

形を先に固定して判定基準を後から書くと、基準が来た時点でやり直しになる。M2 で 3 回起きた。最終形で切るのは永続資産と外から見える資源同定に限り、導出テーブルの列は書くコードと同じ変更で決める。

| 先に固定したもの | 後から来た判定基準 | 代償 |
|---|---|---|
| スキーマ v1「最終形で切る」 | 不変条件 9 / 10 | reservations のマイグレーション 6 本 |
| ロール分類 | ソケットを持ち続けるか | River ジョブ化と SSE の分離 |
| 多拠点への site 列 | API の資源同定（当時未決） | 複合 PK と全クエリの変更 |

1 つ目の代償は、reservations を 6 本のマイグレーションで変更したことである。churn を避けるための決定が、最も churn した表を生んだ。2 つ目は、ruler / reconciler / watcher をシングルトンロールとして並べたことである。ruler / reconciler / record_sweep の River ジョブ化と、api からの SSE 分離を払った。

3 つ目は、多拠点への site 列を、API の資源同定が未決のうちに入れたことである。複合 PK と全クエリの `$1` を払っているが、高い方（資源同定）が未払いの間は、利益（マイグレーション不要）が担保されていなかった。

派生する規律は 2 つある。1 つ目は、**「最終形で切る」の対象は、永続資産と外から見える資源同定（API のパスと識別子）に限る**ことである。永続資産は、録画・メディア資産・ドロップ統計・ルールの各表を指す。導出テーブルの列は、それを書くコードと同じ PR で決める。churn のコストが非対称だからである。永続資産のマイグレーションはデータ移行を伴って危険だが、導出表は再構築できるので churn がほぼ無害である。

2 つ目は、将来への先払いは高い方から払うことである。安い方（DB 列）を先に払っても、高い方（API の資源同定、クライアントのキャッシュキー）が未払いなら、利益は出ない。

チェック: 新しいテーブル・列・ロール・エンドポイントを足すとき「これを書く / 使うコードは今あるか」を問う。無ければ形を決めず、書き手と同じ PR に回す。

<details><summary>根拠</summary>

- マイグレーションで変更した表: `reservations`
- 多拠点の列とクエリの引数: `site`、`$1`
- 「最終形で切る」の対象の永続資産: `recordings` / `media_assets` / `drop_stats` / `rules`
- 導出テーブル: `reservations` / `*_sync` / 射影

</details>

## 12. 表は行の寿命で割る

**1 表 = 1 つの書き手 = 1 つの寿命。** 別の列へ分けるだけでは足りず、別表の恒久行へ移して初めて分離になる。分割の軸には、概念でなく寿命を取る。

不変条件 9 は列の粒度なので、行に寿命が混ざっているケースを網に掛けられない。

この規律の言語化を促したのは reservations で、この表の 1 行には 3 つの寿命が同居していた。

| 同居していたもの | 寿命 | 分離先 |
|---|---|---|
| ruler の導出出力 | ruler の 1 パス | ここだけであるべき（現在もここだけ） |
| 番組の事実のスナップショット | 放送 | program_snapshots |
| 不可逆な観測 | 永続 | recordings の試行行 |

導出出力は、base・rule_id・dedup 根拠である。番組の事実のスナップショットは、title・開始時刻・尺・チャンネルで、3 表に重複して既にドリフトしていた（同じ番組に異なる開始時刻が保存され、GC の判定が表ごとに違う時刻を使っていた）。不可逆な観測は「schedule が一度も作られなかった」で、導出値と同じ列にあった。

落とし穴は 2 つある。1 つ目は、分割の軸を「概念」に取ると 2 回に分かれることである。ユーザー意図を導出行から出す分割は、軸を「予約という概念」に取ったので 2 回かかった。軸を寿命に取れば 1 回で済む。

2 つ目は、「別の列に分離する」と「別の表に出す」が違うことである。不可逆な観測を専用列に切り出した段階では、表が同じままで、原則を守ったつもりで守れていなかった。別表の恒久行へ移して初めて、1 つ目の落とし穴だけが残った。

チェック: 新しい列を足すとき「この値はこの行と同時に生まれて同時に死ぬか」を問う。違えば、`(site, program_id)` を主キーにした別表にする。1 つの表に書き手が 2 人いるのも同じ兆候である。

<details><summary>根拠</summary>

- 3 つの寿命が同居していた表: `reservations`
- 導出出力の列: `base` / `rule_id`
- 番組スナップショットの分離先: `program_snapshots`
- 不可逆な観測の分離先: `recordings`
- 別表の主キー: `(site, program_id)`

</details>

## 13. 永続表に列を足すとき、書くループが脊椎の書き手でなければ衛星表にする

永続表は列も永続なので、寿命の問いは自明に真になり、列を足しても止まらない。そこで、列を書くループが脊椎の書き手かを問い、そうでなければ衛星表に置く。削除と置換の日時の列は、部分一意索引の述語が参照するので本体に置く。

不変条件 12 の寿命チェック（「この値はこの行と同時に生まれて同時に死ぬか」）は、永続表に対して盲目になる。永続表はどんな列を足しても、表自体が永続なので列も永続で、自明に真が返り、網に掛からない。録画の表が書き手 5 人（watcher / reconciler / ingest worker / api / delete reconcile）まで増えても、12 だけでは止まらなかった理由がこれである。

録画の表の本体は「試行の帰結の観測」だけを持つ脊椎で、別のループが書く状態は、録画 id を FK に持つ衛星表に置く。メディア資産の表がこの形の実例である。自分の書き手（ingest / encode / thumbnail の各 worker）と、自分の状態機械（有効 → 削除中 → 削除済み）を持つ永続の衛星表である。ドロップ統計の表は、メディア資産を指す「衛星の衛星」で、録画の表を直接 FK で指しておらず、状態機械も持たない。

チェックは、列を足すとき「この列を書くループは脊椎の書き手か」を問うことである（録画の表なら、試行を観測する watcher / reconciler）。**既にその表に書いているループ、つまり既存のテナントであることは根拠にならない。** 間借りが次の間借りを正当化してしまうからである。脊椎の書き手でないなら、その表の列にせず、録画 id などの対象行 FK を持つ衛星表にする。

<details><summary>根拠</summary>

- 脊椎の表: `recordings`
- 衛星表の実例: `media_assets`（状態機械は `active`→`deleting`→`deleted`）
- 衛星の衛星: `drop_stats`（`media_asset_id` で `media_assets` を指す）
- 衛星表が持つ FK: `recording_id`

</details>

### 原則の境界

削除と置換の日時の列は、部分一意索引の述語が参照するので衛星に出せない。番組スナップショットの列群は、一度だけ書かれるので脊椎に属する。分割の軸は書き手である。

原則は、絶対視して壊す方が高くつくので、境界を明記する。

削除日時と置換日時の列は、衛星に出せない。部分索引の述語は他表を参照できないからである。「ごみ箱 / supersede で枠が明く」という設計は、この 2 列が本体にいることを、一意索引の機構として要求している。この 2 列は、枠管理の一部であり、間借りには当たらない。

番組スナップショット列群は脊椎に属する。列数は多いが、watcher が行の作成と同時に一度だけ書き、以後誰も触らない。書き手の軸で見れば、観測の一部である。分割の軸は書き手で、概念ではない。「録画情報テーブルが太ったから意味で分ける」をやると、不変条件 12 の失敗をなぞる。

<details><summary>根拠</summary>

- 衛星に出せない列: `deleted_at` / `superseded_at`
- それらを参照する部分一意索引: `recordings_unique_active_event`

</details>

## 14. ライブラリの契約に無い挙動を前提にしない

ライブラリの内部表・非公開の状態・ソースを読んで知った挙動は、契約ではないので前提にしない。外部プロセスとブラウザは対象外で、測っていない挙動を断言しない規律で扱う。先に浮かぶ案は、sqlc に弾かれた SQL を Go の文字列リテラルへ移すことである。

River の表は sqlc のスキーマに無いので、ジョブ表を読む SQL は生成時に落ちる。文字列リテラルの生 SQL は sqlc を通らず、一度消した後も、公開 API に代替の無い回収処理を足すたびに戻った。テストも同じで、投入の確認をジョブ表の SELECT で書く形が増え続けた（代わりは公開のテスト補助）。

lint が落とすのは、呼び出しに直接書いた定数と、単独の const / var 宣言や代入の右辺である。const のグループ内の定数と、実行時に組み立てる SQL（非定数の連結や文字列の結合関数など）は素通りする。

壊すものは、ライブラリの版上げで内部表の列や状態の意味が、気づかないうちに変わりうることである。内部表の列や状態の意味は契約ではない。ライブラリを別の実装へ差し替える道も塞がる。

チェック: 「その前提はライブラリのドキュメントのどこに書いてあるか」を問う。答えられなければ迂回せず提起する。

<details><summary>根拠</summary>

- 読む SQL が落ちる River の表: `river_job`
- テストでの投入確認の代わり: `rivertest.RequireInsertedTx`
- 文字列リテラルを落とす lint: `tools/lintrules`
- 素通りする形: `const ( )` グループ内の定数、`strings.Join` などの組み立て

</details>

### 公開契約の範囲

ライブラリの公開契約には、そのライブラリの CHANGELOG に明記された挙動も含める。CHANGELOG は API doc より説明が弱いことがあるので、実物のライブラリを使うテストでその挙動を固定する。

### 外部プロセスとブラウザ

外部プロセス（mirakc / ffmpeg）は対象外である。ドキュメントに無い挙動を実測で決めざるを得ないので、不変条件 2 と CLAUDE.md の「測っていない挙動を断言しない」で扱う。

ブラウザも対象外である。hls.js のように、ブラウザの実挙動の上で動くものの実測を含む（例: Chrome が HLS の MIME に `canPlayType` で `'maybe'` を返す）。扱いは「測っていない挙動を断言しない」だけで、不変条件 2 は掛からない。

### KEDA のクエリの例外

マニフェストの KEDA クエリは、River の PostgreSQL スキーマを参照する。KEDA のトリガは River の公開 API を呼べないので、この SQL を維持する。クエリは、テストが実 DB で検証する。

<details><summary>根拠</summary>

- KEDA クエリを実 DB で検証するテスト: `deploy/k8s/workloads_test.go::TestScaledJobTriggerQueriesRunAgainstRiverSchema`

</details>
