# 不変条件 9〜13 の経緯と失敗事例

CLAUDE.md の不変条件 9〜13 は「チェック」の一文だけを残し、それを言語化した経緯・失敗事例（表と war story）をここに退避している。**間違えそうになったとき、あるいはルールの根拠を辿りたいときだけ読む。** コードを書くときの判断は CLAUDE.md のチェックで足りる。

**記録は消さない。** もう存在しない列の話でも、同じ間違いを繰り返さないために効いている。消すのは「現在の実装はこうである」と読めて、かつ事実でなくなった記述だけ（CLAUDE.md「ドキュメントと issue の保守」）。

> 9 と 10 は M2-4 / M2-5 で**同じ歪みを 3 回踏んでから**言語化した。11 と 12 は M2 完了後の設計レビューで、9 / 10 自身が**後から来たせいで払った代償**を数えて言語化した（#30 / #31）。13 は 12 が永続表に対して盲目であることを M2 完了後の別レビューで見つけて言語化した（#156）。番号は追加のみ（既存の 1〜8 は docs が番号で参照しているので振り直さない）。

## 9. 導出値と不可逆な事実を同じ列に載せない

毎パス再計算される値と、二度と再取得できない事実を 1 つの列に同居させると、**導出側が事実を上書きする**。踏んだ実例:

| 列 | 混ざっていた 2 つの事実 | 症状 |
|---|---|---|
| `program_intents.action` | ①録る/録るな ②パラメータを上書きしたか | `action NOT NULL` のため「上書きだけ」を表現できず、掃除の判定が別表の `rule_id` に依存して誤答した（#18） |
| `reservations.source` | ①ユーザーが手動予約したか ②いまルールが base を供給しているか | ruler が manual → rule に**不可逆に**書き換え、永続資産の `recordings.source` に恒久的に漏れた（#26） |
| `reservations.state` | ①番組終了後に schedule が観測されなかった ②ルールが base を供給しているか | 導出値（`active`/`detached`）を同期フィルタに使い、**手動予約が黙って録画されなくなった**（M2-4）。列を残したため 2 件が再発した（#30） |

チェック: 新しい列を足すとき「この値は毎パス作り直せるか」を問う。作り直せるなら**列にせず導出する**。作り直せない事実と混ぜてはならない。

**混同は列だけでなく identity・式・適用の瞬間にも起きる。** M2 完了後のレビューで見つかった 3 つの逃げ道:

- **identity**: API の宛先を導出物の id で指定すると、**書ける意図が導出側の状態に依存する**。`POST /api/reservations` は導出行が「無い」ときだけ、`DELETE` は「ある」ときだけ意図を書けるので、`base.skip` を覆す `action='record'` を立てる経路が存在しなかった（#29）。新しいエンドポイントを足すときは「**宛先のキーは誰が作るか**」を問う。導出器が作るキーは宛先にしない
  - **適用先は「宛先」だけではない。導出器が作るキーは、述語の結合キーにも FK 経由の参照にも使わない。** ここを「API のパスの話」と読んだために実装バグを 3 件通した:
    - #98 の実装が `NOT EXISTS (recordings WHERE reservation_id = reservations.id)` で除外を書き、予約が再実体化された瞬間に「never-scheduled 行が無い」ことになって**終了済み予約が毎パス desired に戻り続けた**（表示も「録れた」に戻った）
    - #149 は `recordings.reservation_id`（`ON DELETE SET NULL`）でエンコード方針を引き、録画開始から終了までの窓で予約が再実体化されると NULL に落ちて**黙ってエンコードされない**（ログにも出ない）
    - #152 の開始遅延検出器は `recordings.reservation_id = ANY(...)` で「開始が観測済みか」を引き、録画中に予約が再実体化されると新しい id では届かず、検出窓（開始 + 猶予 〜 終了）の間**毎パス開始遅延を誤検知した**（DB には書かないので実害はゲージと slog.Error のみだが、アラートの信頼を削る）
  - チェック: `WHERE a.x_id = b.id` を書くとき「**この id は誰が作り、いつ変わるか**」を問う。導出器が作るなら、放送イベント `(site, network_id, service_id, event_id)` や `(site, program_id)` のように**外から与えられたキー**で引く。この族は #29 / #53 / #98 / #99 / #149 / #152 の 6 例
  - `recordings.reservation_id` は #149 / #152 で残っていたロジックの読者を放送イベントキー経由に置き換えた後も、列自体は「便利な結合キー」の見た目を保ち続け、7 例目を書く手を止めるのはレビューの運になっていた。**#158 で列自体を DROP し、間違いを表現不可能にした**（不変条件 10）。チェックを「読むたびに問う」から「間違えられる列を無くす」に一段強くした形 —— 導出器が作るキーを保存する列は、読者を移設し終えたら残さない
- **式**: 導出を docs に式で書いても、実装が列に「**遷移**」を保存すると片側の分岐しか持たない。`detached ⟺ rule_id IS NULL AND base IS NOT NULL` と書いたのに、実装は前パスの `rule_id` を見るのでルールを**削除**した経路では detached にならない（#30）。導出は読むたびに評価する。やむなく列に焼くなら**両方向のテストを書く**（CLAUDE.md「テスト規律」）
- **適用の瞬間**: 導出の判定をメモリに持って後で適用すると、その間に別の書き手が割り込む。ruler は `toDelete` を tx の外で計算してから tx 内で DELETE していたので、その窓に着地した `CreateReservation`（intent と予約行を 1 tx で書く）を踏み潰していた。読み順を入れ替えても窓は残る。**距離を作らざるを得ないなら、適用の側で判定条件を再評価する** —— 削除文の WHERE に load-bearing 行の `NOT EXISTS` を置いた。「1 つの表に書き手が 2 人いる」（不変条件 12）が見えたら、その 2 人の直列化契約も要る

## 10. 意味を持たない行を作らない

**行の存在そのものを主張として使う。** 「何も主張していない行」を作ると、それを掃除する規則が必要になり、その規則が判断材料を別表に求めて壊れる。

- `program_overrides`: 空の上書き = 行が無い（`{}` の行を作らない）
- `circuit_breakers`: 行の存在 = 発動中（「停止していない」を表す行は無い）。再開は DELETE

「あってはいけない組み合わせ」は **CHECK で禁止するより表現不可能にする**方が強い。CHECK は覚えておくべき規則だが、表現不可能なら忘れようがない。

## 11. 形を固定する前に、その形を決める判定基準を書く

**分類（ロール）や形（スキーマ・API）を先に固定して判定基準を後から書くと、基準が来た時点でやり直しになる。** M2 で 3 回起きた:

| 先に固定したもの | 判定基準が来た時期 | 代償 |
|---|---|---|
| スキーマ v1「最終形で切る」（#13） | 不変条件 9 / 10 が M2-4 / M2-5 の後 | `reservations` を 6 本のマイグレーションで変更（`source` 削除 / `overrides` を 2 回移設 / チャンネル列追加 / dedup 列追加 / Phase 1 で `state` と番組の事実を丸ごと移設）。**churn を避けるための決定が最も churn した表を生んだ** |
| ロール分類（ruler / reconciler / watcher をシングルトンロールとして並べた） | 「ソケットを持ち続けるか」が M2-20（#25） | ruler / reconciler / record_sweep の River ジョブ化、api からの SSE 分離 |
| 多拠点への `site` 列（#13） | API の資源同定は**当時まだ未決**（#31。のち M3-1 = #29 / #31 / #53 で API のパスとクエリキーに site を通して払い切った） | 複合 PK と全クエリの `$1` を払っているが、高い方（資源同定）が未払いの間は利益（マイグレーション不要）が担保されていなかった |

派生する 2 つの規律:

- **「最終形で切る」の対象は永続資産（`recordings` / `media_assets` / `drop_stats` / `rules`）と外から見える資源同定（API のパスと識別子）に限る。** 導出テーブル（`reservations` / `*_sync` / 射影）の列は、**それを書くコードと同じ PR で決める**。churn のコストが非対称だからである —— 永続資産のマイグレーションはデータ移行を伴って危険だが、導出表は再構築できるので churn がほぼ無害（`00008` / `00010` / `00012` はいずれも Down が片道であることを許容して通っている）
- **将来への先払いは高い方から。** 安い方（DB 列）を先に払っても、高い方（API の資源同定、クライアントのキャッシュキー）が未払いなら利益は出ない

チェック: 新しいテーブル・列・ロール・エンドポイントを足すとき「**これを書く / 使うコードは今あるか**」を問う。無ければ形を決めず、書き手と同じ PR に回す。

## 12. 表は行の寿命で割る

**1 表 = 1 つの書き手 = 1 つの寿命。** 不変条件 9 は**列**の粒度なので、行に寿命が混ざっているケースを網に掛けられない。この規律の言語化を促したのは `reservations` で、この表の 1 行には 3 つの寿命が同居していた:

| 同居していたもの | 寿命 | 当時の状態 |
|---|---|---|
| ruler の導出出力（`base` / `rule_id` / dedup 根拠） | ruler の 1 パス | ここだけであるべき（現在もここだけ） |
| 番組の事実のスナップショット（`title` / `program_start_at` / `program_duration_ms` / チャンネル 4 列） | 放送 | 3 表に重複し、既にドリフトしていた（#27）。**Phase 1 で `program_snapshots` に抽出して解消** |
| 不可逆な観測（`state = 'orphaned'`） | 永続 | 導出値と同じ列にあった（#28 / #30）。**Phase 1 で `orphaned_at` に分離して解消** |

ユーザー意図（`program_intents` / `program_overrides`）を導出行から出したのは正しかったが、**分割の軸を「予約という概念」に取ったので 2 回に分かれた**（#18 → M2-4）。軸を寿命に取れば 1 回で済んだ。

Phase 1 の「`orphaned_at` に分離」は列を分けただけで**表は同じ**であり、この原則はまだ守れていなかった（不可逆な観測が導出表に残っていた）。#98 で `recordings` の試行行へ移設して列自体を廃止し、ようやく①だけが残った。**「別の列に分離する」と「別の表に出す」を混同すると、原則を守ったつもりで守れていない**ことの実例として残す。

チェック: 新しい列を足すとき「**この値はこの行と同時に生まれて同時に死ぬか**」を問う。違えば `(site, program_id)` を主キーにした別表にする。1 つの表に書き手が 2 人いるのも同じ兆候。

## 13. 永続表に列を足すとき、書くループが脊椎の書き手でなければ衛星表にする

不変条件 12 の寿命チェック（「この値はこの行と同時に生まれて同時に死ぬか」）は**永続表に対して盲目**になる。永続表はどんな列を足しても「表自体が永続なので列も永続」で自明に真が返り、網に掛からない。`recordings` が書き手 5 人（watcher / reconciler / ingest worker / api / delete reconcile）まで増えても 12 だけでは止まらなかった理由がこれ（#156）。

**recordings 本体は「試行の帰結の観測」だけを持つ脊椎。別のループが書く状態は `recording_id` を FK に持つ衛星表に置く。** `media_assets` がこの形の実例で、自分の書き手（ingest / encode / thumbnail の各 worker）と自分の状態機械（`active`→`deleting`→`deleted`）を持つ永続の衛星表である。`drop_stats` は `media_asset_id` で `media_assets` を指す「衛星の衛星」で、`recordings` を直接 FK で指してはおらず、状態機械も持たない（`media_assets` をコミットする ingest と同一トランザクションで追記されるだけ）。

チェック: 永続表に列を足すとき「**この列を書くループは脊椎の書き手か**」を問う（`recordings` なら試行を観測する watcher / reconciler。既にその表に書いているループ＝既存のテナントであることは根拠にならない —— 間借りが次の間借りを正当化してしまう）。脊椎の書き手でないなら、その表の列にせず `recording_id`（等の対象行 FK）を持つ衛星表にする。

原則の境界（絶対視して壊す方が高くつくので明記する）:

- **`deleted_at` / `superseded_at` は衛星に出せない。** `recordings_unique_active_event` の部分一意索引の述語がこの 2 列を参照しており、**部分索引の述語は他表を参照できない**。「ごみ箱 / supersede で枠が明く」という設計は、この 2 列が本体に居ることを一意索引の機構として要求している —— 間借りではなく枠管理の一部
- **番組スナップショット列群は脊椎に属する。** 列数は多いが、watcher が行の作成と同時に一度だけ書き、以後誰も触らない —— 書き手の軸で見れば観測の一部
- **分割の軸は書き手であって概念ではない。** `reservations` の分割が 2 回に分かれたのは軸を「予約という概念」に取ったから（不変条件 12）。「録画情報テーブルが太ったから意味で分ける」をやると同じ失敗をなぞる
