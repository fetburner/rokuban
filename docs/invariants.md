# 不変条件 9〜13 の失敗の形

CLAUDE.md の不変条件 9〜13 は「チェック」の一文だけを持つ。ここにはそのチェックが何を止めているか --- **いま同じ列・同じ JOIN・同じ表を足そうとしたときに先に浮かぶ案と、それが壊すもの** --- を置く。**間違えそうになったとき、あるいはルールの根拠を辿りたいときだけ読む。** コードを書くときの判断は CLAUDE.md のチェックで足りる。

番号は追加のみ（既存の 1〜8 は docs が番号で参照しているので振り直さない）。

## 9. 導出値と不可逆な事実を同じ列に載せない

毎パス再計算される値と、二度と再取得できない事実を 1 つの列に同居させると、**導出側が事実を上書きする**。混同は列だけでなく identity・式・適用の瞬間にも起きる。

### 列

| 同じ列に載せたくなるもの | 壊れる形 |
|---|---|
| 「録る / 録るな」と「パラメータを上書きしたか」 | 意図の列が NOT NULL なので「上書きだけ」を表現できず、掃除の判定が別表を見に行って誤答する |
| 「ユーザーが手動予約したか」と「いまルールが base を供給しているか」 | 導出器が前者を後者で不可逆に書き換え、永続資産（録画履歴の `source`）に恒久的に漏れる |
| 「番組終了後に schedule が観測されなかった」と「ルールが base を供給しているか」 | 導出値（`active` / `detached`）が同期フィルタを兼ね、**ルールが外れた手動予約が黙って録画されなくなる** |

3 つ目は今でも先に浮かぶ形なので、規則として残っている: **同期の可否を決めるのは `effective.skip` であって `active` / `detached` ではない。**

### identity

**API の宛先を導出物の id で指定すると、書ける意図が導出側の状態に依存する。** 予約 id を宛先にすると、導出行が「無い」ときだけ作成 API が、「ある」ときだけ削除 API が意図を書けるので、`base.skip` を覆す「録れ」を立てる経路が存在しなくなる。

**適用先は「宛先」だけではない。導出器が作るキーは、述語の結合キーにも FK 経由の参照にも使わない。** ここを「API のパスの話」と読んだために、`recordings.reservation_id`（予約 id への FK）を経由するロジックが同じ族のバグを繰り返し生んだ。壊れ方は 3 種あるが原因は共通で、**ruler の導出削除・再実体化で id が変わった瞬間に結合が切れる**:

- 「この予約に録画行があるか」の除外が引けなくなり、終了済み予約が毎パス desired に戻り続ける
- エンコード方針が NULL に落ちて**黙ってエンコードされない**（ログにも出ない）
- 開始遅延検出器が「開始が観測済みか」を引けず、録画中ずっと誤検知する

チェック: `WHERE a.x_id = b.id` を書くとき「**この id は誰が作り、いつ変わるか**」を問う。導出器が作るなら、放送イベント `(site, network_id, service_id, event_id)` や `(site, program_id)` のように**外から与えられたキー**で引く。

読者を移設し終えても、その列は「便利な結合キー」の見た目を保ち続け、7 例目を書く手を止めるのはレビューの運になる。**導出器が作るキーを保存する列は、読者を移設し終えたら DROP する** --- チェックを「読むたびに問う」から「間違えられる列を無くす」へ一段強くした形（不変条件 10）。

### 式

導出を docs に式で書いても、実装が列に「**遷移**」を保存すると片側の分岐しか持たない。`detached ⟺ rule_id IS NULL AND base IS NOT NULL` と書いても、実装が前パスの `rule_id` を見ていれば、ルールを**削除**した経路（FK が先に `rule_id` を落とす）では detached にならない。導出は読むたびに評価する。やむなく列に焼くなら**両方向のテストを書く**（CLAUDE.md「テスト規律」）。

### 適用の瞬間

導出の判定をメモリに持って後で適用すると、その間に別の書き手が割り込む。ruler は削除対象を tx の外で計算してから tx 内で DELETE していたので、その窓に着地した手動予約（意図と予約行を 1 tx で書く）を踏み潰していた。読み順を入れ替えても窓は残る。**距離を作らざるを得ないなら、適用の側で判定条件を再評価する** --- 削除文の WHERE に load-bearing 行の `NOT EXISTS` を置く。「1 つの表に書き手が 2 人いる」（不変条件 12）が見えたら、その 2 人の直列化契約も要る。

## 10. 意味を持たない行を作らない

**行の存在そのものを主張として使う。** 「何も主張していない行」を作ると、それを掃除する規則が必要になり、その規則が判断材料を別表に求めて壊れる。

- `program_overrides`: 空の上書き = 行が無い（`{}` の行を作らない）
- `circuit_breakers`: 行の存在 = 発動中（「停止していない」を表す行は無い）。再開は DELETE
- `recording_encode_policy` / `recording_ingest_progress`: 行の存在 = 凍結済み / 転送中。列の既定値では「まだ」と「空として確定した」が区別できない

「あってはいけない組み合わせ」は **CHECK で禁止するより表現不可能にする**方が強い。CHECK は覚えておくべき規則だが、表現不可能なら忘れようがない。

## 11. 形を固定する前に、その形を決める判定基準を書く

**分類（ロール）や形（スキーマ・API）を先に固定して判定基準を後から書くと、基準が来た時点でやり直しになる。** M2 で 3 回起きた:

| 先に固定したもの | 後から来た判定基準 | 代償 |
|---|---|---|
| スキーマ v1「最終形で切る」 | 不変条件 9 / 10 | `reservations` を 6 本のマイグレーションで変更。**churn を避けるための決定が最も churn した表を生んだ** |
| ロール分類（ruler / reconciler / watcher をシングルトンロールとして並べた） | 「ソケットを持ち続けるか」 | ruler / reconciler / record_sweep の River ジョブ化、api からの SSE 分離 |
| 多拠点への `site` 列 | API の資源同定が当時未決 | 複合 PK と全クエリの `$1` を払っているが、高い方（資源同定）が未払いの間は利益（マイグレーション不要）が担保されていなかった |

派生する 2 つの規律:

- **「最終形で切る」の対象は永続資産（`recordings` / `media_assets` / `drop_stats` / `rules`）と外から見える資源同定（API のパスと識別子）に限る。** 導出テーブル（`reservations` / `*_sync` / 射影）の列は、**それを書くコードと同じ PR で決める**。churn のコストが非対称だからである --- 永続資産のマイグレーションはデータ移行を伴って危険だが、導出表は再構築できるので churn がほぼ無害
- **将来への先払いは高い方から。** 安い方（DB 列）を先に払っても、高い方（API の資源同定、クライアントのキャッシュキー）が未払いなら利益は出ない

チェック: 新しいテーブル・列・ロール・エンドポイントを足すとき「**これを書く / 使うコードは今あるか**」を問う。無ければ形を決めず、書き手と同じ PR に回す。

## 12. 表は行の寿命で割る

**1 表 = 1 つの書き手 = 1 つの寿命。** 不変条件 9 は**列**の粒度なので、行に寿命が混ざっているケースを網に掛けられない。この規律の言語化を促したのは `reservations` で、この表の 1 行には 3 つの寿命が同居していた:

| 同居していたもの | 寿命 | 分離先 |
|---|---|---|
| ruler の導出出力（`base` / `rule_id` / dedup 根拠） | ruler の 1 パス | ここだけであるべき（現在もここだけ） |
| 番組の事実のスナップショット（title / 開始時刻 / 尺 / チャンネル） | 放送 | 3 表に重複し、既にドリフトしていた（同じ番組に異なる開始時刻が保存され、GC の判定が表ごとに違う時刻を使っていた）→ `program_snapshots` |
| 不可逆な観測（「schedule が一度も作られなかった」） | 永続 | 導出値と同じ列にあった → `recordings` の試行行 |

2 つの落とし穴:

1. **分割の軸を「概念」に取ると 2 回に分かれる。** ユーザー意図を導出行から出す分割は軸を「予約という概念」に取ったので 2 回かかった。軸を**寿命**に取れば 1 回で済む
2. **「別の列に分離する」と「別の表に出す」は違う。** 不可逆な観測を専用列に切り出した段階では表が同じままで、原則を守ったつもりで守れていなかった。別表の恒久行へ移して初めて①だけが残った

チェック: 新しい列を足すとき「**この値はこの行と同時に生まれて同時に死ぬか**」を問う。違えば `(site, program_id)` を主キーにした別表にする。1 つの表に書き手が 2 人いるのも同じ兆候。

## 13. 永続表に列を足すとき、書くループが脊椎の書き手でなければ衛星表にする

不変条件 12 の寿命チェック（「この値はこの行と同時に生まれて同時に死ぬか」）は**永続表に対して盲目**になる。永続表はどんな列を足しても「表自体が永続なので列も永続」で自明に真が返り、網に掛からない。`recordings` が書き手 5 人（watcher / reconciler / ingest worker / api / delete reconcile）まで増えても 12 だけでは止まらなかった理由がこれ。

**recordings 本体は「試行の帰結の観測」だけを持つ脊椎。別のループが書く状態は `recording_id` を FK に持つ衛星表に置く。** `media_assets` がこの形の実例で、自分の書き手（ingest / encode / thumbnail の各 worker）と自分の状態機械（`active`→`deleting`→`deleted`）を持つ永続の衛星表である。`drop_stats` は `media_asset_id` で `media_assets` を指す「衛星の衛星」で、`recordings` を直接 FK で指してはおらず、状態機械も持たない。

チェック: 永続表に列を足すとき「**この列を書くループは脊椎の書き手か**」を問う（`recordings` なら試行を観測する watcher / reconciler。**既にその表に書いているループ＝既存のテナントであることは根拠にならない** --- 間借りが次の間借りを正当化してしまう）。脊椎の書き手でないなら、その表の列にせず `recording_id`（等の対象行 FK）を持つ衛星表にする。

原則の境界（絶対視して壊す方が高くつくので明記する）:

- **`deleted_at` / `superseded_at` は衛星に出せない。** `recordings_unique_active_event` の部分一意索引の述語がこの 2 列を参照しており、**部分索引の述語は他表を参照できない**。「ごみ箱 / supersede で枠が明く」という設計は、この 2 列が本体に居ることを一意索引の機構として要求している --- 間借りではなく枠管理の一部
- **番組スナップショット列群は脊椎に属する。** 列数は多いが、watcher が行の作成と同時に一度だけ書き、以後誰も触らない --- 書き手の軸で見れば観測の一部
- **分割の軸は書き手であって概念ではない。** 「録画情報テーブルが太ったから意味で分ける」をやると不変条件 12 の失敗をなぞる
