## 5. 検索とルール評価の統一

検索とルール評価は、どちらも Postgres に寄せ、1 つのエンジンと 1 つの正規表現方言で動かす。世帯スケールでは、検索性能は問題にならない。

### 規模感: 世帯スケールでは検索性能は問題にならない

録画ライブラリ・EPG プロジェクション・ルール評価のどれも、世帯スケールでは検索性能が問題にならない。「録画が増えると検索が遅くなる」は、実質起きない。

| 対象 | 規模 | 見立て |
|---|---|---|
| 録画ライブラリ | 毎日 20 番組 x 10 年で約 7.3 万行 | pg_trgm GIN 付きの部分一致は、100 倍でもミリ秒台 |
| EPG プロジェクション | 8 日分 x 全サービスで数万〜20 万行 | 録画数と違って増えない（ローリングウィンドウ）ので、永久に上限がある |
| ルール評価 | 数十〜数百ルール x EPG 差分数千番組 | バッチで秒未満 |

### ルール評価も Postgres で行う（検索とエンジン統一）

ルールは、実質「保存された検索」である。UI 検索と ruler 評価が別エンジン（Go RE2 と Postgres）だと、「検索では出るのにルールにマッチしない」という説明不能な不整合が生まれる。そのため、両方を Postgres に寄せる。

正規表現の方言は、POSIX ARE の 1 つに統一する。pg_trgm の GIN インデックスは、LIKE だけでなく正規表現マッチも加速するので、regex ルールもインデックスに乗る。Postgres の regex は UTF-8 を文字単位で扱うため、EPGStation#562（サロゲートペア等）は再現しない。

ARE は、先読みも後読みも使える（PostgreSQL 16.2 で測定・確認）。非互換になるのは、JS の名前付きキャプチャのような、POSIX ARE に無い拡張構文である。測定では、名前付きキャプチャを使った検索が構文エラーになった。`rokuban import epgstation` は、取り込み時に各ルールの正規表現を Postgres で検証する。非互換は警告し、ユーザーに修正を促す（差分テストの allowlist にも追加する）。

<details><summary>根拠</summary>

- 正規表現マッチの演算子: `~`
- 先読み・後読み: `(?=)` / `(?<=)`
- 非互換になる構文: `(?<name>...)`。測定した式は `SELECT '' ~ '(?<name>foo)'`

</details>

### 全角/半角の揺れは immutable 関数 + 式インデックスで吸収する

全角と半角の揺れは、immutable な正規化関数を SQL で定義し、EPG 番組表に式 GIN インデックスを張って吸収する。正規化済みの重複カラムをアプリコードで維持する方式は採らない。

全角の局名のルールで、半角で書かれた番組にマッチさせる正規化は必要である。EPGStation の半角用キーワードのカラムが担っていた、実問題である。

インデックスで持つので、同期漏れ（アプリが正規化列の更新を忘れる）が構造的に起きない。検索 UI と ruler 評価が同じ式を通るので、両者のマッチ結果は定義から一致する。

<details><summary>根拠</summary>

- 全角で書くルールの例: `ＮＨＫ`。マッチさせたい半角の表記: `NHK`
- EPGStation の半角用カラム: `halfWidthKeyword` 系
- 式インデックスを張る表: `epg_programs`

</details>

### PGroonga は最初から入れない

検索基盤は、標準 contrib で運用コストがゼロの pg_trgm で始める。形態素解析ベースの検索が欲しくなったら、段階的に PGroonga に伸ばす。正規化列を自前で維持する検索基盤は作らない。

### 録画検索は rulequery を共有しない

録画一覧の絞り込みは、EPG 検索やルール評価と同じクエリ組み立てに相乗りしない。録画を共有コンパイラの第 2 のターゲットにはせず、共有するのはキーワードの正規化方言だけである。

`GET /api/recordings` の絞り込み（[api.md](../api.md) 「録画一覧: 絞り込み + キーセットページング」）は、`/search`（EPG 検索）や ruler 評価と同じクエリ組み立てに相乗りしない。

<details><summary>根拠</summary>

- 共有しないクエリ組み立て: `internal/store/pgstore/rulesql.go`
- 第 2 のターゲットにしない対象: `recordings`。`EPG.SearchPrograms` の対象にしない

</details>

#### 共有しない 3 つの理由

EPG は消えるが録画は残るので、EPG に JOIN すると古い録画の条件が 0 件になる。列の形も問いも違う。この 3 つが、共有しない理由である。

1. EPG は消えるが、録画は残る。録画は、放送の事実を自前の列に凍結した永続資産である。詳細は §6「録画した番組の情報は予約〜ingest 時点で録画行に非正規化スナップショット」にある（[projections.md](projections.md)）。EPG の表に JOIN して検索すると、EPG のローリングウィンドウから外れた古い録画では、条件がエラーを出さずに 0 件になる。絞り込みとして、最悪の失敗の仕方である
2. 列の形が違う。タイトルの列名が違い、ジャンルの持ち方も違う。チャンネル種別は録画が直持ちで、JOIN が要らない。1 つのコンパイラに 2 つのテーブルを食わせると、列名マップの分だけ「片方でしか通らない条件」が生まれる
3. 問いが違う。録画検索の中心は、EPG に存在しない軸（状態・取得元・ルール・ごみ箱）である。逆に、ルール条件が持つ曜日ビットマスクや、否定付き正規表現の複数 AND は、録画検索には過剰である

<details><summary>根拠</summary>

- 凍結される列: `title` / `description` / `genres` / `channel_type` / `service_name`
- JOIN してはいけない表: `epg_programs`
- 名前の違う列: `title`（録画）と `name`（EPG）
- ジャンルの持ち方: `genres jsonb`（録画）と `genre_lv1 smallint[]`（EPG。両方とも生成列）
- EPG に存在しない軸: `status` / `source` / `rule_id`

</details>

#### 共有するキーワード方言

共有するのは、キーワードの正規化方言だけである。同じ語で EPG 検索と録画一覧の当たり方が変わると、ユーザーに説明できない。そのため、正規化関数を通すか通さないかの判定は、ここだけで揃える。

キーワード検索の特殊文字は、LIKE の構文として解釈せず、文字として照合する。正規表現モードは、入力したパターンとして扱う。テーブルや列名のマッピングは持たない。呼び出し側が、列名を渡す。

<details><summary>根拠</summary>

- EPG 検索のパス: `/search`
- 共有する SQL 述語: `internal/store/pgstore` の `keywordClause`。`compileTextMatch` と録画検索が呼ぶ
- 正規化関数: `normalize_search_text`
- 文字として照合する文字: `\` / `%` / `_`
- 列名の例: `p.name` / `r.title`

</details>

### 性能上の実注意点（検索ではない）

性能上の注意点は 2 つある。EPG テーブルの churn と、番組表グリッドのペイロードである。どちらも、検索性能の問題ではない。

1. EPG テーブルの churn と bloat。1 日に何度も大量 upsert されるので、遅くなるとしたら、書き込みと autovacuum の追従である。バッチ upsert、GIN fastupdate、テーブル別 autovacuum チューニングで対処する（運用ノート）
2. 番組表グリッドのペイロード。転送量と描画の問題である。決定済みの仮想化（TanStack Virtual）と、API の時間窓・サービス絞り込みで対処する
