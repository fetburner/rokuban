## 8. シリーズ同一性

シリーズ棚・番組ハブ・「次のエピソード」は、どの録画とどの番組が同じシリーズかを前提にする。
ここではその正本と、それを API の資源へ写す判断を置く。

### 正本はタイトルからの導出。放送のシリーズ記述子は使わない

mirakc の番組 API は `series` を契約に持つが、地上波 7 局・6960 番組の実測で付与率は 0 件だった。
パイプラインは生きていて、放送に series_descriptor が載っていない。
BS は未測定だが、地上波で常に空になる以上、記述子を正本にはできない。
独立した 2 実装（KonomiTV と stuayu 版 EPGStation）も、記述子を使わずタイトル側に賭けている。

重複排除の類似度（`internal/ruler/dedupe.go`）は流用しない。
あれは「同じ放送の再放送か」を問うもので、ほぼ同一の文字列だけを拾う。
同一枠の別回の組では、類似度 0.5 に届くのが半分しかない。

### 2 層: 分類ルール → 自動キー

実効シリーズは、分類ルールが当たればその値、当たらなければ自動キーとする。
どちらも保存せず、読むたびに導出する（不変条件 9）。
正規化や分類ルールを直すと、過去の録画の棚もその場で直る。

- **自動キー** `series_key(title)` は immutable な SQL 関数である。記号除去と NFKC の後、区切り記号・話数・最初の空白で切る。空・記号のみのタイトルでは NULL を返す
- **分類ルール** `label_rules` はキーワード 1 つと値の組で、`priority DESC, id ASC` の順で先に当たったものが勝つ。同順位で勝者が不定だと、読むたびに棚が入れ替わる
- 分類ルールの値も自動キーと同じ正規化を通して比較する。見出しには正規化した値ではなく、代表の録画の生のタイトルを出す

単一の正規化では決まらない。最初の空白で切る段は同一枠の別回の再現率を 60% から 83% に上げるが、`アニメ` や `NHK高校講座` のような枠名で過剰併合する。
自動キーは再現率の高い側に置き、過剰併合は分類ルール 1 本で割る。
過剰併合は巨大な棚として目に見えるので、直す場所が分かる。

分類ルールの条件はキーワード 1 つに限る。
録画タイトルと EPG の番組名の両方に同じ式を当てるためで、共有するのは `KeywordClause` の方言だけである（[search.md](search.md)「録画検索は rulequery を共有しない」）。
条件をジャンルや局へ広げるなら、その決定と同時に見直す。
LIKE のエスケープは SQL 関数に一本化する。分類ルールのキーワードは DB から読むので、Go 側でエスケープする経路を通らない。

式は録画と EPG で対称でも、入力（録画時のタイトルのスナップショットと現在の番組名）は対称とは限らない。
両者の一致率は未測定である。

### 導出値をどこにも焼かない

- 導出したシリーズを録画の列にも行にも書き戻さない。KonomiTV はシリーズを FK と非正規化列に焼く形を切って止まり、stuayu 版は焼いた引き当てキーの掃除機構を作り続けている
- 「自動棚 A を B に統合する」操作は作らない。導出値を宛先にした上書きは、正規化を変えた時点で宛先を失う
- 録画ルールからラベルを継承させない。勝者ルールだけを継承すると広いルールに黙って負け、作成時にコピーすると予約と録画で値が食い違う。「このルールで録れたもの」は `rule_id` の軸が既に持っている
- 手動でシリーズを上書きする層は置かない。録画にしか付けられないので、EPG 側の「次回」と非対称になる

### 資源同定: 起点は録画 id

番組ハブは、起点にした録画 1 件の id で同定する。
シリーズは起点の実効シリーズと等しい録画の集合として、毎回導出する。

- 正規化キーを URL に置くと、規則を変えた時点で 404 ではなく 0 件で黙って壊れる
- 録画 id は watcher が作る不可逆な事実の id で、導出器が作るキーではない（不変条件 9）
- 録画行は purge 後も tombstone とタイトルのスナップショットが残るので、起点の URL は腐らない
- 棚の中のどの録画を起点にしても、同じ集合になる

まだ録画の無い番組を起点にしたハブは作らない。`(site, programId)` は EPG のローリングウィンドウから外れると宛先を失う。

一覧 API の行の同一性（1 行 = 1 録画）はシリーズで絞っても変えない。
N 予約で同じ放送が 2 拠点から録れていれば、ハブに 2 行並ぶ。ドロップ統計で選び分ける運用では、それが正しい。
同じ放送をまとめるのは「次のエピソード」の UI だけで、再生できる行に限り、起点と同じ site を優先する。
開始時刻がずれて supersede されない failed 行（[schema/recordings.md](../schema/recordings.md)「`superseded_at`: failed 行が後続 record に枠を譲る」）を「次」に入れないためである。

シリーズ内の並びは放送日時順とする。話数は持たないので、重複排除を切ったルールでは再放送が「次」になりうる（頻度は未測定）。

経路はすべて単一ホスト名の Ingress で `/` の catch-all に落ち、api ロールが DB だけで答える（不変条件 1）。
`/api/sites/{site}/recordings` と `/api/media/` の下は streamer 行きの Prefix なので置かない（[api/deployment.md](../api/deployment.md)）。

### 不変条件 7 との整合

放送のシリーズ id を永続テーブルに入れる案は、記述子を使わない時点で消えた。
`label_rules` が持つのはユーザーが書いたキーワードと値だけで、mirakc 固有の概念を含まない。
名前は「ラベル」とし、mirakc の schedule tags（`schedule_sync.tags` / `record_sync.tags`）と区別する。
