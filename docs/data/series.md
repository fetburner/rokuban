## 8. シリーズ同一性

シリーズ棚・番組ハブ・「次のエピソード」は、どの録画とどの番組が同じシリーズかを前提にする。
ここではその正本と、それを API の資源へ写す判断を置く。

### 正本はタイトルからの導出。放送のシリーズ記述子は使わない

mirakc の番組 API は `series` を契約に持つが、地上波 7 局・6960 番組の実測で付与率は 0 件だった。
パイプラインは生きていて、放送に series_descriptor が載っていない。
BS は未測定だが、地上波で常に空になる以上、記述子を正本にはできない。
独立した 2 実装（KonomiTV と stuayu 版 EPGStation）も、記述子を使わずタイトル側に賭けている。

重複排除の類似度（`internal/ruler/dedupe.go`）は流用しない。
あれは「同じ放送の再放送か」を問うもので、ほぼ同一の文字列だけを拾う。
同一枠の別回の組では、類似度 0.5 に届くのが半分しかない。

### 2 層: 分類ルール → 自動キー

実効シリーズは、分類ルールが当たればその値、当たらなければ自動キーとする。
正本はタイトルと分類ルールで、評価の結果は作り直せるキャッシュとして DB に持つ（次節）。

- **自動キー** `series_key(title)` は immutable な SQL 関数である。記号除去と NFKC の後、区切り記号・話数で切る。枠名を 1 語飛ばしてから、最初の空白で切る。空・記号のみのタイトルでは NULL を返す
- **分類ルール** `label_rules` はキーワード 1 つと値の組で、`priority DESC, id ASC` の順で先に当たったものが勝つ。同順位で勝者が不定だと、評価のたびに棚が入れ替わる
- 分類ルールの値も自動キーと同じ正規化を通して比較する。画面のシリーズ名は実効キーを表示し、代表録画の生タイトルを補助表示する。キーを `ドラマ` のような短い値にしても過剰併合が隠れず、ルールを直す場所が見える
- **値にも自動キーの正規化がかかるので、最初の空白などで切れる。** `NHK高校講座 数学I` と `NHK高校講座 化学` はどちらも `NHK高校講座` の棚になり、割るつもりのルールが同じ棚に落ちる（`ドラマ「半沢直樹」` は `ドラマ`）。値を棚のキーとして切り直す案は採らず、API が実効の棚キー（`valueKey`）を返し、一覧とフォームで食い違いを見せる
- 値が正規化で NULL になるルールは作らせない（CHECK）。何も主張しないルールになる（不変条件 10）

単一の正規化では決まらない。最初の空白で切る段は同一枠の別回の再現率を 60% から 83% に上げるが、枠名で過剰併合する。
関東の GR・BS の録画 4 年分では、`アニメ　<作品名>` の形が 1 つの棚に 2,268 件落ち、その下の作品名は 239 種類あった。
分類ルールはキーワード 1 本で 1 作品しか切り出せないので、これは割れない。
ハブの「次回」も同じ棚で誤爆し、候補が 136,053 件になった。
そこで枠名（`アニメ` / `TVアニメ` / `日5`）を関数内の定数として飛ばす。最大の棚は 120 件、ハブの候補は 429 件に落ちた。
枠名を設定にしない理由は、`series_key` を immutable に保つためである。設定にすると生成列にできず、プロセスごとに値が割れうる。
残った過剰併合（`NHK高校講座` など）は分類ルールで割る。巨大な棚として目に見えるので、直す場所が分かる。
未検証: 枠名の 3 語は香川・岡山の site では測っていない。

分類ルールの条件はキーワード 1 つに限る。
録画タイトルと EPG の番組名の両方に同じ式を当てるためで、共有するのは `KeywordClause` の方言だけである（[search.md](search.md)「録画検索は rulequery を共有しない」）。
条件をジャンルや局へ広げるなら、その決定と同時に見直す。
LIKE のエスケープは SQL 関数に一本化する。分類ルールは DB 側のトリガーとジョブで評価するので、Go 側でエスケープする経路を通らない。

式は録画と EPG で対称でも、入力（録画時のタイトルのスナップショットと現在の番組名）は対称とは限らない。
同じ放送イベントで比べた 63 件（GR 35・BS 28）は、生のタイトルが全件一致した。
ただし EPG の保持窓に入る数日分だけの値で、月単位の改名率は未測定である。

### 評価結果の持ち方

読むたびに全録画を評価すると、73,000 行・分類ルール 50 本で 1.59 s かかった（うち `series_key` が約 600 ms）。
利用者が開く棚とハブでは払えないので、評価結果を持つ。予算は、母集団の条件込みで 73,000 行・200 ms とする。
予算を決めた環境では、旧母集団で実効シリーズを書き下した形の棚が 141 ms だった。
別の環境では、同じ回に測ったその形との比（200/141 ≈ 1.42 倍）で読む。
当時は 73,000 行がすべて再生可能で、今の合成データ（65,000 行）と違う。この違いが比をどちらへ動かすかは未検証である。

- **自動キー**は `recordings` と `epg_programs` の STORED 生成列にする（`genre_lv1` と同じ形）。書くループが無いので、導出が事実を上書きする経路が無い
- **分類ルールの当たり**は、録画ごとに勝ったルールの id を衛星表に持つ。行の存在 = そのルールが勝った、で、当たらない録画には行を作らない
- 値ではなく id を持つので、ルールの値を変えた変更は JOIN で即座に反映される。キーワード・priority の変更、追加、削除は全件の再評価になる
- 削除も全件の再評価が要る。当たりの表は勝者しか持たないので、勝者が消えた録画の次点は表から分からない。CASCADE は安全網でしかない
- `label_rules` にも値の正規化結果を生成列で持つ。集計のたびに録画ごとに正規化すると、生成列で消したコストが値の側から戻る

当たりの表には書き手が 2 人いる。両者は評価の関数を 1 つ共有する。

- **1 行の評価**は `recordings` の INSERT と title の UPDATE に付けたトリガーが行う。録画を作る経路は複数あるので、Go 側で呼ぶと 1 つ漏れる
- トリガーは「既存の当たりを消す → 勝者がいれば入れる」の 2 段にする。upsert だけだと、当たらなくなった録画に古い当たりが残る
- UPDATE のトリガーは `title` が変わったときだけ当てる。`UPDATE OF title` は SET 句に title があれば値が同じでも発火する。
  in-place 登録と rescue は title を無条件に書く。
  `WHEN (OLD.title IS DISTINCT FROM NEW.title)` で止める（`TestRecordingsLabelRuleTrigger_SkipsUpdatesThatKeepTheTitle`）
- **全件の再評価**は River のジョブが 1 トランザクションで差分だけ適用する。全件を消して入れ直すと、変化が無くてもデッドタプルと通知が毎回出る
- ジョブは advisory lock で直列化する。並行した 2 本の古い方が後から上書きしうる。rescue の再評価も同じロックを取る（キーは `LockLabelRuleReevaluation` の 1 箇所。`TestRescue_WaitsForLabelRuleReevaluationLock`）
- ジョブは**一意化しない**。実行中に来た 2 本目の編集を捨てないためである。捨てると、1 本目が古いルール集合で評価し終えた時点で打ち止めになり、2 本目の編集が次の定期再評価（15 分）まで反映されない
- 再評価ジョブは cleanup キュー（delete_reconcile / catalog_export と同じ、site 非依存の DB ジョブ用）で走らせる。ruler キューは `MaxWorkers: 1` でサイトごとの ruler パスが並ぶので、全件評価（0.86 s）で塞がない
- 「実行中を除いた状態集合」では代用できない。River が `UniqueOpts.ByState` から `running` を外した集合を挿入時にエラーにするからである（`requiredV3states`）
- 代償は、素早く N 回編集すると全件評価が N 回直列に走ることである（1 回 0.86 s / 73,000 行）。編集はまれな操作なので許容する
- 定期的な全件の再評価を必須にする。ルール編集をまたいでコミットした録画は、旧ルールで評価されうる。この窓は定期の再評価だけが閉じる
- 全件の再評価に母集団の条件を入れない。ごみ箱や tombstone の録画もハブの起点になる。母集団で絞るのは棚と一覧の側である
- 当たりの表は catalog に入れない。作り直せる値なので、`recordings` が戻れば再評価で戻る。**分類ルールの表（`label_rules`）は入れる**。ユーザーが書いた再取得できない設定だからである。rescue は分類ルールを recordings より前に書く（INSERT トリガーが復元済みのルール集合で評価する）。末尾では同じトランザクションの中で全件再評価を回し、当たりの表を閉じる。トリガーは新規行と title 変更しか見ないので、DB に残っていた録画の当たりはこの再評価でしか追従しない（`TestExportRescue_RoundTripsLabelRules`）

通知は、全件の再評価で変化があったときに `recordings` トピックへ 1 回だけ送る。
当たりの表に行トリガーを付けると、全件の再評価で行数ぶん通知が出る。
`label_rules` の変更も通知するので、キーワードを変えた直後は古い棚が一度返り、再評価の完了後に割れる。

`series_key` の本体を変えるマイグレーションでは、`recordings` の既存行の生成列は再計算されない
（SET 句に title を含まない UPDATE では再計算されず、`REINDEX` でも直らない）。
列を作り直す順序は次のとおりである。
`DROP VIEW recording_series` → `DROP COLUMN` → `ADD COLUMN` → `CREATE VIEW`。
`recordings.series_key` に索引は張らない（読み手がいないので落とした）。
ビューが列を参照しているので、列だけは落とせない。関数を変えたら列も変わることを、
マイグレーションのテストで確かめる。
`epg_programs.series_key` は同期の `ON CONFLICT DO UPDATE` が `name` を毎回 SET するので、
この手順は要らず、次の同期で値が入れ替わる。

### 実装で決めたこと

- **値の正規化もキーワードの正規化も生成列で持つ。** `label_rule_winner` は録画 1 行ごとに呼ばれるので、キーワード側を毎回正規化すると (録画行 × ルール本) 回になる。73,000 行 × 50 本で 16.0 s → 0.95 s になった。**この 2 つは最適化ではなく前提**である
- **棚のクエリはプランの形に依存する。** 旧母集団（再生できる録画だけ）では、録画を走査する CTE `playable` を `MATERIALIZED` にしていた。
  過去の実測では、外すと主テーブルの走査が部分一意索引（`recordings_unique_active_event`）に乗った。
  一意索引の行数を 1 と見積もるので下流が全部 1 行の計画になり、代表を求めるソートが外側の行数ぶん繰り返された。
  73,000 行で 141 ms → 617 ms だった（代表と件数を別の CTE に割ると 231 ms）
- **本番の `live` は旧 `playable` に当たるが、`MATERIALIZED` にしない。** 現スキーマ・合成 seed では 617 ms は再現しない。
  旧形から `MATERIALIZED` を外した形は旧形の 0.94〜0.95 倍で、`live` を `MATERIALIZED` にすると本番の 1.06〜1.07 倍遅い。
  617 ms の再現条件は未検証なので、再発したら `live` を `MATERIALIZED` に戻す
- `playable_assets` の `MATERIALIZED` は旧形から引き継いだもので、外したときの計画と速さは未検証
- **測定は `internal/api/shelves_bench_test.go` に残してある。** `ROKUBAN_BENCH_DATABASE_URL` が無ければスキップする。
  あるときは 73,000 行・141 棚の合成データ（録画中・失敗・ごみ箱などを混ぜる）を作る。
  6 つの棚クエリ形を prepared statement 経由で交互に 10 ラウンド測る。
  棚形は本番（sqlc 経由）、旧母集団の形、旧母集団の形から `MATERIALIZED` を外した形、本番の `live` を `MATERIALIZED` にした形である。
  さらに、放送イベント単位の未視聴件数を加えた形と、旧母集団の形で実効シリーズを書き下した形（予算の比の分母）を測る。
  予約一覧は、実効シリーズを LEFT JOIN で足す形と相関サブクエリで足す形を、予約数と予約に載らない EPG の行数を別々に動かして測る。
  速さはアサートせず、棚ごとの再生可能件数・最新開始時刻・形どうしの結果一致を判定する。未視聴数は別のイベント集計と照合する。
  母集団は生きている録画で、LEFT JOIN + `FILTER` を採る。
  開発機の 3 回の実測では、本番は 250〜253 ms、旧母集団の形は 240〜241 ms、旧形から `MATERIALIZED` を外すと約 225 ms だった。
  比は本番を基準にすると 0.95〜0.96 倍と 0.90 倍、旧形どうしでは 0.94〜0.95 倍である。
  `live` を `MATERIALIZED` にすると約 266 ms（本番の 1.05〜1.06 倍）になり改善にならない
- **psql の単発実行を基準にしない。** アプリと同じ pgx の prepared statement 経路で測る。単発の psql と計画が変わるかは、この合成 seed では未検証
- **実効シリーズの定義は `recording_series` ビューの 1 箇所**で、棚のクエリもこれを JOIN する（`COALESCE(lr.value_key, r.series_key)` を書き下さない）。ビュー経由は書き下しより 7〜8% 遅い（旧母集団の形で、合成 73,000 行・141 棚・ルール 50 本、約 240 ms 対 約 223 ms、開発機）
- **棚の母集団は生きている録画全体**（`deleted_at IS NULL AND superseded_at IS NULL`）とし、再生可能件数を別に返す。画面は `value` をシリーズ名、代表録画の生タイトルを補助表示に使い、`NULL` の棚は表示しない。`latestStartAt` は同じ集計から返す
- **未視聴件数は放送イベント数で定義する。**
  生きている録画のうち再生可能な録画を `(network_id, service_id, program_start_at)` で束ねる。
  同じキーを持つ全録画行（削除済み・supersede 済みを含む）に `recording_watched` が無いイベントを 1 件と数える。
  複数拠点の録画や録り直しがあっても 1 件とし、古い行の視聴済み印も読む。
  録画行の数は同じ放送を二重計上するため採らない。
  数えるのは棚ごとである。同じ放送の行が拠点ごとに別の棚へ入ると、各棚で 1 件ずつ数える。棚をまたいだ合計は放送数にならない
- **未視聴件数は棚クエリの同じ集計で返す。** 予約一覧も録画の本数を出すために棚クエリを読む。
  未視聴だけを別クエリにすると、`recording_series` の評価がもう 1 回走る
- **代表と件数は 1 回の集計で出す**（`array_agg` + `GROUP BY`）。`DISTINCT ON` と件数の集計を別の CTE に割ると同じ行をもう 1 度走査する（141 ms → 231 ms）
- 値が `NULL` の棚は実効シリーズを起点に番組ハブを開けないので画面に出さない。API は件数によらず全部の棚を返す
- 測定値（本番形と、未視聴を足した形。73,000 行のうち生きている 71,000・再生できる 65,000、sqlc / pgx 経由の中央値）:
  開発機の 3 回で棚 250〜253 ms、未視聴付き 310〜314 ms。
  未視聴付きは同じ回の書き下し形（222〜224 ms）の 1.40〜1.41 倍で、予算の 1.42 倍に収まる。余裕は 1〜2% しかない
- **予約一覧の実効シリーズは相関サブクエリで引く。** `epg_program_series` を LEFT JOIN すると、予約の `(site, program_id)` がビューの中へ押し下がらない。
  EPG の全行を Seq Scan して `label_rule_winner` を評価してから突き合わせるので、費用が予約数ではなく EPG の行数に比例する
- 測定値（予約一覧、開発機の 3 回、中央値）: 予約 2,000 件・EPG 約 2,000 行では LEFT JOIN 69〜71 ms、相関サブクエリ 74〜76 ms。
  予約に載らない EPG を 134,000 行足すと、LEFT JOIN は 4.44〜4.48 s、相関サブクエリは 76 ms である。
  予約 500 件では約 19 ms。EPG から消えた予約も行として残り、実効シリーズは NULL になる
- ハーネスの検証は「外すと数倍遅い」の再現では行わない。この seed では一度も再現していない。
  代わりに未視聴の集計を壊し、合計の照合で落ちることを確かめた。壊し方は 6 通りある。
  録画行で数える、印を生きている行・再生可能な行・purge されていない行からだけ読む、キーを `event_id` にする、キーからサービスを落とす、である
- 測定値（当時の値。73,000 行がすべて再生できて母集団が旧形、別の環境）: 棚 141 ms / 一覧 50 件の `series` 列 10 ms / 全件再評価 0.86 s。同じ形（書き下し）は開発機で約 223 ms で、値は環境が違うので直接は比べられない
- 測定値（ハブ。録画 73,000 行・棚 141・分類ルール 51 本・EPG 136,053 行、HTTP 経由の中央値）: 一覧 58 ms / 次回 15 ms
  - **次回の費用は「返す行数 × 分類ルール本」に比例する。** EPG 側の候補が 45,351 件になる棚（分類ルールが EPG の 1/3 を 1 つの棚に併合した病理的な場合）では 740 ms で、返す応答が 8.8 MB になる。実データの EPG は 6 日分 1,779 行（GR 19 サービス）なので、候補は数十件である

EPG 側はルールの当たりを持たない。10 分ごとに全行を書き直す同期に、再評価の契機をもう 1 つ足すことになるからである。
ハブの「次回」は起点の実効シリーズ v から引く。E(番組) = v は次のどちらかである。

- 値が v のルールが当たり、それより前（`priority DESC, id ASC` の順）のルールがどれも当たらない
- 自動キーの生成列が v で、どのルールも当たらない。値が v のルールだけを否定すると、別の値のルールに取られた番組が混ざる

**この 2 つを `epg_program_series` ビューの 2 本の UNION ALL として書く。**
`COALESCE(勝者の値, 自動キー)` の 1 式にすると、プランナは `value = $1` を
どちらの枝にも押し下げられない。EPG の全行で勝者を評価してから値を比べることになる
（136,053 行・ルール 51 本・sqlc / pgx 経由で 1.30 s。Seq Scan の Filter で 135,089 行が落ちる）。

2 本に割ると `value = $1` が両方の枝に入る。自動キーの枝は
`epg_programs_series_key_idx`（btree）で、ルールの枝は `epg_programs_name_trgm`
（`normalize_search_text(name)` の GIN）で引く。同じコーパスで 15 ms になる。

ルールの枝の LIKE は `label_rule_winner` の照合より狭くなってはならない。
狭い側にずれると、勝者が居るのに枝から漏れる番組が出る（結果が減るだけで例外は出ない）。

### 評価結果を宛先にしない

- 評価結果は作り直せるキャッシュであって、API の宛先ではない。当たりの行を指す API も、それを上書きする操作も作らない。KonomiTV はシリーズを FK と非正規化列に焼いて宛先にし、stuayu 版は焼いた引き当てキーの掃除機構を作り続けている
- 「自動棚 A を B に統合する」操作は作らない。導出値を宛先にした上書きは、正規化を変えた時点で宛先を失う
- 録画ルールからラベルを継承させない。勝者ルールだけを継承すると広いルールに黙って負け、作成時にコピーすると予約と録画で値が食い違う。「このルールで録れたもの」は `rule_id` の軸が既に持っている
- 手動でシリーズを上書きする層は置かない。録画にしか付けられないので、EPG 側の「次回」と非対称になる

### 資源同定: 起点は録画 id

番組ハブは、起点にした録画 1 件の id で同定する。
シリーズは起点の実効シリーズと等しい録画の集合として、毎回導出する。

- 正規化キーを URL に置くと、規則を変えた時点で 404 ではなく 0 件で黙って壊れる
- 録画 id は watcher が作る不可逆な事実の id で、導出器が作るキーではない（不変条件 9）
- 録画行は purge 後も tombstone とタイトルのスナップショットが残るので、起点の URL は腐らない
- 棚の中のどの録画を起点にしても、同じ集合になる

まだ録画の無い番組を起点にしたハブは作らない。`(site, programId)` は EPG のローリングウィンドウから外れると宛先を失う。

一覧 API の行の同一性（1 行 = 1 録画）はシリーズで絞っても変えない。
N 予約で同じ放送が 2 拠点から録れていれば、ハブに 2 行並ぶ。ドロップ統計で選び分ける運用では、それが正しい。
同じ放送をまとめるのは「次のエピソード」の UI だけで、再生できる行に限り、起点と同じ site を優先する。
開始時刻がずれて supersede されない failed 行（[schema/recordings.md](../schema/recordings.md)「`superseded_at`: failed 行が後続 record に枠を譲る」）を「次」に入れないためである。

シリーズ内の並びは放送日時順とする。話数は持たないので、重複排除を切ったルールでは再放送が「次」になりうる（頻度は未測定）。

経路はすべて単一ホスト名の Ingress で `/` の catch-all に落ち、api ロールが DB だけで答える（不変条件 1）。
`/api/sites/{site}/recordings` と `/api/media/` の下は streamer 行きの Prefix なので置かない（[api/deployment.md](../api/deployment.md)）。

### 不変条件 7 との整合

放送のシリーズ id を永続テーブルに入れる案は、記述子を使わない時点で消えた。
`label_rules` が持つのはユーザーが書いたキーワードと値だけで、mirakc 固有の概念を含まない。
名前は「ラベル」とし、mirakc の schedule tags（`schedule_sync.tags` / `record_sync.tags`）と区別する。
