## 6.5 チューナー射影と容量超過の判定

チューナーの本数と対応種別を `tuner_sync` に射影する。**不変条件（api は mirakc に問い合わせない）より、EPGStation のように起動時に `/api/tuners` を叩いて in-memory に持つ形は取れない**。EPG プロジェクションと同じ使い捨てプロジェクションとして扱えば、真実は mirakc のまま保てる。

対応種別が必須なのが決め手。GR 専用チューナーに BS は載らないので、本数だけを設定に手書きする案は成立しない。

### 主張するのは「超過」だけ。勝敗は予測しない

**着色・警告の対象は番組ではなく区間**。個別番組への「競合」表示は「この番組が負ける」という勝敗の主張だが、決めるのは mirakc であり、しかも Rokuban から見えない消費者（EPGStation の並走・ライブ視聴・EPG 収集ジョブ）がいるので我々には決められない。超過は区間の性質であって番組の性質ではない。

主張は**下界**に限る: **「超過している」は確実だが「収まる」は保証できない。** UI の文言も「この予約は競合しています」ではなく「この時間帯はチューナーが不足しています」。

これにより EPGStation 式の実装から消えるものが多い --- 予約ごとの競合フラグ列、優先度による貪欲詰め、負ける側を決定論的に決める順序、マージンの織り込み（mirakc は予約ごとのマージンを持たない）。

### 判定: 種別部分集合に縮約した Hall 条件

**需要の単位は「異なる物理チャンネル数」**。予約件数ではない（同一物理チャンネルなら 1 本で相乗りできる）。副産物としてマルチ編成が自然に畳まれる --- サブサービスは同一チャンネルなので需要 1。

数えるのは**reconciler が実際に schedule を作る予約だけ**。effective の `skip` が true の行と、never-scheduled（番組が終了したのに schedule が一度も観測されなかった事実）の欠測行がある予約は需要にならない。欠測は `never_scheduled_events` 表を放送イベントキーで引く。mirakc 由来の failed 試行は `recordings` にだけ現れるので需要除外にはならず、再試行経路を妨げない。

#### 縮約の条件は「隣接集合が同じ」であること

上では便宜的に「種別」と書いたが、縮約が成り立つ本当の条件は**需要の隣接集合が一致すること**（twin vertices）。同値類を何で切るかは予約モデルに依存する。

**N 予約の決定（[録画エンジン](../recording.md) §3.1）により、同値類は `(site, channel_type)` になる。** ruler は「マッチした全サイトで予約を作る」ので、BS 番組 P に対して `予約(site=A, P)` と `予約(site=B, P)` が独立に生まれ、reconciler はそれぞれのサイトの mirakc に schedule を作る。**サイトの選択は容量判定の自由度ではなく、ruler が既に行使し終えた選択**であり、判定が答えるのは「サイト A のチューナーでサイト A の予約群を賄えるか」だけになる。

これは電波の性質ではない。BS はどのサイトでも受信できるので、物理的には「BS 番組を録る」需要は全サイトの BS 対応チューナーに隣接している。分解が成り立つのは**予約が site に束縛されているという設計の帰結**である。

#### 判定はサイトごとに独立して行う

上記により二部グラフは**サイトごとに非連結**になる。

```
G = ⨆_site G_site        （サイト間に辺が存在しない）
```

Hall の条件は非連結グラフでは各成分について確認すれば十分。よって**予約とチューナーを site で分割し、各サイトについて独立に 15 通りを判定する**。種別を `(site, channel_type)` に拡張して `2^(サイト数 x 4)` 通り調べる必要はない --- 異なるサイト `A`, `B` は隣接集合が交わらないので `|N(A ∪ B)| = |N(A)| + |N(B)|` かつ `Σd(A∪B) = Σd(A) + Σd(B)` となり、混合した部分集合の制約は満たされた 2 つの制約の和として自動的に成立する。

**site は分割キーであって需要のキーには入らない。** 分割の内側では `(channel_type, channel)` が物理チャンネルを一意に定める（GR 27ch が東京と高松で別物であることは分割が処理する）。

**「1 予約 + サイト選好」に変えると分解は崩れる。** その設計（[録画エンジン](../recording.md) §3.1 で却下）では BS / CS の需要がサイトに束縛されないため、同値類は `{ (東京, GR) }, { (高松, GR) }, …, { BS 全サイト横断 }, { CS 全サイト横断 }` となり、`2^(サイト数 + 2)` 通りの判定になってサイト別計算はできない。縮約自体は生き残るが、**分解という都合の良い性質は N 予約の決定に依存している**。

#### 多サイト時は「サイトの不足 ≠ 番組の喪失」

分解の代償として、サイト A の不足はその番組が録れないことを意味しない --- A で負けても B の予約が生きていれば番組は残る。同一 `program_id` の予約が他サイトにあってそこが不足区間でなければ実質カバーされている、という判定は容易に書ける。警告が過剰に不安を与えないよう、多サイト時はここを区別する価値がある（サイトが 1 つの現状では意味を持たない）。

出力（超過区間リスト）もサイト単位になる。予約一覧のバッジは予約行の `site`（API が返す。[api.md](../api.md) の `Reservation`）を見るだけで決まり、メトリクスは `site` ラベル付きのゲージになる。**多サイト時のグリッド表示は未解決**（BS / CS は全国共通なので 1 行に畳めるが、地上波はサイトごとに別物なので畳めず、帯もサイトごとに要る）。多サイト化の論点として残す。

二部グラフの頂点は個別のチューナーだが、**同じ `channel_type` の需要はチューナーから見て隣接集合が完全に一致する**（twin vertices）ため、Hall の条件を**需要の部分集合ではなく種別の部分集合**について確認すれば十分になる。

需要 `d` の隣接集合は `N(d) = { t : type(d) ∈ t.types }` で `type(d)` にしか依存しないので、任意の `S ⊆ D` について `A = types(S)` とおくと `N(S) = N(A)`。`A` を固定すると `|N(S)|` は一定だが `|S|` は最大 `Σ_{t∈A} d[t]` まで動くので、**その最大ケースだけ調べれば同じ `A` を持つ他の全部分集合も自動的に満たされる**。

```
∀S ⊆ D: |N(S)| ≥ |S|   ⟺   ∀A ⊆ Types: Σ_{t∈A} d[t] ≤ |N(A)|
```

指数が `2^|D|` から `2^|Types|` に落ちる。種別は 4 つなので非空部分集合は 15 通り。

```
d[t]   = その区間で必要な種別 t の異なるチャンネル数
cap(A) = 種別集合 A のいずれかに対応するチューナー本数

すべての A ⊆ {GR,BS,CS,SKY} について   Σ_{t∈A} d[t] ≤ cap(A)
```

破れた `A` の `Σd − cap(A)` が**不足本数**、その `A` が**詰まった種別**の証拠になる。出力が boolean ではなく「BS が 1 本不足」になる。

GR/BS 両対応チューナーが混ざると単純な「重なり数 vs 総本数」では検出できないケースが出る。T1={GR}, T2={GR,BS} に対し「GR 1 + BS 2」は総本数（2）が足りているのに `{BS}`: 2≤1 が破れる。

`cap` に数えるのは**存在して恒久的に壊れていない**チューナー（設定で無効化・故障報告は除外）。**現在の利用者は引かない** --- 一時的な占有であり将来の区間の容量とは無関係で、「見えない消費者は数えない = 下界」の性質と一貫する。

**この除外条件は Mirakurun のセマンティクスであって、mirakc に対しては恒真である。**
`/api/tuners` は Mirakurun 互換 API である。Mirakurun 本体では `isFault` は
チューナープロセスの `error` を 3 回数えたら立つラッチで、以後クリアされない
（`TunerDevice.ts`）。`isAvailable` は fault が立っていると二度と true に戻らない。
**mirakc はこの 2 つを実装していない。** リテラルの `true` / `false` を返す。
根拠は `mirakc-core/src/models.rs` の doc comment（`Always true.` /
`Always false.`）。2019 年の初回実装から条件分岐が入った形跡は無い。
設定で無効化したチューナーはそもそも一覧に現れない（mirakc が起動時に落とす）。
したがって mirakc 相手では `is_available AND NOT is_fault` は射影の全行に一致する。
**式は残す** --- 互換 API の契約としては正当で、mirakc が将来実装したときに効く。
ただし**この条件が容量を減らすことに依存した設計をしてはいけない**（減らない）。

### これは原理的に近似であり、誤りの向きが偏っている

**予約が競合するかを確実に知る術はない。** 見えない消費者（EPGStation の並走・ライブ視聴・EPG 収集ジョブ）がいる以上、この判定は本質的に近似値であって、正解を計算しているわけではない。したがって選定基準は厳密性ではなく**有用性と説明可能性**であり、計算量のために近似で妥協するのは正当な選択肢になる。

twin vertices の縮約も、実は前提が完全には成り立たない。mirakc の `TunerConfig` には `excluded_channels`（特定チャンネルを除外する設定）があり、これを使うと**同一種別内で需要の隣接集合が異なる**ため縮約の前提が壊れる。ただし `/api/tuners` のレスポンス（`MirakurunTuner`）に `excluded_channels` は含まれないので、**API 経由で知る術がない = 種別のみが API の許す精度**である。

**既知の盲点はすべて「警告しすぎない」方向に偏っている**ことを認識しておく。

| 盲点 | 実際の容量への影響 | 誤りの向き |
|---|---|---|
| 見えない消費者（並走 EPGStation / ライブ視聴 / EPG 収集） | 減る | 警告を見逃す |
| `excluded_channels` による除外 | 減る | 警告を見逃す |

（mirakc の多段集約によるサイト間の容量共有は盲点にならない --- その構成自体を非サポートとする。[録画エンジン](../recording.md) §9）

つまり **「不足している」という主張は信頼できるが、沈黙は保証ではない**。UI は沈黙を「大丈夫」と読ませてはいけない（だから文言は「この時間帯はチューナーが不足しています」の側だけを出し、「収まります」とは言わない）。

縮約は必須ではない。将来 `excluded_channels` が API に載るか設定から読めるようになったら、素の二部マッチングに戻せばよい（需要 ≤ 10、チューナー ≤ 10 の規模なので素朴な増加路法で足りる）。縮約を選ぶ理由は計算量ではなく、**不足本数と詰まった種別が副産物として出る**という UI 上の利点にある。

### 計算: 累積和はチャンネル単位に張り、0↔1 遷移だけを拾う

重いのは 15 通りの判定ではなく**各区間での異なりチャンネル数の数え直し**。

**純粋な imos 法（予約に ±1 して累積和）は誤り。** 需要は和ではなく異なり数なので、同一チャンネルの 2 予約は 1 と数える必要がある。累積和はチャンネル単位に張り、`0→1` / `1→0` の遷移でのみ `d[t]` を増減させる。既に埋まっているチャンネルへのイベントは `d` を変えないので判定をスキップできる（チャンネル共有が効くほど計算量が落ちる）。

部分集合の判定も差分化できる。`d[t]` が ±1 したとき影響を受けるのは `t` を含む 8 通りだけなので、16 個の `Σd − cap(A)` を保持して 8 個更新し最大値を見れば `O(1)` 判定。

**窓ごとに解かず、地平線全体を 1 回解く。** 予約集合はローリングウィンドウで有界なので、8 日分を 1 回走って**結合済みの超過区間リスト**を作り、全クエリをその上の範囲検索に落とす。

| クエリ | 計算 |
|---|---|
| グリッドの帯（窓 [a,b]） | 二分探索 + 交差 |
| 予約一覧のバッジ | 自分の区間との交差判定 |
| メトリクスのゲージ | 区間数を数える |
| 「この予約を追加したら超過するか」 | 候補を足して再走査（`O(E)` なので素直に） |

区間リストは `(予約, チューナー射影)` の純関数なので api プロセス内にメモリキャッシュできる。**ただし api は NOTIFY を LISTEN しない**（LISTEN セッションは notifier ロールの持ち物であり、api はサーバーレスで scale-to-zero する前提のため常駐 LISTEN を持てない。[api.md](../api.md) 参照）。したがってこのキャッシュの無効化は NOTIFY 経由の即時無効化ではなく **TTL 依存**にする。導出状態なので複数レプリカが各自で持ってよく、キャッシュミス/期限切れは毎回 8 日分を再走査するだけで数十マイクロ秒のオーダーに収まるため、TTL だけで十分回復する（キャッシュは念のための位置づけであり、鮮度を NOTIFY に頼る設計にはしない）。

### 実装で決めたこと

`internal/capacity`（`Compute` が純関数、`Load` が DB 読み）と `internal/worker/tuner.go`（射影ジョブ）。

**射影が 1 行も無いサイトは何も主張しない**（超過区間を返さない）。これは docs に無かった case で、実装時に決めた。`tuner_sync` からは「チューナーが 0 本」と「まだ同期していない」を区別できず、後者を容量ゼロとして扱うと全区間が超過になって警告が洪水になる。上に書いた「既知の盲点はすべて警告を見逃す方向に偏っている」という性質を、**我々自身の無知で崩さない**ための規律である。ただし**行が 1 つでもあれば全台が故障でも判定する** --- それは射影された事実であって無知ではない。

- `cap` に数えるのは `is_available AND NOT is_fault`。この判定は `internal/capacity` 側に置き、**SQL では絞らない**（SQL で絞ると上記の「0 行」と「全台故障」が区別できなくなる）
- 未知の `channel_type` を含むチューナーは**そのチューナーごと捨てる**。未知の種別だけ落として残りを投影すると「その種別に対応していないチューナー」として `cap(A)` に数えられ、警告を見逃す方向に誤る（`EpgSyncWorker` が未知の種別のサービスを捨てるのと同じ規律だが、捨てる単位が違う）
- **区間の結合は `(不足本数, 詰まった種別)` が一致するときだけ。** 隣接区間を無条件に結合して最大値を報告すると、不足が小さい部分区間について知らないことを主張してしまう（下界に限る原則に反する）
- `jammedTypes` は破れた `A` のうち**不足本数最大 → 要素数最少**を選ぶ（「BS が 1 本不足」と狭く言い当てるため）
- 半開区間性を保証しているのは**同時刻イベントをまとめて反映してから判定すること**であって、開始/終了の処理順ではない。当初は「終了を先に」ソートしていたが、その並べ替えを反転しても結果が変わらないことが確認できたので削除した（観測できない規則を残さない）
- 15 マスクは毎遷移で全再計算する。docs が挙げた差分化（`t` を含む 8 通りだけ更新）は 64 演算に対して割に合わないため未実装

未実装のまま残したもの: メモリキャッシュ（TTL 依存）、多サイト時の「同一 `program_id` が他サイトでカバーされている」区別（サイトが 1 つの現状では意味を持たない）。

### 前提: 予約にチャンネルのスナップショットが要る

需要の単位が `(channel_type, channel)` なので、予約側に `network_id` / `service_id` / `channel_type` / `channel` のスナップショット列が必要になる。**使い捨ての EPG 射影への JOIN に頼ると、射影が刈られた/欠損した瞬間に容量判定が壊れる**。録画行への非正規化スナップショット（§6、[projections.md](projections.md)）と同じ規律で、予約時に焼き付ける。この列は `reservations` ではなく `program_snapshots`（[スキーマ](../schema.md) §3.7）にあり、`reservations` は `(site, program_id)` の FK で JOIN して読む

既知の盲点: mirakc の `update-schedules` ジョブは周期が分かっているので、cron 設定を取得できれば需要に織り込んで精度を上げられる（API で取得可能かは未確認）。

## 経緯と失敗事例

- チューナー射影の設計は issue #21、実装は M2-10
- 需要から除外する never-scheduled の判定は、当初 `reservations` の `orphaned` 状態（のちの `orphaned_at` 列）、次に `recordings` の擬似 failed 行から導出していた。現在は試行と欠測を分け、`never_scheduled_events` 専用表の行の存在を放送イベントキーで引く。`recordings` の failed 試行は除外条件に含めない
