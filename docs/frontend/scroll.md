# 番組リストの時間窓の読み込み

番組リスト（[programs.md](programs.md)「番組リスト」）の時間窓の継ぎ足し。窓の管理は
`pages/programs.tsx`、仮想化は `components/program-list.tsx`、純関数は
`lib/program-list.ts`。

**この領域は jsdom で原理的に検出できない壊れ方を繰り返した経緯がある**
（[web/e2e/README.md](../../web/e2e/README.md) 冒頭）。

## 進行方向の読み込み

- 6 時間（`windowHours`）ぶんずつの自動読み込み + ボタンの受け皿。リスト末尾の
  番兵を IntersectionObserver で見て `fetchNextPage()` を呼ぶ。失敗したら自動を
  無効化しボタン + エラー表示に落とす（さもないと失敗したまま無限にリクエストを
  投げ続ける）。「さらに読み込む」ボタンは自動が効いている通常時は隠すが、消しは
  しない --- 番兵が発火しない環境・キーボード操作・失敗後の再試行の受け皿として残る
- **計測できない環境（`lib/list-virtualization.ts` の `domLayoutMeasurable()` が
  false）では IntersectionObserver 自体を作らない。** jsdom は番兵が常時可視と
  判定されるおそれがあり、際限なく読み込みを走らせてしまう。この環境ではボタン
  だけを受け皿にする
- `pages/programs.tsx` の `useInfiniteQuery` は pageParam / ページの形を
  `{ startMs, endMs }`（取得した半開区間そのもの）にしてあり、`step` のような
  抽象的なカーソルにしていない
- **レイアウト・スクロール位置は jsdom で計測できない。** 計測できない環境では
  仮想化・IntersectionObserver・`scrollToIndex` を使わず、合否判定は `web/e2e/`
  の実ブラウザで行う（`web/e2e/README.md`）

## 遡行（前の時間窓の先頭挿入）はしない

到達経路が「DayStrip で未来の日へジャンプ → 上端まで戻る → 押す」の一択で、
代替（DayStrip で前の日をタップ）が既にある。先頭挿入の位置復元は仮想化・sticky
ヘッダと構造的に衝突し、実機退行 3 回分の機構（`web/e2e/README.md`）を要した。

## ボトムタブの裏に隠れる行

`main` の `padding-bottom`（`--bottom-nav-height`）が防げるのは**ドキュメント
最下端まで実際にスクロールしたときの重なりだけ**である。それ以外のスクロール
位置（初回表示を含む）で行の境界がタブの上端とずれれば、その行はタブの裏に
半分入る（390×844 の実測で 29px。`web/e2e/programs-bottom-nav.mjs` の④が
毎回この値を表示する）。

**「初回表示だけ重なり量ぶん `window.scrollBy` で押し出す」は採らない。**
リストの先頭行は常に日付ヘッダ（`sticky`）の直下に隙間なく続く。一様に
スクロールすると、末尾で消した量とちょうど同じだけ先頭行が日付ヘッダの
裏へ入る（実測で 29px → 29px）--- 同じ欠陥を反対の端に動かすだけである。

未解決: 消すには `<main>` をタブの高さぶん削って内側スクロール容器にする、
あるいはタブを重ねずに専有領域として確保するなど、ページ全体スクロール
という前提を変える設計判断が要る。以下はその判断基準。

### 判定基準: 高さの式を持つか、持たないか

候補は 2 つある。(A) `<main>` を `100dvh - navHeight` の内側スクロール容器に
する。(B) タブを重ねない専有領域にする。

この 2 つは実装として収斂する。タブを「常に見える」まま「専有領域」にする
には、タブを flex の兄弟として `h-dvh` の外枠に組み込むしかない。残りを
`<main>` に `flex-1` で持たせる形である。「専有領域」と「常時可視」を
`sticky` だけで両立する手段は無い --- `sticky` はその要素の静的位置が現在の
スクロール範囲に入っているときしか効かない。番組リストの途中を見ている間、
タブの静的位置は文書の末尾にあるままなので効かない。つまり (A)(B) どちらを
選んでも、番組リストの仮想化を `useWindowVirtualizer` から要素スクロール
（`useVirtualizer` + 自前のスクロール容器）へ移す設計変更を伴う。この移行
コストは選ぶ側に依らない。

決め手になるのは、その後に残る「タブの高さを誰が保証するか」の 1 点である。

- **(A)**: `<main>` の `height` を `100dvh - var(--bottom-nav-height)` の
  ような式で決める。この式が正しく動くには、`--bottom-nav-height` が実際の
  描画高さと一致し続ける必要がある。**これはこの症状そのものを生んだ計算式
  と同じ形**である。同じ変数から境界線の 1px 分が抜け落ちていた過去の
  不具合も、この式の入力がずれて起きた。式の入力を増やしても「転記が
  ずれたら壊れる」性質そのものは消えない。
- **(B)**: タブを `position: fixed` から外し、外枠の flex レイアウトの実際の
  子（`shrink-0`）にする。`<main>` 側は `flex-1` を持つだけで高さの式を書か
  ずに済む。ブラウザの box model がタブの実寸をそのまま消費するので、
  `--bottom-nav-height` の値が実際の描画高さとずれるという failure mode が
  構造的に存在しなくなる。

不変条件 9〜13 の精神（導出できる値を式に焼くと転記がずれる）に照らすと
(B) が優先される。決め手は「タブの高さを表す値を、別要素の高さ計算の入力
として複製するか（A）、ブラウザの box model にそのまま解かせて複製自体を
無くすか（B）」である。後者は failure mode そのものが起こらない。

### 実測: 移動するコードと引き継がれない前提

- 仮想化: `web/src/components/program-list.tsx` の `useWindowVirtualizer` を
  `useVirtualizer` に変える。`scrollMarginRef`（`listRef.current?.offsetTop`
  で計測）と `ProgramListHandle.scrollToDayOffset`
  （`virtualizer.scrollToIndex`）は仕組み自体は残る。ただし測る対象を
  window から新しいスクロール容器へ付け替える必要がある。
- `web/src/pages/programs.tsx` の日付ジャンプ時のリセット（`originMs` 変化を
  見る `useLayoutEffect`）は `window.scrollTo(0, 0)` と
  `window.dispatchEvent(new Event('scroll'))` で virtualizer を同期させて
  いる。要素スクロールでは対象をスクロール容器の ref に変える。
  `dispatchEvent` もその要素に対して行う必要がある。
- **既存の位置復元 e2e が 2 本、この移行で壊れる。**
  `web/e2e/checks.mjs`（日付ジャンプ・再タップの位置復元）は `window.scrollY`
  / `document.documentElement.scrollHeight` / `page.mouse.wheel` に依存
  する。`web/e2e/programs-bottom-nav.mjs` の `atBottom` 判定と末尾までの
  スクロールループも同じ window API に依存する。要素スクロールに変えると、
  これらは落ちるのではなく**黙って無意味な値を測り続ける**（スクロールが
  要素側で起きるので `window.scrollY` が動かなくなる）。書き換え忘れに気付く
  手段が無いので、移行と同じ PR で両方とも書き換えることが要る。
- sticky な日付見出し（`program-list.tsx` の
  `h2[data-testid="program-list-date-heading"]`）は仕様上「最も近いスクロール
  祖先」を基準にする。`<main>` が新しいスクロール祖先になっても仕組みは
  変わらないはずである。ただし**実ブラウザでの確認はまだ無い**（未検証）。

### 未検証: `100dvh` と動的 URL バー

モバイル実機（Safari・Chrome for Android）は、ページ本体のスクロールに応じて
アドレスバーの表示・非表示を切り替える。その分だけ `100dvh` の解決値が変わる
（`100svh` は常に小さい方、`100lvh` は常に大きい方に固定される）。

**この挙動が web/e2e の Playwright では再現できないことを実測した。**
`100dvh` / `100svh` / `100lvh` それぞれの高さを持つ `div` を 3 つ置いた
ページを作った。390×844 の Playwright ビューポートで開いた。3 つとも
`844px`（`window.innerHeight` と同一）になり、区別がつかなかった。
Playwright はツールバーの開閉という実ブラウザの副作用を再現する手段を
持たない。これは web/e2e というハーネス自体の限界であり、実機でしか測れない。

したがって次は未検証のまま残る。

- 番組リストのスクロールを window から `<main>` 内の要素スクロールへ移した
  とき、実機のツールバー開閉判定がその内側スクロールにも反応するか
- 反応しない場合、ツールバーが閉じて可視領域が広がっても `100dvh` ベースの
  高さが展開時の値に固定され、閉じた分だけ余白や隙間が実際に見えるか

これは実装した後でないと実機でしか測れない。実装 PR 側で実機確認
（`docs/runbook.md`）を要求する。

### 観測④を合否へ格上げする条件

`web/e2e/programs-bottom-nav.mjs` の④（初回表示でタブの裏に入っている画素数）
は、(A)(B) いずれかが実装され、かつ次の 2 つを満たすまでは表示のみに留める。

1. **④ を「初回表示だけ」から「スクロール範囲を複数点サンプルした状態」に
   広げる。** 今の②③が最下端しか見ていないのと同じ理由で、初回表示だけでは
   この症状（任意のスクロール位置で起きる）を代表しない。少なくとも scrollTop
   が 0 / 中間 / 最下端の 3 点で `straddling` が空であることを見る。
2. **位置復元の既存判定が新しい実装に対して green であることを確認する。**
   対象は `web/e2e/checks.mjs` の①②。④ を格上げする同じ PR で見る。④ だけを
   直しても、位置復元が壊れていないことを別に確認しないと、「隠れなくなった
   が位置復元も一緒に壊れた」を green のまま見逃す。

しきい値は `straddling.length === 0`（0px、寛容度なし）にする。①が計算の
一致を 0.5px の丸め誤差だけ許すのとは違い、これは「行がタブの裏に入って
いるか」という真偽の性質である。③で述べた「意味の無い数字を期待値にしない」
注意はここには当てはまらない。構造的に直っていれば、任意のスクロール位置で
常に 0 件になるはずである。1px でも出ればまだ直っていない。

### 推奨: (B)

(A) は「タブの高さを表す値を式に複製する」という failure mode をそのまま
残す。この失敗の形は、この症状と過去の境界線 1px 分の計算漏れの両方を生んだ
ものと同じである。式の入力を変えるだけでは failure mode 自体は消えない。
(B) はこれを box model に解かせて構造的に無くす。

番組表グリッド（`lg` 以上）は既に `ProgramGridView` で内側スクロール容器を
持つ。高さは `--page-header-height` と `--sticky-banners-height` を引いた
`100dvh` の calc 式である。(B) はこのパターンをモバイルのリストにも一貫させる
形になる。グリッドは既に「ページ全体スクロール」という前提を持たない。
リスト側だけがその前提を残す理由は薄い。

`--bottom-nav-height` は `toaster.tsx` のトースト位置合わせにも使われている。
(B) で `<main>` の高さ計算からこの変数を外しても、トースト側は別の理由で
この変数を要り続ける可能性がある。これはリストのスクロール容器とは別の関心
である。この判断がトーストの実装まで変える必要は無い。

ただし (B) は `components/app-shell.tsx` 全体のレイアウトを変える差分になる。
(A) より影響範囲が広い。`StickyBanners` / `BottomTabs` / 外枠の flex 構造
すべてが対象になる。着手前に、この広さが 1 PR で閉じる粒度かを確認する。
閉じないなら前置タスクに割ること。

## テストの範囲

**フレーム単位の跳ね・スクロール位置合わせの見た目自体は、jsdom では検証
できない。** `getBoundingClientRect` が常に 0 を返しレイアウトを計算しない
環境なので、`ProgramList` はこの環境では仮想化そのものをバイパスし
`scrollToIndex` を呼ばない。実機（Playwright を使った実ブラウザでの計測。
`web/e2e/`）で判定している。「いま見ている日」のスクロール追従も同様に
自動テストでは検証できない（純関数の導出ロジック自体はテスト済み）。グリッドの
「受け入れは実機で行う」（[programs.md](programs.md)）と同じ扱い。
