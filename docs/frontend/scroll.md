# 番組リストの時間窓の読み込み

番組リスト（[programs.md](programs.md)「番組リスト」）の時間窓の継ぎ足し。窓の管理は
`pages/programs.tsx`、仮想化は `components/program-list.tsx`、純関数は
`lib/program-list.ts`。

**この領域は jsdom で原理的に検出できない壊れ方を繰り返した経緯がある**
（[web/e2e/README.md](../../web/e2e/README.md) 冒頭）。

## 進行方向の読み込み

- 6 時間（`windowHours`）ぶんずつの自動読み込み + ボタンの受け皿。リスト末尾の
  番兵を IntersectionObserver で見て `fetchNextPage()` を呼ぶ。失敗したら自動を
  無効化しボタン + エラー表示に落とす（さもないと失敗したまま無限にリクエストを
  投げ続ける）。「さらに読み込む」ボタンは自動が効いている通常時は隠すが、消しは
  しない --- 番兵が発火しない環境・キーボード操作・失敗後の再試行の受け皿として残る
- **計測できない環境（`lib/list-virtualization.ts` の `domLayoutMeasurable()` が
  false）では IntersectionObserver 自体を作らない。** jsdom は番兵が常時可視と
  判定されるおそれがあり、際限なく読み込みを走らせてしまう。この環境ではボタン
  だけを受け皿にする
- `pages/programs.tsx` の `useInfiniteQuery` は pageParam / ページの形を
  `{ startMs, endMs }`（取得した半開区間そのもの）にしてあり、`step` のような
  抽象的なカーソルにしていない
- **レイアウト・スクロール位置は jsdom で計測できない。** 計測できない環境では
  仮想化・IntersectionObserver・`scrollToIndex` を使わず、合否判定は `web/e2e/`
  の実ブラウザで行う（`web/e2e/README.md`）

## 遡行（前の時間窓の先頭挿入）はしない

到達経路が「DayStrip で未来の日へジャンプ → 上端まで戻る → 押す」の一択で、
代替（DayStrip で前の日をタップ）が既にある。先頭挿入の位置復元は仮想化・sticky
ヘッダと構造的に衝突し、実機退行 3 回分の機構（`web/e2e/README.md`）を要した。

## ボトムタブの裏に隠れる行

`main` の `padding-bottom`（`--bottom-nav-height`）が防げるのは**ドキュメント
最下端まで実際にスクロールしたときの重なりだけ**である。それ以外のスクロール
位置（初回表示を含む）で行の境界がタブの上端とずれれば、その行はタブの裏に
半分入る（390×844 の実測で 29px。`web/e2e/programs-bottom-nav.mjs` の④が
毎回この値を表示する）。

**「初回表示だけ重なり量ぶん `window.scrollBy` で押し出す」は採らない。**
リストの先頭行は常に日付ヘッダ（`sticky`）の直下に隙間なく続く。一様に
スクロールすると、末尾で消した量とちょうど同じだけ先頭行が日付ヘッダの
裏へ入る（実測で 29px → 29px）--- 同じ欠陥を反対の端に動かすだけである。

未解決: 消すには `<main>` をタブの高さぶん削って内側スクロール容器にする、
あるいはタブを重ねずに専有領域として確保するなど、ページ全体スクロール
という前提を変える設計判断が要る。以下はその判断基準。

### 未決: ブレークポイントの適用範囲

(A)(B) どちらを選ぶ場合も、先に決めることがもう 1 つある。内側スクロール
容器化を **モバイルだけ**（`md` 未満）に限るか、**全幅**に広げるかである。

**この 2 つは対称な選択ではない。** `BottomTabs` は `md:hidden`、`<main>` は
`md:pb-0` である（`app-shell.tsx`）。つまり**この症状自体が `md` 未満でしか
起きない**。全幅にしてもユーザーから見える利益は無く、得るのは仮想化フックを
1 つにできることだけである。

- **モバイルだけ**にすると、デスクトップ（`lg` 以上のグリッド、`md` 以上の
  リスト）は今のまま window スクロールに残る。ただし `ProgramList` の
  仮想化フックはブレークポイントをまたいで**切り替えられない**（フックは
  マウント中に別のフックへ差し替えられない。React のフック規則そのもの
  である）。`useWindowVirtualizer` と `useVirtualizer` の両方を持ち、幅で
  出し分ける実装が要る。**この出し分け自体も新たなコストを生む**: 画面幅が
  `md` をまたぐたびに一方のフックからもう一方へコンポーネントごと入れ替わる
  （1 つのコンポーネント内でフックの並びを変えると React が例外を投げるため、
  幅で出し分けるには 2 つのコンポーネントかキー付き再マウントが要る）ため、
  リサイズやウィンドウ移動で `md` をまたぐと仮想化の内部状態が作り直され、
  スクロール位置が失われる。
- **全幅**にすると、フックは 1 つで済むが、デスクトップのスクロールモデルも
  変わる。`web/e2e/checks.mjs`（1280×800 で実行）が対象に入り、
  `ProgramGridView` が既に持つ `100dvh` の内側スクロール容器
  （`programs.tsx:984`）の中に、リストの内側スクロール容器がさらに
  ネストする形になる。存在しない症状のためにこの 2 つを払う。

この選択によって、後述の e2e 影響範囲・実装コストの両方が変わる。次の
各節は「どちらを選んでも共通のコスト」と「選択に依存するコスト」を
分けて書く。

### 判定基準: 高さの式を持つか、持たないか

候補は 2 つある。(A) `<main>` を `100dvh - navHeight` の内側スクロール容器に
する。(B) タブを重ねない専有領域にする。

**両方とも、内側スクロール容器化を伴う。** `useWindowVirtualizer` から
要素スクロール（`useVirtualizer`）への移行も両方に共通する。決め手は
そこではない --- 確保した空間が**ドキュメントの末尾**にあるか**現在の
ビューポート**にあるかである。

`position: sticky; bottom: 0` を文書の最後尾に置く第 3 の案を実測した
（`html,body` を編集しない window スクロールのまま、`nav` だけ `sticky`
にする）。65px 分の flow 空間は確かに確保され（`scrollHeight` が nav を
消すと 65px 縮む）、nav は全スクロール位置で `visible: true` のまま
（`navTop` が常に 779px で不変）だった。**これは今の `fixed` +
`padding-bottom` と同じ振る舞いである。** 確保した空間はドキュメントの
末尾にあるままなので、末尾以外のスクロール位置では相変わらず行が nav の
裏に回り込む。実測（60 行 × 80px、390×844）:

| scrollY | navTop | straddling |
|---|---|---|
| 0 | 779 | 1 |
| 1000 | 779 | 1 |
| 4081（末尾） | 779 | 0 |

**`sticky` は今の重なりから逃れる手段ではない。** 確保した空間を
「ビューポートの下端」に置く必要がある。それには、スクロールする箱を
`100dvh` 相当に収める内側スクロール容器化が要る。これが (A)(B) 共通の
コストの正体である。

決め手になるのは、その内側スクロール容器化の**先**に残る「タブの高さを
誰が保証するか」の 1 点である。

- **(A)**: `<main>` の `height` を `100dvh - var(--bottom-nav-height)` の
  ような式で決める。この式が正しく動くには、`--bottom-nav-height` が実際の
  描画高さと一致し続ける必要がある。**これは以前このリポジトリで一度
  ずれた式と同じ形**である --- `--bottom-nav-height` から境界線の 1px が
  抜け落ちていた過去の不具合（式の入力が実測とずれた）。ただしその不具合
  自体は今回の 29px の重なりを生んだものでは**ない**（当時の実測では
  最下端の重なりはちょうど 0px で、見た目に隠れていた行は無かった。式が
  持つ「転記がずれたら壊れる」性質だけが同じである）。
- **(B)**: タブを `position: fixed` から外し、外枠の flex レイアウトの実際の
  子（`shrink-0`）にする。`<main>` 側は `flex-1` を持つだけで高さの式を書か
  ずに済む。ブラウザの box model がタブの実寸をそのまま消費するので、
  `<main>` の高さ計算に関しては `--bottom-nav-height` の値が実際の描画高さ
  とずれるという failure mode が構造的に存在しなくなる（ただし他の消費者は
  残る。下記「実測」参照）。

不変条件 9〜13 の精神（導出できる値を式に焼くと転記がずれる）に照らすと
(B) が優先される。決め手は「タブの高さを表す値を、`<main>` の高さ計算の
入力として複製するか（A）、ブラウザの box model にそのまま解かせて複製
自体を無くすか（B）」である。

### 実測: 移動するコードと引き継がれない前提

- 仮想化: `web/src/components/program-list.tsx` の `useWindowVirtualizer` を
  `useVirtualizer` に変える。`scrollMarginRef`（`listRef.current?.offsetTop`
  で計測）と `ProgramListHandle.scrollToDayOffset`
  （`virtualizer.scrollToIndex`）は仕組み自体は残る。ただし測る対象を
  window から新しいスクロール容器へ付け替える必要がある。
- `web/src/pages/programs.tsx` の日付ジャンプ時のリセット（`originMs` 変化を
  見る `useLayoutEffect`）は `window.scrollTo(0, 0)` と
  `window.dispatchEvent(new Event('scroll'))` で virtualizer を同期させて
  いる。要素スクロールでは対象をスクロール容器の ref に変える。
  `dispatchEvent` もその要素に対して行う必要がある。
- sticky な日付見出し（`program-list.tsx` の
  `h2[data-testid="program-list-date-heading"]`）は仕様上「最も近いスクロール
  祖先」を基準にする。`<main>` が新しいスクロール祖先になっても仕組みは
  変わらないはずである。ただし**実ブラウザでの確認はまだ無い**（未検証）。
- **`StickyBanners` と `PageHeader` のオフセット結合が崩れる。**
  `StickyBanners`（`app-shell.tsx`）は今 `<main>` の**兄弟**で、window を
  共通のスクロールポートとして共有している。`PageHeader`
  （`page.tsx:59`）は `top: var(--sticky-banners-height, 0px)` でこの共有
  ポートに合わせて自分をずらしている。`<main>` だけが要素スクロールに
  変わると `StickyBanners` は新しいスクロールポートの外に出て、もう
  スクロールに追従しない。バナー発動中は `PageHeader` のオフセットが
  二重取りになり、`<main>` の上端にバナーの高さぶんの隙間が残る。これは
  `<main>` を触る作業と同じファイルで発生する既知のコストであり、未検証の
  棚上げにはしない。
- **`--bottom-nav-height` の消費者は `<main>` だけではない。** `toaster.tsx`
  のトースト（`pb-[calc(var(--bottom-nav-height)+0.5rem)]`）も同じ変数を
  使う。`recordings.tsx` の一括操作バー（`bottom-[var(--bottom-nav-height)]`）
  も同じである。どちらも `fixed` のまま、この変数でタブの上に自分を
  持ち上げている。
  (B) が消すのは `<main>` の高さ計算からの依存だけである。この 2 箇所は
  変数が実測とずれる余地を残したまま残る。「(B) はこの failure mode を
  構造的に無くす」は**`<main>` の高さ予算に限った話**であり、リポジトリ
  全体からこの変数の転記依存が消えるわけではない。

### 既存 e2e が壊れる形はスクリプトごとに違う

内側スクロール容器化は既存の e2e 判定 2 本を壊す。**どちらも「落ちて教えて
くれる」形では壊れない**ので、移行と同じ PR で書き換えることが前提になる。

**`web/e2e/programs-bottom-nav.mjs`（390×844。常にモバイル幅）**: 内側
スクロール容器化した初期状態では `window.scrollY === 0` である。
`document.documentElement.scrollHeight` もビューポート高に一致する。
この 2 つのせいで `atBottom` の判定
（`|scrollY - (scrollHeight - innerHeight)| < 2`）が**初回ビューポートの
まま真になる**。「最下端までスクロールできていない」を検知するはずの
ガードが発火せず、`window.scrollTo(0, scrollHeight)` は no-op のまま
ループが 8 回で抜ける。結果として②③は**初回表示を最下端だと思い込んだ
まま**判定する。このスクリプトの検出力は `min-h-14` → `min-h-16` の変異で
①②が落ちることで確認済みだが、その検出力は丸ごと失われる。

**`web/e2e/checks.mjs`（1280×800）**: 影響は「未決: ブレークポイントの
適用範囲」の選択に依存する。全幅で内側スクロール容器化する場合:

- `:88` の `if (minHeight <= 850)` は、`document.documentElement.scrollHeight`
  が要素スクロール化で恒久的にビューポート高（800px）近辺に固定されるため
  **常に真になり、実際には起きていない「文書高さがビューポートまで潰れた」
  という誤った診断で毎回 NG になる**。issue #299 の再発と誤認されうる。
- `:90` と `:119` は「`scrollY` が一定値以下であること」しか見ない片側だけの
  アサーションである。`window.scrollY` が要素スクロール化で常に 0 に
  固定されると、この 2 つは**復元が完璧に効いた場合と見分けがつかないまま
  素通りする**。`:114-118` のコメントが `scrollY` を主たる oracle だと
  明記している、まさにその値が動かなくなる。
- `:98` の `page.mouse.wheel` は要素スクロールへ切り替わった後も呼び出し
  自体は成立する（例外にならない）が、実際に `<main>` 側のスクロール量を
  進めるかは**未検証**。仮に進まなくても、上記のとおり `window.scrollY` は
  そもそも動かない値になるため、②の判定はどちらにしても意味を失う。

**この 2 本を「移行と同じ PR で書き換える」だけでは足りない。** 書き換えた
版で 2 つを確認する必要がある。(a) 今の window スクロール実装に対して
今までどおり pass すること。(b) `min-h-14` → `min-h-16` の変異で今までどおり
落ちること。この 2 つをレイアウトの変更より**先に**確認できて初めて、
書き換え自体が正しいと言える（次節の「推奨」で PR を分ける理由）。

### 未検証: `100dvh` と動的 URL バー

モバイル実機（Safari・Chrome for Android）は、ページ本体のスクロールに応じて
アドレスバーの表示・非表示を切り替える。その分だけ `100dvh` の解決値が変わる
（`100svh` は常に小さい方、`100lvh` は常に大きい方に固定される）。

**この挙動が web/e2e の Playwright では再現できないことを実測した。**
`100dvh` / `100svh` / `100lvh` それぞれの高さを持つ `div` を 3 つ置いた
ページを作った。390×844 の Playwright ビューポートで開いた。3 つとも
`844px`（`window.innerHeight` と同一）になり、区別がつかなかった。
Playwright はツールバーの開閉という実ブラウザの副作用を再現する手段を
持たない。これは web/e2e というハーネス自体の限界であり、実機でしか測れない。

したがって次は未検証のまま残る。

- 番組リストのスクロールを window から `<main>` 内の要素スクロールへ移した
  とき、実機のツールバー開閉判定がその内側スクロールにも反応するか
- 反応しない場合、ツールバーが閉じて可視領域が広がっても `100dvh` ベースの
  高さが展開時の値に固定され、閉じた分だけ余白や隙間が実際に見えるか

これは実装した後でないと実機でしか測れない。実装 PR 側で実機確認
（`docs/runbook.md`）を要求する。

### 観測④を合否へ格上げする条件

**今の `straddling` 述語（行の矩形がタブの矩形と交差するか）は昇格させない。**
`getBoundingClientRect()` はスクロール祖先の `overflow` でクリップされない。
内側スクロール容器化した (A)(B) の**構造的に正しい実装**で実測した。
`<main>` の外（クリップされて見えていない）行が、なお rect 上は nav と
交差し続ける。①③相当の 3 点（scrollTop = 0 / 中間 / 末尾）で誤検知する:

| scrollTop | navTop | mainBottom | straddling | worst |
|---|---|---|---|---|
| 0 | 779 | 779 | 1 | 31px |
| 1234（中間） | 779 | 779 | 1 | 12px |
| 4081（末尾） | 779 | 779 | 0 | 0px |

正しい実装なのに scrollTop = 0（初回表示）で「31px 隠れている」と出る。
これは今回の症状（29px）より大きい数字で、直したはずの実装を追加の
レイアウト補正で再び壊すよう仕向けかねない。行を容器の矩形でクリップして
から判定する手もあるが、その修正は (A)(B) どちらでも構造的に真になり、
④が何の力も持たなくなる。

**格上げする述語は行ではなく容器の境界にする**: 各サンプル点で
`main.getBoundingClientRect().bottom === nav.getBoundingClientRect().top`
（0px、寛容度なし）。両方とも `<main>` を名指しして読む --- スクロール祖先を
実行時に解決する形にはしない。この等式は「`<main>` がタブの高さぶんだけ
削られた、実際にクリップするスクロール容器である」ことを前提にした代理
指標であり、その前提が壊れているかどうかは見えない（下記）。

(A)(B) 双方を実測した。加えて (A) の式が 1px ずれた場合と、(A) の高さが
小数（nav 64.5px）の場合も実測した。条件は 60 行 × 80px、390×844 である。
scrollTop = 0 / 1234 / 末尾のどこで測っても値は変わらないことも確認済み:

| variant | mainBottom | navTop | delta |
|---|---|---|---|
| (A) 正しい式（`calc(100dvh - 65px)`） | 779 | 779 | 0 |
| (A) 1px ずれた式（`- 64px`） | 780 | 779 | 1 |
| (A) 小数の高さ（nav 64.5px、`- 64.5px`） | 779.5 | 779.5 | 0 |
| (B) flex フレーム | 779 | 779 | 0 |

**(A) では `--bottom-nav-height` がずれた瞬間にこの等式が崩れる**（2 行目）。
**(B) では box model が保証するので崩れようがない**（4 行目）--- これは
「判定基準」節の決め手をそのままオラクルにしたものである。小数の高さ
（3 行目）でも一致は 0 のままだった。両辺が同じ計算値から出るため、丸め
誤差が生じない。①は `getComputedStyle` の `padding` と
`getBoundingClientRect` の高さという違う経路を比較するので 0.5px の丸め
誤差を許すが、この等式は同じ経路どうしの比較である。寛容度を持たせない
根拠はここにある。

**この代理指標には見えない前提が 1 つある**: `<main>` が本当にクリップする
スクロール容器かどうかである。`overflow-y: visible` の `<main>`（クリップ
しない、高さの数字だけ正しい）で実測した。境界の等式は同じく
`mainBottom: 779, navTop: 779`（delta 0）を返した。**正しく見えて、実は
行がタブの上に描画され続ける状態を、この等式単体では検出できない**。
`getComputedStyle(main).overflowY !== 'visible'` を同じアサーションに足し、
この前提が崩れていないことも確認する。

liveness アサーションがこの穴を実質的に塞ぐ。`overflow-y: visible` の
`<main>` は `scrollTop` を要求どおり動かせない（実測: `main.scrollTop = 1234`
と書き込んでも読み返すと `0` のまま）。境界の等式が 0px でも、liveness 側で
判定不能になる。

**この述語が見るのは `<main>` の高さ予算だけである。** `toaster.tsx` /
`recordings.tsx` の `fixed` な消費者（上記「実測」参照）はこのオラクルの
対象外のまま残る。

昇格の条件は次の 2 つ。

1. **④ 自身を「初回表示だけ」から「scrollTop を 0 / 中間 / 末尾でサンプル
   する」形に広げる。** 述語も上記の容器境界アサーション + `overflowY`
   ガードに置き換える。併せて **liveness アサーション**を足す。
   `main.scrollTop` が要求どおり変わったことをサンプルごとに確認する
   （変わっていなければそのサンプル点は判定不能として NG にする。
   スクロール先が固定されたまま何度も同じ値を測って「変化なし＝合格」を
   装う空虚な成功を防ぐ）。
   **注記**: Playwright 上では `mainBottom - navTop` は上表のとおり scrollTop
   に関わらず一定なので、3 点サンプリングは CI では同じ測定を 3 回すること
   と変わらない。実際の検出力は liveness アサーションが担う。3 点を残す
   理由は実機の `100dvh` とツールバー開閉の関係（「未検証」節）にあり、
   CI 上の話ではない。
2. **位置復元の既存判定が新しい実装に対して green であることを確認する。**
   対象は `web/e2e/checks.mjs` の①②。④ を格上げする同じ PR で見る。④ だけを
   直しても、位置復元が壊れていないことを別に確認しないと、「隠れなくなった
   が位置復元も一緒に壊れた」を green のまま見逃す。

**この 2 つを満たすまで、④ は表示のみのまま据え置く。** NG への格上げは
下記「推奨」の PR 2 で行う。

### 推奨: (B)。ただし 2 PR に分ける

**(B) を推す。** 決め手は「判定基準」節のとおり、`<main>` の高さ予算から
式を消せることである。ただし次の理由で 1 PR には収めない。

**推奨の狭め方**: 「番組表グリッドが既に内側スクロール容器を持つので、
(B) はそれに揃えるだけ」という論法は使わない。`ProgramGridView` の内側
スクロール容器（`programs.tsx:984`）は `--page-header-height` と
`--sticky-banners-height` を減算する式である。どちらも JS の
`ResizeObserver` が実測して書き出す変数であり、**これは (A) と同じ形**
である。内側スクロール容器そのものは (A)(B) 共通のコストなので、この
事実に決め手としての重みは無い。むしろグリッドは今のリポジトリに既にある
(A) 型の潜在的な負債として扱う。

**1 PR に収めない理由**: 「未決: ブレークポイントの適用範囲」がまだ決まって
いない。その上、レイアウト・仮想化・e2e 2 本の書き換え・④ の述語差し替えを
まとめて 1 本に積む案がある。**その案では、新しい判定基準を書く人と、
それで採点される実装を書く人が同一 PR 内で同一人物になる。** 新しい
判定基準とは④の容器境界アサーションのことである。その場合、壊れている
今の `main` に対して新しい④が正しく red になることを、レイアウトを
変える前に示す手段が無くなる。

- **PR 1（判定手段のみ、レイアウト変更なし）**: `checks.mjs` と
  `programs-bottom-nav.mjs` の①②③（位置復元）を、window 決め打ちではなく
  実際のスクロール対象を実行時に判定する形に書き換える。④ の述語は
  `<main>` を名指しした上記の容器境界アサーション（+ liveness +
  `overflowY` ガード）に差し替えるが、**表示のみのまま据え置き、NG への
  格上げはしない。** 差し替えた④が今の `main`（window スクロール、
  `overflow-y: visible`）に対して不一致を報告すること --- 壊れている
  実装で正しく red だと分かること --- を確認する。**①②③ が今の window
  スクロール実装に対して今までの結果のまま pass し、`min-h-14` →
  `min-h-16` の変異で①②が今までどおり落ちることを確認して閉じる。**
- **PR 2（レイアウト）**: `app-shell.tsx` のレイアウトと
  `program-list.tsx` の仮想化を (B) の形に変える。PR 1 で書き換え済みの
  ①②③ が green のままであることに加え、④ の述語が一致（0px）を報告する
  ことを確認してから、④ を NG へ格上げする。

この順序なら、④ が「直したはずの実装を red にする」フォールスポジティブと
「壊れているのに green のまま」のフォールスネガティブの両方を、レイアウト
変更の前に潰せる。

## テストの範囲

**フレーム単位の跳ね・スクロール位置合わせの見た目自体は、jsdom では検証
できない。** `getBoundingClientRect` が常に 0 を返しレイアウトを計算しない
環境なので、`ProgramList` はこの環境では仮想化そのものをバイパスし
`scrollToIndex` を呼ばない。実機（Playwright を使った実ブラウザでの計測。
`web/e2e/`）で判定している。「いま見ている日」のスクロール追従も同様に
自動テストでは検証できない（純関数の導出ロジック自体はテスト済み）。グリッドの
「受け入れは実機で行う」（[programs.md](programs.md)）と同じ扱い。
