# ホーム

## 何を解く画面か

起動して最初に見えるのが番組表（「これから録るもの」）だと、運用が安定した
録画サーバーへの再訪の大半（「録れているか」「今夜なにが録れるか」「見るもの
はあるか」「異常はないか」の確認）に 1 画面で答えられない。部品（録画中の状態・
予約一覧・サーキットブレーカーバナー・容量バッジ・ドロップ統計）は揃っていた
のに、それらを集約する面が無かった。ホーム（`/`）はその集約面で、**新しい API
は作らず**既存のエンドポイントの組み合わせだけで作る。

## ルート: `/` はホーム、番組表は `/programs`

`/` を新設のホームに譲り、番組表はここに移設した。一等地（`/`）を新しい起点に
割り当て、番組表はナビの 2 番目に置く。

サーバー側は変更不要 --- `internal/api/spa.go` は `/api/` 以外を index.html に
フォールバックするので、`/programs` は既に配れる。

## ナビ: ホームが一等地の先頭、予約は「その他」へ

`navItems` の先頭に「ホーム」を足す。並び・畳み方の全体は
[shell.md](shell.md) §項目の並びは頻度順が権威。ここでは要点だけ:
ボトムタブの常時項目（`MOBILE_PRIMARY_COUNT`）は 3 のまま変えず、
ホーム・番組・録画の 3 個に置き換わる。予約はホームの新設で常時タブから
「その他」へ戻った（今夜これで録れているかの確認はホーム自身が担うため）。

## セクション: 窓・上限・空のときの扱い

| セクション | データ | 窓 / 上限 | 0 件のとき |
|---|---|---|---|
| いま録画中 | `GET /api/recordings?status=recording` | 全件（同時録画数はチューナー数で上界がある） | セクションごと消す |
| 今夜〜明日の予約 | `GET /api/reservations` をクライアントで窓切り | 今から**明日の暦日の終わり**（`lib/day-offset.ts` の `dayOrigin(2, now)`。0 時基準に揃えた窓）まで / 上限 10 件、超過分は「予約をすべて見る」リンク | セクションごと消す |
| 警告 | `GET /api/breakers` + `GET /api/capacity/overages`（今夜〜明日の予約と同じ窓） + ドロップ統計（下記「ドロップ警告の検出範囲」参照） + `GET /api/recordings?status=failed`（下記「失敗録画は警告への追加項目」参照） | 発生しているものだけ | セクションごと消す |
| 直近の完了 | `GET /api/recordings?status=finished&limit=20`（警告のドロップ検出と共用。下記参照） | 表示は先頭 6 件 | セクションごと消す |

**上限 10 / 6 は実測ではなく、「1 セクションが画面を占有しない」ために置いた
恣意的な上限。** 窓の方（今夜〜明日の予約の終端）は既存の日境界（番組表の
`dayOrigin`）に揃えたという根拠がある。

### 完了録画へ一操作で移動する

ヘッダーに「直近の完了へ」アンカーを置き、`直近の完了` セクションの先頭へ移動
できるようにする。リンクは新しいルートや API を追加せず、既存の
`GET /api/recordings?status=finished&limit=20` が**成功して 1 件以上返った後だけ**
表示する。取得中・空・取得失敗のときは、確認できていないものを存在すると読ませ
ないためリンクを出さない。

アンカー先は既存セクションの `#home-finished`。固定ヘッダーと sticky banner の
高さを `scroll-margin-top` に反映するので、移動後に見出しがヘッダーの下へ隠れない。
`limit=20` の警告検出範囲、表示先頭 6 件、警告の全文表示は変更しない。

到達（固定ヘッダー・下部ナビに隠れないこと、1 操作で完了すること）の合否と
実測値は `e2e/design.mjs`「視聴対象への到達距離」の節が権威 --- ここに px 値を
転記すると数値が二重管理になり必ずドリフトする。

### ドロップ警告の検出範囲は「直近の完了」の表示件数から独立させる（クエリは 1 本）

警告セクションのドロップ検出の範囲（`DROP_WARNING_SCAN_LIMIT` = 20）は、表示用の
「直近の完了」の件数（`RECENT_FINISHED_LIMIT` = 6）とは**独立した定数**にする。
表示件数（レイアウトの都合）と検出範囲（正しさの都合）を同じ値に乗せると、
レイアウト都合で表示件数を下げただけで警告の遡り幅まで黙って縮む。20 もまた
実測ではない恣意的な上限だが、少なくとも表示件数の変更が検出範囲に連動しない。

**問い合わせは 1 本にする**（`limit=20` で取り、表示だけを先頭 6 件へ切る）。
同じ絞り込み・同じ既定順（`program_start_at` 降順）なので `limit=6` の集合は
`limit=20` の先頭 6 件と一致し、2 本目は何も新しい情報を持ってこない。定数 2 つの
独立性はスライスでも保たれる（判定: `pages/home.test.tsx`「表示上限（6 件）の
外にある録画のドロップも警告には出る」。表示のスライスを警告の材料にも掛けると
落ちる）。

一時期は本当に 2 本のクエリに分けていた。分ける根拠として「表示件数を変える
変更と警告を壊す変更が同じ 1 行の定数変更に潰れる」と書いていたが、それは
スライスでも潰れない（定数は 2 つとも残る）ので根拠になっていなかった。
一方で払っていた代償は実在した。問い合わせが 1 本増え（マウント時も
`recordings` の SSE invalidate のたびも 2 本走る）、表示ゲートが待つクエリも
1 本増える。さらに**2 つの応答の間に録画が 1 本完了すると、同じ画面の中で
表示リストと警告の検出リストが食い違いうる**。

### 失敗録画は警告への追加項目（専用セクションは持たない）

**失敗録画（`status=failed`）はホームに専用のセクションを作らず、「警告」への
追加項目としてのみ出す**。「直近の完了」は `status=finished` の絞り込みで
取っているため、failed 行はそもそも混ざらない。警告に材料を 1 本足すだけで
既存の 4 セクション構成を変えずに済む。取る範囲は表示専用の限度を持たない
（`FAILED_RECORDING_SCAN_LIMIT`。ドロップ検出のような表示/検出の分離が要る
理由がここには無いので、値だけ他の上限と共有せず独立した定数にしてある）。

**取った失敗録画のうち、警告に出すのは recency 窓の中だけにする**。窓は
`FAILED_RECORDING_WARNING_WINDOW_MS` で、`startAt` 基準の 7 日である。他の警告
材料（ブレーカーは発動中のみ・容量超過は今夜〜明日の窓・ドロップは「直近 20 件の
完了」で実質 recency がある）はどれも自然に消える。しかし失敗だけは
`FAILED_RECORDING_SCAN_LIMIT` 件に収まる限り、いつの失敗でも出続ける。稼働の
長いサーバーでは警告セクションが古い失敗で常時埋まってしまう（issue の受け入れ
基準も「直近の」失敗録画と言っている）。値
（7 日）は実測ではなく他の上限と同じ性質の恣意的な上限。

**行では予定尺（`durationMs`、番組の放送尺のスナップショット）と、実際に録れた
尺（`startedAt`〜`endedAt`）を区別する**。録画が開始した直後に終わった失敗を
予定尺だけで表示すると、「ほぼ予定通り録れた」ように誤読できる。実際は 0 分に
近いのに `durationMs` は番組の予定尺のままである（実機観測: 開始・終了が同じ秒
なのに表示尺は番組の予定尺だった）。`startedAt` / `endedAt` は独立に書かれる
（`UpdateRecordingStatus` は `started_at` を無条件に、`ended_at` は非 NULL の
ときだけ書く）。そのため 3 通りある。両方ありなら実際尺を出す。`startedAt` のみ
なら、開始した事実はあるが実際尺は主張しない（mirakc の failed record に
`endTime` が無かった場合）。両方無しなら、**rokuban が開始を観測していない**。
「未開始」と明示する。3 つ目で mirakc 側の事実（「mirakc が録画を開始しなかった」）
は主張しない。`started_at` を書くのは record を観測した経路だけで、
`CreateFailedRecording` は書かない。そのため record の観測より先に
`recording.failed` の SSE が届いた窓でも同じ形になる。3 通りの中の区切りは `・` に揃える ---
メッセージ全体が `（尺 / 理由: …）` で ` / ` を「尺と理由の境目」に使っているので、
尺の中でも使うと 1 行に 2 種類の意味のスラッシュが並ぶ。

**警告の中での並びは「今止まっている（ブレーカー）→ 既に失われた（失敗録画）→
これから足りない（チューナー不足）→ 品質が落ちた（ドロップ）」である**。失敗は
`FAILED_RECORDING_SCAN_LIMIT` 件まで並びうるので、失敗が多いと行動可能な
「チューナー不足」が下へ押し下げられる。件数上限は入れていない（押し下げが
実運用で問題になるかは未検証。問題になるなら上限より並びの入れ替えが先）。

**`?status=failed`（通常一覧）は supersede 済みの failed 行を返さない**。API 側で
`superseded_at IS NULL` を絞る（`internal/api/recordings_query.go`）。判定は
`TestListRecordings_FailedFilterExcludesSuperseded`。本物の record が観測されて
置き換わった擬似 failed 行を警告が拾わないので、実際は録れているのに「録画失敗」と
出る偽陽性と、同じ番組が警告に 2 行並ぶ形（擬似行 + 置換で作られた行）はどちらも
起きない。無条件一覧・`trash=true` は履歴として両行を残す（`docs/schema/recordings.md`）
ので、フロントは追加の絞り込みをしない。

**失敗理由は `quality_events`（追記専用の履歴）の失敗系イベント（`recording.failed`
/ `recording.record-broken`）の最後の要素の `reason` から取る**。あればそれを出し、
無ければ「理由不明」と沈黙を区別する。最後の要素そのものではなく失敗系に絞るのは、
`quality_events` に `bcas_anomaly` も混ざるためである（末尾が `bcas_anomaly` だと
直前の失敗理由を読み飛ばす）。`reason` は mirakc の生の理由をそのまま保持した
ものである（不変条件 7）。書き手はどちらもオブジェクトである。`recording.failed` は
`{ type, message?, osError?, exitCode? }`（`mirakc.FailedReason`、discriminated
union）を `json.Marshal` したもの。`recording.record-broken` は
`{ reason: string }` である。それぞれ `type` / `reason` を読み、期待した形でない場合
（未知の `event` を含む）だけ録画単体ページの「品質イベント」欄と同じ流儀
（`JSON.stringify`）で読める形にフォールバックする。**読めたが空文字だった
場合は JSON へ落とさず「理由不明」に寄せる** --- `FailedReason.Type` に
`omitempty` は無いので `{"type":""}` はあり得る形である。それをそのまま出すと
「理由: {"type":""}」になり、材料が無い（沈黙）ことと区別できる文言にならない。

### 容量超過クエリの `start` はレンダー時刻を量子化してから渡す

**`start` に生の `Date.now()` を渡さない**。レンダーごとに変わる生ミリ秒を
クエリのパラメータ（延いては TanStack Query のキャッシュキー）に直接載せると、
レンダーのたびに新しいキーになる。その結果「未解決 → 即解決 → 再描画 →
また未解決」が閉じない無限再取得になる。

`end`（`dayOrigin(2, now)`。日境界）は元から量子化済みで問題が無かった。
`start` も同じ関数で時境界へ量子化する（`dayOrigin(0, now)`）。これは
`pages/programs.tsx` が「今日」の起点を作るのに使っているのと同じ関数・同じ
考え方である。**キャッシュキーに入る値は、答えが変わる粒度まで量子化する**
という規律を、`end` 側だけに適用して `start` 側に適用し忘れていたのが
この不具合の構造的な原因である。`useRef` / `useState` で「now を固定する」
ような対症療法は採らない。それは症状を消すだけで、量子化の欠落という原因は
残ったままになる。

**この欠陥は jsdom も実ブラウザも時計を止めている構成では見えなかった。**
時計に起因する挙動は、時計を止めない経路を別に用意して判定する
（`web/e2e/README.md` §判定を足すときの規律）。

量子化で窓が実際の「今」より前に広がる分（最大 59 分）は、`activeOverages`
（`pages/home.tsx`）が「実際の今より後に終わる」区間だけへクライアント側で
絞り込んで補正する。量子化はキャッシュキーの安定のためだけの手段で、表示する
内容の正しさを緩めてよい理由にはしない。`start` を時頭まで後退させて新たに
入ってくるのは「[時頭, now] に終わった区間」だけである（`openapi.yaml` の `start`
は「この時刻より後に終わる区間が対象」）。そのため `endAt > now` がちょうど
その分を落とし、進行中の区間は量子化の前後で欠落しない。**この回収には両方向の判定が
ある**（`pages/home.test.tsx`「既に終わった超過区間は警告に出さない」/「時境界
より前に始まり進行中の超過区間は警告に出す」。前者はフィルタを `() => true` に
変えると落ちる）。回収が無いと「もう終わったチューナー不足」が最大 59 分ぶん
警告に出続ける。

### 時境界を越えた瞬間に警告を消さない（`keepPreviousData`）

量子化の代償として、容量超過クエリのキーは毎時 0 分に 1 回変わる。新しいキーには
まだデータが無いので、素のままだと `isPending` → 警告セクションが 1 RTT だけ消える。
**警告だけが可視だった場合（アイドルなサーバーでブレーカーだけ発動している状態）は、
ページ全体が読み込みスケルトンに戻る**。この画面の主題は「セクションが理由なく
消えないこと」なので、`placeholderData: keepPreviousData`（TanStack Query）を
置いて、キーが進んでいる間は前のキーのデータを見せ続ける。

**古いデータを見せている間も、終わった区間が警告に出ることはない** —— 毎時の境界で
進むのは `start` だけなので、前のキーのデータは窓が最大 1 時間だけ広い同じ問い合わせの
結果（新しい窓の上位集合）である。そのうえで `activeOverages` が毎レンダー「今」で
絞り直す。**逆に取りこぼす側の境界は日境界にある** —— `end`（`dayOrigin(2)`）が進む
深夜 0 時には前のキーのデータが新しい窓の**部分集合**になるので、新しく窓に入った
超過が 1 RTT だけ見えない。1 RTT で自己回復するため許容する。**この側は未検証**
（毎時の側は下記のテストで測っているが、日境界の側は測っていない）。

判定は `pages/home.test.tsx`「容量超過クエリのキーが進み、新キーが未解決のままでも
警告セクションは残る」である（`placeholderData` を外すと落ちる）。このテストは
キーが実際に進んだことと、**2 回目の応答が assert の時点でまだ未解決であること**
も確認している。後者が無いと、遅延の仕掛けが効かなくなったときに空虚な成功へ転ぶ。

### セクションの可視性は個別に、「全部空」の判定だけ全解決を待つ

各セクションの表示/非表示はそのセクション自身のクエリ（警告は 4 本の合成 ---
サーキットブレーカー・容量超過・完了録画のドロップ検出・失敗録画）の
解決だけを待つ。**各セクションの独立した可視性を、ホームの読み込み中 CLS より
優先する**。`GET /api/reservations` は絞り込みを持たない全件取得で取得件数に
上限がない。そのため、それに「いま録画中」のような最も見たいセクションまで
引きずられて隠れる方が不利益が大きい。

この独立性を保つ結果として、固定された表示順と不定の応答順によるホームの
レイアウトシフトは許容する。ホームに CLS 0.10 以下の受け入れ基準は置かず、
CLS の機械判定は検索画面に限定する。

「全セクションが空」（ページ全体の単一空状態）の判定だけは全クエリの解決を
待つ。個別のクエリが解決する前に「空だから隠す」を判定すると、読み込み中の
一瞬を「セクションが無い」と誤読する（CLAUDE.md「非同期の空虚な成功」）。
未解決のセクションは「消えている」のではなく「まだ何も言っていない」。

**0 件のセクションは文言も出さず、セクションごと消す。** 一覧画面の空
（「条件に合う録画がありません」= 探した結果の報告）とホームの空（何も
主張しない）は意味が違う。ホームに「予約がありません」と出すと、それは
「異常なし」の裏返しの肯定的な主張になり、`docs/data.md` §6.5 の
「肯定的な文言を持たない」規律に反する。**全セクションが空のときだけ**、
ホーム全体として 1 つの空状態（「表示できる項目がありません」）を出す。

**取得の失敗は「0 件」とは区別する。** 個別のセクションのクエリが失敗した
場合、そのセクションを消さずに取得失敗を表示する --- 失敗を沈黙にすり替えると
「録れていない」のか「確認できていない」のか区別できなくなる。ただし警告
セクションの材料（サーキットブレーカー・容量超過・完了録画のドロップ検出・
失敗録画）については、他の画面（`CircuitBreakerBanner` / 予約一覧の容量バッジ）
と同じ流儀に揃えている。この流儀は「取得失敗は警告が無いことにする」である。
`docs/data.md` §6.5 が言う「既知の盲点は警告を見逃す方向に偏っている」ことを
承知のうえで、既存の踏襲先が同じ判断をしている。材料のうち完了録画の一覧は「直近の完了」の表示も
兼ねるので、取得が失敗すればそちら側にはエラーが出る（警告としては黙って
警告なしに縮退する）。**失敗録画は表示専用のセクションを持たない唯一の材料
なので、取得が失敗すると「失敗録画の警告が出ないこと」がどの画面にも出ない。**

## スコープ外

- ストレージ残高タイル（[recordings.md](recordings.md) の `StorageBalance`）は
  ホームに置かない。録画一覧側の関心事として独立させたままにする。
- ingest 進捗はホームに出さない。`Recording.ingest`（[recordings.md](recordings.md)
  §取り込み中であることを画面に出す）は録画一覧・録画単体ページにある。
  **「いま録画中」の行にも取り込みの状態は付く**（追従 ingest が録画開始から走るため。
  [recording/ingest.md](../recording/ingest.md) §5.1）が、ホームは録画中かどうかだけを
  見せる面であり、取り込み進捗の数字まで出すのは一覧側の関心事として分けたままにする。
  取り込み中の録画を載せたくなったらセクションの絞り込み自体を変える話になるので、
  そのときに決める。
