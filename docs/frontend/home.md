# ホーム

## 何を解く画面か

運用が安定した録画サーバーへの再訪では、「何を見るか」と「録れているか」の
どちらも確認したい。旧ホームで 5 つの管理セクションと再生候補を同じ重みで積んでいた
ときは、どちらの主役も面積を得られなかったため、ホーム（`/`）を「見る」と「管理」
の 2 モードに分ける。
**新しい API は作らず**、既存のエンドポイントの組み合わせだけで作る。

初回は「見る」を既定にする。モードは URL の `?mode=watch|ops`、端末の
`rokuban:home:mode`、既定値の順で決め、管理側の警告件数は両モードの切替に載せる。
見る側にもブレーカーだけは帯で出し、失敗・容量超過・ドロップは警告バッジに留める。

## ルート: `/` はホーム、番組表は `/programs`

`/` を新設のホームに譲り、番組表はここに移設した。一等地（`/`）を新しい起点に
割り当て、番組表はナビの 2 番目に置く。

サーバー側は変更不要 --- `internal/api/spa.go` は `/api/` 以外を index.html に
フォールバックするので、`/programs` は既に配れる。

## ナビ: ホームが一等地の先頭、予約は「その他」へ

`navItems` の先頭に「ホーム」を足す。並び・畳み方の全体は
[shell.md](shell.md) §項目の並びは頻度順が権威。ここでは要点だけ:
ボトムタブの常時項目（`MOBILE_PRIMARY_COUNT`）は 3 のまま変えず、
ホーム・番組・録画の 3 個に置き換わる。予約はホームの新設で常時タブから
「その他」へ戻った（今夜これで録れているかの確認はホーム自身が担うため）。

## 表示は「見る / 管理」の 2 モード

ホームの右上に `role="group"` の「見る / 管理」2 択を置く。選択状態は
`aria-current` で示す。URL の有効な `mode` を最優先し、無い / 未知の値なら
`localStorage` の `rokuban:home:mode` を読み、そこにも有効値が無ければ「見る」にする。
保存値は読むたびに検証し、保存の読み書きが使えない環境では保存なしとして扱う。

「管理」には、要対応の一覧を作る 6 種の結果（ブレーカー・容量超過・完了録画の
ドロップ・失敗録画・録画されず・CM 検出失敗）を同じ `warnings` 配列から数えたバッジを置く。5 クエリ（CM 検出失敗はドロップと同じクエリを共有するので数は増えない）が解決する
までは出さず、0 件なら出さない。「見る」ではブレーカー発動中だけヘッダー直下に
「{停止中の操作}が停止中」と「管理で見る」を出す。失敗・容量超過・ドロップをこの帯に
出さない。

### 見る

本文の最初に「次に見る 1 本」を置き、desktop では 16:9 サムネイルに本文幅の過半を使い、
題名・放送日時・局・再生位置・主ボタンを横に並べる。サムネイルの幅は最大 64rem とし、
高さは 16:9 の比率を保ったまま最大 36rem にする。phone ではサムネイルを全幅にし、
その下へ縦に並べる。主役は `GET /api/recordings/continue-watching` の先頭を優先する。
無ければ、`watchedAt` が無く `sizeBytes` または `encodedAssets` がある完了録画から、
放送日時が最も新しいものを選ぶ。両方の取得が解決するまで決めず、候補が無ければこのブロックは出さない。

続きからなら主ボタンは「続きから再生」、副ボタンは「最初から」。完了録画から選んだときは
主ボタンを「再生」にする。再生元チップは出さず、主ボタンは録画詳細へ遷移する。
「最初から」は再生位置を復元しない録画詳細へ遷移する。
主役のサムネイルも主ボタンと同じ録画詳細へ遷移する（録画中は `#chase` 付き）。
絵のリンクはマウス・タッチで押せる面を広げるためのもので、同じ行き先を 2 回読ませないよう Tab 順と読み上げから外す。
主役のサムネイルには左下に局名、下端に進み具合の線を重ねる（「ほかの新着」には付けない）。
再生位置はサムネイル下端の線とメタ行の「経過時間 / 再生時間」の文字で示し、文字の列には線を置かない。
映像の外の線はシークバーに見え、時間軸が二本あるように読めるため。
続きからの主役は、再生可能な encoded と保存位置が揃うときだけ、その位置のコマを表示する。
カット版では資産の `keepRanges` で写し、描画できない場合は固定サムネイルへ戻す。
一覧は番組を探しやすくし、動画取得を増やさないため固定画像のままにする。

その下の「ほかの新着」は、続きからの 2 件目以降、続けて条件に合う完了録画を並べる。
録画 ID の重複を除き、desktop は 176px のカードが 1 行に入る件数にする。phone は 3 件にする。
見出しの右から
`/series` へ移動できる。録画中は「録画中 N」・題名・追っかけ再生を細い 1 行に畳む。
0 件の行は出さない。予約・容量超過・ドロップ・失敗の一覧は見る側に置かない。

### 管理

管理モードは、**時間軸 + 要対応の一覧 + ストレージの 1 行**で「録れたか」
「いま録っているか」「この時間帯に不足区間があるか」を並べて見る。段は重なった番組を
読み分けるために詰めた位置であり、チューナー割り当てではない。容量超過は API が返した
区間と種別だけを示し、どの予約が録れないか・返らない時間帯が収まるかは主張しない。

#### 時間軸の窓と行

窓は常に今日の 0 時から、既存の予約窓と同じ `dayOrigin(2, now)`（明日の暦日の終わり）
までの 48 時間にする。始点を現在時刻に依存させない。午後始まり（正午）の窓だと、午前に
開いたとき始点が未来になり、「いま」の線が窓の左端に張り付き、午前の録画・録画中も窓から
落ちる。窓の長さは測定値ではなく、すべての幅で同じ窓を比較できるようにする選択である。
見出しは窓を明示する（「今日 0 時 → 明日の終わり」と、行になった種別「地デジ / BS ごと」）。
目盛りは日の境界を語で読めるようにする（「18時」「翌0時」）。窓は 2 日にまたがり、同じ
時刻が 2 回出るためである。

行は `site × channelType`（単一サイトでは種別だけ）。録画は
`GET /api/recordings` を `status=recording|finished|failed` の 3 本に分け、`limit=200` を付ける。
録画・予約とも**窓と重なるもの**を時間軸へ置き、窓の端で切って描く。API の `from` / `to` は
開始時刻の範囲なので、`from` に窓の始点を渡すと 0 時より前に始まった日またぎの録画が
録画中でも 0:00 から終わるまで消える。録画中は `from` / `to` を付けない（件数はチューナー数で
抑えられる）。完了・失敗は窓の始点の 24 時間前からを取り、窓と重なるものに絞る。24 時間を
超えて窓に食い込む録画は落ちる（番組の最長尺は測っていない）。判定は `pages/home.test.tsx`
「0 時をまたぐ録画は…」。`status=failed` は API 側で supersede 済みの擬似 failed 行を除く。
要対応用のドロップ 20 件と失敗 7 日窓は時間軸とは別の取得を維持する。
予約は既存の `GET /api/reservations` を共有する。
管理モードでは、見るモードだけが使う「録画中の無条件一覧」と「続きから」は取らない。

時間軸の窓全体は 1 画面へ縮小せず、枠の中だけを横にスクロールする。行見出しは枠の外に
固定し、初期位置は現在時刻の 3 時間前にする。スクロールバーは常に見える高さを持ち、
凡例の末尾に「枠の中を横にスクロールできます」と書く。縮尺はモックに合わせて window 幅
480px 以下の phone で 30px/h、それ以外の desktop で 64px/h。**切替は window 幅だけで
決める**。時間軸の枠の幅で決めると、切替がラベル幅を変え、ラベル幅が枠の幅を変える帰還
ループになり、ある窓幅で 2 つの縮尺を往復した（単一 site で 592–598px、複数 site で
660–676px を実測）。目盛りラベルは、枠の境界で全体が収まらないものと「いま」の pill の
下に隠れるものを隠す。ラベルと pill の箱は実幅で測る（中心 ± 20px の固定箱だと、端から
20px 以内の「18時」まで隠し、過去側に目盛りが 1 本も無くなった）。判定は午前から深夜の
4 つの時刻とスクロール 5 位置の実ブラウザ測定（`e2e/design.mjs`。jsdom は使わない）。

各行の番組は開始時刻順に並べ、終了した最初の段へ置く。時間区間は半開区間として扱うため、
前の終了時刻と次の開始時刻が等しければ同じ段を使う。表示順と段数は
`lib/home-timeline.ts` の純関数で固定する。凡例には「段は重なりの表示で、チューナーの
番号ではありません」と明記する。

容量超過は `GET /api/capacity/overages` の `jammedTypes` に列挙された**すべて**の種別行へ、
サイトが一致する場合だけ、斜線・破線枠・「N 本不足」で重ねる。個々の予約には印を付けない。
予約 API から重なる題名を取得できるときは「この時間帯の予約: …」を要対応行の副行に
置く。並べるのは `jammedTypes` に含まれる種別の予約だけで、詰まっていない種別の予約は
不足と無関係なので並べない。予約の勝敗や tuner 本数は表示しない。容量クエリの `start` はこれまでどおり
`dayOrigin(0, now)` に量子化し、終端は `dayOrigin(2, now)` にする。時頭の量子化で返りうる
終了済み区間は `endAt > now` で除く。

録れた = 無彩の塗り、録画中 = タリーの塗り、予約 = 枠線、失敗 = destructive の文字・淡い地・
枠、ドロップあり = 録れた塗りと下端の destructive 線、容量超過 = 琥珀の斜線で表す。緑は
使わない。ブロックは操作標的にせず、時間軸直下の折りたたみ「録画・予約の詳細」に
24px 以上の詳細リンクを並べる。ブロック自体をリンクにすると 30 分枠でも 15px 幅、行も
20px 高さで最小標的寸法を満たせないためである。この一覧は詳細へ行く唯一の導線なので、
開始時刻順に並べ（状態ごとの連結にしない）、各行に日（今日 / 明日）・種別（複数 site では
site も）・状態（録れた / 録画中 / 失敗 / 予約）を出す。窓は 2 日にまたがるため日が無いと
同じ時刻が区別できない。

ヘッダーの「直近の完了へ」アンカーは置かない。完了録画は時間軸の過去側（今日 0 時以降）と
この詳細一覧に出て、それより前は録画一覧で辿る。管理モードのホームから完了録画へは
「録画・予約の詳細」を開いて行を選ぶ 2 操作で着く。合否は `e2e/design.mjs`
「ホーム管理モード: 完了録画への到達」が実クリックで測る。

読み込み中は時間軸のスケルトン、取得失敗時はエラー、行が無いときは時間軸本体を出さない。
管理モードの全材料が確定して表示対象も無ければ単一の空状態を出す。

#### 要対応とストレージ

「要対応」は行を、種別チップ + 太字のタイトル + 副行の形で、ブレーカー → 失敗録画 →
録画されず → チューナー不足 → ドロップの順に置く。0 件なら一覧を出さない。色はチップだけが持つ
（チューナー不足 = 琥珀、ほかは destructive）。例: 失敗録画は「録画失敗」/ 番組名 /
「今日 17:00 · Eテレ · 未開始 / 理由: …」、ドロップは「ドロップ 12」/ 番組名 / 放送日時と局。
「録画されず」は `reservations.state = orphaned` の予約を 1 件ずつ出し、予約詳細へリンクする。
この状態は schedule と録画試行のどちらも観測されなかった意味で、「EPG から消失」ではない。
放送終了から `epg.retention_grace`（既定 24 時間）まで検出できる。`reservations` は
`program_snapshots` の GC とともに CASCADE 削除されるので、ホームから消えたことは録画成功の
保証にならない。「録画漏れはありません」のような肯定文は出さない。
チューナー不足の主文は「今夜 23:30–23:56 地デジが 1 本不足しています」の形式、副行は
「この時間帯の予約: …」。時間区間の不足と予約の重なりを示すが「この予約は録れません」
とはしない。

「ストレージ」は一覧の下に 1 行だけ置く。録画一覧の `StorageBalance` と同じ保存先、
平均 bitrate、完了録画サンプル、今後 7 日の予約スケジュールと沈黙規則を使い、残り容量・
見込み消費・必要な場合だけ満杯までの日数・エンコード待ち件数を出す。媒体 root や各材料が
取得できない場合は、その値を作らず対応する行・見積もりを省く。観測時刻が古い場合だけ警告する。

見るモードでは、録画中の細い行・続きから・ほかの新着を表示し、管理側の一覧は出さない。
ブレーカーだけは既存の停止中バナーで知らせ、管理モードの警告件数はモード切替の badge に
使う。

### ドロップ警告の検出範囲は時間軸の窓から独立させる（クエリは 1 本）

要対応のドロップ検出の範囲（直近の完了 20 件。コード上の `DROP_WARNING_SCAN_LIMIT`）は、
時間軸の窓（今日 0 時以降）とは**独立した定数**にする。表示の都合で窓を狭めたとき、
検出の遡り幅まで黙って縮まないようにするため。20 は実測ではない恣意的な上限だが、
窓の変更が検出範囲に連動しない。判定は `pages/home.test.tsx`「今日 0 時より前の
finished drop も 20 件の警告 scan から拾う」（窓の外の録画のドロップも要対応には出る）。

完了録画の一覧は 1 本だけ取る。見るモードの主役・ほかの新着の材料とドロップ検出の
材料を兼ね、同じ絞り込み・同じ既定順なので 2 本目は新しい情報を持たない。2 本に分けると、
2 つの応答の間に録画が 1 本完了したとき、同じ画面で表示とドロップ検出の集合が食い違いうる。

### 失敗録画は時間軸と要対応へ出す（専用セクションは持たない）

**失敗録画（`status=failed`）は専用のセクションを作らず、時間軸内の失敗 block と
「要対応」の行に出す。** 「続きから」は見るモードにだけ置く。時間軸の failed query は
`status=failed` を必須にして supersede 済みの擬似 failed 行を避け、窓と重なるものだけを
置く。警告用 query は時間軸と独立しており、上限は
`FAILED_RECORDING_SCAN_LIMIT`。ドロップ検出と違い、表示と検出の範囲を分ける
必要はないため、この値は他の上限と共有せず独立した定数にする。

**取った失敗録画のうち、警告に出すのは recency 窓の中だけにする**。窓は
`FAILED_RECORDING_WARNING_WINDOW_MS` で、`startAt` 基準の 7 日である。他の警告
材料（ブレーカーは発動中のみ・容量超過は今日〜明日の窓・ドロップは「直近 20 件の
完了」で実質 recency がある）はどれも自然に消える。しかし失敗だけは
`FAILED_RECORDING_SCAN_LIMIT` 件に収まる限り、いつの失敗でも出続ける。稼働の
長いサーバーでは要対応一覧が古い失敗で常時埋まってしまう（issue の受け入れ
基準も「直近の」失敗録画と言っている）。値
（7 日）は実測ではなく他の上限と同じ性質の恣意的な上限。

**失敗の要対応行では予定尺（`durationMs`、番組の放送尺のスナップショット）と、実際に録れた
尺（`startedAt`〜`endedAt`）を区別する**。録画が開始した直後に終わった失敗を
予定尺だけで表示すると、「ほぼ予定通り録れた」ように誤読できる。実際は 0 分に
近いのに `durationMs` は番組の予定尺のままである（実機観測: 開始・終了が同じ秒
なのに表示尺は番組の予定尺だった）。`startedAt` / `endedAt` は独立に書かれる
（`UpdateRecordingStatus` は `started_at` を無条件に、`ended_at` は非 NULL の
ときだけ書く）。そのため 3 通りある。両方ありなら実際尺を出す。`startedAt` のみ
なら、開始した事実はあるが実際尺は主張しない（mirakc の failed record に
`endTime` が無かった場合）。両方無しなら、**rokuban が開始を観測していない**。
「未開始」と明示する。3 つ目で mirakc 側の事実（「mirakc が録画を開始しなかった」）
は主張しない。`started_at` を書くのは record を観測した経路だけで、
`CreateFailedRecording` は書かない。そのため record の観測より先に
`recording.failed` の SSE が届いた窓でも同じ形になる。3 通りの中の区切りは `・` に揃える ---
メッセージ全体が `（尺 / 理由: …）` で ` / ` を「尺と理由の境目」に使っているので、
尺の中でも使うと 1 行に 2 種類の意味のスラッシュが並ぶ。

**CM 検出失敗の材料はドロップと同じ、直近 20 件の完了録画クエリ
（`DROP_WARNING_SCAN_LIMIT`）を共有する**。表示と検出でクエリを分けると、応答の間に
完了録画が増えたとき対象がずれる。同じ画面でドロップと CM 検出の対象が食い違わないよう、
CM 検出だけの新しい取得は足さず、ドロップと同じ録画集合から状態を読む。したがって、要対応に出ない
ことは CM 検出失敗が無い保証ではない。

**要対応の行は直す操作の単位に合わせる**。`cmDetection.state='failed'` のうち
`stage='logo'` / `'area'` / `'match'` / `'resolution'` / `'adopt'` は局の CM ロゴ画面で
直せる。`logo` は枠を教えて候補を採用、`area` は枠を教え直し、`adopt` は候補を採用、`match` はロゴを忘れるか枠を教え直して候補を採用、`resolution` はその解像度の録画から枠を教えて採用する。
`networkId` と `serviceId` の組ごとに 1 行へまとめ、リンク先は
`/cm-logos/{networkId}/{serviceId}` とする。その他の段階（段階不明を含む）は
録画単位で 1 行にし、録画詳細へ移動する。`detecting`（検出中または再試行待ち）と
`disabled` は失敗ではないので出さない。警告には失敗の事実と件数、対象を特定する録画名・局名
だけを出し、技術的な原因は推測しない。見るモードのバッジもこの行数を数えるため、局単位に
まとめた失敗は 1 件として数える。CM 検出失敗の行の並びは、局単位の行が先、録画単位の行が後で、
それぞれ完了録画の応答（番組開始の新しい順）に従う。局単位の行は 1 操作で複数の録画を解消できるので先に置く。
未解決: `/cm-logos` の `failedCount` は録画でしか直せない段階を局の要対応に数え、逆に `adopt` は数えていない。ホームの局まとめとは件数が一致しない。
未解決: 局のロゴは 1 局に 1 解像度だけ。解像度が混ざる局（マルチ編成時に主サービスが 480i になる局が実在する）では、`resolution` を局で直すと、もう一方の解像度の録画が `resolution` で失敗する。

**警告の中での並びは「今止まっている（ブレーカー）→ 既に失われた（失敗録画・録画されず）→
これから足りない（チューナー不足）→ 品質が落ちた（ドロップ）→ CM 検出失敗」である**。
CM 検出に失敗しても録画自体は見られるため、失敗録画やチューナー不足より後ろに置く。
失敗録画は
`FAILED_RECORDING_SCAN_LIMIT` 件まで並びうるので、失敗が多いと行動可能な
「チューナー不足」が下へ押し下げられる。件数上限は入れていない（押し下げが
実運用で問題になるかは未検証。問題になるなら上限より並びの入れ替えが先）。

**`?status=failed`（通常一覧）は supersede 済みの failed 行を返さない**。API 側で
`superseded_at IS NULL` を絞る（`internal/api/recordings_query.go`）。判定は
`TestListRecordings_FailedFilterExcludesSuperseded`。本物の record が観測されて
置き換わった擬似 failed 行を警告が拾わないので、実際は録れているのに「録画失敗」と
出る偽陽性と、同じ番組が警告に 2 行並ぶ形（擬似行 + 置換で作られた行）はどちらも
起きない。無条件一覧・`trash=true` は履歴として両行を残す（`docs/schema/recordings.md`）
ので、フロントは追加の絞り込みをしない。

**失敗理由は `quality_events`（追記専用の履歴）のうち、失敗系イベント
（`recording.failed` / `recording.record-broken`）の最後の要素の `reason` から取る**。
あればそれを出し、無ければ「理由不明」と沈黙を区別する。`quality_events` に
いま書くのは `recording.failed` / `recording.record-broken` の 2 種類だけだが、
読むときは失敗系に絞る。スクランブル件数は
`drop_stats.scrambled` から導けるため、重ねて記録しない。`reason` は mirakc の生の理由を
そのまま保持したものである（不変条件 7）。書き手はどちらもオブジェクトである。
`recording.failed` は `{ type, message?, osError?, exitCode? }`（`mirakc.FailedReason`、
discriminated union）を `json.Marshal` したもの。`recording.record-broken` は
`{ reason: string }` である。それぞれ `type` / `reason` を読み、期待した形でない場合だけ録画単体ページの「品質イベント」欄と同じ流儀
（`JSON.stringify`）で読める形にフォールバックする。**読めたが空文字だった
場合は JSON へ落とさず「理由不明」に寄せる** --- `FailedReason.Type` に
`omitempty` は無いので `{"type":""}` はあり得る形である。それをそのまま出すと
「理由: {"type":""}」になり、材料が無い（沈黙）ことと区別できる文言にならない。

### 容量超過クエリの `start` はレンダー時刻を量子化してから渡す

**`start` に生の `Date.now()` を渡さない**。レンダーごとに変わる生ミリ秒を
クエリのパラメータ（延いては TanStack Query のキャッシュキー）に直接載せると、
レンダーのたびに新しいキーになる。その結果「未解決 → 即解決 → 再描画 →
また未解決」が閉じない無限再取得になる。

`end`（`dayOrigin(2, now)`。日境界）は元から量子化済みで問題が無かった。
`start` も同じ関数で時境界へ量子化する（`dayOrigin(0, now)`）。これは
`pages/programs.tsx` が「今日」の起点を作るのに使っているのと同じ関数・同じ
考え方である。**キャッシュキーに入る値は、答えが変わる粒度まで量子化する**
という規律を、`end` 側だけに適用して `start` 側に適用し忘れていたのが
この不具合の構造的な原因である。`useRef` / `useState` で「now を固定する」
ような対症療法は採らない。それは症状を消すだけで、量子化の欠落という原因は
残ったままになる。

**この欠陥は jsdom も実ブラウザも時計を止めている構成では見えなかった。**
時計に起因する挙動は、時計を止めない経路を別に用意して判定する
（`web/e2e/README.md` §判定を足すときの規律）。

量子化で窓が実際の「今」より前に広がる分（最大 59 分）は、`activeOverages`
（`pages/home.tsx`）が「実際の今より後に終わる」区間だけへクライアント側で
絞り込んで補正する。量子化はキャッシュキーの安定のためだけの手段で、表示する
内容の正しさを緩めてよい理由にはしない。`start` を時頭まで後退させて新たに
入ってくるのは「[時頭, now] に終わった区間」だけである（`openapi.yaml` の `start`
は「この時刻より後に終わる区間が対象」）。そのため `endAt > now` がちょうど
その分を落とし、進行中の区間は量子化の前後で欠落しない。**この回収には両方向の判定が
ある**（`pages/home.test.tsx`「既に終わった超過区間は警告に出さない」/「時境界
より前に始まり進行中の超過区間は警告に出す」。前者はフィルタを `() => true` に
変えると落ちる）。回収が無いと「もう終わったチューナー不足」が最大 59 分ぶん
警告に出続ける。

### 時境界を越えた瞬間に警告を消さない（`keepPreviousData`）

量子化の代償として、容量超過クエリのキーは毎時 0 分に 1 回変わる。新しいキーには
まだデータが無いので、素のままだと `isPending` → 要対応一覧が 1 RTT だけ消える。
**警告だけが可視だった場合（アイドルなサーバーでブレーカーだけ発動している状態）は、
ページ全体が読み込みスケルトンに戻る**。この画面の主題は「セクションが理由なく
消えないこと」なので、`placeholderData: keepPreviousData`（TanStack Query）を
置いて、キーが進んでいる間は前のキーのデータを見せ続ける。

**古いデータを見せている間も、終わった区間が警告に出ることはない** —— 毎時の境界で
進むのは `start` だけなので、前のキーのデータは窓が最大 1 時間だけ広い同じ問い合わせの
結果（新しい窓の上位集合）である。そのうえで `activeOverages` が毎レンダー「今」で
絞り直す。**逆に取りこぼす側の境界は日境界にある** —— `end`（`dayOrigin(2)`）が進む
深夜 0 時には前のキーのデータが新しい窓の**部分集合**になるので、新しく窓に入った
超過が 1 RTT だけ見えない。1 RTT で自己回復するため許容する。**この側は未検証**
（毎時の側は下記のテストで測っているが、日境界の側は測っていない）。

判定は `pages/home.test.tsx`「容量超過クエリのキーが進み、新キーが未解決のままでも
警告セクションは残る」である（`placeholderData` を外すと落ちる）。このテストは
キーが実際に進んだことと、**2 回目の応答が assert の時点でまだ未解決であること**
も確認している。後者が無いと、遅延の仕掛けが効かなくなったときに空虚な成功へ転ぶ。

### 管理モードの読み込み・失敗・空状態

管理モードでは時間軸、要対応、ストレージを別々に描く。時間軸は録画 3 種の窓内 query・
予約・容量超過がすべて解決するまでスケルトンを出し、いずれかの取得が失敗した場合は
時間軸の取得失敗を表示する。解決後に行が無ければ chart は出さないが、別の要対応や
ストレージ材料があればその表示は続ける。要対応はブレーカー・容量超過・完了録画の
ドロップ検出・失敗録画・予約一覧の 5 query が解決した後にだけ出し、0 件なら一覧を出さない。
予約一覧が解決する前は「録画されず」の件数が分からないため、要対応と管理モードの警告件数の
どちらも確定しない。
材料の取得失敗は従来どおり警告無しへ縮退する。

ストレージ行は `GET /api/storage` が成功した場合だけ作る。媒体 root が無ければ行を出さず、
root があっても bitrate sample・予約・encode queue が失敗した場合は、その材料を必要とする
見積もりまたは値だけ省く。エラーを 0 や「余裕あり」と解釈しない。

ページ全体の単一空状態（「表示できる項目がありません」）は、時間軸・警告・ストレージの
表示材料がすべて確定し、時間軸にイベントも不足区間もなく、警告も媒体 root も無く、
時間軸・ストレージ取得自体にエラーが無い場合に限る。ロード中の一瞬を「何も無い」と
誤読させない（CLAUDE.md「非同期の空虚な成功」）。

## スコープ外

- 視聴モードにはストレージ残高を置かない。管理モードは [recordings.md](recordings.md)
  の `StorageBalance` と同じ材料・沈黙規則を使い、残り容量と 7 日の予約消費見込みなどを
  1 行で示す。
- ingest 進捗はホームに出さない。`Recording.ingest`（[recordings.md](recordings.md)
  §取り込み中であることを画面に出す）は録画一覧・録画単体ページにある。
  **「いま録画中」の行にも取り込みの状態は付く**（追従 ingest が録画開始から走るため。
  [recording/ingest.md](../recording/ingest.md) §5.1）が、ホームは録画中かどうかだけを
  見せる面であり、取り込み進捗の数字まで出すのは一覧側の関心事として分けたままにする。
  取り込み中の録画を載せたくなったらセクションの絞り込み自体を変える話になるので、
  そのときに決める。
