# 検索

## 検索は独立ルート `/search`

番組表は EPG を時間軸で眺める画面、検索は **ruler と同じ条件コンパイラ
（`internal/rulequery`）を叩く「ルールの条件を試す画面」**で、関心事が違う。
「検索 API と ruler 経路の programId 集合が一致する」ことはテストで
担保されている（下記「経緯と失敗事例」）ので、ここで当たりを確認してから
ルールにできる。

- **未検索と 0 件を構造的に別の状態として扱う**（`isIdle` と `success && 空`）。
  文言が入れ替わらないようにする
- 結果は **programId 昇順**（API の契約）で時刻順ではないため、番組表のような
  sticky 日付ヘッダは使わず行に日時を出す
- **「問わない」次元はリクエストのキーごと落とす**（`null` を明示しない）。
  不変条件 10（意味を持たない行を作らない）の精神をリクエストにも適用する
- **フォームで止めるのは「送るとサーバーが壊れる」ものと「黙って嘘の絞り込みに
  なる」ものだけ。** 矛盾した範囲（下限 > 上限）は 0 件が正しい答えなので検証しない。
  曜日ビットが 0 のときだけ止めるのは、`rulequery` が範囲外エラーを返し API が
  400 に変換しないため 500 になるという実装上の理由
- **サイトの選択肢は置かない。** `GET /api/sites` でレジストリは
  取れるが、`<SiteGate>`（`components/site-gate.tsx`）は先頭サイトだけを
  `SiteContext` に流し、2 サイト以上のレジストリでは残りが UI 上に一切現れない
  --- 多サイトの運用実績が無い状態で切り替え UI の形を先に決めない
  （不変条件 11）。先頭以外が「見えるが空に見える」（黙って自分のサイトの不足を
  他サイトのものとして出す、のような静かな壊れ方）ではなく「そもそも見えない」
  ことを選んでいるので、複数サイトを運用し始めたときに気付きやすい
- ジャンルの未知コード（12 / 13 の予備）は数値のまま出す。「その他」に丸めると
  ARIB の本物の「その他」（15）と区別できない（`lib/genre.ts` と同じ規律）

## 検索とルールは同じ条件 UI を双方向に共有する

`ProgramSearchRequest` と `RuleInput` の条件部分は同形で、サーバーは
`internal/rulequery` という同じコンパイラを通る。この同一性を UI 側でも保つため、
条件の入力は `components/condition-fields.tsx`（`<ConditionFields>`）1 つだけにし、
検索画面とルール画面の両方がこれを使う。**片方だけに次元が増えると、
「試した条件」と「保存される条件」が食い違う。**

下書き（`SearchDraft`）と `RuleInput` の相互変換は `lib/program-search.ts` の
`buildRuleInput` / `ruleToDraft` に置き、**往復テストで固定する**。分と ms、
ローカル壁時計と UTC の取り違えは UI 越しには見えにくい。

- **検索 → ルール**: 検索画面の「この条件でルールを作成」（`?ruleId` を伴わない
  通常の検索から）。条件は `buildSearchRequest` の結果をそのまま流用する
  （変換を 2 箇所に書かない）
- **ルール → 検索**: `/search?ruleId=N` でそのルールの条件を下書きに写して自動検索する。
  **ハイドレーションは `ruleId` ごとに 1 回だけ**（ref でガードする）。refetch のたびに
  写すと、ユーザーが条件を編集した直後に入力が巻き戻る
- **`?ruleId=N` で開いた画面の保存は上書き（`PATCH /api/rules/{id}`）が既定動作。**
  検索画面はマッチする番組を見ながら条件を詰められるので、そこが実質のルール
  編集画面になる、という判断（以前は「ここでの編集は元のルールを変更せず、
  保存すると別の新しいルールになる」としていたが、編集体験として一本化した）。
  元のルールを残したまま別のルールとして保存する経路（`POST /api/rules`）も
  副動作として残し、押し間違えないよう主動作と見た目を変える。名前が元の
  ルールと同じままこの副動作を押すと `〜 のコピー` を付ける（`rules.name` に
  一意制約が無いため、そのまま引き継ぐと一覧で見分けられない同名のルールが
  2 本並ぶ）
- **ルール画面（`/rules`）の条件編集フォームも残る。** 同じルールを 2 画面
  （検索画面の上書き保存とルール画面）が書けることになるが、どちらも導出
  ロジックの介在しないユーザーの同期的な編集なので、単に最後に保存した方が
  勝つ（不変条件 9 が扱う「導出値と不可逆な事実の混同」には当たらない —
  両方とも同じ不可逆な事実を人間が書き換えているだけである）
- **UI が持たない次元は勝手に埋めない。** `sites`（ルールの `rule_sites` 相当）は
  条件 UI に出していないので新規作成では送らない（空 = 全サイト）。ただし既存
  ルールを編集・フォークするときは `buildRuleInput` の `preserve` で引き継ぐ ——
  `UpdateRule` は子テーブル全置換なので、落とすとユーザーの設定が黙って消える
  （`description` / `dedupe*` / `filenameTemplate` / `metadata` も同じ）
- **条件ゼロのルールは全番組にマッチする。** 検索では「絞り込まない」が正しい問い
  でありうるが、ルールでは録画が走り続ける。保存時に明示的な確認を挟み、
  一覧でも警告として出す（作った後に気付ける経路も要る）

## 経緯と失敗事例

- `/search` は M2-11 で追加した
- 「検索 API と ruler 経路の programId 集合が一致する」ことは M2-2 のテストで
  固定した
- サイトレジストリの API（`GET /api/sites`）は issue #184（M4-12）で入った
