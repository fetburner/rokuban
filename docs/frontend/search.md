# 検索

## 検索は独立ルート `/search`

番組表は EPG を時間軸で眺める画面、検索は **ruler と同じ条件コンパイラ
（`internal/rulequery`）を叩く「ルールの条件を試す画面」**で、関心事が違う。
「検索 API と ruler 経路の programId 集合が一致する」ことはテストで
担保されている（下記「経緯と失敗事例」）ので、ここで当たりを確認してから
ルールにできる。

- **未検索と 0 件を構造的に別の状態として扱う**（`isIdle` と `success && 空`）。
  文言が入れ替わらないようにする
- 結果は **programId 昇順**（API の契約）で時刻順ではないため、番組表のような
  sticky 日付ヘッダは使わず行に日時を出す
- **「問わない」次元はリクエストのキーごと落とす**（`null` を明示しない）。
  不変条件 10（意味を持たない行を作らない）の精神をリクエストにも適用する
- **フォームで止めるのは「送るとサーバーが壊れる」ものと「黙って嘘の絞り込みに
  なる」ものだけ。** 矛盾した範囲（下限 > 上限）は 0 件が正しい答えなので検証しない。
  曜日ビットが 0 のときだけ止めるのは、`rulequery` が範囲外エラーを返し API が
  400 に変換しないため 500 になるという実装上の理由
- **サイトの選択肢は置かない。** 検索 API は
  `POST /api/sites/{site}/programs/search` で site が資源同定に入るが、対象は
  `useCurrentSite()`（`<SiteGate>` が配るレジストリの先頭サイト）に固定する ---
  多サイトの運用実績が無い状態で切り替え UI の形を先に決めない（不変条件 11）。
  同じ理由で条件フォーム（`<ConditionFields>`）のサービス選択肢も先頭サイトから
  作る --- これは `/rules` にも同居する。UI 全体でのサイトの扱い（site の出所で
  切る。一覧は全サイト、出所の無い入口だけ先頭サイト固定）は
  [shell.md](shell.md)「サイトの扱い」
- ジャンルの未知コード（12 / 13 の予備）は数値のまま出す。「その他」に丸めると
  ARIB の本物の「その他」（15）と区別できない（`lib/genre.ts` と同じ規律）
- **サービスチップは名前が重複するとき補助ラベルを付ける**
  （`lib/epg-grid.ts` の `serviceDisambiguator`）。ワンセグ / サブサービスは
  主サービスと同じ名前で並ぶことがあり、名前だけではどれを選んでいるか
  分からない。材料は `Service` が既に返す識別子（リモコン番号 →
  物理チャンネル → serviceId の順）だけを使い、programId は分解しない ---
  同じ材料が番組表のチャンネルピッカー（`channel-picker.tsx`）にもあるので、
  検索・ルールと番組表で「どの局か」の見分け方が揃う。1 つのグループ内では
  全員に同じ段数の材料を付ける（一部だけ短いラベルにすると表記が揃わない）
- **主操作（検索・条件をクリア）は条件フォームの先頭に置き、かつ送信が決着した
  ら結果の先頭（`検索結果` セクション）へスクロールとフォーカスを移す。この 2 つ
  は対で入れる。** チップ列（サービス・チャンネル種別・ジャンル・時間帯）が画面の
  大半を占めるため、主操作を末尾に置くと 390px 幅ではスクロールしないとボトム
  タブの上に出てこない。**ただし上に出すだけでは足りない** —— 入力 → 主操作 →
  値札 → ルール保存 → 結果を 1 本の縦カラムに積んでいる限り総スクロール量は
  変わらないので、主操作をカラムの上端へ動かしても負担が送信前から送信後に移る
  だけになる（押しても折り目の中では何も変わらず、無反応に見える）。移動先は
  **結果の先頭（件数行）**で、値札とルール保存はその直前に残す —— 値札を保存の
  隣に常置するという判断（下記「保存前の値札」）を動かさずに済むため。合否は
  実ブラウザで測る（`web/e2e/search-mobile.mjs`。座標もスクロール位置も jsdom
  では測れない）
- **`<ConditionFields>` のテキスト条件は 1 行目を常に編集可能な状態で出す**
  （「条件を追加」を押した先に初めて出す形にしない）。この節は
  `<ConditionFields>` の先頭に来るので、これだけで「最初に打つ場所」が
  クリック無しで届く
- **1 行目の実体化は入力の瞬間まで遅らせ、配列が空の間は「条件を追加」も削除
  （X）も出さない。** 触っていない行を `SearchDraft.textMatches` に置くのは何も
  主張していない行（不変条件 10）で、「指定なし（すべての番組が対象）」のまま
  送られるという意味も壊れる。実体の無い行に追加・削除を出すと押しても何も
  起きないボタンになる。**文言に画面固有の動詞（「検索すると」）を入れない** ——
  `<ConditionFields>` は `/rules` も使うので、ルール画面では誤りになる（条件ゼロ
  のルールは検索結果が全件になるのではなく録画が走り続ける。下記「条件ゼロの
  ルールは全番組にマッチする」）
- **`<ConditionFields>`（`components/condition-fields.tsx`）はサービスの節を
  最後に置く。** サービス一覧の取得は他の節（チャンネル種別・ジャンル・時間帯・
  無料放送・放送時間・期間）と違って非同期で、「読み込み中…」の 1 行からチップの
  複数行へ描画が入れ替わる。同期的に描かれる節より前に置くと、その入れ替わりが
  既にレイアウト済みの後続の節を下へ押し、読み込み中の CLS を作る（Lighthouse で
  検索モバイルが要改善域まで出た実測。`web/e2e/cls.mjs` でも 390x844 で 0.165）。
  Layout Instability API は「既に描画済みの要素が動く」ことだけを数えるので、
  非同期に育つ要素を同期的な要素より後ろに置くと**押される側が折り目の外に出る**。
  **「押される側が無くなる」わけではない** —— `pages/search.tsx` は `<form>`
  （`<ConditionFields>` を含む）の後ろに値札・ルール保存・検索結果を同じ 1 本の
  縦カラムで積んでいるので、押される要素そのものは残り、残差も 0 ではない
  （`cls.mjs` と同じ 24 局のフィクスチャでの実測: 390x844 で 0（ちょうど 0）、
  1280x900 で 0.00093、縦に長いビューポートでは増えて 1024x1366 で 0.012、
  390x1180 で 0.024。いずれもしきい値 0.10 以下なので対策の有効性は変わらない）。
  **フォームを短くする変更（節の折りたたみ・サービスより下の要素を上へ移す）は
  この前提を崩す** —— 折り目の外に出ていた押される側が中に戻るとシフトが黙って
  復活するので、そのときは測り直す。判定は `web/e2e/cls.mjs`（jsdom はレイアウトを
  測れないので実ブラウザ側）
- **サービスが最下部に来る動線上の代償は、CLS と引き換えに意図的に受け入れて
  いる。** 実測（390x844、`cls.mjs` と同じフィクスチャ）でサービスのチップ列は
  top=1027 —— 折り目 844 の 183px 下で、チャンネルで絞るには初画面から 1 スクリーン
  以上スクロールが要る（並べ替え前は `テキスト条件` の直後で top=329、折り目の中に
  あった）。主操作を先頭へ出す判断（上記）と同じ「チップ列が画面の大半を占める」
  画面であり、しかも `<ConditionFields>` は `/rules` の条件編集も兼ねるので代償は
  そちらにも及ぶ。それでもラボ CLS 0.165 → 0 を採った。**高さの予約とチップ列の
  スケルトンは採らない** —— どちらも「何行ぶん予約するか」を先に決める必要がある
  が、チップ列の高さはそのサイトのサービス数と幅ごとの折り返しで決まるので、予約
  する高さが恣意的になる（多すぎれば解決後も空白が残り、少なければシフトがそのまま
  残る）。動線の代償が受け入れられないと判断したときは、並べ替えをやめてスケルトン
  側に寄せる設計判断になる（`cls.mjs` はそのまま判定に使える）

## 検索とルールは同じ条件 UI を双方向に共有する

`ProgramSearchRequest` と `RuleInput` の条件部分は同形で、サーバーは
`internal/rulequery` という同じコンパイラを通る。この同一性を UI 側でも保つため、
条件の入力は `components/condition-fields.tsx`（`<ConditionFields>`）1 つだけにし、
検索画面とルール画面の両方がこれを使う。**片方だけに次元が増えると、
「試した条件」と「保存される条件」が食い違う。**

下書き（`SearchDraft`）と `RuleInput` の相互変換は `lib/program-search.ts` の
`buildRuleInput` / `ruleToDraft` に置き、**往復テストで固定する**。分と ms、
ローカル壁時計と UTC の取り違えは UI 越しには見えにくい。

- **検索 → ルール**: 検索画面の「この条件でルールを作成」（`?ruleId` を伴わない
  通常の検索から）。条件は `buildSearchRequest` の結果をそのまま流用する
  （変換を 2 箇所に書かない）
- **ルール → 検索**: `/search?ruleId=N` でそのルールの条件を下書きに写して自動検索する。
  **ハイドレーションは `ruleId` ごとに 1 回だけ**（ref でガードする）。refetch のたびに
  写すと、ユーザーが条件を編集した直後に入力が巻き戻る
- **`?ruleId=N` で開いた画面の保存は上書き（`PATCH /api/rules/{id}`）が既定動作。**
  検索画面はマッチする番組を見ながら条件を詰められるので、そこが実質のルール
  編集画面になる、という判断（以前は「ここでの編集は元のルールを変更せず、
  保存すると別の新しいルールになる」としていたが、編集体験として一本化した）。
  元のルールを残したまま別のルールとして保存する経路（`POST /api/rules`）も
  副動作として残し、押し間違えないよう主動作と見た目を変える。名前が元の
  ルールと同じままこの副動作を押すと `〜 のコピー` を付ける（`rules.name` に
  一意制約が無いため、そのまま引き継ぐと一覧で見分けられない同名のルールが
  2 本並ぶ）
- **ルール画面（`/rules`）の条件編集フォームも残る。** 同じルールを 2 画面
  （検索画面の上書き保存とルール画面）が書けることになるが、どちらも導出
  ロジックの介在しないユーザーの同期的な編集なので、単に最後に保存した方が
  勝つ（不変条件 9 が扱う「導出値と不可逆な事実の混同」には当たらない —
  両方とも同じ不可逆な事実を人間が書き換えているだけである）
- **UI が持たない次元は勝手に埋めない。** `sites`（ルールの `rule_sites` 相当）は
  条件 UI に出していないので新規作成では送らない（空 = 全サイト）。ただし既存
  ルールを編集・フォークするときは `buildRuleInput` の `preserve` で引き継ぐ ——
  `UpdateRule` は子テーブル全置換なので、落とすとユーザーの設定が黙って消える
  （`description` / `dedupe*` / `filenameTemplate` / `metadata` も同じ）
- **引き継いだ `sites` はフォークだけ 400 になりうる（未解決）。** API は保存済みの
  site 名をレジストリ照合から免除するが、免除の単位は「そのルール」なので
  `PATCH`（上書き保存）にしか効かない。レジストリから site が消えると、
  同じ `preserve` を `POST` に載せる「別の新しいルールとして保存」だけが
  400 `unknown site` になる（[DB スキーマ](../schema.md) の `rule_sites` 節。
  Go 側の `TestRuleSites_RegistryDriftRejectsFork` が測っている）。`sites` は条件 UI に
  出していないのでユーザーが画面内で外すこともできず、いまはエラーの toast が出て
  終わる。**未解決: フォーク時に「レジストリに無い site」を見せて明示的に外させるか、
  API 側の免除をフォークにも届かせるか。** 黙って落とす選択は取らない —— 絞り込みが
  無音で全サイトへ反転するのは、書き込み時照合が防ごうとしている失敗そのもの
- **条件ゼロのルールは全番組にマッチする。** 検索では「絞り込まない」が正しい問い
  でありうるが、ルールでは録画が走り続ける。保存時に明示的な確認を挟み、
  一覧でも警告として出す（作った後に気付ける経路も要る）

## 保存前の値札（件数・時間の見込み）

ルールは保存した瞬間から録画（チューナー・ストレージ）を消費し続けるが、保存前に
見えるのはマッチする番組リストだけで量としてのコストが無音だった。「この条件で
ルールを作成」「上書き保存」の近くに `RuleCostSummary`（`pages/search.tsx`）を
常置し、`lib/rule-cost.ts` の `estimateRuleCost`（純関数）で 7 日あたりの見込み
件数・時間を出す。

- **値札は警告ではない。** しきい値で色を変えたり保存を止めたりしない --- 多いか
  少ないかの判断はユーザーのもの。文字色は他の情報表示と同じ `text-muted-foreground`
  を使う（`--warning` は「条件ゼロ」「期間指定の恒久化」用、`--destructive` は
  「壊れた」用で、どちらも意味が違うので流用しない）
- **GB 換算はやらない。** ビットレートの実測の出所が未決で、件数と時間は検索結果
  だけから導出でき未決に依存しないため、そこをスコープの切れ目にしている
- **母数は厳密。** 検索 API（`POST /api/sites/{site}/programs/search`）は
  `rulequery.MatchProgramIDs` の結果を `LIMIT` なしでそのまま返す（ページングも
  上位 N 件打ち切りも無い、`internal/rulequery/query.go` で確認済み）ため、件数
  （`totalCount`）は常に全件から厳密に出せる
- **時間は近似で、かつサンプルは無作為抽出ではない。** 検索 API 自体は
  `programId` しか返さないため、番組ごとの `durationMs` は
  `GET /api/programs/{id}` を個別に叩いて集める必要がある。全件を叩くと数百件
  規模のルールでリクエストが数百本に膨らむため、結果一覧の表示のために既に
  読み込んでいる分（`ids.slice(0, visibleCount)`。追加のリクエストは発生しない
  --- `search.test.tsx` の実測テストで確認）の平均から全件に外挿する。
  **読み込みが母数に追いついていない間はその旨を明記する**（黙って過小に見せない。
  文言は「先頭 N 件」と言う）。全件読み込み終わると外挿ではなく実測の合計になり、
  注記は消える。**この「先頭 N 件」は無作為抽出ではない**: `programId` は
  `ORDER BY p.program_id` で昇順に並び、`programId` 自体がネットワーク・サービス
  順に固まる値（`(networkId*100000 + serviceId)*100000 + eventId`）のため、
  複数チャンネルに跨がるルールでは尺の偏った標本になりうる（詳細は
  `lib/rule-cost.ts` の `RuleCostSample` のコメント）
- **7 日（1 週間）に正規化するが、この分母は近似であり方向の保証は無い。**
  ルールの時間帯条件は曜日単位（1 週間周期）なので、EPG の前方保持日数の目安である
  8 日（[../data/projections.md](../data/projections.md)「ローリングウィンドウ
  （8 日 + 猶予）」、`epgWindowDays`）という半端な単位のまま見せると直感的な判断が
  しにくく、これを固定の分母にして 7 日に正規化する。**ただし検索結果の実際の観測
  スパンは「未来 8 日」だけではない**: EPG の刈り取り（`PruneEpgPrograms`）は
  `end_at < 基準時刻 - retention_grace` で、`retention_grace` の既定値は 24 時間
  （設定キー `epg.retention_grace`。フロントからは見えない）ぶん放送済みの番組が
  残る。さらに `rulequery` には「未来だけに絞る」述語が無い（`start_at` を暦上の
  範囲で絞るのは `periodStartAt` / `periodEndAt` の 2 箇所だけで、検索条件で明示
  しない限り効かない。時間帯条件も `start_at` を読むが曜日・壁時計の時刻に落とす
  だけで暦上の範囲は絞らない）。したがって条件を指定しない検索の観測スパンは既定で
  「過去 24h + 未来 ~8 日 ≒ 9 日」になりうる。8 日固定の分母では**過大に**出ることが
  ある。逆に、EPG が前方に丸 8 日ぶん入っているとは限らないので**過小にも**振れる
  （番組表が上限に使う `limitMs` は「8 日先の 0 時」（[programs.md](programs.md)
  「EPG のローリングウィンドウの終端」）で、そこから逆算した「今からの残り日数」は
  7〜8 日で揺れる。これは番組表 UI 自身の上限で検索は適用しないが、「丸 8 日とは
  限らない」ことの目安になる。実際の前方の量は未計測）。**「多めには出ない」のような
  一方向の保証は書かない**（一度も真でなかった記述は古い記述より悪い --- CLAUDE.md
  「測っていない挙動を断言しない」）。厳密に測るには「今」・窓の終端・
  `retention_grace` を突き合わせる追加の問い合わせが要り、値札 1 つのために増やす
  コストに見合わないため、固定値のままにしている
- **期間条件（`periodStartAt` / `periodEndAt`）で絞った検索では「8 日分を 7 日換算」
  という根拠を出さない。** その根拠は「検索結果は EPG の前方保持ぶんの観測」という
  前提に立っており、期間を絞った検索は観測スパンがその期間そのものになるため
  前提が崩れる（8 日分ではないのに 8 日分と言うと偽の根拠になり、issue #237 の罠
  「黙って過小に見せない」に反する）。代わりに「期間条件で絞っているため、週あたり
  の見込みは実際より小さく出ます」と明記する
- **値札の数値とその根拠は同じ検索から導く。** 期間の有無の判定は下書き（`draft`）
  ではなく**実行した検索**（`search.variables`。`buildSearchRequest` が空の期間を
  キーごと落とすので、キーの有無がそのまま判定になる）から取る。数値は実行済みの
  検索の産物なので、根拠だけをフォームの現在値から取ると再検索するまでの間ズレ、
  期間を入れて検索したあと欄を空にするだけで「8 日分を 7 日換算」という偽の根拠が
  期間で絞った数値に付き直す（逆向きも同様）。`CreateRuleForm` / `RuleEditForm` に
  ある同名の `hasPeriod` は「この下書きを保存すると恒久的な期間制限になる」という
  **下書き**についての警告なので、そちらは下書きから導くのが正しい（同じ式に見えて
  由来が違う）
- **「未検索」と「検索したが 0 件」を混同しない。** どちらも件数は 0 だが、
  条件を指定し忘れているだけなのか正しく絞り込めているのかは区別が要る
  （上記「未検索と 0 件を構造的に別の状態として扱う」と同じ精神）

## 経緯と失敗事例

- `/search` は M2-11 で追加した
- 「検索 API と ruler 経路の programId 集合が一致する」ことは M2-2 のテストで
