# 検索

## 検索は独立ルート `/search`

番組表は EPG を時間軸で眺める画面、検索は **ruler と同じ条件コンパイラ（`internal/rulequery`）を叩く「ルールの条件を試す画面」** で、関心事が違う。「検索 API と ruler 経路の programId 集合が一致する」ことはテストで担保されているので、ここで当たりを確認してからルールにできる。検索条件は番組表と `cond` で往復でき、検索結果から同じ条件を重ねた番組表のグリッドへ移れる。

保存時に新たに生じる容量不足は検索結果へ混ぜず、予約・意図・録画履歴まで読む独立したプレビュー API で導出する。仮定の値札は保存操作がある検索画面にだけ置き、番組表の閲覧状態には持ち込まない。

- **未検索と 0 件を構造的に別の状態として扱う**（`isIdle` と `success && 空`）。文言が入れ替わらないようにする
- **検索結果は番組表と同じ `ProgramRow` を使う。** 行本体のタップで詳細を展開し、右端の予約列は番組表と同じ開閉規則（hover / フォーカス / 展開）にする。単発予約はルールを作成せず、番組表と同じ `useReservationActions`（楽観更新・トースト・取消 Undo）を通す。複数 site の結果では site 名も行に表示する
- site レジストリの取得中は検索操作を無効にして理由を表示する。取得失敗時はエラーと再試行を表示し、対象サイトが無い検索を無言の no-op にしない
- 結果は **開始時刻順**に並べ、日付が変わる箇所に番組表と同じ見た目の日付ヘッダを出す。ただし番組表と違い `sticky` にはしない。同時刻は site、programId の順で固定する。検索結果は番組表と同じ行の語彙で表示するため、行ごとに日時を繰り返さない
- **「問わない」次元はリクエストのキーごと落とす**（`null` を明示しない）。不変条件 10（意味を持たない行を作らない）の精神をリクエストにも適用する
- **フォームで止めるのは「送るとサーバーが壊れる」ものと「黙って嘘の絞り込みになる」ものだけ。** 矛盾した範囲（下限 > 上限）は 0 件が正しい答えなので検証しない。曜日ビットが 0 のときだけ止めるのは、`rulequery` が範囲外エラーを返し API が 400 に変換しないため 500 になるという実装上の理由
- **サイトは `sites` として条件フォームに出す。** 検索 API は `POST /api/programs/search` で、検索対象を絞る軸は本文の `sites` である。`GET /api/recordings` の `?site=` と同じ規約で、軸内は OR、空なら全サイトを対象にする。
- サイトチップはレジストリと下書きの和集合が 2 つ以上のときだけ出す（下記「サイトチップの選択肢は…」）。録画一覧の絞り込みも同じ判定規律である。チップは `SearchDraft.sites` を編集し、`buildSearchRequest` / `conditionsToDraft` / `buildRuleInput` がそのまま運ぶ。
- 検索結果は表示に必要な最小情報を使い、初期表示で番組詳細を取りに行かない。行を展開したときだけ説明・出演者・映像音声を取得する。検索結果の行数は予約見込みの行数と一致する。
- 結果行の identity は site と programId の組にする。site は検索条件で選び、結果のパスには含めない。
- 条件フォームのサービス選択肢は、検索対象の `sites` とは別の理由で全 site の和集合にする。保存されたルールは全 site で評価される（`sites` が空なら全サイト）ので、先頭 site の観測だけから作ると、その site が受けていないチャンネルを条件として名指しできない。
- site は識別子の一部ではなく存在のスコープでしかない。そのため識別子を問う選択肢は、1 site の観測ではなく識別子の集合（`Service.id` で畳んだ和集合）で答える（`lib/all-sites-services.ts`。`/rules` にも同居する）。
- 結果行のサービス名解決も同じ和集合を使う。結果が複数 site にまたがりうる以上、先頭 site の観測だけでは他 site だけが受けているサービスの名前を引けない。
- サービス名は networkId と serviceId の組で引く。serviceId 単独は network をまたぐと一意でなく、番組詳細 API（`GET /api/sites/{site}/programs/{programId}`）は合成済み `Service.id` を返さないため、番組側で組み直す。
- ジャンルの未知コード（12 / 13 の予備）は数値のまま出す。「その他」に丸めると ARIB の本物の「その他」（15）と区別できない（`lib/genre.ts` と同じ規律）
- **チャンネル名が重複するときは補助ラベルを付ける。** マルチ編成のサブサービスは主サービスと同じ名前を持つことがある。
- 地上波は規格の 3 桁チャンネル番号、物理チャンネル、networkId と serviceId の順で補助ラベルを作る（`lib/service-label.ts` の `serviceDisambiguator`）。3 桁番号はリモコン番号を 2 桁にゼロ埋めし、末尾にサービス番号（`serviceId` の下位 3bit）+ 1 を付ける。
- 3 桁番号を採るのは、視聴者がリモコンで読む番号と同じ粒度で主/サブを見分けられるためである。リモコン番号の出所は、番組表のチャンネルピッカー（`channel-picker.tsx`）がリモコン番号バッジに使っているものと同じである。
- この復元式は規格が定めた割り当て規則そのものなので、測った site の外にも効く。ただし域外局とリモコン番号が衝突する受信機は 3 桁番号に枝番 `051-1` を付けるので、実機の表示と 1 文字単位で一致するとは限らない。
- 材料は `Service` が既に返す値だけを使い、programId は分解しない。
- BS / CS は 3 桁番号を復元できないため、従来どおり種別、物理チャンネル、networkId と serviceId の順にする。
- 同じ名前のグループ内では全候補に同じ段数の材料を付ける。表示の形を揃えるためである。
- `Service.hasPrograms` は、マルチ編成のないサブサービスで false になる（`openapi.yaml` の説明どおり）。ルールがそのサービスも参照できるよう、API 自体は絞り込まない。
- false のサービスだけを条件にしたルールは、現時点で番組に 1 件もマッチしない。そのため同名グループに番組を持つ側がいるときだけ、持たない側の末尾に「番組なし」を足す。
- 「番組なし」は主/サブを示すラベルではなく、「今このサービスを条件にしても 0 件」というヒントである。全員が false のグループ（初回 EPG 取得前は全サービスが false）では出さない。
- `hasPrograms` は放送内容で変わる状態であり identity ではない。識別には使わず、ID による区別が終わった後の補助表示にだけ使う。
- `Service` に type（`epg_services.type`）は加えない。到達するサービスでは実質一定で、API の形を広げる利益がないためである。
- mirakc-arib のサービス scanner は `IsAudioVideoService` が false の種別を取り込み前に除外する。ワンセグ（`0xC0`）はその対象なので Rokuban にはそもそも届かない。届くサービスは実測（高松 mirakc 19 件）でも全件 `type=1` だった。
- **チップは補助ラベルで親の幅を超えうる**ので `Chip` に `max-w-full` を置いて自身の中で折り返させる（`components/ui/chip.tsx`）。`shrink-0` の flex-basis が内容の最大幅を要求するため、これが無いとページ全体が横に伸びる。合否は実ブラウザ 320px の実測で出す（`web/e2e/chip-overflow.mjs`）--- レイアウトの判定なので jsdom では原理的に測れない
- **主操作（検索・条件をクリア）は条件フォームの後ろに置く。** 入力から送信までを上から下へ進めるためである。画面下への固定は、ソフトウェアキーボード表示中にボタンとタブバーが可視領域を占めるため採らない。値入力には `enterKeyHint="search"` を付け、フォームの Enter 送信で検索できるようにする。保存 UI は検索フォームの外にある別フォームなので、名前欄の Enter はルールを作成し、検索を再実行しない。送信が決着したら結果の先頭（`検索結果` セクション）へスクロールとフォーカスを移す。合否は実ブラウザの検索フォーム gate（`web/e2e/issue-1232-search.mjs`、`pnpm e2e:issue-1232-search`）で測る（座標とフォーム送信は jsdom では測れない）
- **`<ConditionFields>` のテキスト条件は 1 行目を常に編集可能な状態で出す**（「条件を追加」を押した先に初めて出す形にしない）。この節は `<ConditionFields>` の先頭に来るので、これだけで「最初に打つ場所」がクリック無しで届く
- **最初のテキスト条件は入力値があるときだけ実体化する。** 空欄のまま対象・モード・チップを選んでも検索条件の配列は空に保つ。
- 空欄の行の選択はローカル state に残し、後で値を入れたときに条件へ反映する。単一行を全消ししたら未実体化へ戻し、複数行の空欄は編集位置を保つため残す。空欄を条件配列に置くと検索・保存が入力エラーで止まり、選択を捨てると再入力時に意図が消えるためである。
- 複数行のうち 1 行を空にした場合は編集位置を保つため勝手に消さない。明示的な削除（X）だけが、その行の選択も捨てる。
- 配列が空の間は「条件を追加」と X を出さず、「指定なし（すべての番組が対象）」を出す。
- 共用の条件説明には「検索すると」のような画面固有の動詞を入れない。`<ConditionFields>` は検索からの新規作成と既存ルール編集で共用するため、どちらの操作でも同じ意味になる文言にする。条件ゼロのルールは検索結果が全件になるのではなく、録画が走り続けるためである（下記「条件ゼロのルールは全番組にマッチする」）。
- **検索画面の詳細条件は初期状態で折りたたむ。** `/search` はまずキーワードを入力して結果を確かめる画面なので、テキスト条件は常に表示する。チャンネル種別・ジャンル・時間帯・無料/有料・放送時間・期間・サイト・チャンネルは `ConditionFields` の `collapsible` 節へまとめる。新規作成・既存ルール編集も `/search` でこの同じ詳細条件を使う。URL (`cond` / `ruleId`) や `localStorage` から条件を復元しても検索画面は閉じたままで、現在の下書きだけを「設定中の詳細条件: N件」と条件種別ごとの短い要約にする。要約の X はその種別全体を下書きから解除する（自動検索や URL 更新はしない）。要約から開けばその場で編集でき、閉じた詳細内の検証エラーがあるときだけ自動展開して修正欄を見せる。
- **モバイルのテキスト条件は値入力を専用行に分ける。** 360/390px では対象とモードを同じ行に残し、値入力を次の行で利用可能な幅いっぱいにする。実ブラウザの実測は 360px で入力幅 302px（フォーム内 328px）、390px で 332px（同 358px）。旧一行レイアウトを実ブラウザで再現した比較では 360px が 62px、390px が 92px しかなかった。デスクトップでは従来どおり一行レイアウトを保つ。`web/e2e/search-mobile.mjs` がこの breakpoint と、要約のキーボード開閉・日本語入力編集・種別解除を固定する。
- **サービスの節は `<ConditionFields>` の最後に置く。** サービス一覧は非同期で、読み込み中の 1 行から複数行のチップへ変わる。
- 非同期の節を先に置くと、後続の同期節が下へ押されて CLS を作る。これは Lighthouse で検索モバイルが要改善域に出た実測であり、`web/e2e/cls.mjs` でも 390x844 で 0.165 だった。
- Layout Instability API は移動した描画済み要素を数えるため、押された要素が折り目の外へ出ることはあっても、ページから無くなるわけではない。`pages/search.tsx` は `<form>`（`<ConditionFields>` を含む）の後ろに値札・ルール保存・検索結果を同じ 1 本の縦カラムで積むので、押される要素は残り、残差も 0 ではない。
- 残差は、`cls.mjs` と同じ 24 局のフィクスチャで詳細節を明示的に開いて測った値で、390x844 で約 0.03、1280x900 で約 0.016。いずれもしきい値 0.10 以下である。検索画面は詳細節を初期非表示にしているが、`cls.mjs` は非同期のサービス節が表示中のフォームを押す従来のシナリオを維持するため、明示的に開いて測る。
- フォームを折りたたむなどサービス節より下の内容を上へ移すと、測定時の可視状態が変わる。レイアウトを変更するときは可視状態も含めて測り直す。
- **サービス節を末尾に置く動線上の代償は受け入れる。** チップ列はサービス数と幅ごとの折り返しで高さが変わる。高さを多く予約すると空白が残り、少なく予約するとシフトが残る。
- **高さの予約とチップ列のスケルトンは採らない。** どちらも「何行ぶん予約するか」を先に決める必要があるが、サービス数と幅で高さが変わるため予約値が恣意的になる。
- チャンネル絞り込みは初画面より下になるので、検索とクリアは条件の後ろに置き、値欄から Enter でも検索できるようにする。画面下固定はソフトウェアキーボードとタブバーが操作欄を占めるため採らない。
- `<ConditionFields>` は検索・新規作成・既存ルール編集で同じ順序を使う。動線の代償が受け入れられないと判断したときは、並べ替えをやめてスケルトン側に寄せる設計判断になる。`cls.mjs` はそのまま判定に使える。

## 検索とルールは同じ条件 UI を双方向に共有する

`ProgramSearchRequest` と `RuleInput` の条件部分は同形で、サーバーは `internal/rulequery` という同じコンパイラを通る。この同一性を UI 側でも保つため、条件の入力は `components/condition-fields.tsx`（`<ConditionFields>`）1 つだけにし、検索画面の新規作成・既存ルール編集がこれを使う。**片方だけに次元が増えると、「試した条件」と「保存される条件」が食い違う。**

下書き（`SearchDraft`）と `RuleInput` の相互変換は `lib/program-search.ts` の `buildRuleInput` / `conditionsToDraft` に置き、**往復テストで固定する**。分と ms、ローカル壁時計と UTC の取り違えは UI 越しには見えにくい。

- **検索 → ルール**: 検索画面の「この条件でルールを作成」（`?ruleId` を伴わない通常の検索から）。条件は `buildSearchRequest` の結果をそのまま流用する（変換を 2 箇所に書かない）
- 新規ルールの名前候補は、除外でないキーワード条件を「・」で連結する。それが無ければ、解決できたサービスが 1 件のときのサービス名・ジャンル・最初の時間帯を既存のラベルで連結し、名前欄を編集するまでは条件に追従させる。保存後はユーザーが確定した名前として保持し、条件変更で作り直さない（導出値と確定した事実を同じ列に載せない）。
- **番組 → 検索**: 番組詳細の「この番組名で検索」はタイトル全文を `name` の keyword 条件として `/search?cond=` へ渡す。`sites` は保存ルールが全 site で評価されるため含めない。
- **ルール → 検索**: `/search?ruleId=N` でそのルールの条件を下書きに写して自動検索する。**ハイドレーションは `ruleId` ごとに 1 回だけ**（ref でガードする）。refetch のたびに写すと、ユーザーが条件を編集した直後に入力が巻き戻る
- **`?ruleId=N` で開いた画面の保存は上書き（`PATCH /api/rules/{id}`）が既定動作**。検索画面はマッチする番組を見ながら条件を詰められるので、そこが実質のルール編集画面になる、という判断である。以前は「ここでの編集は元のルールを変更せず、保存すると別の新しいルールになる」としていたが、編集体験として一本化した。元のルールを残したまま別のルールとして保存する経路（`POST /api/rules`）も副動作として残し、押し間違えないよう主動作と見た目を変える。名前が元のルールと同じままこの副動作を押すと `〜 のコピー` を付ける。`rules.name` は一意ではなく、同名のルールには一覧側で `#<id>` が付くが、コピー元と意図的に別の名前であることを通常の表示だけで読めるようにするためである。
- **ルール作成・既存ルールの上書きの入口は検索画面に一本化する。** 新規作成も `/search` へ案内する。値札（件数・時間の見込み）と一致する番組の一覧が常に作成ボタンの近くに出る検索画面に入口を揃えるためで、`/rules` の作成フォームにはそのどちらも無かった。強制はしておらず、`/search` でも検索せずに保存まで進める（その間の値札は「検索すると…」の案内だけ）。`/rules` はルールの一覧・有効切替・削除だけを持ち、一覧のルール名リンクから既存ルールの条件を変える `/search?ruleId=N` を開く。検索画面ならマッチする番組を見ながら条件を詰められ、`RuleEditForm` が UI を持たない項目も `preserve` で引き継ぐため、`/rules` に同じ上書きフォームを残す必要はない。
- **UI が持たない次元は勝手に埋めない。** `sites` はいまや条件 UI（サイトチップ）の次元なので、`buildSearchRequest(draft)` の一部としてそのまま送る（空 = 全サイト）。UI が今も持たない項目（`description` / `dedupe*` / `filenameTemplate` / `metadata`）だけを `buildRuleInput` の `preserve` で引き継ぐ。`UpdateRule` は子テーブル全置換なので、落とすとユーザーの設定が黙って消える
- **サイトチップの選択肢は「レジストリの site」と「下書きが既に持つ site」の和集合にする。表示するかどうかの判定（2 つ以上か）もこの和集合で取る**。`?ruleId=` で開いたルールの `rule_sites` にレジストリから消えた site 名が残っていても、和集合に含めることでチップとして見え、明示的に外せる。レジストリの一覧だけを選択肢や表示判定に使うと、レジストリが 1 site に縮んだ環境で下書きが別の site を持つケースが「見えない」に戻る。消えた site はチップごと消え、画面内で外す手段が無くなる。以前はこれが未解決の問題だった。`sites` を条件 UI に出していなかったため、フォーク（`POST`）だけが 400 `unknown site` になっても画面内で外せなかった（レジストリ照合の免除は `PATCH` にしか効かない）
- **`sites` はスコープ軸であって条件ではない**。サイトのチップだけを選んだ下書きは「条件ゼロ（全番組が対象）」の警告・確認の対象から外れてはならない。判定は 2 箇所にあり、どちらも `sites` を条件として数えない。`lib/program-search.ts` の `hasNoConditions` と、`components/rule-condition-summary.ts` の `summarizeRuleConditions` である。片方だけ揃えると、一覧では「条件なし」の警告が出るのに保存時の確認だけスキップされる、という食い違いが起きる
- **条件ゼロのルールは全番組にマッチする。** 検索では「絞り込まない」が正しい問いでありうるが、ルールでは録画が走り続ける。保存時に明示的な確認を挟み、一覧でも警告として出す（作った後に気付ける経路も要る）

## 保存前の値札（件数・時間の見込み）

ルールは保存した瞬間から録画（チューナー・ストレージ）を消費し続けるが、保存前に見えるのはマッチする番組リストだけで量としてのコストが無音だった。「この条件でルールを作成」「上書き保存」の近くに `RuleCostSummary`（`components/rule-form.tsx`）を常置する。見込みの件数・時間は `lib/rule-cost.ts` の `estimateRuleCost`（純関数）が 7 日あたりで出す。

- **値札は警告ではない。** しきい値で色を変えたり保存を止めたりしない --- 多いか少ないかの判断はユーザーのもの。文字色は他の情報表示と同じ `text-muted-foreground` を使う（`--warning` は「条件ゼロ」「期間指定の恒久化」用、`--destructive` は「壊れた」用で、どちらも意味が違うので流用しない）
- **GB 換算はやらない。** ビットレートの実測の出所が未決で、件数と時間は検索結果だけから導出でき未決に依存しないため、そこをスコープの切れ目にしている
- **母数は厳密で、畳まない行数がそのまま件数になる**。検索 API（`POST /api/programs/search`）は `rulequery.MatchPrograms` の結果を `LIMIT` なしでそのまま表示用の行として返す。ページングも上位 N 件打ち切りも無い（`internal/rulequery/query.go` で確認済み）。したがって件数（`totalCount`）は常に全件の行数から厳密に出せる。**`programId` で畳んではいけない** --- 同一放送が複数 site でマッチすれば複数行になる。ruler はマッチした全 site で予約を作る（N 予約が既定）ため、畳むと実際に走る録画の本数をサイト数ぶん過小報告する。`totalCount` は「マッチする番組数」ではなく「ruler が作る予約の見込み数」を数えている
- **時間は検索レスポンス全件の `durationMs` を使う。** 検索 API は表示に必要な `networkId`、`serviceId`、`startAt`、`durationMs`、`name`、`isFree` を各行に載せる。そのため値札は表示中の先頭 N 件や番組詳細 GET の完了状況に依存せず、検索結果全件の `durationMs` を合計して算出する。値札のために追加の HTTP は発生しない。
- **件数と時間は 7 日（1 週間）に正規化するが、分母は近似であり、見積もりの方向は保証しない。** ルールの曜日条件は 1 週間周期なので固定分母を使う。
- EPG の前方保持は目安 8 日だが、既定 24 時間の保持猶予により過去番組も検索に残る。条件を指定しない検索は過去 24 時間と未来約 8 日、計約 9 日を含み得るため過大になる場合がある。刈り取り（`PruneEpgPrograms`）の述語は `end_at < 基準時刻 - retention_grace` である。さらに `rulequery` には「未来だけに絞る」述語が無い。`start_at` を暦上の範囲で絞るのは `periodStartAt` / `periodEndAt` の 2 箇所だけで、検索条件で明示しない限り効かない。時間帯条件も `start_at` を読むが曜日・壁時計の時刻に落とすだけで、暦上の範囲は絞らない。
- 反対に前方へ丸 8 日ぶん番組が入っているとは限らず、過小にもなり得る。実際の前方の量は未計測であり、「多めには出ない」といった片方向の保証は書かない。
- 厳密な値には現在時刻・窓の終端・`retention_grace` を照合する追加問い合わせが必要になる。値札 1 つのための追加コストに見合わないため、固定分母を使う。
- **期間条件（`periodStartAt` / `periodEndAt`）で絞った検索では「8 日分を 7 日換算」という根拠を出さない**。その根拠は「検索結果は EPG の前方保持ぶんの観測」という前提に立っている。期間を絞った検索は観測スパンがその期間そのものになるため、前提が崩れる（8 日分ではないのに 8 日分と言うと偽の根拠になり、「黙って過小に見せない」ことに反する）。代わりに「期間条件で絞っているため、週あたりの見込みは実際より小さく出ます」と明記する
- **値札の数値とその根拠は同じ検索から導く**。期間の有無の判定は下書き（`draft`）ではなく**実行した検索**から取る（`search.variables`）。`buildSearchRequest` が空の期間をキーごと落とすので、キーの有無がそのまま判定になる。数値は実行済みの検索の産物なので、根拠だけをフォームの現在値から取ると再検索するまでの間ズレ、期間を入れて検索したあと欄を空にするだけで「8 日分を 7 日換算」という偽の根拠が期間で絞った数値に付き直す（逆向きも同様）。`CreateRuleForm` / `RuleEditForm` にある同名の `hasPeriod` は「この下書きを保存すると恒久的な期間制限になる」という**下書き**についての警告なので、そちらは下書きから導くのが正しい（同じ式に見えて由来が違う）
- **「未検索」と「検索したが 0 件」を混同しない。** どちらも件数は 0 だが、条件を指定し忘れているだけなのか正しく絞り込めているのかは区別が要る（上記「未検索と 0 件を構造的に別の状態として扱う」と同じ精神）
- **保存時に追加される不足は専用 API で導出する。** `POST /api/capacity/preview` の結果を値札（`RuleCostSummary`）の隣に出す。入力は実行した検索条件と任意の `ruleId`。候補から予約済み・skip 意図（`program_intents.action = 'skip'`）・fulfilled・重複排除で skip になる番組を除く。残りを既存需要に加え、`capacity.Compute` で再評価する。ルール編集時は、そのルールの現予約を需要から外して候補として改めて判定する。
- **「追加」は区間の集合差ではない。** 保存後の不足区間から、保存前に同じ site で同じかそれ以上の不足本数がある部分だけを除く。既存不足が 1 本から 2 本へ悪化した部分も表示する。各区間に日時・詰まった種別・不足本数を出し、複数 site のときは site 名も添える。区間リンクは `/programs?view=grid&at=<開始>&cond=<検索条件>` で、「この時間帯の一致番組を番組表で見る」と案内する。仮定の不足帯は番組表に出ないため、リンクの対象を番組に限る。
- **値と説明は実行した検索から導く。** `search.variables` の条件を容量 API とリンクへ使い、フォーム下書きの条件は使わない。区間が 0 件、取得中、取得失敗のどの場合も「収まる」とは表示しない。取得失敗は確認できなかったことを伝え、成功した 0 件と取得中は何も描画しない（沈黙は保証ではない）。取得中に「確認中」の行を描くと、検索より遅く返るプレビューが 0 件のとき描画済みの結果一覧が 1 行ずれる（CLS）。
- **放送済みの番組は候補にしない。** `epg_programs` は放送済みを保持猶予ぶん残すが、終了が現在時刻以前の番組は録れないので、需要に加えると偽の不足を主張してしまう。**フォームの「有効」を外して保存するケース**（新規ルール、または有効なルールの編集）でもプレビューは有効なルールとして数えるので、実際より多めに出る。保存済みの無効なルールを編集するときだけ、需要ゼロとして扱う。
