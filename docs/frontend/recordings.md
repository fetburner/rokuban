# 録画一覧・検索・再生

## 録画単体の着地先

録画は一覧内展開でしか見られず単体の URL を持たなかったため、skip 理由
（「重複（録画 #345）」）や予約 → 録画の導線がリンクの終点を持てなかった。
着地先は `/recordings/$id`。`recordings.id` は ingest（watcher）が一度作ったら
変わらない、不可逆な事実の id である。そのためそのまま URL に使ってよい ---
予約詳細（`pages/reservation-detail.tsx`）が `(site, programId)` を宛先にして
いるのとは事情が異なる。reservations 行は ruler が削除・再作成しうるので、
行ではなく programId という概念そのものを宛先にしている。「一覧内スクロール +
展開」は無限リストで対象が読み込み済みとは限らず成立しないため、別ルートにした。

本体（プレイヤー・メタデータ・削除系操作）は `RecordingDetail`
（`components/recording-detail-panel.tsx`）が持つ。対象は下記「ブラウザ再生」節と
「ドロップ統計」節である。単体ページ
（`pages/recording-detail.tsx`）がこれを描画する。一覧はこの本体を
インライン展開せず、行本体から単体ページへ移動する。以下の各節（ブラウザ再生の
出し分け・ごみ箱の非表示規律）は単体ページに適用される。

**単体ページ自身のクエリキーは、一覧の invalidate に前方一致させてある**
（`lib/recording-detail-cache.ts` の `recordingDetailQueryKey`）。先頭要素を
`getListRecordingsQueryKey` と同じ `'/api/recordings'` に揃えるためである。
削除 / 復元 / 完全削除 / 追加エンコードの 4 つは、この 1 本の呼び出しに集約されて
いる。`RecordingDetail` の下から
`queryClient.invalidateQueries({ queryKey: ['/api/recordings'] })` を呼ぶだけ
である。呼ぶのは `RecordingActions.invalidate` / `AddEncodeProfilesAction` の
`onSuccess` である（どちらも `components/recording-actions.tsx`）。これにより
単体ページも自動的に再検証される。
prop で 1 段ずつ配線する形（`onMutated` のような穴）は採らなかった ---
`RecordingDetail` の下に mutater を足すたびに「単体ページへの配線を通す」
ことを覚えていないといけない。その形は通し忘れても型エラーにならず黒く抜ける。
最初の実装がこれで、`RecordingActions` にだけ配線したため
`AddEncodeProfilesAction` が素通しになり、「事後エンコードを依頼しても単体
ページの『追加済み』表示が更新されない」を実機再現された。

`GET /api/recordings/{id}` はごみ箱の録画も 200 で返す（メタデータの
可視性はメディア配信の 404 契約とは別の判断。[api/rest.md](../api/rest.md)
「録画単体」）。単体ページはこの `deletedAt` の有無で、下記のごみ箱の
出し分け規律をそのまま適用する。

## 録画詳細の面積配分と構成

画面の面積は「視聴する人にとっての重要度」で配る。
同じ重みの見出し付きパネルを縦に並べず、次の四層にする。

| 層 | 誰が・いつ見るか | 内容 | 面積 |
|---|---|---|---|
| 見る | 開いた人のほぼ全員が毎回 | 映像と操作バー | 16:9 を保ち、タイトルと説明の先頭2行も初期画面に入る高さにする |
| 録画を知る・次を見る | 多くの人が毎回 | タイトル行、説明、シリーズ、次の回 | タイトル行と説明は映像の直下、シリーズ棚は desktop で映像の下の右列 |
| 整理・管理 | ときどき | 版、ダウンロード、原本保持、追加エンコード、CM 操作、ルール、削除 | タブとメニューの中 |
| 診断 | 問題が起きたとき | 取り込み、エンコード、ドロップ、CM 検出結果、品質イベント | 「記録」タブ |

映像の上に見出しを付けない。
プレイヤーは本文の全幅には広げず、16:9 のままページ見出し・チャプター要約・タイトル・説明の先頭2行が初期画面に入る高さに制限する。
その上限は `calc((100dvh - 18rem) * 16 / 9)` とする。18rem は映像の上下に置くもの（上はページ見出し、下はチャプター要約・タイトル・説明の先頭2行）の高さの見積もりで、`recording-detail-panel.tsx` に理由を残す。
映像・タイトル列・棚を含む本文全体を映像の上限幅に揃えて中央に置く。下段の左端を映像と揃えるためである。
編集モードには上限を掛けない。映像の横に区間一覧を置くので、映像が全幅を占める前提の上限式が成り立たない。
`web/e2e/recording-detail-layout.mjs` が実ブラウザで 1280×720、1280×800、1920×1080 の初期画面への収まりを測る。
あわせて、棚の上端がタイトル行の上端と揃うこと、棚が下段の左列の右にあり右端が映像の右端に揃うことも測る。
編集モードの本文幅が上限で絞られないことは `web/e2e/chapters.mjs` が測る。
400×800 では棚を隠し、シリーズなし録画では映像と下段の左右位置と幅が揃うことも確認する。
チャプター編集は再生設定から専用画面へ入る。編集中はタブとシリーズ棚を隠し、デスクトップは
左にプレイヤー、右に区間一覧、下に全幅のフィルムストリップを置く。スマートフォンでは
プレイヤー、フィルムストリップ、境界調整を上から並べ、区間一覧だけをスクロールさせる。
下部ナビも高さの予算から引き、ページ自体はスクロールさせない。
映像下端の帯では「前後 3 秒」の隣の小さなボタンを押して、
通常再生と同じ 0.5〜2 倍の速度を巡回する。400px 幅に収めるためこの形にし、
編集用の速度は `rokuban:chapter-edit-playback-rate` に別保存するので、
CM 確認のために上げても普段の視聴速度には残らない。
編集に入る前の `<video>` は作り直さない。別の木に描き直すと再生位置が 0 に戻って止まるので、
編集用の部品はプレイヤーの兄弟として足すだけにする。

映像の下では、タイトル行とタブを左列、同じシリーズの録画棚を右列に置く。
棚はデスクトップだけに出し、スマートフォンには出さない。

タイトル行はタイトル、局、放送日時（開始と終了）、尺、状態・取り込み・エンコード・ドロップのバッジを持つ。
一覧と同じ条件の site と、説明の先頭二行も持つ。
説明は押すと全文を開き、番組タブには繰り返さない。
番組時刻と実録画時刻が一致する場合、実録画時刻は出さない。
ずれがある場合だけ「30 秒早く開始」「30 秒遅れて終了」のように出す。
番組タブの実録画の開始と終了は秒まで出す。
分までだと、30 秒のずれが番組の開始・終了と同じ表示になるためである。

番組の時間枠より前後を録画した部分は、シークバーの中に破線で示す。
シークバーは複数の段に分けず、一本に収める。
カット版の再生中は描かない。
割合は原本の時間軸で出したもので、カット版の動画には当てられない。
破線が実際に描かれることは `web/e2e/recording-next-episode.mjs` ① が画素で測る。

画面には「番組 / 版 / 記録」のタブを置く。
タブの中身は選択したものだけを描き、非選択タブは見出し一行ぶんの面積だけを使う。
初期選択はデスクトップでは「版」、スマートフォンでは「番組」にする。
タブの選択状態は画面内の React state に持ち、URL・hash・履歴には書かない。
バッジを押したときは「記録」タブを選ぶ。
詳細ページの hash は追っかけ再生の指定（`#chase`）に使われ、hash を変えると `RecordingDetail` が作り直される。
そのため、タブの切替で hash を変えない。

| タブ | 内容 | 表示条件 |
|---|---|---|
| 番組 | 物理チャンネル（種別と番号つき）、ずれがある実録画時刻、録画のしかた | 常時。ごみ箱ではこのタブだけ |
| 版 | ある版を一行ずつ（再生中の印、サイズ、ダウンロード）、原本 TS、原本保持、追加エンコード | ごみ箱以外で表示する内容があるとき |
| 記録 | 取り込み、エンコード、CM 検出、ドロップ、品質イベント | ごみ箱以外 |

録画のしかたは、ルールがあれば「ルール「名前」」とし、名前をルールへのリンクにする。
ルールが無ければ「手動予約」など、録画の出自を出す。

「版」タブには、手元にある版を一行ずつ並べる。
原本 TS の行は、ダウンロード / VLC のリンクを持つ。
その下に原本保持の現在値（「原本: 常に保持」）と「この回だけ変える」、追加エンコードの操作を置く。
凍結された保持値がルールの現在の既定と同じときだけ、「（ルールの既定）」と添える。
違うときは何も言わない。ルールの既定が後から変わった場合を区別できないためである。
エンコードの全候補が追加済みなら、その旨だけの枠を作らない。
エンコード後の原本削除を選ぶと再エンコードできない説明は残す。
エンコード版のダウンロードは、この「版」タブだけが受け持つ。プレイヤーの設定メニューには置かない。
版が 1 つも無いときは、行の無い枠も出さない。
ごみ箱では再生、サムネイル、ダウンロードを出さない。
録画中は「版」タブに取り込み中の原本だけを出す。
中身が無いタブは出さない。

「記録」タブは、取り込み・エンコード・CM 検出・ドロップを一行ずつ示す。
異常はタイトル行のバッジにも示す。
CM 検出が局で直せる段階（`logo` / `area` / `adopt` / `match` / `resolution`）で失敗したときは、その行から局の CM ロゴ画面へ進める。`adopt` のリンクは「ロゴ候補を確認して採用する」、他の 4 段階は「CM 検出のロゴを教える」と出す。
ドロップの PID 表と品質イベントなどの詳細は、該当するデータがあるときだけ開ける。
異常のない録画に「0」や「異常なし」の行を増やさない。

ページ見出しの右上に `⋮` メニューを置き、ルールを開く（右にルール名を添える）、CM 検出のやり直し・停止、ごみ箱への移動を入れる。
原本が無い録画では「やり直す」を押せない形で出す。再検出は原本から読むため、押すと API が 409 を返す。
メニューの行の高さはラフどおり 36px にする。部品の既定（28px）では詰まって窮屈になる。
下限は `web/e2e/recording-detail-layout.mjs` がデスクトップとスマホの両方で測る。
ごみ箱への移動は、見終えたときの終端カードにも置く。
これはカードがその場面で引き受ける整理操作である。
完全削除はごみ箱に入った録画の画面だけに出し、確認ダイアログを通す。
通常の録画のメニューから一クリックで完全削除できる状態にはしない。

### 次のエピソードとシリーズ

シリーズへの導線（`/recordings/$id/series`）は、どの状態でも幅ごとに 1 つだけ見せる。
棚がある幅（lg 以上）では、棚の見出しのシリーズ名「ニュース７ ›」を下線付きのリンクにし、タイトルの下には出さない。
棚が無い幅（lg 未満）と、棚を出さないごみ箱では、タイトルの下に「シリーズ ニュース７ ›」の形で置く。
見出し語と下線を付けるのは、回のタイトルとシリーズ名が同じ録画でタイトルの繰り返しに見えないようにするためである。
操作バーには「このシリーズへ」を置かない。棚の見出しと役割が重なる。
どの幅で何が見えるかは `web/e2e/recording-next-episode.mjs` ⑦ が 1280 と 400px で、各状態について測る。
各状態はエンコード版・原本のみ・録画中・ごみ箱である。
次のエピソードの選び方は `lib/series.ts` の `nextEpisode` で、再生できる録画だけを対象にする。
操作バーの右側に「次: 10/1(水)」を置く。スマホでは ▶▶ のアイコンだけにする。
操作バーが無い状態では、同じリンクをタイトル行のシリーズ名の隣に出す。
バーがあるときは重ねて出さない。

終端では映像の上に終端カードを出す。
カードはサムネイル、「次のエピソード · N 秒後に再生」、次の回のタイトルと放送日時、カウントダウンの輪を持つ。
ボタンは「今すぐ再生」「取り消す」「この回をごみ箱へ」の 3 つを 1 行に置く。
映像の暗い地の上に出すので、ボタンはカード専用の固定色にする。
テーマのボタン部品は明るい地を前提にしており、黒いカード上では白地に白文字になった。
文字と地のコントラスト比 4.5 以上を `web/e2e/recording-next-episode.mjs` ② が測る。
カウントダウンは 3 秒（`AUTO_ADVANCE_SECONDS`）で、「取り消す」で止められ、カウントダウン中にページを離れたらタイマーを片付ける。
次の回が無ければ、「最後のエピソードです」の下に「もう一度見る」とごみ箱への移動だけを出す。

自動で移った先は再生を始める。全画面で見ていたなら、全画面を保つ。
そのため、次の回へ移るとき `RecordingDetail` を作り直さない。
ページ側の `key` は hash だけにして、録画 id を含めない。
全画面は全画面要素が DOM から消えると解除される。
プレイヤーの枠は再生元（encoded・原本 HLS・追っかけ）ごとに作り直されるので、全画面は枠ではなく、再生元が替わっても残る再生グループの要素に要求する。
枠の下に出る兄弟（カット版が古い警告・チャプター検出中の表示・チャプターエディタ）も全画面の中に入る。
全画面中は枠を先頭に置き、溢れた分は縦にスクロールさせる。枠と下端の操作バーを画面の外へ追い出さないためである。
録画ごとの state は、id の変化を見て既定に戻す。
`RecordingDetail` はタブ・説明の展開・追っかけの位置・選んだ画質を戻す。
プレイヤーも id の変化で選んだ画質を捨てる。編集モードは「どの録画で入ったか」を覚え、別の録画へ
移ると抜ける。下書きが綺麗なまま次の回が編集モードで開き、終端で止まらずに進める経路を作らないためである。
未保存のまま移動しようとした場合は SPA 遷移を止め、編集を続けるか下書きを捨てるかを画面内で選ばせる。
`web/src/pages/recording-detail.test.tsx` の「次の回へ移ると…」の 4 件と、`web/e2e/recording-next-episode.mjs` ⑨ が測る。
移動先の詳細は、一覧で持っている行を先にキャッシュへ入れてから描く（`lib/recording-detail-cache.ts` の `seedRecordingDetail`）。
詳細の取得が終わるまでスケルトンにすると、その間にプレイヤーごと消えるためである。
キャッシュの行は stale にして、描画後に取り直させる。
自動遷移も、バーの「次のエピソード」と棚からの移動も、履歴を積む。ブラウザの「戻る」で見ていた回へ戻れる。
実ブラウザで再生・全画面・履歴を測る判定は `web/e2e/recording-next-episode.mjs` ④ にある。原本のみの回への自動遷移で全画面と再生が続くことと、全画面で枠と操作バーが画面に収まることは同 ⑪ が測る。
未解決: 自動で進むことを嫌う人向けの設定は足していない。

棚はシリーズの録画を新しい順に並べ、過去の回も含める。
見出しに本数と合計サイズ（原本とエンコード版の和）を出す。
棚は「次のエピソード」の問い合わせ（いまの回以降を昇順）とは別に、`seriesOf` を新しい順で 1 本引く。
使い回すと過去の回が出ず、件数も誤る。
1 回で引く上限（200 件）に達したら「200 本以上」とだけ出し、合計サイズは出さない。
棚の行を押すとその録画の詳細へ移る。まとめて操作する機能は持たせない。それはシリーズの画面の仕事である。
録画中の録画は、開いている回でも「再生中」ではなく「録画中」と出す。
各行のサムネイルの下端に視聴の進み線を重ねる。視聴済みは全幅、途中まで見た回は保存位置の割合で、未視聴の回には出さない。
線はホームの「次に見る」と同じ部品（`ThumbnailProgressLine`）を使う。

### タブ構成で保つ操作規律

四層とタブに組み替えても、操作は対象との結び付きで置き分ける。
再生位置・前後移動・選択中の画質・チャプター編集は映像を見ながら使うため、プレイヤーとその直下に置く。
原本保持・追加エンコード・ダウンロードなど録画資産の管理は「版」タブに置く。
取り込み・品質イベント・ドロップなどの診断は「記録」タブに置く。

データが空の診断行は表示しない。
特にドロップがすべて 0 の録画には、ドロップのバッジ、要約行、PID 表を出さない。
「異常あり」のような共通見出しも作らない。
正常な取り込み進捗は、値があるときに表示してよい。
信号の強さはタイトル行のバッジで示し、タブや行の並び順を異常の重さの順にはしない。

長い内容を畳む場合は、CM 検出器の結果・PID 表だけを対象にし、ネイティブな `<details>` を初期状態で閉じる。
診断の存在自体を閉じたパネルに隠さない。
前後チャプターと CM スキップは、スパンがありカット版を再生していないときに使える。
「チャプターを直す」は、保存版があり、自動検出が終わり、カット版以外を再生している場合に
再生設定へ出す。原本だけの録画、ごみ箱、検出中、カット版再生では出さない。

状態ごとの主な導線は次のとおり。希少で破壊的な操作だけを overflow に置く。
原本保持と追加エンコードは入力を伴う管理操作なので「版」タブに残す。

| 状態 | 主な導線 |
|---|---|
| 通常、エンコード済みあり | 再生 |
| 録画中、ライブ有効 | 再生枠。通常表示はポスター上の再生ボタン、`#chase` 直リンクはそのまま開始 |
| 放送終了後・ingest commit 前、ライブ有効 | 再生枠は追っかけ。`#chase` 直リンクはそのまま開始 |
| 録画中、ライブ無効 | ブラウザ再生なし。取り込み状態を表示 |
| エンコードも依頼済みプロファイルも 0 件、原本あり | 「版」タブで追加エンコード |
| 依頼済みプロファイルあり | 待機・実行中・再投入待ちを状態バッジで示す |
| ごみ箱 | 復元。完全削除は確認後に実行 |

### 検出器の結果

検出結果の有無は量子化前の `cmDetection.ranges` を使って決める。
CM 検出が検出済みの場合だけ、
チャプター情報に応じた出し分けを評価する。検出区間が 0 件なら `<details>` を作らず、
検出器の結果を一文で伝える。

検出区間が 1 件以上ある場合の出し分けは次のとおり。

| チャプター情報 | 検出器の結果 |
|---|---|
| 原本のみで編集できない | 出す |
| チャプターを読み込み中 | 何も出さない |
| チャプターの取得失敗 | 出す |
| `source = 'user'` | 出す |
| 自動、`spans` が 0 件 | 出す |
| 自動、`spans` が 1 件以上 | 省く |

省く判断には、API が返すフレーム丸め済みの `spans` を使う。
丸め前の検出区間と等価とはみなさない。1 フレーム未満の区間は丸め後に消えうる。
Go の量子化処理を TypeScript に複製して比較しない。

### 下書きと保存値

通常再生の目盛り・自動スキップ・前後チャプターは保存済みの値を使う。専用編集画面では
フィルムストリップの境界を選ぶと、そのフレームへ移動して一時停止する。← → で選択を移したときも
同じである。ドラッグはプレビュー中に下書きを変えず、ポインターを離した時に新しい境界へ移動して
一時停止する。±1 秒・±1 フレームと `,` / `.` も、境界を動かした後のフレームへ移動して止まる。
入力欄・シークバー・メニューの中を除き、`,` は 1 フレーム戻し、`.` は 1 フレーム進める。
境界を動かす操作は、キー・±ボタン・長押し・ドラッグ・再生位置に合わせるのどれも同じ経路を通る。
下書きの正規化と「元に戻す」の履歴を通り、動かした先の境界が合併で消えたときは残った最寄りの境界を
選んで、そこへ移動する。

±ボタンは押した瞬間に 1 回動かし、450ms 押し続けたら 200ms ごとに送る。初回遅延が無いと、200ms を
超えるクリック・タップで 2 フレーム動いてしまう。450ms は OS のキーリピートの初回遅延（おおむね
250〜500ms）に揃えた。200ms は 1 秒に 5 回で、1 フレームの違いを目で追える速さである。長押し
全体は「元に戻す」1 回で押す前へ戻る。`,` / `.` の OS キーリピートも同じく 1 件にまとめる。
動かした先の境界が合併で消えたら連続送りを止める。続けると、利用者が押していない別の境界を動かし始めるためである。seek 中に次の操作が来たときは、ブラウザで処理中の 1 回が
終わってから最後に選ばれた境界へ移る。

長押しの seek が詰まらないかは実ブラウザで測った（`recording-playback-timeline.mjs`。ボタンを
1.5 秒押し続けて 7 フレーム送る）。seeking から seeked までの最大は Chrome で 17〜33ms、WebKit で
16〜39ms で、200ms 間隔の seek が重ならず、離した後は最後の境界のコマ中央に着地した。測ったのは
ローカルの小さな fixture（非カット MP4 と原本 HLS）だけで、ネットワーク越しの実録画は未測定である。

境界のフレームを表示して一時停止している間は、「境界の直後（次の区間の先頭）」と表示する。
区間は `[start, end)` なので、境界上のフレームは後ろ側の区間に属する。再生中や境界から離れた後は
表示しない。

下書きの区間は、境界のドラッグを離す・±1 秒 / ±1 フレーム・再生位置へ合わせる・区間を追加する・
「切る」を切り替える操作の確定時に、クライアントで重ならない形へ正規化する。cut と非 cut が重なれば
cut を残して非 cut の重なりだけを削る。非 cut が cut に挟まれたら、両側へ同じラベルを残し、cut が
全体を覆えば非 cut を取り除く。同じ cut 値でラベルが同じか片方に無い区間は重なりを和にし、異なる
ラベルなら今回動かした境界を持つ区間、または追加した区間を優先して相手から重なりを削る。境界を共有する
前後の区間は両方を操作対象とする。操作対象が同じ優先度で競合すれば、時間上で先に始まる区間を残す。
同じ cut 値とラベルの区間は接しても一つにまとめ、ラベルが違えば境界を保つ。ドラッグ中もこの規則を
プレビューへ適用し、離した後の下書きと形を揃える。

「元に戻す」と Ctrl / ⌘+Z は確定した一操作を戻す。ラベル欄ではフォーカス中の変更を一手にまとめ、
欄にフォーカスがある間の Ctrl / ⌘+Z は文字入力側へ渡す。「最初からここまで切る」と
「ここから最後まで切る」は録画の先頭・終端までの cut 区間を追加する。サーバーの `Validate` は今まで通り
量子化後の重なりを拒否する。切り取りで生まれた 1 フレーム未満の断片は、量子化で空になりうるので、クライアントの正規化が落とす。
サーバーの量子化は最寄りのフレーム境界への丸めで、1 フレーム以上の区間は空にならない。
そのため判定に Go の量子化の複製は要らない。利用者が元から持つ区間は落とさず、サーバーが拒否する。合併をサーバー保存後に行うと画面の下書きと保存値がずれるため、
クライアントの下書きで操作が確定した時点に行う。

調整ボタンを選んだ境界にだけ出す理由は 2 つある。境界ごとに 6 個ずつ並べると、境界が増えるほど
面積を取り、どのボタンがどの境界に効くかを目で追わされる。もう 1 つは、フレーム単位の仕上げは
映像を見ながら 1 か所ずつ詰める作業なので、「いま見ている境界」が 1 つに定まっていれば足りることだ。
選択はカードの強調と同じ 1 つの値で、← → は編集画面のどこにフォーカスがあっても前後の境界へ移す
（入力欄・シークバー・メニューの中を除く）。境界の時刻と再生位置はミリ秒まで出す。秒単位では
+1 フレームの結果が見えない。

再生型は映像下端の帯にまとめ、「前後 3 秒」「境界まで」「境界から」と編集中の再生速度のボタンを同じ場所に置く。フィルム
ストリップの調整行は境界の値と編集操作に使い、再生ボタンを重ねない。再生帯に集めると、スマホ幅でも
映像と再生操作を同時に見ながら選べる。400×800 の帯で、再生・時刻・3 つの再生型・速度が枠内に収まり重ならないことを実ブラウザで確認する。

ストリップの 1 マスは 10 秒のシークタイル 1 枚をそのまま縮めて出す。シークプレビューと同じ格子画像を
使い、別の画像は取りに行かない。拡大は 1 マスの幅がタイルの実画素幅（160px）を超える手前で止める。
それ以上広げると 1 枚が引き伸ばされて粗くなるだけで、タイルは 10 秒ごとなので情報は増えない。
開いた直後の範囲は入る前の再生位置の周りで、1 マスが約 76px になる長さにする。

下書きに変更があるときは「保存」で API の全体置き換えへ GET と同じ `version` を送る。
自動層が未変更かつ stale でなければ「このまま確認」を押せる。GET の `spans` と `version` を
そのまま PUT し、明示的な操作でユーザー層へ引き取る。自動層が空でも同様に確認でき、これは
CM なしとして全編を残す判断を表す。検出失敗・CM 区間なし・安全弁で CM なしに倒れた結果も、
見えている状態をそのまま確定する操作として扱う。確認済み（`source` が `user`）で未変更なら
主ボタンは押せない。「自動に戻す」は編集所有の行を削除し、`source` が `user` のときだけ使える。
保存・確認・自動に戻すはいずれも成功後に編集画面を閉じる。
下書きが変わっている状態で「やめる」か SPA のページ遷移を選ぶと、画面内で「変更を捨てる /
編集を続ける」を選ばせる。アプリ内の移動にブラウザ標準の `confirm()` は使わない。
リロードとタブを閉じる操作だけは画面内の確認バーを出せないので、未保存の下書きがあるときに限りブラウザ標準の確認（beforeunload）を出し、
下書きが無いときは登録しない。版の更新が検出された場合も
下書きは残し、最新値からやり直す操作を明示する。

### 版タブへの導線

プレイヤーの空状態（エンコードが無い録画）には、版タブへ移すボタンを持たない。
追加エンコードはタブを開いて行う。未解決: 空状態から版タブを開く導線が要るかは、利用者の迷い方を見てから決める。

### 原本サイズの二つの役割

原本サイズは「版」タブの原本 TS の行に、操作対象の値札として置く。
エンコード済みが 0 件のとき、プレイヤーの空状態にある VLC リンクは唯一の視聴手段なので消さない。
「版」タブの原本 TS のダウンロード / VLC リンクとは別に、両方を並存させる。
原本 VOD で live プロファイルが 0 件の分岐にある VLC リンクも同じ扱いである。

## 録画のブラウザ再生

詳細画面の再生枠にはプレイヤーを 1 つだけ置き、録画の状態から再生元を選ぶ。録画中、または `finished` で `ingest.state` が `pending` / `transferring` の間は、ライブ能力が有効なら追っかけを使う。commit 後は cut でない active な encoded があれば encoded MP4 を使い、無くて live 能力と原本があれば原本 HLS を使う。それらが無ければ active な encoded を使い、さらに無ければ既存の空状態と原本リンクを出す。ごみ箱・失敗・キャンセル状態にはプレイヤーを出さない。再生元を一か所で決めることで、状態ごとに別々の再生面や開始操作を増やさない。

原本と cut 版の両方がある録画では「版」タブから各 encoded を再生できる。原本が残り、live 能力が有効なら同じタブから原本 HLS へ戻れる。cut だけの録画は原本 HLS を既定にして編集できるようにし、比較・確認のため cut 版を選んだ間はチャプター編集を止める。

再生中の録画状態更新だけでは再生元を替えない。版タブで明示的に選んだ原本 HLS は範囲外シークでは選び直さず、新しい offset で張り直す。encoded のプレイヤーは範囲外シークを通知しないので、版タブで選んだ encoded もシークでは替わらない。自動選択の追っかけ・原本 HLS は範囲外シークで選び直す。どちらの選択でも、再生元のエラーと画面の開き直しでは最新の録画状態から選び直し、現在位置を録画開始からの秒で渡す。状態更新のたびに切り替えると録画終了やエンコード完了の通知だけで再生が中断されるため、この切替時機にする。

選び直した結果が今と同じ再生元なら、詳細画面は替えずにプレイヤー自身が張り直す。追っかけは新しい offset のセッション、原本 HLS は新しい offset の playlist で、どちらも同じ `<video>` のまま再生を保つ（`<video>` を作り直すと一時停止する）。全画面も枠を作り直さないので保つはずだが、全画面は未検証。ingest commit 後は新しい追っかけセッションを作れないため、追っかけが入力エラーになったときは REST で録画を取り直して再生元を選び、範囲外のシークも原本 HLS / encoded へ移る。再生元が替わるときは、再生中だったかも持ち越す。カット版 encoded では今再生している `keepRanges` で位置を写す。

切替時の `currentTime` 停止は実ブラウザ E2E で測り、2 秒以下を合格にする。フィクスチャの HLS segment は 2 秒なので、1 segment 分の読み込み余地を認めながら、それ以上続く停止を検出できる。

終端（`ended`）では選び直さず、終了の状態のまま止める。追っかけの `ENDLIST` は、streamer が録画ファイルの終端まで変換したときにだけ付く（[api/media.md](../api/media.md) の追っかけの節）。終端と判定するのは、mirakc が録画の終了を返して最後の Range も空だったときか、record が消えた後に読んだ位置がコミット済み原本の終端と一致したときである。そのため追っかけの終端は、壁時計の録画時間（`endedAt - startedAt`）との差や録画完了の取得の前後によらず録画ファイルの終端で、移った先に見る続きが無い。壁時計の録画時間と比べて「手前で終わった」と判定すると、真の終端の位置を完了後の再生元へ渡してしまう（原本 HLS はその offset を範囲外の 416 にしうる）。通常の再生元エラーは同じ再生元でも張り直す（idle GC で消えた追っかけの再取得）が、続けて 2 回までで止め、それでも失敗したらエラー表示に落とす。追っかけ入力の失敗後は streamer が録画 ID 単位で 10 秒間、新しいセッションの作成を止める。すでに動作中の健全な offset は引き続き共有される。新しいセッションが必要な要求には `502` と `Retry-After` を返す。この `502` は `Retry-After` を伴うものだけを、容量不足の `503` と区別して入力失敗として表示し、同じ再生元の自動張り直しを続けない。利用者は cooldown 後に「再読み込み」を押せる。idle GC による通常の再取得はこの cooldown に入らない。`Retry-After` の無い 502 はプロキシ由来なので、他のエラーと同じく再生元の選び直しに回す。一度も再生していないセッションのエラー（押す前に録画が終わって追っかけが 404 になった等）では位置を作らず、保存位置・先頭から・シークで選んだ offset をそのまま持ち越す。0 秒を明示の位置として渡すと保存位置を上書きして先頭から始めてしまう。

追っかけ・原本 HLS は変換セッションを作るので、詳細を開いただけでは起動しない。通常表示ではポスターと共通の再生ボタンを出し、押した時点で変換を始める。ホームの「録画中」帯や番組表から使う `/recordings/{id}#chase` は「開いたら再生する」直リンクとして残す。encoded MP4 は変換セッションを作らないため、通常の encoded プレイヤーを表示する。画質の設定は元が live profile でも encoded profile でも別名前空間なので、再生元が変わった先ではその側の既定に戻す。

録画中のポスターには保存位置の「続きから」、録画済み時間、予定終端までの録画済み範囲と「先頭から見る」を並べる。保存位置が無いときは「再生」だけを出す（同じ操作を 2 つ並べない）。時間軸は映像と同じ 16:9 の枠の中の下端に重ね、再生の前後で枠の寸法を変えない（枠の外に帯を足すと押した瞬間にページが跳ぶ）。原本 HLS のポスターは視聴済みの操作も枠の中に置く。サムネイルは録画中だと未生成が普通なので、取れなければ画像を外して地を見せる。再生ボタンは押した操作のままプレイヤーを自動再生で始める（`#chase` 直リンクも同じ）。番組の軸は 60 分を超えても合計分で表示する（70 分 12 秒は `70:12`）。録画先端はプレイヤーをマウントせずローカル時計で更新するため、再生前に streamer へ要求を送らない。

active な encoded がある完了録画は **MP4 progressive + Range**。streamer の
`GET /api/media/recordings/{id}/file?profile=<name>` を controls の無い `<video>` の src に
渡し、映像の下端に自前の再生操作バーを重ねる。原本だけが残る完了録画は streamer の一時 HLS 経路
（`/api/sites/{site}/recordings/{id}/original-vod/playlist.m3u8`）でブラウザ再生する。
原本自体は MPEG-2 TS のまま読み、変換したファイルは保存しない。encoded MP4 の経路では
HLS / hls.js を使わない。原本 HLS の詳細は [api/media.md](../api/media.md)
「録画原本のブラウザ再生」。

- 利用可能な MP4 プロファイルは `Recording.encodedAssets`（active な encoded のみ。各要素は
  `profile` + `sizeBytes`）。プロファイルの選択は操作バー内の設定メニューの「画質」に置く。
  選択肢にはサイズを付け、サイズが無い資産もプロファイル名を出す。原本だけの完了録画は live の HLS
  プロファイルを使って一時変換し、複数なら同じメニューで画質を選べる。音声は標準 / 主 / 副の 3 択を
  常にメニューへ出す。音声切替は選択中の `LivePlayer` の音声トラックだけを変え、playlist と HLS
  セッションは作り直さない。原本 TS は VLC 等で開けるリンクも残し、プレイヤー内のダウンロードには置かない
- **再生位置は `/api/recordings/{id}/playback-position` に原本時間軸の ms で保存する**。
  追っかけ・原本 HLS・encoded MP4 は同じ録画行の値を共有し、画質プロファイルでは分けない。
  カット版だけは、再生開始時に固定した `keepRanges` で原本時間軸と相互変換する。
  位置の保存は 15 秒ごと、pause / seeked / pagehide で行い、2 秒未満は削除する。
  同じページ内で画質を切り替えると `<video>` が作り直される。録画詳細クエリの
  `resumePositionMs` はページを開いた時点の値のままなので、直前まで見ていた位置は
  原本の ms でプレイヤーの ref に持ち越し、新しいファイルの `keepRanges` で写して復元する
  （保存の成否に依らない。テスト: `RecordingPlayer` の「同じページ内の画質切替」）。
  90% 到達の視聴済み PUT が通ったら録画クエリを取り直し、ボタンと未視聴の印を更新する。
  速度だけは端末ごとの好みなので `localStorage` に残す。既存の localStorage 位置キーは
  起動時に削除する
- 追っかけの offset は `chaseStartByteOffset` による推定値で、原本 HLS・encoded の位置と
  映像上で一致する精度は未検証である。再生元を切り替えた後の原本時間軸はその再生元の時刻で
  表示するため、切替の瞬間に映像が飛んで見える場合がある
- 原本 HLS は変換中の EVENT playlist なので、シークできる範囲は変換の先端まで伸びていく。
  `endedAt` があれば、操作バーの時間軸は録画ファイル先頭から `endedAt` までの実尺を使い、
  予定尺 `durationMs` や HLS の変換先端を分母にしない。ファイル先頭は
  `max(startedAt, startAt)` とする。`started_at` はチューナーを開いた時刻で、ファイル先頭ではない。
  現在位置は `session offset + video.currentTime` で原本時間軸に直す。
  シーク先が現在セッションの offset から seekable 終端までにあれば同じセッション内で移動し、範囲外なら
  離した時点でその位置を offset にして張り直す。変換済み範囲は seekbar に描かず、変換の完了待ちもさせない。
  `endedAt` が無い録画は予定尺を分母に代用する（分母が 0 だとシークバーが効かない）。
  範囲はバッファではなく seekable の終端で判定する。WebKit は先端の 3 target duration 手前より先への代入を
  seekable の終端に丸めるので、その先は張り直す。
  開始位置は offset 0 や続きから位置が無いときも必ず明示し、canplay で明示し直す。
  WebKit のネイティブ HLS は、明示しないと ENDLIST の無い playlist のライブ端の近くから始める。
  canplay の後に再生を始めると、受け付けた位置もライブ端へ動かす。自動再開・操作バーの ▶・
  映像クリック・一時停止中にセッション外へシークして張り直した後の ▶ のどれでも起きるので、
  再生の開始経路ではなく、セッションを張った後の最初の `playing` でもう一度明示する
  （利用者のシークで解除。`web/e2e/recording-original-vod.mjs` ⑤-a ⑤-d ⑤-manual ⑤-route）。
  再生中に張り直したときは再生を続ける。
  手動の ▶ 経路は、再生ポリシーによる初回 `play()` の拒否を模擬し、テストから位置を戻さず測る。
  fixture は 6 segment の EVENT playlist から始まり、待機中の再取得で 1 秒ごとに 1 segment 伸びる。
  Playwright WebKit 26.5 では押下前の待ち時間 0 / 1 / 3 秒に対し、押下 1 秒後の `currentTime` は
  0.64 / 0.73 / 0.65 秒、再表明を外すと 3.64 / 3.75 / 3.65 秒だった。映像クリックの 1.5 秒後は 1.26 秒
  （外すと 4.30 秒）、一時停止中のセッション外シーク後の ▶ は offset 31 から 1.68 秒
  （外すと 17.15 秒でライブ端へ飛ぶ）だった。
  シークバーの長さは DB の実尺なので、末尾付近の offset は映像の終端を越えて 416 になりうる。
  エラーにはせず、最後に取れた offset を下限に手前へ丸めて張り直す（同 ⑤-f）。
  続きから再生は「始まる前のシーク」として扱う。保存位置を秒に切り下げた offset のセッションで始め、
  1 秒未満の端数を `startPosition` に渡す。
  offset 0 のまま保存位置を渡すと、位置が変換済みの端より先になり、変換が追いつくまで始まらない
  （25 分先なら J4125 の 4〜6 倍速で 4〜6 分。推定）。
  offset 0 に 4.5 秒を渡した 1 回の測定では、Chromium は端を待ち、WebKit はセッションの先頭へ丸めた
  （最初の EVENT が 2 秒で、2 秒ごとに伸びる fixture）。
  保存位置より前への巻き戻しは、既存のセッション外シークとして扱う。終端を越えた 416 も、
  既存の後退丸めで扱う（端数は捨てる）。
  開始 offset は録画ごとに最初の保存位置で固定する。固定しないと、再生中の保存で位置が動くたびに
  セッションを張り直す（`live-player.test.tsx` の「…最初の保存位置で固定し…」）。
  実ブラウザでは同 ⑧〜⑪ で見る。着地は `offset の起点 + currentTime` で判定する。
  操作バーの枠（自動非表示・フォーカス・映像のタップ・全画面・PiP）は encoded と同じフックを使う。
  終端の 90% 到達で視聴済みにする判定は ENDLIST 後だけ行う。信号は hls.js の level details が
  `live === false` になることと、`ended` イベントである。ネイティブ HLS は ENDLIST を直接
  見られず、`ended` だけを信号にする。`web/e2e/recording-original-vod.mjs` が原本 HLS の
  再開位置と ENDLIST のない先端を確認する
- デスクトップ（`md` 以上）の操作バーは下端の帯 1 本である。シークバーの下の行に、左から再生、
  前 / 次のチャプター（チャプターがありカット版でないときだけ）、ミュート / 音量、時刻、いまのチャプター名を置く。
  右には字幕（CC）、視聴済み（✓ のトグル。完了録画だけ）、設定（歯車）、PiP、全画面を置く。

  `md` 未満でもマウスで幕を押せば、映像のクリックと同じく再生 / 一時停止する（同 ⑨）
- 操作バーの右側には、再生できる次のエピソードがあれば「次: 10/1(水)」（▶▶ のアイコン。スマホはアイコンだけ）を置く。
  次のチャプター（▷|）とは別のアイコンにする。終端カードは映像の上に重ねる（§次のエピソードとシリーズ）
- 操作バーの ✓ は固定の名前「視聴済み」と `aria-pressed` のトグルにする。プレイヤー外のボタンは押した後の

- 時刻の横にいまのチャプター名を「· 気象情報 ›」の形で出す。区間の隙間は「本編」と出す。名前を押すと、

  （`web/e2e/chapters.mjs` ⑦ ⑧）
- 字幕（CC）ボタンは設定メニューの字幕スイッチと同じ操作の近道で、オンの間は下線を付ける
- **設定メニューは「アイコン・項目名・現在値 ›」の行リストにする**（動画サービスの定石）。基本の行は CM を飛ばす・
  字幕・再生速度・画質の 4 つで、原本 HLS と追っかけでは音声も加える。2 択はスイッチ、3 択以上は「›」で下の階層に入る。下の階層は同じ枠の

  （フォームの部品をバーから開くだけでは直感的に操作できない）。選択肢を選ぶとメニューを閉じる

  並びは画質を一番上にし、PiP の行を足す。原本 HLS と追っかけもエンコード版と同じ順にし、音声の行は画質の隣に置く
  （デスクトップは画質の直前、スマホは直後）。どちらもメニューは全画面要素の内側（プレイヤー枠の中）に描く
  （外に描くと全画面中に設定を変えられない）。形は `web/e2e/chapters.mjs` ⑦ ⑧ が実ブラウザで測り、
  原本 HLS の順は `web/e2e/recording-original-vod.mjs` ① が測る
- メニューの行は `menuitem` / `menuitemcheckbox` / `menuitemradio` の役割を持つ。↑ / ↓ / Home / End で

  再生ボタンを押した時点で始め、編集モードに入るだけでは作らない。
  live.enabled が無効でブラウザ再生できる encoded も無い場合は、チャプターを確認する手段が無い。

- 全画面は、映像と操作バーを含む枠を持つ再生グループの要素に要求する（理由は §次のエピソードとシリーズ）。ページの `F` キーも同じ経路を通る。

### 録画再生で共有する単位と外枠

追っかけと原本 HLS は、録画内のある秒を起点にする HLS セッションである。
セッション開始後の offset は両方が使うカスタムフックが持つ。
呼び出し元は明示の offset・保存位置・先頭から、のどれで始めるかを渡し、現在位置の報告を受け取る。
開始の意図が変わったら新しいセッションとして始める。
`pages/live.tsx` は一つの `LivePlayer` のままライブと追っかけを切り替え、詳細画面は `key` で
作り直す。どちらも開始意図を渡す形で扱い、親に offset の張り直しを頼む `onChaseOffsetChange` は無くす。
これで、追っかけと原本 HLS のセッション外シーク、保存位置からの開始、張り直し後の再生意図を
同じ規則にまとめる。

URL の組み立て、セッション起点の写像、範囲終端、416 後の後退丸めは呼び出し元に残す。
これらは配信元ごとに異なり、各規則を使う呼び出し元が一つだからである。
原本 HLS の起点はフレーム格子へ写し、追っかけは整数秒を使う。
追っかけの範囲は伸びるライブ端まで、原本 HLS は固定した録画尺までである。
416 後の後退丸めは原本 HLS だけが使う。

再生の外枠は新しいフックを作らず、`usePlayerFrame` に寄せる。
ファイル再生は `recording-player.tsx`、原本 HLS・追っかけ・ライブは `live-player.tsx` にあり、
どちらも同じ操作バーを出す。再生バーの操作は見た目と対象が同じなので、再生元ごとに分けない。
ページキー、全画面対象、字幕 cue の位置、定期・pagehide 保存の共通部分もこのフックに置く。
シークの意味と字幕 track の選択は再生元ごとに渡す。キーごとの適用範囲と動作は §キー操作を唯一の表に置く。

| 振る舞い | ファイル再生 | 原本 HLS | 追っかけ | ライブ |
|---|---|---|---|---|
| F の全画面対象 | 共有の再生グループ | 同左 | 同左 | 同左 |
| ショートカットを無視する要素 | 共通のセレクタ | 同左 | 同左 | 同左 |
| 字幕 cue を操作バーの上へ移す | ○ | ○（WebKit の native HLS は ×） | 同左 | 同左 |
| 字幕として扱うトラックの判定 | 再生元ごとに決める | 同左 | 同左 | 同左 |
| 視聴済みを保存する | ○ | ○ | × | × |
| 再生速度を選べる | ○ | ○ | ○ | × |

ショートカットを無視する要素は入力欄・選択欄・リンク・ボタン・編集可能領域・
`[role="slider"]` であり、`<video>` は含めない。追っかけでは尺が伸び続けるため、
0〜9 の割合シークと視聴済み判定は行わない。追っかけの速度設定は録画再生と共有するが、
録画中の WebKit では EVENT playlist の再生を 1 倍に固定し、完了後に保存速度へ戻す。
字幕として扱うトラックの判定は再生元ごとに行い、共通化しない。
HLS 字幕 track は、Chromium と WebKit の両方で `kind="subtitles"` と実測した。
Chromium では HLS cue の負の `line` と、表示画素の下端が操作バーの上端より上にあることを測る。
WebKit の native HLS は track を公開するが cue を JavaScript に公開しないため、`cue.line` を書き換える
引き上げが効かない。字幕の表示前後のスクリーンショット差分から描画矩形を測るが、これはブラウザ既定の
配置の観測で、実装の検証ではないので NG の判定にはしない。
測定コードは `web/e2e/recording-original-vod.mjs` と `web/e2e/subtitles.mjs` にある。

未解決: WebKit の native HLS では字幕 cue を操作バーの上へ上げられない。
上の表で WebKit の native HLS だけ × なのはこのためである。ファイル再生は HLS ではなく `<track>` の WebVTT で、WebKit でも `cue.line` が負になることを `web/e2e/subtitles.mjs` ① で測った。

字幕の位置と全画面対象は jsdom では測れないため、実ブラウザで判定する。

操作バーは `RecordingPlaybackControls` の一つを保ち、`playbackMode` ではなく必要な事実を受け取る。
シークバーは時間軸の記述（範囲、使えない区間、印、ホバー表示、シーク可否）を描画する。
固定尺・追っかけ・ライブの番組軸はそれぞれの規則を持つ純関数で作る。
操作バーは再生速度を変えられるか、音声の選択肢があるかを受け取り、ライブ固有の印・診断・設定名・
ボタン配置は呼び出し元が差し込む。`recording-player.tsx` と `live-player.tsx` は同じ操作バーを使うため、
シークバーの描画規則は共通にする。3 種の時間軸の作り手はそれぞれ異なる範囲と印を導出するため、
一つにまとめない。

### 視聴状態（続きから・視聴済み）

**再生位置と視聴済みの印は、サーバーに世帯でひとつの値として置く。** 以前の決定
「サーバー側視聴履歴は作らない」はこれで覆す。localStorage のままでは、リビングの TV で
見始めた続きをスマホで開けない。未視聴の印も端末ごとに食い違い、どちらが正しいかを
利用者は判定できない。これは [design.md](design.md) §個人化の「サーバーへ移す条件」に当たる。
Rokuban は利用者を持たないので（[api/deployment.md](../api/deployment.md) §認証）、
値は世帯グローバルで、利用者ごとの表にはしない。

選ばなかった案:

- **localStorage を続ける**: 端末をまたぐ「続きから」を捨てることになり、未視聴の印が端末ごとに
  食い違う
- **位置はローカル、視聴済みの印だけサーバー**: TV からスマホへの続きが解けない。そのうえ
  「終端で位置を消し、印を立てる」が 2 つの書き先に割れる

**作るのは再生位置と視聴済みの印の 2 つだけ。** 「いつ何を見たか」の履歴は作らない。
「続きから」にも「未視聴」にも要らず、置けば推薦や分析へ用途が広がる。

**2 つは寿命が違うので表を割る**（不変条件 9 / 12）。どちらも `recordings` の衛星表で、
書き手は api ロールである。`recordings` を書く watcher / reconciler ではないので
本体の列にしない（不変条件 13）。

| | 再生位置 | 視聴済みの印 |
|---|---|---|
| 主キー | `recording_id` | `recording_id` |
| 寿命 | 何度も上書きされ、見終えたら消える | 一度だけ立つ。取り消しは DELETE |
| 行の不在 | 続きが無い | 未視聴 |

見直している録画では両方の行が同時にある。そのため 1 つの状態列にもまとめない。
`recordings` の行は本番では DELETE されないので、衛星表の行を掃除する役は作らない。
掃除役を足すと 2 人目の書き手になる（不変条件 12）。

#### 再生位置の基準軸は原本の秒

**保存する位置の基準は、非カット版の録画先頭からの経過時間（ms）とする。**
プロファイルでは分けない。非カット版はどのプロファイルもこの軸を共有する。
原本 HLS はセッションの offset を足し戻してこの軸へ変換する。追っかけも同じ変換を
前提にするが、開始点を `-ss` ではなくバイト位置（`chaseStartByteOffset`）で決める別経路なので、
下の測定の対象外であり未測定である。カット版の切り出し（`internal/ffargs/cut.go`）は、
チャプターの原点を入力の最早 `start_time` とみなして切っている。

ただし、合成 fixture の測定では、この前提は非カット版の軸と 10.02ms ずれた。原本 TS の映像
`start_time` は 11.100700s、最早（音声）は 10.389978s で、映像は最早から 710.722ms 後だった。
一方、非カット MP4 の映像 `start_time` は 0.700700s（21 フレームちょうど）で、最早基準の
0.710722s より 10.02ms 前である。これが encoder のフレーム格子への丸めか filtergraph
（trim の前後）かは**推定・未検証**である。カット版は窓を半フレーム手前へずらしており、
10.02ms（半フレーム未満）がカット版の境界に効くかは未測定である。

ブラウザが報告する `requestVideoFrameCallback` の `mediaTime` は経路ごとに測る。
測定には `web/e2e/recording-playback-timeline.mjs` を使う。**期待値は非カット MP4 を
ffprobe して得た各目印フレームの PTS** である。チャプターの軸が非カット版の経過時間だからだ。
原本 HLS（offset 0 と offset 10 秒）と非カット MP4 をこの期待値と比べる。
参考値として、原本 TS の「目印 PTS - 入力全ストリームの最小 `start_time`」との差も
ログに出す（判定には使わない）。Chrome の hls.js 再生と WebKit の native HLS 再生を
測定対象とする。許容差は 29.97fps の半フレーム（16.68ms）。

合成 MPEG-2 TS は 30000/1001fps、先頭 PTS は非ゼロ、音声は映像より 710.722ms 先行する。
目印は 10 秒 offset の前後に置いた。表は（非カット MP4 基準 / 参考: 原本 PTS 基準）の差である。

| 経路 | HLS offset 0 | HLS offset 10 | 非カット MP4 |
| --- | ---: | ---: | ---: |
| Chrome + hls.js | +66.73ms / +56.71ms | +90.10ms / +80.08ms | 0.00ms / -10.02ms |
| WebKit native HLS | 0.00ms / -10.02ms | +23.37ms / +13.34ms | 0.00ms / -10.02ms |

非カット MP4 基準では、Chrome の原本 HLS が両 offset で、WebKit の offset 10 が許容差を超える。
WebKit の offset 0 と両ブラウザの非カット MP4 は範囲内である。E2E はこの差を NG として
報告するため、実行は exit 1 になる。原本 PTS 基準だと WebKit は範囲内に見えるが、
それは基準の取り方による結論で、チャプターの軸では崩れる。差は目印ごとに一定だった。

差の形は**推定・未検証**である。Chrome の +2 フレーム（66.73ms）は、HLS 映像の先頭 PTS が
1.4s に 0.066733s を足した値と一致する。libx264 の B フレームによる 2 フレームの遅延を
hls.js が引かず、Safari は引いているように見える。WebKit の offset 10 の +13.34ms
（原本 PTS 基準）は、`-ss 10` 後の原点からの端数 9.289278s を 33.367ms で割った 278.4 フレームの
0.4 フレーム分と一致する。エンコードでのフレーム格子への丸めがシーク位置ごとに位相を変えているなら、
差は定数補正では直らない。

- 未解決: 原本 HLS の時刻補正をどこに置くか
- 未解決: 実録画（GR/BS）での同一シーン比較は未測定

- **カット版の秒と原本の秒の変換はクライアントが行う。** 材料はいま再生しているファイルの
  凍結済み keep 区間（`media_asset_cuts.keep_ranges`）である。カット版を作り直しても、
  保存される原本の秒はずれない。無効化の規則も要らない
- 主キーに軸やプロファイルを入れる案は採らない。カット版は同じプロファイル名のまま
  作り直されて時間軸が変わる（上記「カット版」）。名前で分けると古い軸の秒が残り、
  非カット版どうしでも続きが割れる
- 復元する秒が CM（keep 外）に落ちたときは、次の keep 区間の先頭へ寄せる
- 区間による変換は、字幕の時刻の付け替えとして worker にもある。端の扱い（字幕は捨てる・
  クリップ、位置は寄せる）は違うが、区分線形の変換そのものは同じ導出である
- 未測定の残差: カット版の区間ごとの半フレーム窓 / ドロップで PTS が飛んだ録画での keep 区間と
  `currentTime` のずれ / 実録画の GR/BS での同一シーン比較

#### 視聴済みは放送イベントで束ねて読む

**印は押した録画の行 1 つに立てる。読むときは同じ放送イベント
`(network_id, service_id, program_start_at)` の全行を束ねる。** どれかに印があれば視聴済みとする。
「見た」は録画の行ではなく放送の内容についての事実である。2 拠点で同じ放送を録った場合や、
ごみ箱に入れてから録り直した場合に、行ごとに読むと片方だけ未視聴に残る。

- 束ねる母集団は削除済み・supersede 済みの行も含む全行とする。live な行に絞ると、
  見てからごみ箱へ入れた時点で、もう片方が未視聴に戻る
- 未視聴に戻す操作は、同じ放送イベントの全行の印を消す。押した行だけ消すと、
  束ねた読みでは視聴済みのまま残る
- 印を他の行へ複製しない。書き手が意図していない行を作ることになる
- **位置は束ねない。** 2 拠点の録画は録画開始の時刻が違うので、原本の軸がずれる。
  位置は行ごと、印は放送イベントごとという非対称は意図したものである

#### いつ視聴済みにするか

- 終端の 90% に達したら視聴済みにし、その行の位置を消す。閾値は Jellyfin / Plex の既定に
  倣った。判定はクライアントが `<video>.duration` で行う。api はファイルの実際の長さを知らない
- 90% を超えた後は位置を書かない。書くと見終えた録画が「続きから」に戻る
- **duration が伸びている間は判定しない。** 追っかけ中と、変換中の原本 HLS がこれに当たる。
  先端の 90% は「見終えた」を意味しない
- 手動の「視聴済みにする / 未視聴に戻す」も置く。他の手段で見た番組に印を付けるためである
- 同じ録画を 2 台で同時に見たときは、後から書いた方が勝つ。世帯スケールなのでガードしない
- **同じプレイヤーの書き込みは、前のものが完了するまで次を送らない。** 先に出した位置 PUT が
  後から出した視聴済み PUT を追い越すと、視聴済みが消した位置行を PUT が作り直し、見終えた録画が
  「続きから」に戻る。サーバー側でガードしないのは上の決定のためで、順序はクライアントが守る。
  pagehide の keepalive は待てないので、この列に載せずに即送る。未完了の書き込みがあれば
  追い越しうるが、窓は直前の 1 往復だけなので受け入れる

#### 移すもの・移さないもの

- 再生速度とその他の個人設定は localStorage に残す（端末ごとの好みで、事実ではない）
- localStorage にある既存の再生位置は移行しない。見ている途中の録画が一度だけ先頭に戻る
- catalog エクスポートには視聴済みの印を入れ、位置は入れない。印は取り戻せない事実だが、
  落ちても全件が未視聴に見えるだけで安全側に倒れる。そのため `schemaVersion` は上げない
  （分類ルールの配列を足したときと同じ扱い。[storage.md](../storage.md) §8）

## CM 検出のロゴ位置

`/cm-logos` は、録画局ごとに CM 検出器が探すロゴの位置を教える画面である。
番組表の局ロゴとは別の情報を扱う。局画面の共有 URL は
`/cm-logos/<networkId>/<serviceId>?recording=<id>` とし、録画詳細の古い
`?network=&service=&recording=` リンクは局画面へリダイレクトする。

- 一覧は上から「要対応」「検出待ち」「問題なし」の順に置き、「問題なし」は折りたたむ。行には横長の覚えたロゴ、局名・サイト、状態の一文、`直す →` だけを出し、ID は表示しない。色は要対応バッジだけに使う
- 局画面は、局名・サイト・状態の一文、コマ、コマ直下の時刻スライダー、右側（狭い画面では下）の操作欄、影響する録画、高度な操作の順に置く。録画欄は成功した録画も含め、録画詳細リンクと、原本があり CM 検出が有効な録画（失敗・検出済み）の再検出を出す。誤ったロゴで「成功」した録画の回復経路になる
- スライダーの分母は EPG の `durationMs`、初期位置は中央である。コマを取る録画は、局の一覧のうち原本のある録画から選ぶ。ディープリンクの録画を優先し、別の局のものや原本の無いものは捨てて `frameRecordingId` に落とす。ドラッグ中はコマを取り直さず、ポインタを離す・キー操作を確定したときだけ取り直す。古いシークタイル格子は使わない
- コマは `X-Coded-Width` / `X-Coded-Height` と `X-Sample-Aspect-Ratio` を使って表示する。枠は記録上の coded 座標で保存し、SAR による横倍率と縦倍率を別々に扱う
- 枠の外をドラッグすると描き、内側は動かし、四隅のハンドルはリサイズする。外側は暗く、枠は黒白の二重線にする。カーソルは外側が crosshair、内側が move、四隅が `nwse-resize` / `nesw-resize`、スライダーが pointer である。X/Y/幅/高さの数値入力は同じ枠へ双方向に反映する。入力中はテキストを下書きとして持ち、blur / Enter で映像内と最小サイズへクランプする（打鍵ごとにクランプすると、幅に 400 を打つ途中の 4 が下限へ戻って 800 になる）。ハンドルは見た目の要素自身が当たり判定で、座標の許容を別に持たない。表示枠の比は SAR から導き、ドラッグ結果は整数へ丸める
- 「枠に寄る」は押した時点の枠の中心を焦点に固定して拡大し（枠の現在位置から毎回導くと、ドラッグで枠がポインタから逃げる）、「全体」は全体表示へ戻す。固定の右上拡大は持たない
- 主ボタンは「ロゴを解析」である。枠と録画を送って候補解析を依頼し、採用するまで今のロゴはそのまま使う。解析は画面を離れても続く
- 編集面の下に候補の状態を全幅で置く（狭い側の列に押し込むと、原寸のロゴが横に潰れるか見切れる）。「解析中です」と数分程度の目安は、`running` の行があるときに加え、枠があり候補の行が無く学習が無い（または枠より古い）ときにも、原本のある録画があれば出す。原本の有無は API が返す `frameRecordingId > 0` で近似する（desired view とは `purged_at` の扱いが違う）。job は worker が拾うまで待つので `running` 行は遅れて現れ、メモリ上の「依頼した」state には頼らない。この間は候補の有無にかかわらず再取得を続ける。原本が無ければ解析は始まらないので、理由を一文で出して再取得しない。スピナーは置かない。`failed` は工程名から作った一文を出し、生ログは出さない。「枠を描き直して解析し直す」は枠で直る工程（`area` / `logo` / `match`）のときだけ添える
- `ready` は今のロゴと候補を市松模様の地に横へ並べる。候補の録画の `X-Sample-Aspect-Ratio` を両方に掛け、画像は縮ませず原寸（幅は画素数×SAR、高さは画素数）で描く。採用前のチェックボックスは既定でオンにし、検出済みの録画件数と原本が残る件数を表示する
- 採用は `POST .../candidate/adopt` に `redetect` を送る。オンなら原本が残る録画を再検出し、採用後は「検出待ち N 件。数分〜数十分かかります」と表示する。破棄は候補を消し、原本のある録画があれば同じ枠で解析し直す
- 「覚えたロゴを捨てる」は、枠がある局では、原本のある録画があれば枠から解析し直して新しい候補を作る。「枠を消して自動に戻す」は候補と採用待ちを取り消して自動の学習に戻す。どちらも高度な操作に置く

CM 検出に失敗した録画の詳細には、局と録画を指定した局画面へのリンクを出す。
原本が無い録画ではコマを取り寄せられないため、枠を教える面は表示しない。
保存済みの枠とコマの coded 解像度が違うときは枠を適用せず、その理由を表示する。
技術的な raw log は画面に出さず、工程名を利用者向けの一文へ変換する。
局画面の「影響する録画」も工程を見る。ロゴの採用待ちで止めた録画（`adopt`）は採用待ちの文を出し、再検出は出さない（採用するまで進まない）。
表示枠の座標変換と異なる横・縦倍率は単体テストで確認し、今のロゴと候補の描画寸法（画素数×SAR）・欄からの見切れ・解析待ちのポーリング・採用 body・
URL リダイレクトは
`web/e2e/cm-logo-area.mjs` で行う。

### チャプター（CM の目盛り・自動スキップ・修正）

`GET /api/recordings/{id}/chapters` が返す区間を、シークプレビューと同じシークバーに描く。
**返るのは CM とユーザーが印を付けた区間だけで、本編の区間は返らない** —— 区間の
隙間が本編である。目盛りの割合は `<video>.duration` を分母にする（DB が持つのは
EPG 上の番組長だけで、ファイルの実尺ではない）。

- **合成は Go の `internal/chapters/` 1 か所にある**（量子化・隙間の本編・CM 率 50%
  超の安全弁・所有の有無による層の選択）。TS 側は結果を描くだけである。プレイヤーの
  描画とカット版の encode が同じ関数を通る。TS に複製しない（シークタイルの固定値が
  Go と TS の 2 か所にあった轍を踏まない）
- **境界の整数 ms とフレームの表示区間を分ける。** フレーム k の映像は
  `[k×T, (k+1)×T)` 秒に表示される。一方、Go が保存する境界 ms は `k×T` を整数 ms に
  丸めた値である。丸めで `k×T` より手前になった ms をそのまま `currentTime` に渡すと、
  シーク位置がフレーム k−1 の表示区間に入り、境界カードで 1 つ前の映像が出る。
  `lib/chapters.ts` の `chapterBoundaryMsToSeekSeconds` は境界 ms からフレーム番号を戻し、
  そのフレームの中央へシークする。これは画面表示と再生位置の変換であり、保存値の量子化や
  比較ではない。Go の `MsToFrame` / `QuantizeMs` とサーバー保存形式は変えない。
  編集一覧、前 / 次チャプター、自動スキップの着地点、フィルムストリップの境界ボタン、
  ±調整、「境界から」の開始位置、「境界まで」の停止後は境界変換を通す（自動スキップは動画の長さで
  頭打ちにする）。シークバー、再生位置を動かすキー、フィルムストリップの帯（境界以外）のクリック、
  「前後 3 秒」と「境界まで」の開始位置は境界変換を通さない。そこは任意の再生位置を指す操作で、
  位置をフレーム中央へ寄せると利用者が指定した時刻をずらすためである。
- **再生位置から境界を作るときは、表示中フレームの `mediaTime` を使う。**

  一時停止した直後の `currentTime` は、表示中フレームの開始より手前にあることがある
  （合成 fixture の Chrome で -0.09〜-0.36 フレーム、WebKit で -0.41〜+0.14 フレーム）。
  そのため `floor(currentTime / T)` は 1 つ前のフレームを返しうる。
  編集モードの間だけ `requestVideoFrameCallback` で最後に表示されたフレームの `mediaTime` を持つ。
  `seeking` で捨てる。`displayedFrameBoundaryMs` が `round(mediaTime / T)` でフレーム番号を求める。
  取れないとき（通知がまだ来ていない、API が無いブラウザ）は `currentTime` の floor に
  戻す。原本 HLS では `mediaTime` が offset セッション内の時刻なので、入力 seek と同じ
  フレーム格子に合わせたセッション起点を足して原本の軸へ戻す。WebKit でシーク後に通知が来るか、
  Firefox、59.94fps 出力は未検証。
- この挙動は `web/e2e/recording-playback-timeline.mjs` で、非カット MP4 の全目印を
  編集カードから選び、表示フレームの画素を読む。押す前は境界の 0.5 秒手前に置き、目印が
  映っていないことも確かめる。目印のフレームで一時停止して「現在位置に合わせる」を押し、
  保存した PUT の ms が目印のフレームの境界であることも見る。再生時刻の判定をすべて
  終えた後、別の周回で行う。Chrome と WebKit の両方で動かす。
  編集モードの境界操作も、非カット MP4 と原本 HLS（offset 0 / 10）で見る。対象は、境界の選択
  （一時停止して目印のコマが映る）、±1 フレーム、「境界まで」（目印のコマで止まる）、「境界から」
  （開始が目印のフレーム内）、長押し、400×800 の帯の重なりである。
  WebKit の原本 HLS も、`currentTime` ではなく表示されたフレームで判定する。
- 未解決: WebKit のネイティブ HLS で、一時停止中に境界を選ぶか ±1 フレーム送ると、
  `currentTime` は選んだフレームの中央なのに前のフレームが映ったまま残る。
  製品を通さない素の `currentTime` 代入でも起き、同じ位置へもう一度 seek すると映る。
  測ったのは合成 fixture と Playwright WebKit だけで、実録画と Safari 実機は未測定である。
  手順と測定値は [`web/e2e/README.md`](../../web/e2e/README.md) にある。
- 実録画（GR / BS、Chrome / WebKit）8 ケースでも、整数 ms へのシークは 6 ケースで 1 つ前の
  フレームが出て、フレーム中央へのシークは 8 ケースで意図したフレームが出た。表示中フレームの
  `mediaTime` から境界を作る操作は実録画では未測定である。
- **自動スキップは `cut=true` の区間だけを飛ばす。** 飛ばすのは**通常の再生で
  区間の先頭に差し掛かったときだけ**で、手動のシークで区間の中に入ったときは
  飛ばさない（見たくてシークした人を追い出さない）。判定は「直前の観測位置が
  先頭より手前で、今回の観測位置が区間の中」で行う（`lib/chapters.ts` の
  `skipTarget`）。区間の終端が動画の終端を越えるときは終端で止める
- ON / OFF は `rokuban:playback-rate` と同じく端末ごとに localStorage へ持つ
  （キー `rokuban:chapter-skip`、既定は有効）
- **3 種類の境界再生中は自動スキップを止める。** `前後 3 秒` は境界の 3 秒前から
  `currentTime >= 境界 + 3 秒` まで、`境界まで` は 3 秒前から境界まで、`境界から` は境界から
  3 秒まで再生する。停止は実時間でなく再生位置で判定し、再生速度に追従させる。`境界まで` は
  `timeupdate` が粗いため、停止後に境界変換でシークし直す。実時間のタイマーは再生が進まない場合の
  保険にとどめる（2 倍速の判定は `web/e2e/chapters.mjs` ⑤ と ⑤-b）。
- **直前の観測位置は `seeking` で更新する。** シークの処理順は seeking → timeupdate → seeked である。
  `seeked` で更新すると、再生中のシークで最初の `timeupdate` がシーク前の位置を直前位置にしてしまう。
  すると区間の中へシークした人を追い出す。判定は `web/e2e/chapters.mjs` ③ の再生したままのシークにある
- 編集 UI は**cut でない encoded がある、または live.enabled が有効で原本 HLS を
  再生できる**ときに出す。原本 HLS の編集では原本 TS から直接作るフィルムストリップと、
  原本の ms 軸に戻した再生位置を使う。**カット版を再生しているときは編集できない** ——
  cut 区間を取り除いた別の時間軸で、原本の ms で置かれた境界をその動画に当てられない
- cut だけで凍結した録画の後から live.enabled を無効にすると、原本 HLS が使えず
  「チャプターの確認待ち」から進まない。`until_encoded` なら原本は残る。live.enabled を
  有効に戻すか、`POST /api/recordings/{id}/encode-profiles` で cut でないプロファイルを
  追加すると回復できる
- **編集 UI は検出中（`detectionPending`）には出さない。** 検出中の空の層は「CM 無し」ではなく「まだ分からない」である。それを基にした下書きは、検出 commit 後に「CM 無し」で引き取られてしまう。GET が返す `version` を PUT（`/chapter-edits`）へそのまま返し、サーバーが行ロックの後で比べて違えば 409 にする
- **サーバーの値（または版）が変わったとき、下書きがあれば黙って捨てない。** 「サーバー側の内容が変わりました」を出して保存を止め、破棄して最新の内容から編集し直させる。下書きが無い（基と同じ）か、自分の保存が成功した直後のときだけ追随する。サーバーは境界をフレーム境界へ丸めて保存するので、保存後の値は下書きと一致しない。クライアントで丸めを複製せず、成功後に届く次の値を無条件で採用する
- 編集の単位は**タイムライン全体の置き換え** 1 つだけである。境界ごとの差分を
  送らない理由は、境界の修正が「その時点の検出結果に対する差分」であり、再検出で
  境界が動くと意味を失うためである。境界は前後の区間で共有されうるので、同じ値の
  境界はまとめて 1 行に出す
- ラベルが空の区間の `cut` は外せない（本編と区別が付かなくなる。サーバー側の
  CHECK と同じ規則）。**表現できない状態を UI で作らせない**
- **区間の位置・スキップのタイミング・前後再生は jsdom では測れない**（シークバーの実寸と
  実再生が要る）。判定は `web/e2e/chapters.mjs` にある
- 「自動検出（未確認）/ 確認済み」は所有の行の有無から導出した `source` を出す。
  「自動に戻す」は所有の行を消すだけで、取り込み直しの操作は無い

### カット版（`encodedAssets[].cut`）

`cut: true` のプロファイルで作った派生物は、**原本の時間軸から cut 区間を取り除いた別の動画**である。シーク位置・クリック・時刻表示はカット版の時間軸を使う:

- **シークプレビューは出す。** タイルは原本の時間軸で作られている。ホバー位置から格子を選ぶときだけ `cutMsToOriginalMs(cutSeconds * 1000, selectedAsset.keepRanges)` で原本時刻へ写す。使う `keepRanges` は再生中の動画ファイルに固定された値で、現在のチャプターから作り直さない。空ならタイルを取りに行かない。タイルが 404 のときはプレビューを出さず、再生面はそのままにする
- プレビューの時刻ラベルとクリック先はカット版の時間軸を使う。原本時刻へ写すのはタイル格子の選択だけである
- **チャプターの目盛り・一覧・自動スキップを出さない**（境界は原本の ms で、その動画には当てられない）
- 編集 UI を出さない（上の「チャプター」節と同じ理由）

**「編集前の内容です」は `encodedAssets[].cutStale`**（凍結した keep 区間が現在の量子化済みタイムラインと一致しない）。**自動では作り直さない** —— 作り直すとユーザーが確認していない区間が黙って本編から消える。バナーと「作り直す」ボタンを出し、押すと `POST /api/recordings/{id}/encoded/{profile}/reencode` でジョブを積む。

置き換えは新しい世代のパスへ書くが、**URL は `?profile=` のままで世代を含めない**（資源同定は変えない）。そのため置き換えた瞬間に視聴中のクライアントの再生は壊れる（受け入れ済み。再読み込みで直る）。

### 操作点にサイズを常置する（値札）

**資源を消費する操作には実行前に値札。値札は事実（実測サイズ）のみ**（転送時間の
見積などは書かない）。サイズの常置先は、設定メニューの「画質」の下の階層の各選択肢
（`menuitemradio`）と VLC リンクである。選択肢はプロファイル名の右にサイズを置き、値は
`formatBytes`（`lib/format.ts`）で作る（`components/recording-playback-controls.tsx`）。
画質が 1 つでも「画質」の行と選択肢は常に出すので、切り替える前にサイズを見られる。

**サイズが取れない資産は隠すのではなくサイズだけ省く**。`EncodedAsset.sizeBytes`
（openapi.yaml）は省略可能な形にしてある --- 選択肢（プロファイル名）自体は
分類の失敗（ここではサイズの欠落）を理由に隠さない。ドロップ統計の「分類できな
かった PID は種別を空にして PID 数値だけ出す」（下記「ドロップ統計」節）と同じ
判断。`media_assets.size_bytes` は `NOT NULL` 列制約なので、active な encoded 行が
ある限り実際には常にサイズが付く。同テーブルの CHECK 制約は `kind` / `profile` /
`state` にしか掛かっておらず、`size_bytes` には無い。それでも型としては
省略可能にして、この表示規律をテストで固定している（`recording-player.test.tsx`）。

### 一覧の行は詳細へのリンクにする

録画一覧はインライン展開も常時の「再生」列も持たず、行本体を
`/recordings/$id` へのリンクにする。再生可能な行だけ右端に塗りのボタンを置くと
行の形が揃わず、単体ページができた後も一覧が同じ `RecordingDetail` を二重に
抱えることになる。視聴・削除・エンコードはすべて上記「録画単体の着地先」に寄せる。

ごみ箱の行と `encodedAssets` が空の行も詳細へリンクする。前者は詳細側が
`deletedAt` を見てプレイヤーを出さず、後者は原本のダウンロード / VLC リンクを
詳細側が引き受ける。再生可否は一覧から詳細へ行けるかどうかの条件にしない。

一覧はリスト表示とカード表示を切り替えられる（`RecordingsPage` ヘッダーの
トグル）。出す情報はどちらも同じで並べ方だけが変わる（`RecordingRow` の
`view` 分岐）。表示形式の置き場所（localStorage か URL か）の判断は
[design.md](design.md) §個人化。

一覧から `.play()` 相当を呼ばない判断は、詳細へ寄せても変わらない。詳細は自前の
操作バーを表示し、利用者が再生ボタンを押すか映像をクリックするまで `.play()` を呼ばない。
コストのかかる本編転送を一覧の行選択だけで始めないという値札の方針を保つ。

ネイティブ controls を外した `<video>` は `tabIndex={0}` を明示し、映像自身も Tab stop にする。
`web/e2e/design.mjs` は録画一覧の行リンクを Enter で開き、詳細ページで `<video>` に
Tab 到達できることを実ブラウザで機械判定する。

### キー操作

| キー | 動作 | ファイル再生 | 原本 HLS | 追っかけ | ライブ |
|---|---|---|---|---|---|
| Space | 再生 / 一時停止 | ○ | ○ | ○ | ○ |
| ← / → | 10 秒戻る / 進む | ○ | ○ | ○ | × |
| J / L | 30 秒戻る / 進む | ○ | ○ | ○ | × |
| M | ミュート切り替え | ○ | ○ | ○ | ○ |
| F | フルスクリーン | ○ | ○ | ○ | ○ |
| 0〜9 | 尺の 0〜90% へ移動 | ○ | ○ | × | × |

原本 HLS の変換中 EVENT playlist は WebKit で `video.duration = Infinity` を返すため、0〜9 はメディア要素の尺ではなく既知の録画尺から位置を求める。`web/e2e/recording-original-vod.mjs` ⑫-a はこの状態で offset が張り直されることを測る。

上記のキー操作はページ単位の追加ショートカットである。ボタン・入力欄・選択欄・リンク・
編集可能領域・`[role="slider"]` にフォーカスがあるときはグローバル処理を無視し、`<video>` は除外しない。
シークバー自身が ← / → を処理して 10 秒ずつ動かすため、ページ側の 10 秒シークと二重に
動かない。映像にフォーカスがあるときも、対応する再生元ではページのショートカットを使える。

## 出自ラベルは行のメタデータ列に置く

行のメタデータ列（site バッジの次から serviceName・日時と続く並び）の先頭に、source（ルール / 手動 / 帰属なし）のラベルを常に出す。RecordingVerdictBadge / IngestBadge / EncodeStatusBadges / DropBadges はこの録画の状態やパイプラインがどこで止まっているかを説明するバッジ群である。出自は別の軸なのでその間に挟まない。

## 取り込み中であることを画面に出す

`status = finished` は mirakc の録画完了であって取り込み完了ではない。原本が
コミットされるまで再生も事後エンコードもできないのに、それを表すものが
`sizeBytes` の省略しか無かった。`Recording.ingest`（サーバーが DB 行から毎回導出する。
[recording/ingest.md](../recording/ingest.md) §5.6）を 2 段に分けて出す。

- **行のバッジ**（`IngestBadge`。一覧の行と単体ページのヘッダー）: 「取り込み待ち」/
  「取り込み中 42%」/ 分母が無ければ「取り込み中 1.2 GB」。進捗が 60 秒以上更新されて
  いなければ「（停滞）」を添える
  - **録画中は割合を出さない。** 追従 ingest は録画開始から走るので、録画中の
    分母は「mirakc がその時点で観測しているサイズ」であり最終サイズではない。
    `writtenBytes` がそれを追い越すことがあり、割合にすると「録画全体の 100% を
    取り込んだ」と読める嘘になる（実機で観測した）。録画中はバイト数だけを出し、
    % は分母が確定する録画終了後から出す
- **録画詳細の「取り込み」欄**（`RecordingDetail` の `<dl>`）: 分母が取れていれば
  「転送中 1.2 GB / 3.4 GB（35%）」まで出す

**表示しないケースを決めておく**（言うことが無いときに行を並べない）:

- 正常に取り込めて原本もある録画（`committed` かつ `sizeBytes` あり）: 何も出さない
- `ingest` そのものが無い（API が古い）: 推測で埋めない
- **ingest ジョブが来ない録画（`failed` / `canceled`）**: `state` が `unknown` で
  返るので何も出ない。ここで「取り込み待ち」を出すと、**来ない未来を UI が断定する**
  ことになる。`sizeBytes` について直したはずの誤りを `pending` について作り直す
  形だ。`pending` の根拠を `record_sync` 行の**存在**に取るとこれが起きる。根拠は
  **watcher が ingest を投入する条件と同じ述語**（`record_sync.status` が
  `recording` または `finished`）に揃える。**状態の名前が「これから起きる」を含むなら、
  起きる根拠を述語として書けるか確かめる**
  - **リトライで消えなかった進捗行が残っていても `unknown` になる。** worker は
    cancel / fail を観測したとき進捗行を消してからジョブを終端するが、その DELETE は
    失敗してもログだけで続行する。server 側の導出が `failed` / `canceled` の観測を
    `transferring` より優先するので、二度と取り込まれない録画が
    「取り込み中（停滞）」を名乗り続けることはない

**`status = 'recording'` も取り込みを出す。** watcher は録画開始を観測した時点で
ingest を投入し、worker が録画に追従する（[recording/ingest.md](../recording/ingest.md)
§5.1）。したがって録画中の行にも「取り込み待ち」（進捗行がまだ無い開始直後の数秒）と
「取り込み中」が出る。以前は「録画中に取り込みの数字は動かない」前提でここを伏せて
いたが、追従では数字が動く。**停滞を出さないことの根拠も変わった** --- 追い付いている
状態は正常なので worker が `observed_at` を進める（§5.6）

**色は使わない**（`bg-muted` のまま）。停滞も含めて状況の説明であって、タリー
（いま電波に乗っている）でも destructive（取り返しがつかない）でもない
（[design.md](design.md)「色は信号のみ」）。停滞は文言で言う。

**「原本は削除済み」と言えるのは `committed` かつ `sizeBytes` 無しのときだけ**。
`sizeBytes` の省略は「取り込んだ後に消した」と「まだ取り込めていない」の両方を
含む。そのためこれだけを見ると、権限不足で ingest がリトライ中の録画に
「削除済み」と読める表示が出る。
サーバーが「`kind='original'` の行が `state` を問わず存在するか」を見て `committed` を
返すので、UI 側はその区別をそのまま使える。

**進捗は REST の再取得で収束させる**（SSE はヒント。不変条件 5）。ただし
**5 秒間隔を張るのは「進捗の数字がいま動いている」間だけ**にする
（`lib/ingest.ts` の `hasLiveIngestProgress`）。一覧は無限リストなので、
常時ポーリングすると積んだページ全部を取り直すことになる。

短い周期を張らないもの（`state` としては未完了でも）と、その代わりに何が
収束させるか:

- **`pending`**: いつ始まるかはこちらから分からない。**失敗し続けている ingest も
  ここに落ちる** --- 権限不足で `MkdirAll` に失敗する場合、進捗行が書かれる前に
  落ちるので、River が再試行し続ける間ずっと `pending` のまま（実環境で起きた
  壊れ方）
- **停滞した `transferring`**: River のバックオフ待ちや、discard 後に
  record_sweep（5 分周期）が再投入するのを待っている状態。分オーダーでしか
  動かないものを 5 秒で叩かない。**再開すれば `observedAt` が新しくなって自動で
  短い周期に戻る**（自己回復する）

**`status = 'recording'` は張る側。** watcher が録画開始時点で ingest を投入し
worker が追従するので、進捗が新しい間は 5 秒周期の対象になる。追い付いた状態
（`written_bytes` が止まって見える）は上記の「停滞した `transferring`」と同じ
扱いで、`observed_at` が健全なポーリングで進む限り短い周期を保つ。**この周期は
録画時間の間ずっと続く**（無限リストの積んだページを毎回取り直す）。

いずれも [shell.md](shell.md) の 60 秒 invalidate（`lib/events.ts` の
`operationalRefreshIntervalMs`）が拾うので、放置ではなく「周期を落とす」だけになる。
**「終わっている画面はポーリングしない」を保つには、未完了の状態すべてを短い周期の
対象にしてはならない** --- `record_sync` 行が消えない以上、「未完了」は恒久的に残り
うる。そのため失敗録画が 1 件でも読み込み済みページにあれば、ポーリングが恒久化する。

**この 5 秒周期は録画時間の間ずっと続くが、実測したコストは許容範囲なので周期は
変えない。** 録画中の一覧を開きっぱなしにしたときに相当する負荷（5 秒ごとに一覧を
1 回叩く）を実環境で測った値:

- api ロールの CPU は 1 ポーリングあたり 3.3 / 4.6 / 4.2 ms だった。この値は録画が
  無いときの 3.8 ms と同じで、同じ DB へ ingest が書き込む競合は測れなかった
- 一覧のレイテンシは p50 で 40〜52 ms（keep-alive・ポートフォワード経由）。
  録画が無いときの 39.8 ms と差が無い
- 1 時間の録画に換算すると api の CPU は約 2.9 秒（1 コアの 0.08%）で、
  ブラウザへ落とすバイトは約 12 MB になる
- 5 秒という間隔そのものは、worker が進捗を書き直す最短間隔（2 秒）より粗い。
  間隔を決めているのは画面の数字が動く速さであって、サーバーの負荷ではない

**積んだページ数には線形に効く。ページの深さには効かない。** 同じ一覧クエリを
録画行数 50 / 400 / 4,000 / 40,000 行で計測した。中央値は順に 1.7 / 2.3 / 2.3 /
2.8 ms である。page 2〜8 もほぼ同じ値だった。キーセットなので `OFFSET` の
ような後戻りが無い。`useInfiniteQuery` の定期再取得はページを**逐次**引く
（`infiniteQueryBehavior` の `await` ループ）。同時に使う DB 接続は 1 本である。

**「一覧を開いたまま放置」はこの周期に当たらない。** `refetchIntervalInBackground`
は既定 false である。`@tanstack/query-core` 5.102.8 の `queryObserver` は
`focusManager.isFocused()` が偽なら発火しない。この既定を固定するテストはこの
リポジトリに無い。依存の既定に頼っている箇所である。

## エンコードの待ち・実行中・失敗を画面に出す

`Recording.encodeProfiles`（desired）と `Recording.encodedAssets`（observed、
再生可能なもの）の差だけでは「まだ来ていない」としか言えない。いま走っているのか
失敗して再試行待ちなのかは区別できなかった。`Recording.encodeStatus`
（openapi.yaml）をバッジで出す（`EncodeStatusBadges`。一覧の行と単体ページの
ヘッダー、`IngestBadge` の隣）。desired のうち observed にまだ現れていない
プロファイルだけを、`queued` / `running` / `failed` のいずれかで列挙する。

- **`running` は進捗イベントを受け取るまで `%` を出さない**。worker が実入力を
  ffprobe して得た duration を分母にし、ffmpeg の `-progress pipe:1` の `out_time`
  から割合を作る。duration を取得できない場合や SSE を取りこぼした場合は
  架空の割合で埋めず「エンコード中」のままにする
- **プロファイル未設定・全プロファイル完了済みの録画では `encodeStatus` が
  省略される**。そのため `EncodeStatusBadges` は何も描かない --- 機能しないキュー
  画面や空の進捗バーを出さない判断は、サーバー側のこの省略で表現されて
  いる。フロントはそれをそのまま描くだけでよい
- **`failed` だけ destructive**（`bg-destructive/10` + `text-destructive`。
  `DropBadges` と同じ判断: 実害があるので色で目立たせる）。`queued` /
  `running` は `IngestBadge` と同じ `bg-muted`（状況の説明であって信号ではない。
  [design.md](design.md)「色は信号のみ」）
- **バッジにはプロファイル名を前置する**（`h264: エンコード失敗`）。事後追加で
  複数プロファイルを依頼した録画では「どのプロファイルが失敗したか」が言えないと
  運用判断に使えない（ドロップ統計の種別列と同じ判断）
- **`queued` は「来る根拠」があるものしか出ない**（サーバー側の導出。ごみ箱の
  録画とプロファイル自体が丸ごと省略されるので、フロントは何もフィルタしない）。
  `failed` は「二度と来ない」の断定でもない --- River の既定リトライと、録画単位の
  恒久失敗（入力ファイルの破損など）に対する `EncodeReconcileWorker` の 15 分ごとの
  再投入のたびに `running` へ戻る（`queued` へは戻らない --- 試行行は成功するまで
  消えないので `queued` は初回試行の前だけ）。判断の詳細は
  [schema/recordings.md](../schema/recordings.md) の `recording_encode_attempts`
  節
- ホームに出す場合は失敗録画と同じ「異常」の置き場に合わせる想定だが、本機能
  自体はホームへの統合を含まない --- 一覧・単体ページで沈黙と区別できれば足りるため
- **完了・失敗の真実は引き続き REST の `encodeStatus` / `encodedAssets`。**
  `encode-progress` SSE は接続中だけ届く揮発テレメトリで、`running` の文言に割合を
  重ねるためだけに使う。durable 状態が `running` でなくなったら最後の値を破棄し、
  `progress=end` や 100% だけで完了を断定しない
- **進捗はテーブルへ保存しない**。再起動後に不要な秒単位の値で WAL・dead tuple・
  vacuum 対象を増やさないためである。worker → PostgreSQL NOTIFY → notifier の
  EventHub → SSE という best-effort 経路で、最大 1 回/秒だけ運ぶ。画面を途中から開いた場合は REST
  由来の `running` を先に出し、次のイベントから割合を表示する
- `queued` / `running` / `failed` の収束は既存の
  `operationalRefreshIntervalMs`（`/api/recordings` を再取得する 60 秒周期。
  `web/src/lib/events.ts`）にも乗る。背面タブでは定期取得を投げず、前面へ戻ったときは
  `refetchOnWindowFocus` が拾う。進捗イベントを取りこぼしても durable 状態の完了・
  失敗判定はこの再取得で正しく収束する

### 待機列の全体像は録画一覧に置く

専用ページは作らず、録画一覧のヘッダー内にある管理情報行へ「待機中 N 件 /
実行中 N 件」を置く。通常時はストレージ残高の要約と同じ行に収め、録画一覧へ
到達した時点で容量とエンコード待機列の全体像を同時に確認できるようにする。
単一世帯では件数を常時監視する頻度が低く、既存の録画行へ絞り込めれば全体像と
個別の状態を同じ画面で確認できるためである。見る頻度やジョブ数が増え、履歴や
所要時間の予測が必要になった時点で専用ページを検討する。

件数は `GET /api/encode-queue` が River の active な encode ジョブを数える。
待機中は `available` / `pending` / `scheduled` / `retryable`、実行中は `running`。
単位は録画数ではなく録画 × プロファイルなので、1 本に 2 プロファイルあれば 2 件になる。
集計はごみ箱の録画に残る active ジョブも含む。ボタンは現在のライブラリタブを
絞り込むため、複数プロファイルやごみ箱のジョブがあれば件数と表示行数は一致しない。
件数を押すと `GET /api/recordings?encodeState=queued|running` で該当録画へ絞り込む。

この件数に `encode-progress` SSE は使わない。SSE は接続中の ffmpeg 進捗率を
録画行と録画詳細のバッジへ重ねるためだけの揮発テレメトリで、待機列の真実ではない。
ホームにも同じ件数を複製しない。録画一覧が全体像の置き場であり、0 件でも
「待機中 0 件 / 実行中 0 件」と確認できる。

## 録画が見られるかを結論で示す

録画一覧の行と録画詳細の見出しでは、「この録画を見られるか」の結論を
`recordingVerdict` で決める。再生元は録画詳細と同じ
`selectRecordingPlaybackSource` で選び、状態の絞り込みは DB の `status` を
そのまま使う。

結論の優先順は次の通り。

1. `status = recording` は「録画中」。タリーレッドの塗りで示す。
2. `status = failed` は「録画失敗」。destructive で示す。
3. 再生元があれば視聴可能で、結論バッジを出さない。原本だけの場合はライブ機能が
   有効なときに視聴可能となる。
4. `status = finished` で再生元がなく、取り込みが待ちまたは転送中、あるいは
   エンコードが待ちまたは実行中なら「準備中」。停滞した転送も準備中に含む。
5. `status = finished` で再生元も進行中の処理もなければ「再生不可」。キャンセル
   された録画も再生元がないため「再生不可」とする。

ライブ機能の capability が `pending` または `unknown` の間、原本だけの録画は
再生できないと断定しない。能力 API の読み込み中や一時的な失敗で「再生不可」が
一覧全体に現れるのを防ぐ。この未確定の判定は「準備中」より先に行うので、エンコード中でも
結論を出さない。能力が `enabled` なら視聴可能、`disabled` ならエンコード中は準備中、
それ以外は再生不可と判定する。

「完了」を無印にするのは、録画処理が完了した事実だけでは視聴可能か分からないため。
見られる録画は結論を表示せず、見られない理由が準備中ならその状態を出す。
結論の後ろには取り込み・エンコード・ドロップの内訳バッジを並べ、判断の根拠を示す。
ごみ箱の行には結論を出さない。削除日時がその行で確認すべき状態である。

行の語に「要対応」は使わない。視聴可能でもエンコードに失敗した録画はあり、
「要対応」だけでは視聴可否を隠してしまう。必要な対処はエンコード失敗やドロップの
内訳バッジを destructive で示す。

## ドロップ統計はバッジ + PID 表

録画一覧にドロップ / エラー / スクランブルを色付きバッジで出す。**0 のものは出さない**ので
正常な録画ではバッジが 1 つも出ない。録画行では行長に制約があるためドロップの
バッジをメタデータ列の末尾に置き、詳細では壊れた信号を連ねて読めるよう状態・
取り込み・エンコードの直後に置く。PID 別内訳は詳細ページだけが持ち、狭幅で 7 列が
収まらないときは表の容器だけを横スクロールさせる（ページ本体は横スクロールさせない）。

PID 表には**種別**列を置く（映像 / 音声 / PAT 等）。PID 数値だけの統計では
「映像が壊れたのか EIT が数回落ちただけか」を区別できず運用判断に使えないため
（[recording.md](../recording.md) §1「例外の境界」）。分類できなかった PID は
種別を空にして PID 数値だけ出す — 分類の失敗で統計そのものを隠さない。

ドロップ位置は「録画開始からの経過」と原本内の byte offset で表示する。PCR を
観測できなかった、または PCR の逆行 / PCR を運ぶパケット自身の discontinuity で
時計を無効にした位置は時刻不明とし、位置そのものは隠さない。位置は PID ごとに
最大 100 件なので、保存件数が真の `drops` より少ないときは「N 件中 M 件を表示」
と出す。

**ただし保存が 0 件なら「N 件中 0 件」とは出さない**。ドロップ位置を採る前に
ingest した録画は、`drops > 0` でも位置を 1 件も持たない。同じ文言にすると、
上限で切り詰めたのか元から採っていないのかが読者に区別できない。位置が 0 件
かつ `drops > 0` は「未採取」、`drops` も 0 なら「異常なし」として出し分ける。

## 録画検索は `/recordings` に同居する

EPGStation にある「録画済みの検索」に対応する機能だが、`/search`（EPG 検索。
[search.md](search.md)）とは**別ルートにしない**。録画検索は録画一覧そのものの
絞り込みである。`/search` を
独立ルートにした理由（「番組表は EPG を時間軸で眺める画面、検索は ruler と同じ条件
コンパイラを叩く別の問いの画面」）は、録画には当てはまらない。録画一覧に検索専用の
別画面を作ると、絞り込み結果と一覧が別画面になる。その結果、「絞り込んだ録画を
そのまま操作（削除・復元・エンコード追加）する」という主用途が 2 画面に分裂する。

**`/search` と条件モデルを共有しない**。`ProgramSearchRequest`（`internal/rulequery`
を通る EPG 検索・ルール条件）と `GET /api/recordings` の絞り込みは別のクエリである。
フィールドの意味も重ならない。録画検索の `status` / `source` は録画の観測・出自で、
`/search` にはそもそも無い次元である。
あちらの条件をこちらに持ってくる導線（相互流用）も
作らない --- 両者は別の問いに答えている。

### 条件は URL に持つ。`lib/recording-search.ts` に純関数として集約する

`RecordingsPageSearch`（型）・`parseRecordingsSearch`（`validateSearch`）・
`buildListRecordingsParams`（→ API クエリ）はすべてここに置く。
`describeRecordingsFilters`（→ 適用中の条件チップ）・`clearRecordingsFilters`
も同様である。
`lib/program-search.ts`（`/search` の下書き）とは意図的に分離している ---
条件モデルを共有しないので、変換ロジックを共有する理由も無い。

- **チャンネルは `Service.id` で、site は `?site=` で URL と API に載せる。**
  `serviceId` は network をまたいで一意でないが、合成 id なら BS 101 と CS 101 を
  独立に選択・解除できる。**site を identity に混ぜない** --- 混ぜると
  「高松の録画を全部」がチャンネルの列挙でしか表せず、`service` だけが
  他の軸と違う意味論（3 つ組の選言）になる。軸内は OR、軸間は AND
- **ルールは絞り込みパネルの「ルール」節から選べる。** 候補はルール一覧の返す順で
  並べ、選択した `ruleId` を URL と `GET /api/recordings` に渡す。`rules.name` は
  一意ではないので、同名の候補には `#<id>` を名前に添えて押し分ける。名前が
  重複していない候補には補助ラベルを付けない。適用中のチップは同じ一覧から
  ルール名を解決し `ルール: <名前>` と表示する（他のチップと同じく軸を
  前置する）。一覧で解決できないとき（削除済みルール。`recordings.rule_id` は
  `ON DELETE SET NULL` だが `?ruleId=N` の URL 自体は残る）は `ルール #N` と表示する
  --- select 側も同じ `ruleId` をフォールバック option として足し、一覧に無い値で
  先頭（「問わない」）へ落ちないようにする。**節自体はルールが 1 件以上あるか
  `ruleId` が決まっているときだけ出す**（サイト節と同じ「機能しないコントロール
  は置かない」規律。新規インストールでルールが 0 件なら節ごと出さない）。
  `ruleId` が決まっているとき、0 件になる「手動」「帰属なし」は選べないように
  する（`source='rule'` は矛盾しないので対象外）。どのルールかが分かれば出自を
  さらに問う必要がなく、常に 0 件になる組み合わせを選べるまま残すより、条件を
  設定したのに結果が 0 件になる理由を探させない方が明確だからである。**この
  組み合わせは URL のパース時点（`parseRecordingsSearch`）でも落とす** ---
  パネル操作の経路（`updateRuleFilter`）を塞ぐだけでは、URL を直接編集した
  リンクや古い共有リンクが `ruleId` と `source=manual` を独立に運べてしまい、
  種別チップが active のまま disabled になる（表現不可能になっていない）。
- **サイト絞り込みの選択肢は、レジストリと現在の `?site=` 絞り込みの和集合から作る。**
  レジストリから消えた site が絞り込みに残っていても見えて解除できるようにするためで、
  `/search` のサイトチップと同じ判定規律に揃える。**節自体は選択肢が 2 件以上のときだけ
  出す** --- 単一サイト構成で "default" だけの節が常に表示されるのを避ける。
- **録画行と詳細の site は、サイトレジストリと録画が持つ site の和集合が 2 件以上のときに
  表示する。** レジストリから消えた site の録画でも拠点を識別できるようにするためで
  ある。録画一覧では無限スクロールで別 site の行を後から読み込んだ場合、既存行にも
  site が表示される。
- **チャンネル種別（`channelType`）・`qTarget` は UI に出さない**。チャンネルは
  個々のサービスを選べる `<ChannelPicker>`（`Service.id`）の方が細かく絞れる。
  種別だけの選択肢を並列に置く理由が無い。`qTarget` も UI 案に
  無い次元で、出しても検証できないコントロールを増やすだけ（「機能しない
  コントロールは置かない」の逆）。パラメータ自体は `ListRecordingsParams` に
  残るので、共有 URL に手で `qTarget=title` を足す使い方は塞がない
- **キーワードはチップにしない。** 検索欄自体が値を表示しているので、消すのは
  入力欄の編集で足りる。配列条件（ジャンル・チャンネル）は値ごとに 1 チップ
  （個別に外せる）、スカラー条件（状態・種別・期間・ルール）は次元ごとに
  1 チップにする。期間のチップは md 未満でだけ出す（次節）

### ツールバーと期間

ツールバーは `[検索][期間][絞り込み][並び順]` の 1 行にする。
期間は録画を探す主な軸なので、絞り込みパネルの中に置かず独立した操作にする。
md 以上の 3 つは、今の選択をボタンに出す pop-up button（HIG）にする。
期間のボタンは「2026 夏」「今週」、並び順は「新しい順」を出す。
並び順は透明に重ねたネイティブの `<select>` が操作を受け、見た目だけを期間・絞り込みと揃える。

- **区切りは日本時間で明示して計算する**（`lib/recording-period.ts`）。
  クールの境目は放送の暦で決まり、ブラウザのタイムゾーンでは変わらない。
  クールは 1/4/7/10 月 1 日 0:00 JST から次の期の始まりまで。
  URL と API の意味（`from` 以上・`to` 未満）は変えない
- **日付の終了日はその日を含む。** 6/30 を入れると `to` は 7/1 0:00 JST になる。
  「この時刻未満」を入力させると、6/30 まで含めたいときに 7/1 と打たせることになる
- **期間ボタンとチップは同じ `periodLabel` で表示する。** 1 クールちょうどならその名前、
  上段の選択肢と一致すればその名前、それ以外は「8/10〜8/16」（終わりは含む最終日）。
  2 つの関数を持つと片方だけが直る。今年でない端には年を、0:00 JST でない端
  （古い共有 URL）には時刻を添え、表示から範囲を読み違えさせない
- **期間のチップは md 未満でだけ出す。** md 以上はボタンが中身を表示しているので二重になる
- **上段とクールは押すと閉じ、日付は閉じない。** 上段とクールは 1 回の選択で範囲が決まる。
  日付は開始と終了の 2 欄を続けて入れるので、1 欄目で閉じると開き直させることになる
- **週は月曜に始まる**（ISO 8601 / JIS X 0301）。日曜始まりにすると、土曜と日曜の深夜帯が
  別の週に割れる
- **今週・今月は終わりを開く**（`to` なし）。放送中・これからの録画も入り続ける
- **まだ始まっていない期は押せない。** 録画が 1 件も無いことが確定している

**検索・ルールの期間（`condition-fields.tsx`）とは部品も変換も共有しない。**
あちらは未来の番組の条件で、ルールでは `periodStartAt` / `periodEndAt` として保存される。
「終了日を含む」をそちらへ波及させると、既存ルールの解釈が変わる。

**md 未満は検索欄と枠なしのアイコンボタン 3 つ（44×44px）を 1 行に並べる。**
並び順まで文字で出すと 360〜430px で 2 行に折り返し、録画への到達が 1 行ぶん遠くなる。
条件がかかっているボタンには右上に点を付ける。
並び順は既定（`options[0]`）から外れているときに同じ点を付ける。
アイコンからは今の並びが読めないが、「既定と違う」が分かれば押して確かめられる。
期間・絞り込みのような別の印を並び順だけに作らない。

**md 未満では期間と絞り込みを下から出るシートで開く**（HIG「狭い画面ではポップオーバーを
避け、シートで出す」）。上部につまみ、中央に見出し、右に「完了」を置く。
高さは 85dvh まで、中身はシート内でスクロールさせる。md 以上は従来のポップオーバー。
シートとポップオーバーの切り替えは `components/toolbar-panel.tsx` の `ToolbarPanel` に
1 つにした。呼び出し元の期間と絞り込みは、どちらも「ツールバーのパネルを狭い幅でどう出すか」で
変わるからである。録画詳細の再生設定・チャプター一覧のシート（`popoverClass`）とは共有しない。
あちらは動画に重なるメニューで、プレイヤーの都合で変わる。
角丸・セーフエリア・つまみの見た目だけを揃える。
つまみは見た目だけで、引き下げて閉じる操作は持たない（再生設定のシートと同じ）。

### シリーズ一覧も同じ条件を使う

`/series` は録画一覧と同じ条件・同じ絞り込み UI（`RecordingFilters`）を使う。
条件の意味が同じなので、新しい条件モデルを作らない。
URL のパースは `parseSeriesSearch` で、`parseRecordingsSearch` の結果から棚が受けない次元を落とす（`toSeriesSearch`）。
落とすのはごみ箱（`tab`）・並び順（`order`）・エンコード状況（`encodeState`）である。
エンコード状況は録画 × ジョブの行で絞るので、棚の件数が膨らむ。
作品を探す軸でもない。
並び順は画面ごとに軸が違うので、`RecordingFilters` の外から `children` で渡す。

「録画 / シリーズ」の切り替えは、両方向で条件を引き継ぐ。
シリーズへは `toSeriesSearch` を通して渡し、録画へはそのまま渡す（シリーズ側の条件は録画側の部分集合）。

### ごみ箱タブと検索条件は直交させる

タブ（ライブラリ / ごみ箱）は条件と直交する別の軸だが、リロード・共有で同じ表示を
復元するため URL の `?tab=trash` に持つ。既定のライブラリは URL に書かない。
履歴を汚さず共有 URL を短く保つためである。

`pages/recordings.tsx` は `tab` から `trash` を導き、`buildListRecordingsParams` には
検索条件とは別の引数で渡す。タブ切替は検索条件を保持したまま `replace` で navigate する。

## 一括操作は録画だけを編集モードで出す

単一世帯で必要な一括操作は、見終わった録画をごみ箱へ移すことと、ごみ箱からの復元・完全削除に限る。
ルール変更後に不要になった予約は ruler が再評価で自動的に引っ込めるため、予約一覧の一括取消は持たない。
手動予約とルール予約では取消・Undo の intent も異なり、同じ選択バーへ載せると操作の逆が一意に決まらない。

一括操作は破壊的で頻度が低いため、常時 checkbox を並べず `PageHeader` 右端の「選択」から編集モードへ入る。
編集モード中だけ checkbox を描画し、全面行リンクを外して行クリックも選択トグルにする。
編集モード中の一覧は `role=listbox` の 1 つの Tab 位置にし、行間は ↑ / ↓ で移る。
Space で現在行を切り替え、Shift+↑ / ↓ と Shift+クリックで起点から現在行までを選択範囲にする。
Finder と同じく、Shift の範囲は動かすたびに置き換わり、戻れば縮む。範囲の外でクリックや Space で選んだ行は残す。
選択モードに入ったら、その後のレイアウトで sticky ヘッダーの下端から固定選択バーの上端までに収まる最初の行を現在行と範囲の起点にする。
入る前のレイアウトで選ぶと、checkbox でカードが伸びて押し出され、選んだ行が選択バーの裏に入る。
先頭行にすると、下の方で入ったときに画面外の行へフォーカスが乗り、最初の ↓ で先頭へ飛び、Space で見えない行を選ぶ。
行ごとに Tab を止めると件数分だけ移動させるため、矢印で行を移れる形にする。
行内の 16px checkbox は状態表示として残すが Tab の順から外す。Tab は横取りせず、DOM 順で一覧の次の要素へ進む。
Cmd+A / Ctrl+A は読み込み済みの行だけを選び、Shift+Cmd+A / Shift+Ctrl+A は選択を解除する。
Shift+Cmd+A は Mac の Chrome ではタブ検索の既定ショートカットでもあり、ページに届くかは未検証である。固定バーのボタンでも解除できる。
Esc で選択モードを終了する。選択モード外と入力欄では Cmd+A / Ctrl+A をブラウザの文字選択に任せる。

選択バーは「n 件を選択中」と表示し、全選択は「読み込み済みの n 件を選択」と明記する。
無限スクロールでまだ取得していない録画は対象にしない。

一括操作専用 API は作らず、既存の 1 件 API を `Promise.allSettled` で全件に並列送信する。
成功分だけ一覧から外し、失敗分は選択したまま API の本文を error toast に出す。
ごみ箱送りの toast は成功件数だけを数え、Undo は成功 ID だけを同じ方法で並列復元する。
ごみ箱の完全削除は、選択件数を示す `AlertDialog` で確認してから送信する。

### debounce と URL 同期で履歴を汚さない

キーワード入力は 300ms の debounce を挟んでから条件（URL）に確定する
（`components/recording-filters.tsx` の `KeywordField`）。`RecordingFilters` 自体は
状態を持たず、debounce 用の下書きだけを例外とする。条件の URL への書き込みは、
debounce（キーワード）もチップの個別解除も常に `replace` で navigate する
（`pages/recordings.tsx`）。1 文字ごと・操作ごとに URL を書き換えて履歴を
汚さないためである。

### TanStack Router の `validateSearch` は無効な値を「省略」しても消えない

`parseRecordingsSearch` は非 strict モード（既定）の TanStack Router で使われる。
このモードは、`validateSearch` の戻り値を「生の（未検証の）`location.search` の
上に重ねる」形で合成する。実際のルートマッチでもそうなる。`matchRoutesInternal`
（`@tanstack/router-core` の `router.js` 内）では
`preMatchSearch = { ...parentSearch, ...strictSearch }` を使う。ここで
`parentSearch` は生の未検証の値である。ビルドロケーション用の軽量マッチでも
同じである。`matchRoutesLightweight` の `accumulatedSearch` に
`Object.assign(accumulatedSearch, validateSearch(...))` する。
**戻り値からキーを省略すると、その
キーは上書きされない**。そのため生の不正な値（`?status=bogus` の文字列そのもの等）が
「検証済みのつもり」の結果へそのまま残って漏れる --- 実機で確認済み（壊れた URL の
不正な値がチップにそのまま出た）。対策は**落とした次元も `undefined` を明示的に
代入する**（キーを省略しない）。`{ ...x, k: undefined }` はどちらの合成方式で見ても
実際に上書きになるため、これで確実に消える。

`/live` の `service` と `/search` の `ruleId` はどちらもこの形に揃えてある
（`routes.tsx`）。`routes.test.tsx` が `router.state.matches` の `search` を
直接見て固定している。

### 一覧は自前で組んだ `useInfiniteQuery`

orval は無限クエリのフックを生成しない（生成されるのは単発の `useQuery` ラッパーの
み）。そのため生成された `listRecordings` 関数を、`@tanstack/react-query` の
`useInfiniteQuery` に自分で渡す。`queryKey` は `getListRecordingsQueryKey(絞り込み +
limit)`（カーソル `before` / `beforeId` を含めない）にする。同じ絞り込みの中で
ページを積んでいくのが `useInfiniteQuery` の前提であり、カーソルを含めるとページ
ごとに別クエリになってしまう。先頭要素が `'/api/recordings'` になる形は保たれる。
そのため `RecordingActions` の
`invalidateQueries({ queryKey: ['/api/recordings'] })`（前方一致）が変わらず効く。

進行方向の読み込み（番兵 + IntersectionObserver、失敗後はボタンへ落とす）は、
`pages/programs.tsx` と同じ部品を再利用する。部品は `lib/auto-load.ts` の
`shouldAutoLoadNextPage` / `shouldShowLoadMoreButton` である。計測できない
環境の判定は `lib/list-virtualization.ts` の `domLayoutMeasurable` を使う。
録画一覧はグリッドのような座標系を
持たないリストなので仮想化はしていない。`limit` は API の既定と同じ値（`pages/recordings.tsx` の
`pageSize`）を明示して渡し、カーソルで継ぎ足す。

### 0 件の文言は条件の有無で分ける

録画一覧に「未検索」の状態は無い（条件ゼロ = 全件が正しい。`/search` の
「未検索と 0 件を別状態にする」規律はここには持ち込まない）。ただし 0 件の文言は
分ける --- 条件があるとき「条件に一致する録画がありません」+ 条件をクリアする
導線、条件が無いときだけ「録画がありません」（ごみ箱タブでは「ごみ箱は空です」）。
取り違えると「まだ何も録れていない」と誤読させる。

`components/page.tsx` の `EmptyState` は `<p>` ではなく `<div>` で包む。
条件クリアのボタンを子に持つ呼び出し側があるため --- `<p>` の中に
ブロック要素（`<div>` / 別の `<p>`）を置くと無効な HTML になり、React が hydration
エラーの警告を出す。

## 録画 → ルールの導線

`RecordingDetail` は `recording.ruleId` があるときだけ「ルール」セクションを出す
（`ruleId` が無い手動予約由来の録画では**セクションごと出さない** ---
「機能しないコントロールは置かない」の既存規律）。

- **ルール名の解決は `useListRules` のキャッシュから引く**。ルール専用の単体
  取得エンドポイント（`GET /api/rules/{id}` / `useGetRule`）はあるが使わない。
  `RulesPage` が `useListRules()`（パラメータなし = 常に全件）を引く設計に
  既に乗っているためである。録画ごとに個別の 1 件取得を増やす理由がない。
  `/rules` を経由していればキャッシュに乗っており、していなければ詳細を開いた
  ときに引く。後者は下記の `#N` → ルール名の差し替えとして見える
- 同じ一覧に同名のルールが複数あるときは、名前に `#<id>` を添えて識別する。
  名前が重複していないときは補助ラベルを付けない。録画の帰属とリンク先は
  いずれも `ruleId` で決まるので、表示名の重複を DB の一意性制約で禁止しない。
- **`rules.find` で見つからない ruleId は `#N` 表記に落とす**。**ただしこれは
  「ルールが削除された」ケースではない**。`recordings.rule_id` は `rules`
  への FK が `ON DELETE SET NULL` である。そのためルールを削除すると
  `recordings.rule_id` が NULL になり、`Recording.ruleId` 自体が省略
  される。つまりルール削除後は「ルール」セクションごと消え、`#N` へは
  落ちない。`#N` に落ちるのは `rules.find` が空を返す間の一時的な状態である。
  一覧クエリが未解決 / 失敗（どちらも `query.data` が `undefined`）か、
  返ってきた一覧にその id がまだ無い（新しく作られたルール等）のいずれかで
  ある。判定は `recording-detail.test.tsx`「ルール一覧にまだ載っていない
  ruleId でも #N 表記に落ちて壊れない」で固定した
- **原則「固有名詞はリンク」に従い**、ルールの識別（名前 or `#N`）そのものを
  リンクテキストにする。リンク先は `/search?ruleId=N`（`RuleRow` の
  ルール名リンクと同じ着地先、ルールの実質的な編集画面）。もう 1 本の
  リンク「このルールの録画で絞る」は `/recordings?ruleId=N` である。これは
  同一ページ（`/recordings`）内の検索条件変更であり、既存の
  `parseRecordingsSearch`（`lib/recording-search.ts`）を通るので条件チップにも
  そのまま出る

## シリーズ一覧（シリーズライブラリ）

`/series` は、生きている録画を実効シリーズ単位で眺める入口である。録画一覧の
ヘッダーにある「録画 / シリーズ」の 2 択からも移動できる。ごみ箱は録画一覧の内側に
残し、シリーズ一覧には含めない。

- API の `value` をシリーズ名として大きく表示し、代表録画の生タイトルを補助表示する。
  `value` が `NULL` の棚は番組ハブを開けないので表示しない
- 再生できる件数（`playableCount`）と最新の放送開始時刻（`latestStartAt`）を表示する。
  録画中・取り込み待ち・失敗も総件数には含むため、棚の件数と見られる件数は異なりうる
- 代表録画のサムネイルを遅延読み込みし、失敗時はプレースホルダーを出す。カードと
  リストの切り替えは録画一覧と同じ `rokuban:recordings:view` に保存する
- 初期順は最新順で、件数順・名前順へ画面内で切り替えられる。並び順は URL に載せない
- 絞り込みは録画一覧と同じ条件を URL に持つ（§条件は URL に持つ / §シリーズ一覧も同じ条件を使う）。
  サーバーはグループ化の前に、条件を録画 1 件ずつに当てる。
  件数・見られる件数・未視聴・最新の放送・代表は、条件に当たった回だけから出す。
  当たる回が 0 件の棚は出ない
- 期間は放送時期（番組開始時刻）で、制作時期ではない。再放送は放送した期に入る。
  放送のシリーズ記述子は地上波でほぼ付かず、元の制作時期は分からないからである
- 未視聴は、絞り込みの外にある録画の視聴済み印も読む。`site` で絞っても、
  別 site の録画で見た回は既読のままにする
- **キーワードは録画一覧と同じ `q` 1 つに寄せ、棚名の文字列絞り込み（クライアント側）は置かない。**
  同じ画面に意味の違う検索欄が 2 つあると、どちらに打てばよいか分からない。
  `q` は条件と一緒に URL に載り、切り替えでも引き継がれる。
  自動キーはタイトルから導き、分類ルールの棚にはキーワードがタイトルに含まれる録画だけが入る。
  そのため、タイトルの一部かルールのキーワードを打てば棚が見つかる。
  **表示中の棚名をそのまま打っても見つかるとは限らない。** 棚名は NFKC で正規化した値である。
  `q` の正規化（`normalize_search_text`）は全角英数字と全角空白しか畳まない。
  全角記号や半角カナを含む名前は、棚名どおりに打つとタイトルに当たらない（棚名「ラブライブ!スーパースター」に対しタイトルは「ラブライブ！スーパースター」）。
  分類ルールの値にだけあってタイトルに無い語でも見つからない。
  また `q` は説明文にも当たるので、名前を説明で触れただけの回も別の棚として出る
- `label_rules` の `valueKey` と一致するシリーズには「手動」バッジを付ける。分類
  ルールの作成・編集・削除は、棚一覧の位置を保つため一覧の後ろに置いた `/series` の
  シリーズ分類セクションに集約する。分類結果が効く画面で管理し、予約を作る録画ルールとは
  効果の向きが違うことを混同させない
- カード・行全体のリンク先は正規化キーではなく `/recordings/{representativeId}/series`。
  キーの規則が変わっても番組ハブの宛先を失わない

## シリーズの導線（番組ハブと次のエピソード）

録画から `/recordings/$id/series` を開くと、番組ハブは次の 3 ブロックを出す。
シリーズの同一性は [docs/data/series.md](../data/series.md) §8 が持つ。

- **identity と操作は並び順に依存しない**: 最新録画・最新話・サムネイル・最新日時・
  「毎回録画中」の判定・「自動: X」は、エピソードの並び順とは別に取った新しい順の
  1 ページ目（50 件）から導く。古い順に切り替えても主ボタンは動かない（新しい順の表示中は
  同じクエリキーなので取得を共有する）。**限界（未検証）**: ルール由来か・「自動: X」の判定は
  この 1 ページ目でしか効かず、それより古い回だけがルール由来なら「毎回録画する」が出る。
  同じ値を指す分類ルールが複数あるとき、キーワードの初期値は評価順（`priority DESC, id ASC`）の
  先頭で近似する。どのルールが勝つかは録画ごとの当たり判定で決まり、クライアントは持たない
- **identity**: 最新録画のサムネイルと `Recording.series` の実効シリーズを出す。
  サムネイルの枠は、worker が SAR を補正して生成する画像に合わせた 16:9 とする。
  比率は録画一覧と同じにする。
  `/series` と同じく、対応する `label_rules.value_key` があれば「手動」バッジを
  付ける。手動棚では読み込み済みエピソードの `Recording.seriesKey`
  （`recordings.series_key`）を「自動: X（ほか N）」として補助表示する。これは
  画面に読み込んだ範囲の値だけで、棚全体の統計ではない。`seriesKey` は一覧と
  詳細の同じ録画行から返し、URL や絞り込みの軸には使わない
- **操作**: 再生できる録画のうち最も新しい回へ「最新話を再生」を置く。録画中や
  失敗した最新行は飛ばして、再生できる回へリンクする。「続きから」は出さない。
  エピソードの `ruleId` が現在の録画ルールに解決できれば
  `ルール「名前」で毎回録画中` から `/search?ruleId=N` へ進む。解決できなければ
  「毎回録画する」から `/search?cond=...` を開き、名前のキーワードと起点の
  `networkId/serviceId` を条件に入れる。検索結果を確認してから利用者がルールを
  作る流れにする
- **エピソード**: `GET /api/recordings?seriesOf=<id>&order=desc|asc` の録画を、
  録画一覧と共有する `RecordingRow` で出す。録画中・失敗・取り込み待ちの状態は
  その行のバッジで表示し、古い順／新しい順の切り替えは API の `order` に反映する。
  「次回」は `GET /api/recordings/{id}/upcoming` から取り、
  `(networkId, serviceId, startAt)` で 1 行にまとめて site をチップで出す

overflow の「分類を直す（割る・指定する）」は `/series` と同じ `LabelRuleForm` を
開き、棚の軸 `key=series` と現在の実効シリーズを初期値にする。自動キーは題名の
NFKC 正規化を通る一方、検索条件の照合には別の正規化があるため、「毎回録画する」
で自動キーをそのまま使うと一部の題名を拾えない場合がある。サービス条件は必ず
付けるので、同名番組を別チャンネルへ広げない。

ハブの宛先は導出キーではなく録画 id にする。戻るボタンは履歴を使い、直接開いた
場合は起点の詳細へ戻る。起点の単体 GET が purge 済みで 404 のときは、一覧と次回に
残る行からハブを開き、戻り先を `/recordings` にする。単体 GET の 5xx は purge と
見なさずエラーを出す。一覧も次回も空なら、存在しない id と区別できないため
「録画が見つかりません」とする。

実ブラウザでは `pnpm e2e:design` がデスクトップと 400px 幅の番組ハブを撮り、3 つの
塊の順序、塗りの主ボタンが 1 つであること、overflow メニューの収まりを確認する。

## 番組ハブの宛先と次のエピソード

- **ハブの宛先は録画 id**。`/series/<正規化キー>` や `?series=<値>` にしない ---
  規則を変えた時点で 404 ではなく 0 件で黙って壊れる
- **`Recording.series` が null の録画には導線を出さない**（ハブも「次回」も 0 件になる）。
  `RecordingDetail` はこの 1 条件だけを見て、タイトル行のシリーズ名のリンクと棚を出す
- 「次回」の予約状態は**結合しない**。予約一覧を別に引いて突き合わせるのは番組リストと
  同じ判断（[api/rest.md](../api/rest.md)「予約状態は番組と結合しない」）
- クエリキーの先頭は「次回」が `programsQueryKeyPrefix`、一覧が `recordingsQueryKeyPrefix`。
  **分類ルールを足した直後に開いているハブが SSE で更新される**のは、`recordings`
  トピックが両方の接頭辞を invalidate するためである（`lib/events.ts`）
- **「次のエピソード」は再生できる行に限る**（`sizeBytes` があるか `encodedAssets` が空でない）。
  同じシリーズの中で起点より後、`program_start_at` が最も早い回を選ぶ。
  同じ時刻の候補が複数あれば起点と同じ site を優先し、次に id の小さい方（`lib/series.ts` の `nextEpisode`。詳細パネルが使う。置き場は上の §次のエピソードとシリーズ）。
  開始時刻がずれて supersede されなかった failed 行を指すと、押した先の再生が 404 になる
- 探索は `?seriesOf=<id>&order=asc&from=<起点の startAt>`。再生できない行が起点の後に 49 件以上
  続くとページからはみ出し、「次のエピソード」が出ない（既知の限界）。話数は持たないので、
  重複排除を切ったルールでは再放送が「次」になりうる（既知の限界）

## ストレージ残高と満杯見込み

`/recordings` のヘッダー領域（`RecordingFilters` の下）に、ストレージ残高と
エンコード待機列をまとめた管理情報行を置く（`components/storage-balance.tsx`）。
通常時のストレージ要約は「空き X GB / 詳細」までを常置し、今後 7 日の予約による
見込みは常に「詳細」を展開した側へ移す（警告の有無に関わらない。下記「要約に
出すかどうかは警告に連動させない」参照）。これにより、視聴対象へ向かう録画行の
位置を下げずに、必要な容量情報へは 1 操作で到達できる。`<details>` を展開すると、
`media`（アーカイブ）と、設定されている場合の `scratch`（ローカルスクラッチ）を
名前・総容量・使用済み・空き・観測時刻に分けて表示する。単一世帯では録画一覧
から容量を確認できれば足りるため、専用ページは作らない。見る頻度やストレージ
root の種類が増えた時点で専用ページを検討する。

ただし、情報量を減らすために警告を隠してはいけない。満杯見込み日と、1 時間を
超えた観測の「古い可能性」は要約に残す。観測時刻そのもの（stale でない通常の
値）は要約には出さない --- 展開すれば root ごとの表示（上記）が観測時刻を持つ
ので、展開側の追加行に重ねて二重にしない。ストレージ観測そのものが無い／取得
できない場合の沈黙は従来どおり。エンコードの「待機中 N 件 / 実行中 N 件」も
0 件を含めて省略しない。

### 要約に出すかどうかは警告に連動させない

見込み（「今後 N 日の予約で約 +Y GB」）を要約に出す条件を満杯見込み・stale
などの警告状態に連動させると、「警告でもないのに見込みも観測時刻もどこにも
出ない」抜け穴ができる（`compact` 表示を実装したレビューで発覚）。要約へ出す
判断はどちらも警告状態に依存させない固定則にする --- 見込みは常に展開側、
満杯見込みは常に要約、観測時刻は stale のときだけ要約。展開側の追加行も
見込みだけを持ち、観測時刻は重ねない（root ごとの表示が既に持っているため）。

視聴対象への到達距離（固定ヘッダー・下部ナビに隠れないこと、必要スクロール量）
の合否と実測値は `e2e/design.mjs`「視聴対象への到達距離」の節が権威 ---
ここに px 値を転記すると数値が二重管理になり必ずドリフトする。

見込みの導出は `lib/storage-forecast.ts` に純関数として集約する。
`StorageBalance` 自身は 3 つの API（`GET /api/storage` / `GET /api/recordings` /
`GET /api/reservations`）の取得と表示の出し分けだけを持つ。`/recordings` は
ストレージを最も直接に消費する画面であるため、全体像の設置先にした。

**見込みが参照する root は `media`（`storage.media_dir`、アーカイブ）だけ**。
`scratch` は取り込みの一時領域で、録画の最終的な保存先ではない。そのため
残量の表示には含めるが、今後の予約による消費見込みには使わない。出所は
[storage/contract.md](../storage/contract.md) の §残量の観測と、同ファイル §5
「2 階層: 録画バッファとアーカイブ」である。

### 4 つの沈黙

- **ストレージ観測が無い**（`GET /api/storage` の結果に `root === 'media'` の行が
  無い。初回観測前や statfs 失敗の継続で起きうる）ときは部品ごと何も描かない
- **直近の録画実績が 0 件、または予約の取得が未解決/失敗**のときは残高だけ出し、
  「+Y GB の見込み」「満杯見込み」は出さない --- でっち上げの既定値を置かない
- **予約が正当に 0 件**（取得は成功したものの、今後 7 日の窓に予約が無い）のときも
  「+0 B」は出さない --- 前項と表示結果は同じだが、内部的には別の経路
  （後述）を通る
- **見込み消費が残量に収まる**ときは満杯見込み日を出さない（下界主義。
  `lib/capacity.ts` の「主張は下界に限る」と同じ精神）

**「取得失敗」と「正当な 0 件」を混同しない**。予約の取得が失敗/未解決のときは
`estimateStorageForecast` が `hasEstimate: false` を返す。見込み
そのものを算出しない。判定材料は `lib/storage-forecast.ts` の
`upcomingReservationSchedule` の結果で、それが `undefined` のときである。予約が正当に 0 件のとき（結果が空配列 `[]`）は見込みを
算出した上で `projectedConsumptionBytes: 0` になる。**この 2 つを区別せず
`undefined` を `[]` にフォールバックすると、取得失敗時に「今後 7 日の予約で
約 +0 B の見込み」という、欠損データから捏造した肯定を描いてしまう**。
実際にこの不具合を実装直後のレビューで指摘された。プローブで実際の描画
「空き 931.3 GB今後7日の予約で約 +0 B の見込み観測: 8/13 15:57」を確認済みである。
録画側（`recordings` が `undefined`）も同じ理由で `averageBitrate` を
`undefined` のまま渡し、`0` にフォールバックしない。

ヘッダーの補助情報 1 つのために専用のエラー表示（`ErrorState`）を割かず、
取得失敗はすべて上記の沈黙（残高だけ出す）に縮退させる。

### 母数: 直近 20 件の finished 録画

`GET /api/recordings?status=finished&limit=20`（`lib/storage-forecast.ts` の
`recentRecordingSampleLimit`）。日数ではなく件数にしたのは、録画頻度が運用ごとに
大きく違うため（固定の日数では少ない側で標本が枯渇し、多い側で 1 回のフェッチの
上限 200 件に収まらなくなる）。`status=finished` に絞るのは、`Recording.durationMs`
が番組の放送時間（全尺）であって実際に録画できた時間ではないためである。`failed`
（途中で終わった録画）を含めると「途中までの `sizeBytes`」を「全尺の `durationMs`」
で割ることになり、ビットレートが実際より低く出る方向に偏る。`sizeBytes` が無い
録画（原本削除済み。`Recording.sizeBytes` の説明「原本の実サイズ。ingest 済みの
場合のみ」参照 --- 未 ingest も含む）も除く。

**`sizeBytes` は原本 TS のみでエンコード派生物を含まない**。エンコードプロファイル
を設定しているルール（既定 `keepOriginal: always`。[storage/retention.md](../storage/retention.md)）
では実消費は原本 + 派生物なので、この見込みは**過小**に振れる。逆に
`keepOriginal: until_encoded` を選んでいるルールでは、エンコード完了後に原本が
削除され、実消費が派生物サイズ（原本の 1/4〜1/10、同 doc）へ縮む。原本サイズを
今後も一定と仮定するこの見込みは、そのぶん**過大**に振れる。どちらの方向にも振れることを
前提にしており、`lib/rule-cost.ts` の「見込み」と同じく一方向の保証は書かない。

### 鮮度: 1 時間を超えたら「古い可能性」

`GET /api/storage` の `observedAt` は「観測ループが止まっていても行は消えない」
契約（[storage/contract.md](../storage/contract.md) §残量の観測）なので、鮮度は
UI 側で必ず判定する。worker の観測間隔は現在 **5 分固定**
（`internal/worker/storage.go` の `defaultStorageSyncInterval`）。
`worker.Config.StorageSyncInterval` というフィールド自体はあるが、
`cmd/rokuban/server.go` がどの設定キーからも埋めていないため実質デッドで、
設定からは変更できない。

それでも間隔の値をフロントへ輸入して「5 分の N 倍」を定義しないのは、この値が
worker 側の実装詳細であって `GET /api/storage` の契約に含まれないため。1 時間
（`lib/storage-forecast.ts` の `observationStaleAfterMs`）は代わりに置いた
**独立した固定の安全マージン**である。現在の 5 分間隔に対して 12 倍の余裕があり、
1 回の失敗パスや再起動直後の遅延では誤って「古い」と出ない。一方で観測ループが
本当に止まっていれば、1 時間以内に検知できる。将来この間隔が実際に設定可能になり
既定より大きく延ばす運用が出てきた場合は基準が弱くなるため、そのときに見直す。

この行自体は 5 分周期の定期 invalidate で取り直している（[docs/api/sse.md](../api/sse.md)
の「ストレージ」グループ）。取り直す周期（5 分）と古さの判定基準（1 時間）は
独立に選んだ別の値で、前者は「得るものが無い頻度で REST を引かない」ため、
後者は「1 回の失敗パスで誤検知しない」ための安全マージン。

### 消費見込み: 今後 7 日、skip=true は数えない

対象窓は今後 7 日（`forecastWindowDays`）。`lib/rule-cost.ts` の値札・ルールの時間帯
条件と同じ 1 週間周期に揃えている。`GET /api/reservations` は絞り込みパラメータを
持たないため全件を取得し、クライアント側で `[now, now+7日)` に開始する予約だけを
合算する。

**`skip === true` の予約は消費に数えない**。`skip` は `effective.skip`
（[recording/reservation-model.md](../recording/reservation-model.md) §4.3「同期の
可否を決めるのは state ではなく effective.skip である」）である。true の間
reconciler は mirakc に同期しない --- つまりディスクを消費しない。`state`
（active/detached/orphaned）は表示用の導出値であって同期可否のフィルタに使っては
ならない（同節）ため、フィルタには使わない。

**満杯見込み日は一様分布を仮定しない**。`GET /api/reservations` で各予約の
開始時刻・尺は既に取得済みである。そこで `upcomingReservationSchedule` が
`startMs` 昇順に整列した消費イベント列を作る。`estimateStorageForecast`
（`projectedFullAtMs`）が先頭から累積消費を積み上げ、残量を最初に超える瞬間を
報告する。

**「見込み消費を 7 日間に均等に分布する」線形外挿は採らない。** 予約が窓の終盤/
冒頭に偏ると、実際より早い/遅い満杯見込み日を出す。後者は下界主義に反する
過小警告の方向（`lib/storage-forecast.test.ts` の「予約が窓の終盤/冒頭 1 件に
集中しているとき」の 2 テストがこの 2 方向を固定している）。

**それでも近似が残る --- この列挙は閉じていない。** 現時点で分かっているのは
少なくとも次の 3 つ（1・2 は上の各節で述べた母数・エンコード派生物の近似の
再掲、3 が今回追加で見つかったもの）:

1. 平均ビットレートが直近の標本の外挿であること（上記「母数」節）
2. `sizeBytes` が原本 TS のみでエンコード派生物を含まないこと（同節）
3. **重なる予約を直列（開始順に 1 本ずつ消費）として扱うこと。** 実際に並行して
   録画される予約（複数チューナー構成では普通）があっても合成レートにはしない。
   この近似も両方向に振れる:
   - 同時に始まる複数予約では、直列近似は実際より**遅い**満杯見込みを出す
     （過小警告・危険な方向）。実測では、同時開始の 6 時間予約 2 本が残量を消費
     するとき、直列近似は 2.78 時間後と報告するが、実際の合成レートでは 1.39 時間後
     に満杯になる
   - 長い予約の途中に短い予約が重なるだけなら、直列近似は実際より**早い**満杯
     見込みを出す（過大警告・安全側だが不正確）。実測では、24 時間予約に 30 分
     予約が重なるケースで、直列近似は 10 分後と報告するが、実際は約 23.67 時間後
     である

   誤差の大きさは重なる予約のうち長い方の尺で頭打ちになる（実測で数時間〜
   約 1 日程度）。上記の一様分布の系統誤差（最大で窓の長さそのもの、7 日）
   より小さいが、ゼロではない。`lib/storage-forecast.test.ts` の「既知の近似」
   2 テストが両方向を固定している。**実装は変えていない** --- 重なりを合成
   レートで扱うには、予約どうしの重なり区間を都度計算する必要があり、この
   タスクのスコープを超える。値札の精度を上げるコストが、今の下界主義的な
   運用判断への寄与に見合うほど高くないという判断である。

この 3 つ（と、まだ見つかっていない近似があるかもしれないこと）のために、
「満杯見込み日」はあくまで目安であって確約ではない。`lib/rule-cost.ts` の
「見込み」と同じく、一方向の保証（「多めには出ない」等）は書かない。
