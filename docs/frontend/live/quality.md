### 画質選択と自動降格

**プロファイル（画質）を選ぶ UI を持つ。**選択肢は `GET /api/live-profiles`（`config.live.profiles` の `name` と表示用の `height`）から作り、**並びは設定順のまま**にする。先頭が `?profile=` を省略したときの既定なので、サーバー側の決め方がそのまま既定の根拠になる。表示名は `height` を添える（`hd（720p）`。0 は「スケールしない」なので名前だけ）。

- **選択肢が 1 件以下ならセレクタを出さない。** 選ぶ余地が無いコントロールは「機能しないコントロール」である。一覧が 0 件になるのは `live.profiles` が未定義のときだけである --- **`live.enabled: false` でも profiles が書かれていれば一覧は返る**（`GET /api/live-profiles` は config の写し。[api.md](../../api.md) §一覧の契約）。その構成では画面自体が「無効です」の分岐に落ちるので、セレクタは出ない
- **切替はセッションを作り直さない。** 1 サービス = 1 ffmpeg が全プロファイルを同時に出力しているので、替わるのは同じセッションのプレイリストの URL だけである（[api.md](../../api.md) §資源同定）。`LivePlayer` を unmount せず、`key` も同意判定（`playingKey` / `selectedKey`）も触らない --- **画質の切替を「同意を取り直す」操作と誤読させる形にしない**
- **離脱ヒントも送らない。** ヒントは「このチャンネルを見るのをやめた」の合図で、画質の切替ではない（`LivePlayer` の離脱 effect を `profile` に依存させない）
- **選択は `?profile=` に持つ。** `routes.tsx` の `validateSearch` は**形だけ**を見る（非空の文字列か）。落とすときは `undefined` を明示代入する。**実在の判定はそこでは書けない** --- 選べる名前は実行時に行を引く `GET /api/live-profiles` から来る。照合は一覧を読める `pages/live.tsx` が `validLiveProfile`（`lib/live.ts`）で行う。`?site=` と同じ分担である
- **未知の名前は落ちて既定（先頭）に倒す。** streamer は空の `?profile=` を既定に落とすが、**未知の名前は 400**（`unknown live profile`）を返す。落とさないと、綴り違いの共有リンク・古いブックマークがエラー画面になる
- **既定は URL に書き戻さない。** 明示的に選んだ値だけを載せる（既定は両側で同じ先頭プロファイルに解決するので、URL に書く意味が無い）
- **チャンネルを切り替えても画質を保つ**（チャンネル一覧のリンクが `?profile=` を運ぶ）。画質は「この局」ではなく「この端末の回線」の性質である
- **追っかけ再生にも画質セレクタを出す。** `LivePlayer mode="chase"` は `profile` prop を受けて `?profile=` を組み立てられるので、streamer 側の配線は既にある。選択は `/recordings/$id` の search に `?liveProfile=` として持つ。追っかけの画面は `/recordings/{id}#chase`（録画詳細）にあるが、`#chase` 側に持たせるとハッシュを変えるたびに録画詳細のコンポーネントを作り直し、再生位置の復元もやり直すためである。search はその再マウント用 key に含めないので、画質の切替で `LivePlayer` は unmount しない。

  キー名を `profile` にしないのは、この画面に `encode.profiles`（完了後の VOD）と `live.profiles`（追っかけ）の 2 軸が同居し、素の `profile` ではどちらを読むのか決まらないためである。`liveProfile` は設定キーと一覧 API（`GET /api/live-profiles`）の名前に一致する。URL に明示された値は一覧で検証し、未知の値は既定（先頭）に落とす。一覧が 2 件以上のときだけセレクタを表示し、0 件・1 件では既定のプロファイルで再生する。

  切替は同じ録画・同じ offset のセッションから別プレイリストを取得するだけで、離脱ヒントを送らない。profile は再開位置の軸に使わず、切替直前の再生位置を次の playlist に持ち越す。したがって画質を変えても「続きから」の位置は画質ごとに分かれない。

  録画終了後（`ENDLIST` 済み）でも、保持セッションが残る idle GC までは切り替えられる。保持ディレクトリに全プロファイルのプレイリストが残るためである。GC 後は現行の追っかけと同じ 404 になるので、UI に特別な分岐は置かない。根拠は偽 ffmpeg による `TestFinishedChaseProfileSwitchServesRetainedPlaylists` で、実 ffmpeg では未測定である。

**停滞したら画質を 1 段下げる。**回線が細い場所で、永久にリバッファするかエラーを出すかしかない状態を減らす。**効くのは回線（配信の転送）が律速のときだけである。** 1 サービスの ffmpeg 1 本が全プロファイルを同時に出力しているので、クライアントが下げてもエンコードの負荷は変わらない。エンコードが追いつかずに止まる場合は、12 秒ごとに最下段まで下がり続けて効果が無い（止まった理由を分けない判断の代償。下の「理由を分けない」を参照）。判定の信号は経路で違うが、**閾値は `liveStallTimeoutMs`（12 秒）1 つ**である。

- **ネイティブ経路（Safari）**: `stalled` / `waiting` の既存の猶予が満了したら、従来のエラー表示の代わりに**まず降格を試す**。下げ先が無ければ現行どおりのエラー文言に落ちる（**新しい失敗経路・新しい文言を作らない**）
- **hls.js 経路**: 計器の 1 秒ポーリングに相乗りして **`currentTime` が 12 秒進まない**ことを見る。`stalled` / `waiting` は MSE では正常時にも何度も出るので聴けない。**下げられないときは何もしない** --- 現行の hls.js 経路に停滞の失敗経路は無いので、ここで新設すると**プロファイルが 1 件しかないデプロイの挙動まで変わる**
- **`paused` の間と非表示タブでは数えない。** `<video>` に `autoPlay` は無いので、再生を押す前は `currentTime` が進まないのが正常である。非表示タブでは `setInterval` が間引かれるので、基準を捨てないと復帰時に誤発火する
- **自動再開を待っている間は「利用者が一時停止した」抑止を外す。** 切替の cleanup が `load()` で `paused` にした状態を「利用者が止めた」と読むと、**降格先の配信も死んでいて `canplay` が来ない場合に停滞の検出ごと止まり、黒いまま永久に何も出ない**（降格もエラー表示も起きない）。`resumePending` の間だけ抑止を外す（`canplay` が来たら戻す）
- **「一度でも再生が始まったか」は effect を跨いで持つ。** 切替は effect を張り直すので、effect ごとに持つと**利用者が自分で一時停止した video を「まだ再生していない」と誤読する**。自動降格の直後に WebKit が出す `stalled` を停滞と読み、健全な配信でもエラーや次の降格に進む（実測: 一時停止した要素は `readyState=4` でも 3.7 秒後に `stalled` を出す）帰結として、**一時停止したまま切り替えた先が無応答でも、再生を押すまでエラーは出ない**（一時停止中の抑止と同じ扱い）。再生を押すと `waiting` で猶予が張り直される（`live-player.test.tsx` の「一時停止中に切り替えた先の stalled」で両方向を固定）
- 「進んだ」は `!==` で見る。ライブ同期の補正で `currentTime` は後退しうる
- **`waiting` の回数とバッファ長は使わない。** `currentTime` が 12 秒進まないならどちらも結論を変えない（同じ事象の別の代理変数）
- **止まった理由を「回線」と「配信側」に分けない。** 分けるには帯域の推定が要る（測っていない数字を出さない）。**代償として、配信側（エンコード）が律速の停滞でも下げる。** 下げても負荷は変わらないので最下段まで進み、その画質がチャンネルを跨いで残る。利用者がセレクタで選び直せば戻る

**下げ先の選び方は設定順で前方へ走査し、実効高さが現在より小さい最初の段である**（`nextLowerProfile`）。実効高さは `height > 0 ? height : Infinity`（0 / 省略 = スケールしない = 元の解像度 = 最重）。`[hd 720, sd 480]` なら sd、`[sd 480, hd 720]` なら**下げない**。**「配列は後ろほど軽い」という新しい契約は置かない** --- 置くと `[sd, hd]` の構成で停滞時に重い方へ上げてしまう。順序は運用者の宣言のまま使い、`height` は「上がってしまう段」への拒否権としてだけ使う（帯域の完全な代理ではないが、拒否権なら誤りが「下げない」側に倒れる）。

- **片方向である。上げ直しはしない。** 上げるには「もう足りている」の判定 = 帯域の能力推定が要り、フラッピング抑止用に**測れない 2 つ目の数値**も要る。上げたいときは利用者がセレクタで選ぶ
- **クールダウンは置かない。** 下げると `LivePlayer` の effect が張り直されて計測が 0 に戻るので、次の発火には再び 12 秒の無進捗が要る（観測窓そのものがクールダウン）
- **明示選択は上書きしない。** `?profile=` の有無がそのまま「自動が効くか」である。自動で下げても URL は書き換えないので、**手で選び直すと自動が止まる**が追加コードなしで成立する。チャンネルを切り替えても下げた先を保つ（既存の「画質は『この局』ではなく『この端末の回線』の性質である」と同じ）
- **`live.captions: true`（全プロファイルを束ねた master）では下げない。** そのとき `Playlist` は `?profile=` に関わらず同じ master を返すので、下げても何も変わらないのに「下げました」と表示することになる。判定は probe が読んだ**本文**で行う（`bundlesProfiles`）--- api と streamer に別の config を配る構成では一覧 API の方が嘘をつきうる。**「master かどうか」では判定しない。** captions 無効時も音声レンディションのためにプロファイルごとの master が返るので、それで止めると自動降格が一度も動かない。違いは `#EXT-X-STREAM-INF` の本数である（プロファイルごとの master は 1 本。ffmpeg 9.0 で実測）
- **追っかけ再生（`mode="chase"`）では自動降格しない。** 下げ先（`?liveProfile=`）は追っかけの画面にもある。それでも下げないのは、この降格が `pages/live.tsx` の `autoProfile` に配線されており、同じ下げ方を追っかけのセレクタへ広げるのが別の判断だからである。**再生再開もライブだけ**にする --- 追っかけは位置指定（`startOffsetSeconds`）や保存位置の復元が `canplay` と競合しうるため、今回の自動降格の再開経路を広げない
- **降格のあとは再生を再開する。** 手動の画質選択も同じ扱いにし、切替時の cleanup から `paused` だけを読み、理由は区別しない。
- エラー後の再読み込みで再開するのはネイティブ経路だけである。ネイティブの停滞エラーは `waiting` のまま `paused=false` である。
- hls.js の fatal エラーでは `destroy()` が `load()` を呼び、`paused=true` になる。その後は利用者が再生を押す。
- 切替の cleanup も `video.load()` を呼び、再生中だった要素を `paused` に戻す。
- `src` の代入や `attachMedia` の直後に `play()` を呼んでも間に合わない。後続の load algorithm が `paused` を true に戻す。hls.js 経路では `play()` が呼ばれた後も `paused=true` だった。
- **`canplay` で再開する。** 切替前に再生中だった場合だけ呼ぶ。初回 mount で呼ぶと「再生」ボタンによる同意の分離が壊れる。
- **再開を外すと、降格しても黒い画面のままになる。** セグメント復旧後も `currentTime` が止まり `paused=true` のままになることを実測した。
- **下げたことは映像の左上に 5 秒だけ表示する**（`映像が止まったため、画質を sd（480p）に下げました`。プロファイル名は `liveProfileLabel` と同じ形）。表示は短くして操作面をふさがない。**原因を断定しない**（「回線が細い」とは書かない。測っていない）。この 1 回の知らせだけは `aria-live="polite"` を持つ（毎秒変わる計器ではなく、利用者が読める時間だけ表示する出来事である）。表示が消えた後も、設定メニューの現在画質に「自動で下げた」と添えて状態を伝える。
- **通知は「その再生で下げた」ときだけ出す。** 画質そのものはチャンネルを切り替えても保つが（「この端末の回線」の性質）、別のチャンネルで「映像が止まったため下げました」と言うのは事実と食い違う。下げた再生の同定を一緒に持つ（`playingKey`）
- **成功した一覧をまだ持っていないとき（未着・初回の取得失敗）は `'wait'` を返す。** 判定はクエリの状態（`isError`）ではなく一覧の有無で行う。TanStack Query は再取得に失敗しても前回の一覧を残す。`isError` で保留にすると、手元に一覧があるのに下げなくなる（`pages/live.test.tsx` の「再取得が失敗しても」で固定）。「下げ先が無い」と同じ `false` にすると、hls.js 経路の観測は一度判定すると止まるので**その再生では二度と試さない**（`StallHandling`）。**ネイティブ経路の `'wait'` は現行どおりエラー文言に落ちる** --- あちらの猶予は `stalled` / `waiting` でしか張り直せず、無応答の配信ではそのイベントが再発火しないので、待つと黒いまま何も出なくなる（実測: `stalled` のあと 20 秒待っても来ない）
- **自動で下がった段と同じ値を選んでも自動は止まらない**（`change` が発火しない）。別の段を選べば止まる。セレクタに「自動」を常設しない判断の帰結である（停滞が一度も起きないデプロイに UI を 1 行足さない）

**判定手段**はユニット、画面、実ブラウザの 3 層である。閾値 12 秒の比較、停止中と非表示タブの抑止、下げ先と master 判定は、実時間を使わずに `lib/live.test.ts` で分けて確認する。

画面では、自動選択なら降格して通知を出し、明示選択（`?profile=hd`）なら下げないことを両方向で確認する。下げ先が無い場合は、ネイティブ経路で既存のエラー表示に落ちる（`live.profiles` が 1 件のデプロイがこの経路に必ず入る）。

**実測（実バイナリ + 実ブラウザ）**: 実再生させてから配信を止めると 22〜23 秒で sd のプレイリストを取りに行く（12 秒の閾値 + 停止までの消費 + ポーリング）。通知とセレクタは下げた先に一致し、離脱ヒントは飛ばない。配信を復旧させると、そのまま再生が続く（`currentTime` が進み `paused=false`）。

**直す前の実装では⑪が NG 3 件となる。** 降格後の再開を外した版でも、⑪ の「復旧後に再生が続く」が落ちる。対照の明示選択側は緑のままで、切替に帰せることを確認した。

**この降格は ⑦ の猶予を伸ばす。** WebKit でセグメントが応答しない場合、猶予の満了で 1 回降格を試み、その先でまた停滞して初めてエラー表示になる（**実測 31.5 秒**。降格の導入前は 30 秒以内に収まっていた）。「永久に黒いままにならない」という ⑦ の主張は変わらないが、窓は 40 秒にしてある（窓そのものが「黒いままにならない」の上限である）。**降格は段が尽きるまで繰り返す**ので、プロファイルが N 件あるデプロイではエラー到達が約 N × 12 秒に伸びる（e2e のフィクスチャは 2 件なので ⑦ は 1 回だけ降格する。実運用の見積もりはこの比例を掛ける）。
