# 番組リストと番組表グリッド

## M4-19: 全 site の和集合

`/api/sites` の全 site へ番組表を問い合わせ、リスト・グリッドとも結果を和集合として
表示する。番組には取得元の `site` を付与し、同じ `programId` が複数 site に存在しても
行の identity は `site:programId` で区別する。サービス列も
`site:networkId:serviceId` を identity とし、サービス名・予約状態・詳細・予約操作は
その site を引き継ぐ。単一 site の列幅・時刻・表示は従来どおりである。

容量超過は API が返す `overage.site` を落とさず対応する site の番組列へ重ねる。予約一覧
からのバッジは `/programs?view=grid&at=...` に遷移し、番組表が全 site を取得することで
第2 site の番組も表示対象になる。

## リストを第一級に置く。グリッドはその上に足す

EPGStation はグリッドが主でリストが従なので、モバイルでは常にグリッドの窮屈な
縮小版か単局表示になる。番組表は本質的にデスクトップ形状（2 次元 × 数十チャンネル ×
24 時間）なので、この構造だとモバイル体験が構造的に犠牲になる。

Rokuban は**リストをモバイルの妥協物ではなく第一級のビューとして設計する**。
グリッドは `lg` 以上でのみ出し、モバイルは常にリストのままにする。

グリッドの価値は「見やすさ」ではなく**同時性を空間に符号化すること**であり、
このドメインでは同時性がチューナー本数というハード制約に直結する
（判定の設計は [data.md](../data.md) §6.5）。

### 実装で決めたこと

座標系は `web/src/lib/epg-grid.ts` の純関数（React 非依存）、グリッド本体は
`web/src/components/program-grid.tsx`。

- **セルの高さに下限を設けない。** 5 分番組は 5 分ぶんの高さ（10px）になる。見やすさの
  ために下限を入れると同時性の符号化が崩れ、グリッドの存在理由そのものが失われる
- セルが 108px 以上なら 2 行の概要、150px 以上ならジャンル名も出し、未満のセルには
  時刻と題名以外を足さない。放送終了セルは減光して読み上げ名でも伝えるが、過去番組の
  詳細を開けるよう `disabled` にはせず、5 分セルは読み上げだけに留める
- **列幅はコンテナ幅に追従し、176px から 260px の範囲に収める。** 最小幅は番組名を
  2 行で読める幅であり、列数が多く収まらないときは横スクロールを保つ
- **仮想化はライブラリを入れず自前。** 縦軸は連続量で番組セルは目盛りをまたぐ
  「区間」なので、行の並びを前提とする仮想化ライブラリの模型に乗らない。
  可視判定は純関数 2 つ（`visibleTimeWindow` / `visibleColumnRange`）に落ちるので、
  依存を増やすより検証しやすい（下記「経緯と失敗事例」）
- **未計測（DOM 計測が 0）なら全部描く**方向に倒す。jsdom のように計測できない環境で
  「空のグリッドなのにテストが通る」（CLAUDE.md の「非同期の空虚な成功」の変種）を
  構造的に防ぐ
- **出し分けは `matchMedia`（JS）で行い、CSS で隠さない。** グリッドが自前のクエリ
  （全サービス × 24h）と仮想化を持つため。`view` の選択は画面幅で捨てないので、
  狭くするとリストへ倒れ、広げるとグリッドに戻る
- **容量超過の帯は `ProgramGrid` の `overlay` prop で受ける。** 番組セルより上・ヘッダより
  下の「全チャンネル縦断の層」（`pointer-events-none`。帯がクリックを飲むと予約操作が
  壊れる）で、`spanToPx(axis, from, to)` を呼べば番組セルと同じ座標に必ず乗る。
  現在時刻インジケータが最初の利用者
- **グリッドの窓は 24 時間を 1 回で取得**する（リストのような窓の積み上げにしない ---
  積み途中が「番組がない時間帯」と見分けられない）
- **セルの中に操作を置かない。** 選択した番組を既存の `ProgramRow` としてグリッドの上に
  出すので、予約・取消・詳細展開・重なり警告がリストと同一実装になる
- 列は「窓内に番組があるサービス」だけ。順序は種別 → リモコン番号 → site → serviceId の全順序。
  **サービス取得の失敗はグリッドではエラー扱い**（列が構造なので、列 0 本を
  「番組がない」と区別できない）
- ジャンル色は**補助**。意味の本体は `aria-label` のラベルで、知らないジャンルは
  「その他」に丸めない（ARIB の本物の「その他」= コード 15 と、分類できなかったことを
  区別する）。色は Tailwind 標準パレットの 50 / 950 に限定し、未知は既存トークンへ戻す
- **予約済みは見える「予約」と右端の墨の帯で示す。** 輪（`ring`）は選択中だけに
  残す。予約に同じ `ring-primary` を足すと、ジャンルの左罫・選択中と形が重なり、
  差が太さだけになる。色は信号のみなので予約にタリー / 琥珀 / destructive は
  足さない。5 分セル（10px）でも帯が残る（見た目の差は
  `web/e2e/grid-reserved.mjs` が実画素で見る）

**未検証**: 「全サービス × 24 時間でスクロールが落ちない」は jsdom で計測できないため
実ブラウザで確認していない（縦横とも間引く実装は入っている）。受け入れは実機で行う。
セル間の矢印キー移動も未実装（グリッド領域の focus とスクロールまで）。
リストでは重なりが見えないため、グリッドとは別に画面幅に依存しない伝達手段が必要
（後述「容量超過は番組ではなく区間に描く」）。

## グリッドで横スワイプによるナビゲーションを使わない

Android のジェスチャーナビは左右端からの横スワイプが「戻る」なので、
グリッドの横パンと確実に喧嘩する。

## 番組リスト: 時間順フラット + 日付・サービス絞り込み

- 常に「今」から始まる連続フィード（`pages/programs.tsx`）。上限はどの日付を
  選んでも共通の「EPG のローリングウィンドウの終端」（8 日先の 0 時）で、
  24 時で打ち切らない。sticky 日付ヘッダで日付境界を示す
- **API が返す番組を無条件にリストの先頭へ出さない。** API は問い合わせた時間窓に
  **重なる**番組を返す（`start_at < window_end AND end_at > window_start`）ため、
  読み込んだ最も手前の窓の開始時刻（`listStartMs`）より前に始まった番組（＝まだ
  読み込んでいない前の窓との重なりで一緒に返ってきた番組）がリストの先頭に混ざる。
  これを見せたままにすると、日付ヘッダと「いま見ている日」の導出（どちらも
  リストの先頭の番組から日を決める）が両方とも前日を指してしまう不具合を実機で
  確認した。`lib/program-list.ts` の `filterProgramsFromListStart`
  で `pages/programs.tsx` 側が絞ってから `ProgramList` へ渡す。ただし
  `listStartMs` が下限（now を時で切り捨てた時刻）と一致するとき（＝今日を
  見ているとき）は絞り込まない ---
  単純に切ると放送中の番組（起点は時刻境界なので、開始が起点より前になりうる）
  まで消えてしまうため
- **仮想化は TanStack Virtual（`useWindowVirtualizer`）を使う**
  （`components/program-list.tsx`）。グリッドが自前実装を選んだ理由（縦軸が
  連続量で番組セルが目盛りをまたぐ区間なので、行の並びを前提とする仮想化
  ライブラリの模型に乗らない）はリストには当てはまらない ---
  リストは**行の並びそのもの**なので素直に乗る。内側にスクロール容器を持たず
  ページ全体がスクロールするため、`useVirtualizer` ではなく
  `useWindowVirtualizer` を使う
- 行は `position: absolute` + `transform` ではなく通常のフローに残し、可視範囲の
  前後を高さぶんのスペーサー（padding）で埋める。sticky な日付ヘッダは通常の
  フローに乗った要素にしか効かないため。行の高さは `ProgramRow` の段階的開示で
  可変なので `measureElement` で実測する
- **未計測（DOM 計測が 0）なら全部描く**方向に倒す（`lib/list-virtualization.ts`）。
  jsdom はレイアウトを計算しないため `measureElement` が常に高さ 0 を読み、
  動的計測をそのまま使うと可視範囲の計算が壊れる。グリッドの
  `visibleTimeWindow` / `visibleColumnRange` と同じ「未計測なら間引かない」
- 日付とチャンネルは選択肢の性質が違うので、絞り込みの形も分けている。
  どちらも横スクロールにはしない ---
  単一選択なのに選択中の値が画面外に出て読めなくなることと、
  画面端からの横スワイプが Android のジェスチャーナビの「戻る」と
  衝突すること（前述「グリッドで横スワイプによるナビゲーションを
  使わない」と同じ衝突）、ヘッダが伸びるとグリッドの高さ予算
  （`--page-header-height` を引いた残り）を削ることの 3 つの実害がある
- **日付**（`components/day-strip.tsx` の `DayStrip`）は「いま見ている日」の
  表示 + ジャンプ先の指定の 2 つの概念に分けている。
  `dayOffset`（URL の `day` から初期化する state）はタップして跳ぶ先である。
  ハイライトは可視範囲の先頭の番組から導出した「いま見ている日」
  （`onVisibleDayChange` / `lib/program-list.ts` の純関数）で、ジャンプ先とは別に表示しない ---
  タップ直後は一致するが、その後リストをスクロールすればハイライトだけが動く。
  **未キャッシュの日へ跳ぶ間も前のリストをプレースホルダとして残し、
  `ListSkeleton` へ挿し替えない。** 挿し替えると文書高さがビューポートまで潰れて
  `scrollY` がクランプされる。ジャンプ時は明示的にページ先頭へ戻し、前の日の
  スクロール位置を引き継がない。プレースホルダ中は前の日の可視範囲から
  `visibleDay` を更新せず、選んだ日のハイライトを保つ。
  グリッド表示中はスクロールで日をまたがないので、ハイライトにジャンプ先を
  そのまま渡す。ハイライトは押下状態ではないので `aria-current="date"` を使う
  （`aria-pressed` ではない）。今日のセルは 0 時ではなく「今」から始まるので、
  `今` という別枠のセルは無い（8 日分で有界。横スクロールなしの等幅グリッドに
  並べて必ず 1 画面に収める）。ヘッダのタイトル行の下にフル幅で置く
- **チャンネル**（`components/channel-picker.tsx` の `ChannelPicker`）は
  「番組を持つサービス」（マルチ編成のないサブサービスは番組を持たないので
  自動的に消える）という非有界な集合なので列挙を畳み、現在値を常に表示する
  トリガーボタン + 開いたときに縦スクロールするポップオーバーにする。トリガーは
  `PageHeader` のタイトル行右端（`actions`）に置く。
  **グリッド表示中もトリガーを出したままにする** --- 選択はグリッドの
  列にも効くので、隠すと解除手段のない 1 列グリッドになる
- チャンネルは**複数選択**（`ChannelPicker` は `Service.id` の
  `ReadonlySet<number>`。空集合 = すべて）。
  「見たい局だけをグリッドの列にする」という使い方に直結するため
- **絞り込み URL は `?service=<Service.id>` に持つ。**
  `lib/programs-search.ts` の `ProgramsPageSearch.service` が複数可・OR・空集合を
  `undefined` で表す。**検証は openapi.yaml から生成した zod スキーマ
  （`src/api/zod.ts`）に委ね、値域や正規表現を手で書き写さない**
  （`lib/url-search.ts` が URL 固有の都合 --- 文字列で届く / 単一値と配列が
  混ざる / 不正な要素だけ落とす --- だけを繋ぐ）。id 配列は昇順に正準化し、
  選択履歴で URL / queryKey を揺らさない。
  選択日は `?day=YYYY-MM-DD` のローカル暦日として URL に持つ。`DayStrip` が出す
  今日から 8 日間だけを受け取り、範囲外の古い共有 URL は既定の今日に落とす。
  既定の今日は URL に書かない。日付操作で履歴を汚さず共有 URL を短く保つためである。
  `at` と `day` が矛盾するときは「この瞬間を見る」という要求である `at` の日を優先し、
  どちらの値も URL から削除しない。
  `view`（表示形式）も URL 状態にしてある --- 容量不足バッジが `search={{ view: 'grid', at }}`
  でグリッドを明示するため。
  ピッカー操作は `replace` で navigate し、1 局ずつ選ぶたびに history を汚さない
- **絞り込みはサーバー側でかける。** 選択した `Service.id` の配列を
  `programs.tsx` から渡し、返るのは選択したサービスの番組だけになる。
  100 サービス規模で無絞り込みの 24 時間ぶんが実測 1.7 MB になり、全件取得してから
  クライアント側で絞る形は維持できないため
- **ピッカーの候補は `Service.hasPrograms` から作る。** 表示中の（絞り込んだ後の）
  番組から候補を導くと、1 局に絞った瞬間に候補がその 1 局だけになり、他局へ
  直接切り替えられなくなる。`hasPrograms` は絞り込みの入力に一切依存しない
  ため、候補集合が絞り込み結果から独立し、この壊れ方が構造的に起きない。
  グリッドの列は絞り込んだ後の番組（サーバーの返り値そのもの）から導く ---
  選んだ局がそのまま列になればよく、独立させる理由が無い
- **ピッカーが実際に表示・列挙できる集合は「候補（`hasPrograms` から作る
  `filterableServices`）∪ 現在選択中の id」。** 選択は URL から入るため、候補に
  無い値も無視しない。名前が引けない古いブックマークは `チャンネル #<id>` に
  落とし、個別に解除できる形を維持する（`pickerServiceDomain`）。同じ
  `serviceId` の別 network は合成 id が違うので、同じ候補へ潰れない
- sticky な小見出しの `top` はハードコードしない。`PageHeader` が
  `ResizeObserver` で実測して `--page-header-height` を親要素に書き出す
  （フィルタ行の増減や文字サイズでずれる）
- **ライブ視聴（`/live`）からは「この局の番組表」で厳密な 1 局へ飛べる。**
  番組表と同じ `?service=<Service.id>` の 1 要素配列を使う（1 局のためだけの
  別形式を持たない）。逆方向（番組表 → ライブ）はページ単位の導線を置かない ---
  放送中の番組の展開に「ライブで見る」を出す導線は行（`ProgramRow`）単位の担当
  （issue #229）にする。ページ全体に 2 つ目のライブ導線を足すと、複数
  チャンネルを絞り込んでいるとき・放送中の番組が絞り込みの外にあるときに
  どこへ飛ぶかを決める基準が無く、個々の番組から飛べる導線と役割が重複する
  （issue #231 の決定）

時間窓の継ぎ足し（進行方向の自動読み込み）は [scroll.md](scroll.md)。

## 「既にジャンプ先になっている日」の再タップ

`DayStrip` のタップは `dayOffset`（state）を書き換えて跳ぶ、で足りると思われて
いたが、**タップした日が既に `dayOffset` と同じ場合**が抜けていた
（実機で確認した不具合）。`setDayOffset(同じ値)` は React が
再レンダーの理由にしないため、クエリもスクロールも一切動かない。ユーザーは
スクロールで「いま見ている日」（`visibleDay`）がジャンプ先から離れていることが
あり、その状態での再タップは「その日の先頭へ戻る」ことを期待しているので、
`dayOffset` が変わらなくても何かしら起きる必要がある。

- **タップは常にその日へ移動する意味を持つ。** `dayOffset` と一致する場合は
  クエリの起点を付け替えず、**読み込み済みの `programs` の中からその日の
  先頭へ `scrollToIndex` する**（`components/program-list.tsx` の
  `ProgramListHandle.scrollToDayOffset`。`virtualizer.scrollToIndex` を直接
  呼ぶ）。対象の添字は `lib/program-list.ts` の
  `firstIndexForDayOffset`（「可視範囲の先頭 → dayOffset」を導く
  `visibleDayOffset` と対になる、逆向きの純関数）で引く。見つからなければ
  （まだ読み込んでいない日）何もしない
- `ProgramList` は `forwardRef` + `useImperativeHandle` で `ref` 経由の命令的 API
  （`ProgramListHandle`）を公開する。`pages/programs.tsx` はこの `ref` を
  `selectDay` から呼ぶだけで、`dayOffset` を書き換えるかどうかの分岐は
  `selectDay` 側が持つ

## 段階的開示

行は「時刻 / タイトル / サービス」だけ。説明の続きと出演者・映像音声属性は
展開時に `GET /api/sites/{site}/programs/{programId}` で取る
（[api.md](../api.md) の「EPG の読み取り」）。

## 展開領域の外向き導線

行本体（タップで展開）と行右端 44px（予約 / 取消）というタップ予算
（[reservations.md](reservations.md) §予約はワンタップ + トーストから取消）に
触れないよう、**固有名詞（放送中のチャンネル・予約という実体）へのリンクは
折りたたみ行ではなく展開領域側に置く**。`components/program-row.tsx` の
展開パネルに次の 2 本を持つ:

- **放送中**（`startAt <= now < endAt`）の番組: 「ライブで見る」 →
  `/live?service=<Service.id>`。番組表・録画の絞り込みと同じ `Service.id`
  （合成 id）を渡す --- `ProgramListItem` は SI の `networkId` / `serviceId`
  しか持たないため、`composeServiceId`（`lib/service-id.ts`）で合成してから渡す
  （[live.md](live.md)「フロントエンド実装」）。
  `live.enabled` が無効なデプロイでは主ナビと同じ判断（`lib/capabilities.ts` の
  `useLiveEnabled()`）で出さない
- **予約済み**の番組: 「予約の詳細」 → `/reservations/$site/$programId`。overrides
  編集は予約詳細画面の担当で、番組行の展開パネル（未予約時の encodeProfiles /
  keepOriginal 欄）はここを引き継がない

`now` の判定は「展開されて描画される瞬間（とその後の再レンダー）」で行い、専用の
tick タイマーは持たない。このリンクは番組 ID を運ばず `networkId` + `serviceId` を渡すため、
番組境界を挟んで多少ズレても遷移先を誤らない --- 遷移先の `/live` 画面が自前で
「いま何が流れているか」を再取得するので、真実はそちら側にある。

## 容量超過は番組ではなく区間に描く

チューナー不足の表示は**番組への着色ではなく区間の帯**にする。番組を着色すると「この番組が負ける」という勝敗の主張になるが、決めるのは mirakc であり、Rokuban から見えない消費者（EPGStation の並走・ライブ視聴・EPG 収集）がいるので予測できない。判定と根拠は [data.md](../data.md) §6.5。

- **グリッド（`lg` 以上）**: 超過区間を全チャンネル縦断の帯で着色する。区間は結合済みで返るので描く帯は少ない
- **リスト・予約一覧・モバイル**: 同じ文言のバッジ。グリッドが出ないモバイルでも情報が届く（画面幅に依存しない伝達手段が別に必要、という要件）
- **文言は「この予約は競合しています」ではなく「この時間帯はチューナーが不足しています」。** 主張できるのは下界（超過している）だけで、収まることは保証できない。不足本数と詰まった種別まで出せるので「BS が 1 本不足」と具体的に書く

## 容量超過の帯とバッジ

`web/src/lib/capacity.ts` に交差判定と文言の純関数がある。`components/capacity-band.tsx`
はグリッドの `overlay` に渡る帯（色 + 罫線）と `gutterOverlay` に渡る見えるラベルを持つ。
`components/capacity-shortfall-badge.tsx` は予約一覧のバッジを持つ。座標は必ず
`spanToPx` を通す（番組セルと同じ関数を通すことが「帯とセルが同じ時刻で同じ位置に
来る」ことの保証）。

- **肯定的な文言を一切持たない。** 「競合なし」「収まります」は出さない。区間が
  返らないときは何も言わない（沈黙は保証ではない。[data.md](../data.md) §6.5）
- **複数区間に跨る予約では種別を合併せず、最も不足の大きい区間を採る。** 合併すると
  「どの区間でも成り立っていない主張」になる
- **見えるラベルは局の列ではなく時間軸列（gutter）に出す。** 帯の内側に出すと、帯の
  上端が番組セルの上端と重なったときセルの時刻文字と同じ px に描かれる。時間軸列は
  番組セルを一切置かないので、この列に出す限り衝突しない
- **時間軸列のラベルは自分の内容ぶんの高さしか持たず、帯の上端にアンカーする。**
  帯の高さに引き伸ばすと、範囲内の時間軸の目盛りや現在時刻チップまで不透明な
  地の下に隠してしまう
- **不足区間がちょうど正時に始まると、目盛り（「00:00」等）と同じ位置に来る。**
  番組境界は :00 / :30 に落ちることが多く、不足区間の境界も同じ単位なので
  珍しくない。ラベルはその行を避けて 20px（= 10 分ぶん）下にずれる
  （`avoidTickRow`）。正時起点では常態で、ほぼ毎回この分岐を通る
- **ただし押し下げても自分の帯の外へは出さない。** 正時起点で高さが
  20px + ラベル自身の高さ 16px（9〜18 分の帯）未満だと、押し下げた先が
  自分の帯の下端 --- すなわち直後に隣接する帯の領域 --- にはみ出し、その
  帯のラベルと同じ位置に重なる。この高さを下回るときは見えるラベルを一切
  描かない。**失うものを正直に書く**: 番組表の画面上には、種別・本数まで言う
  手段が残らない。帯の色（琥珀）は BS / GR / CS で同一なので種別を伝えず、
  予約一覧のバッジは別画面にあり、帯自身は `pointer-events-none` の overlay
  の中にあるので hover の手がかりも無い（`program-grid.tsx`）。見える範囲では
  「この区間は何か不足している」までしか分からない。もう一方の選択肢（位置を
  ずらして描く）は警告そのものが消える（隣接する帯のラベルの下に完全に隠れる）
  --- どちらを選んでも画面上の情報は削られるので、削れない方を消したという
  判断。支援技術の利用者は帯の `sr-only`（`shortageRangeMessage`）で
  種別・本数・時刻を含む全文を変わらず得られる
- **時間軸列（56px）は予約一覧のバッジより幅が狭い。** 専用の短い形
  （`shortageLabelCompact`。「BS-1」）を持つ。バッジの全文（「チューナー不足
  （BS が 1 本）」）はここでは省略記号で切れて種別も本数も読めなくなる。読み上げ
  用の全文は帯の `sr-only`（`shortageRangeMessage`）が持つので、見た目だけ削ってよい
- **短縮ラベルには警告アイコンを添える。** 色（琥珀の文字）だけに頼ると、
  「BS-1」のような短い英数字が日本語 EPG の時間軸列では実在のチャンネル名
  （NHK BS1 等）と読み違えられうる
- **同一 site 内の不足区間は重ならない**（サーバー側の判定がそう保証する）。
  site を保ったまま各グリッドへ渡すので、異なる site の同時刻の帯も誤って同じ番組の
  状態にはしない
- 鮮度は SSE の `reservations` トピックと予約 mutation 後の invalidate に相乗りさせる
  （容量超過は予約集合の導出値なので専用トピックを作らない）
- **交差判定は予約自身の `site` と突き合わせる。** `Reservation` は `site` を返す。
  クライアントに定数を持たせないのは、他サイトの不足を
  自分の不足として出す形で静かに壊れるのを避けるため。フィクスチャが全部 `default`
  だと定数を書いた実装でもテストが通ってしまうので、**`default` 以外のサイトの予約に
  自サイトの不足を当てるケース**を置いてある
- **skip / orphaned の予約にもバッジが出る。** サーバーの需要計算はこれらを除外して
  いる（= その予約は超過の原因ではない）ので、区間の性質としては真だが因果の誤読を
  招きうる。フィルタするかは未決

## 番組表への `at` 導線

容量不足バッジ（予約一覧。[reservations.md](reservations.md) §容量不足バッジから
番組表へ）は番組表ルート（`/programs`。ホーム新設（[home.md](home.md)。M8-3）前は
`/` だった）へ、不足区間の開始時刻を `at`（epoch ms。
`lib/programs-search.ts` の `ProgramsPageSearch.at`）と `view: 'grid'`
（同 `ProgramsPageSearch.view`）を積んだ `Link` で飛ぶ。

着地後の反映先は画面幅・表示形式で 3 つに分かれる。**グリッドが唯一「その時間帯」を
帯で直接見せられる形なので、それが選べる画面幅ではバッジが `view: 'grid'` を明示する**。

- **`lg` 以上**: URL の `view=grid` がそのままグリッド表示になり、`at` をグリッドの
  初期スクロール位置に使う（`ProgramGrid` の `scrollToMs`）。表示形式が URL 状態なので、
  `at` の有無と画面幅から「グリッドにしたい」を**推論する必要が無くなった**
  （`showGrid` 自体は `wideScreen`（`useMediaQuery`）の判定を待つので、グリッドの
  マウントが初回レンダーより 1 レンダー遅れる点は変わらない）。ユーザーが手動で
  リストへ戻すと URL の `view` も `list` に replace されるので、画面幅の再評価
  （resize）だけではグリッドに戻らない --- 以前は resize のたびに再評価して
  自動切替するかどうかを判定していたが、`view` を URL に持たせたことで
  「resize で切替を再検討する」という概念自体が無くなり、代わりにリンクを
  踏むたびグリッドが永続するようになった
- **`lg` 未満・リスト表示中**: グリッドが無い/選ばれていないので帯を出す手段が無い。
  次善として「`at` が属する日」への日付ジャンプ（`DayStrip` のジャンプ先）に留める
  （`lib/day-offset.ts` の `dayOffsetForMs`）。一覧の該当行自体には容量不足バッジ
  （画面幅に依存しない伝達手段）が出るので、日を合わせれば「その時間帯」に近づける
- 日付ジャンプは表示形式に関わらず効く（グリッド表示中でも `at` の日にジャンプする）

**`at` は URL から消費・削除しない。** 「1 回使ったら `navigate` で消す」実装を試したが、
`navigate` の非同期解決がグリッドの初回スクロール確定より先に終わってしまい、肝心の
初回スクロールが「今」にしか効かなくなる退行を e2e で検出した（`useMediaQuery` が
`false → true` になるのに最低 1 レンダーかかる一方、`navigate` はそれより早く
解決しうる）。**`view` を URL に持たせたことはこの競合を解消していない** ---
`showGrid` は今も `wideScreen`（`useMediaQuery`）の判定を待つ。グリッドが実際に
マウントされるのは初回レンダーから 1 レンダー遅れたままであり、その間に `at` を
`navigate` で消すと同じ退行が起きる。`view` の URL 化で無くなったのは「`at` の有無から
グリッドにしたいかを推論する」処理だけで、この初回レンダーの遅れそのものは変わって
いない。代わりに **`scrollToMs`（グリッドへ渡す実際の値）を
「いま見ている日が `at` の指す日と一致している間だけ」に条件付ける**
（`pages/programs.tsx` の `scrollToMs`）。`at` 自体は URL に残ったままだが、「今日」
ボタンや日付ストリップで別の日へ移った瞬間に `scrollToMs` は自動的に `undefined` へ戻り、
以後の軸変更は「今」へスクロールする既定の挙動に戻る --- URL を書き換える経路を持たずに
同じ保証を得られる。

**既知の弱点**: `at` が「今日」の**過去**の時刻（不足区間がもう終わっている等）を指す
場合、グリッドは正確な位置へはスクロールしない。`ProgramGrid` の初期スクロールは
「軸の範囲内かどうか」しか見ておらず、範囲内でも過去の `at` は現在スクロール中の窓の
先頭（`scrollTop = 0`）に落ちる（`components/program-grid.tsx` の
`useLayoutEffect` のコメント参照）。容量不足バッジが指す時間帯は通常これから録画される
予約の時間帯なので実害は薄いが、精密な位置合わせを主張しない。

**罠**: グリッド上の容量帯（`components/capacity-band.tsx`）は `pointer-events-none`
（帯がクリックを飲むと予約操作が壊れる）。リンクにするのはバッジ側だけで、グリッドの
オーバーレイには触れない。

## 経緯と失敗事例

- UI の構造（リスト第一級・ナビゲーション）は M1-7 で確定し、グリッドは M2-9、
  容量超過の帯とバッジは M2-10 で実装した
- 容量バッジ・skip 理由の録画参照をリンク化する導線は M6-5（issue #233）。
  グリッドの実際のスクロール位置は jsdom で測れないため、判定手段
  （`web/e2e/badge-links.mjs`）を実装より先に作った。その判定手段自身が、
  「`at` を URL から navigate で消費する」素朴な実装の退行（初回スクロールが
  「今」にしか効かなくなる）を検出し、`scrollToMs` を「いま見ている日が `at`
  の指す日と一致する間だけ」で条件付ける方式へ設計を差し替えるきっかけになった
- グリッドの同時性の符号化と「画面幅に依存しない伝達手段が別に必要」という要件は
  [issue #21](https://github.com/fetburner/rokuban/issues/21)
- 設計 issue #5 / #24 は仮想化に TanStack Virtual を名指ししていたが、グリッドは
  本文の理由（縦軸が連続量で、行の並びの模型に乗らない）で自前実装にした。
  リスト側は模型に乗るので TanStack Virtual を使う
- チャンネルピッカーの「番組を持つサービス」は
  [issue #17](https://github.com/fetburner/rokuban/issues/17) の S3
- `Reservation` は当初 `site` を返しておらず、UI に単一サイト前提の定数を
  置いていた。#24 のレビューで API に足した
- 「リスト先頭に前の窓との重なりで返ってきた番組が混ざり、日付ヘッダと
  『いま見ている日』が前日を指す」「既にジャンプ先の日を再タップしても何も
  起きない」は、いずれも実機確認で見つけて直した
