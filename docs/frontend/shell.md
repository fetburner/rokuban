# 共通シェル

画面をまたいで共有する骨格（ナビゲーション・生成クライアント・リアルタイム通知・文書設定）をここに置く。

## ナビゲーション: モバイル = ボトムタブ / デスクトップ = サイドバー

ルート定義は 1 つで、レイアウトのみブレークポイントで切り替える。

ボトムタブは画面下端に密着させず `env(safe-area-inset-bottom)` + 最低 8px を空ける。

- **iOS のホームインジケータ**と重なると最下段が押せない。実害が大きい
- **Android のジェスチャーナビ**は下端からの上スワイプがホームなので、
  スクロール中に指が滑ると誤爆する

`index.html` の viewport に `viewport-fit=cover` が必要（無いと `env()` が 0 になる）。
高さは `--bottom-nav-height` として CSS 変数に持ち、本文の下パディングと共有する。

**この変数はタブの実際の描画高さと一致していなければならない**（本文の下パディングは
これをそのまま使うので、足りなければ最下端で行がタブに食い込む）。境界線ぶんは
`--bottom-nav-border` を両方（nav の `border-top-width` と高さの計算）で使うことで
構造的に揃えてあるが、**タブ本体の高さや padding はこの変数に追従しない** ---
それらを変えるときは `index.css` の計算も直し、`web/e2e/programs-bottom-nav.mjs`
（CI では回らない）で実測との一致を確認する。最下端以外のスクロール位置での重なりは
これでは消えない（[scroll.md](scroll.md)「ボトムタブの裏に隠れる行」。未解決）。

**ブラウザのビューポートはシステムナビゲーションバーの下には入らない**ので、
Web ページのボトムバーが Android の戻る/ホームボタンと重なることはない。
懸念は上記 2 点だけで、いずれもパディングで解決する。

デスクトップのサイドバー（`components/app-shell.tsx` の `Sidebar`）は
`sticky top-0` + `h-dvh` でビューポートに固定し、本文だけがスクロールする
（`position: fixed` + 本文側の手動 margin にはしない。flex のフローに
残したまま高さだけ固定するので、本文の左オフセットは flex レイアウトが
自動で確保する）。画面が低くて項目が入りきらない場合はナビ項目側だけ
`overflow-y-auto` で縦スクロールする。

ハンバーガートグルで幅 `w-48`（展開）⟷ `w-[52px]`（アイコンのみのレール）を
切り替えられる。**完全には隠さない**のは、トグル自体をレールの先頭に常駐
させ、どのページからでも展開に戻せるようにするため。
`pages/reservation-detail.tsx` だけは `components/page.tsx` の `PageHeader`
を使わず独自の見出しを持つため、トグルをヘッダー側に置く設計だとこの
ページだけサイドバーを戻す手段が無くなる。畳んだ状態でもラベルは DOM から
消さず `sr-only` にするので、読み上げ名は失わない（マウス向けには `title`
を補う）。畳み状態は `localStorage`（キー `rokuban:sidebar:collapsed`）に
持続し、再読み込みでも復元する。

### 項目の並びは頻度順、モバイルは 4 タブ + 「その他」

`components/app-shell.tsx` の `navItems` はデスクトップのサイドバーとモバイルの
ボトムタブで共有する 1 つの定義だが、並びは実装順ではなく**触る頻度**で決める
（[design.md §頻度 3 段](design.md)）:

| 段 | 項目 | 置き場 |
|---|---|---|
| 一等地 | ホーム・番組・録画 | 常に最短の導線 |
| 中間 | 予約・ライブ | 一等地の次 |
| 端 | 検索・ルール | 意図して探しに行く位置 |

ホームはホーム画面の新設（[home.md](home.md)）で一等地の先頭に加わった。
サイドバーは 7 項目を頻度順（ホーム / 番組 / 録画 / 予約 / ライブ / 検索 /
ルール）に並べるだけでよいが、ボトムタブは頻度の低い 4 項目（予約・ライブ・
検索・ルール）を畳んで一等地のタブを広く取ると決めた。**根拠は誤タップ対策
ではなく、頻度の低いものを畳んで場所を稼ぐこと。**実測（390px 幅、Chromium）
では 4 タブ = 97.5px/個で、`min-h-14` が確保する最小タップ領域 44px は満たして
いる。**畳まずに全項目を常時タブへ並べた場合の値（以前は「6 タブ = 65px/個」
と比較していた）は、M8-3 で項目数が 6→7 に増えたため比較対象自体が無くなった
--- 7 タブでの値は測り直していない。**「畳む」という結論そのものは項目数が
増えても変わらない（畳まなければ一等地がいまより狭くなる一方のため）ので、
根拠として古くなった数字だけを落としてある。そこで**モバイルは一等地の
3 個（ホーム・番組・録画）を常時タブに出し、残り（予約・ライブ・検索・
ルール）を「その他」ポップオーバー 1 個に畳んで、常時 4 タブに抑える**
（`useNavItems` の `primary` / `more`。境界は `MOBILE_PRIMARY_COUNT`）。

**予約は常時タブから「その他」へ戻した。** ホーム新設前は「今夜これで
録れているか」を録画と同じ頻度で確認する対象という仮説で予約を中間段から
常時タブに繰り上げていたが、ホームがその確認そのもの（今夜〜明日の予約
セクション）を持つようになったため、確認の頻度はホームに移った
（[home.md](home.md)）。**この頻度の割り当ても元の仮説と同じく実測ではない**
（design.md 同様、単一世帯の運用なので自分の行動で検証してよい）。

「その他」はシートではなくポップオーバー（`components/ui/popover.tsx`、
base-ui の `Popover`）で実装した。中身がリンク 4 個だけの単純な一覧で、
フォーム操作や長いコンテンツを持たないため、全画面/半画面を覆うシートは
過剰と判断した（base-ui にはドロワー相当の primitive もあるが、この用途では
使っていない）。

固定されたボトムバーの上に浮くポップオーバーは、はみ出し・バーの上に
出るか・safe-area との重なりが jsdom では原理的に測れない。`app-shell.test.tsx`
が固定しているのは DOM の有無と順序だけなので、実ブラウザでの合否は
`e2e/design.mjs` の「その他」判定（開いた状態でビューポート内に収まるか /
トリガーより上に出るか / ボトムタブが 4 個か）が担う。

### 無効な機能の項目は出さない

サーバー側で無効な機能（今は `live.enabled: false` のライブ視聴だけ）はナビから
落とす（`useNavItems`。issue #209）。判断は `GET /api/capabilities` に一本化し、
フロント側の入口も `lib/capabilities.ts` の 1 つに限る --- ライブへの導線は
ナビだけでなく番組行にも増える予定（#229）なので、判断が導線ごとにばらけると
「ナビからは消えたが別の場所からは行ける」状態になりやすい。

**未確定（取得前・取得失敗）は「無効」に倒す。** 有効なデプロイでは初回描画の
あいだナビ項目が 1 つ遅れて現れる（`staleTime` 30 秒に乗るのでページ遷移の
たびには起きない）。逆に倒すと、無効なデプロイで導線が一瞬出てから消える ---
その瞬間に押せてしまえば行き先は「無効です」の画面で、消したかったものが
復活する。

**ただしこの fail-closed が無料なのは「導線を出すか」の判断に限る。**
`lib/capabilities.ts` が真偽値（`useLiveEnabled`）と 4 値
（`useLiveCapability`: `pending` / `unknown` / `enabled` / `disabled`）の 2 つを
配っているのはこのため。**原因を名指しする画面は 4 値を見る** --- 未確定を
`false` に潰したまま「サーバーの設定で無効です」と書くと、能力 API が瞬断した
だけの有効なデプロイで誤った原因を運用者に指す（[live.md](live.md)）。
黙って消えるナビと、理由を述べる画面で、必要な確信の強さが違う。

常時タブとその他の切れ目は**除外後の並び**に対して取る（今の並びでは差は出ない
---ライブは既にその他側にいる。将来この形の項目が常時タブ側に来ると、除外前に
切ったときだけボトムタブが 3 個 + その他に痩せる）。

「その他」トリガー自身のアクティブ表示は、配下の項目（予約・ライブ・検索・
ルール）のいずれかが現在地のときに立てる。個々のリンクは「自分のページに居るとき」
だけ `aria-current="page"` を持つのに対し、トリガーはページそのものではなく
「その他」という集合の現在地を表すので `aria-current="true"` を使い分ける
（両方向とも `app-shell.test.tsx` でリテラルな期待値に固定している）。

## サイトの扱い: site の出所で切る（先頭サイト固定は「出所が無い入口」だけ）

`<SiteGate>`（`components/site-gate.tsx`）は `GET /api/sites` を解決し、レジストリの
**先頭サイト**を `SiteContext` に流してから `<Outlet>` を描く（`routes.tsx`。
ナビとサーキットブレーカーバナーはこの外側にいる）。ただしこれは「先頭以外のサイトが
UI に一切現れない」という意味ではない。**切れ目は「その site を誰が名乗ったか」に
あり、画面の単位でも、呼ぶエンドポイントが `/api/sites/{site}/...` の形かどうかでも
ない**:

| site の出所 | どこ | 何が起きるか |
|---|---|---|
| **行が運ぶ**（`GET /api/reservations` / `/api/recordings` / `/api/capacity/overages` / `/api/breakers`） | ホーム・予約一覧・録画一覧・ブレーカーバナー | **全サイトの行が混ざって出る**（api は site に束縛されない --- 不変条件 1、[api.md](../api.md)「既定は全サイトを返す」）。行から始まる操作は行の `site` を使う: 予約詳細への遷移（`/reservations/$site/$programId`）・容量バッジの交差判定・ブレーカー再開 |
| **URL が運ぶ** | 予約詳細（`/reservations/$site/$programId`） | 行から持ってきた site をそのまま資源同定に使う。取消・上書き・重複警告もその site |
| **出所が無い**（mirakc に「何があるか」を訊く入口） | 番組表・検索・ライブ / 検索とルールの条件フォームのサービス選択肢 | ここだけ `useCurrentSite()` = **先頭サイト固定**。ここから始まる操作（番組表からの予約・スキップ・番組詳細）も現在サイトを引き継ぐ |
| **レジストリが運ぶ** | 録画検索のチャンネル選択肢 | `GET /api/sites` の全 site からサービス一覧を引き、`Service.id` を選択の identity にする。**同じ `Service.id` は site をまたいでも 1 つの選択肢**（site は別軸の `?site=`）。録画一覧の述語は site を `ANY`、チャンネルを `(network_id, service_id)` の行値 `IN` で引く |
| **site を持たない資源** | ルール一覧・エンコードプロファイル・ストレージ残高・能力・録画詳細 | `/api/rules` / `/api/encode-profiles` / `/api/storage` / `/api/capabilities` に site は無い（アーカイブ用ストレージが単一なのは [api.md](../api.md)）。録画詳細（`/recordings/$id`）も id が site 非依存だが、観測対象の録画が運ぶ `site` は多サイト構成で表示する。ストレージ残高はこの単一の観測に、上段の全サイト分の録画・予約から作った見込みを重ねる（`components/storage-balance.tsx`。site で絞らない） |

**`/api/sites/{site}/...` という URL の形は判別子にならない。** ブレーカー再開
（`POST /api/sites/{site}/breakers/{name}/resume`）と予約詳細
（`GET /api/sites/{site}/programs/{programId}/reservation`）はこの形だが、site は
行 / URL から来るので先頭サイト固定ではない。逆に、site を含まない URL の一覧が
全サイトの行を返す。**「どのエンドポイントを呼ぶか」ではなく「その site を誰が
名乗ったか」で見る。**

1 つの画面が複数の段にまたがることもある。`/rules` はルール行そのものは site を
持たない（`GET /api/rules`）が、条件フォームのサービス選択肢は先頭サイト
（`components/condition-fields.tsx`）。`/recordings` は一覧もチャンネル選択肢も
全サイトを対象にし、新しく作る選択肢と述語を `(site, networkId, serviceId)` で結ぶ。

**現在サイトを持つ画面が上段の一覧（全サイト）を重ねるときは、その画面の側で
`site` を突き合わせる。** 例はライブの中断予測 --- 全サイトの予約を受け取ってから
`reservation.site` が現在サイトと一致するものだけを見る
（`lib/live-interruption.ts`。`programId` は site スコープの値だが、同じ放送を
2 サイトで受ければ値は一致するので、`programId` の突き合わせだけでは足りない）。
番組表も同じ突き合わせを持つ --- 「予約済み」判定は `reservation.site` で、容量超過の
帯は `overage.site` で現在サイトに絞ってから重ねる（`pages/programs.tsx`）。

**サイト切り替え UI は持たない。** 多サイトの運用実績が無い状態で切り替えの形
（グローバルなセレクタか画面ごとか / URL に載せるか）を先に決めると、その形が合って
いるかの判定基準を持たないまま固定することになる（不変条件 11）。

以前ここには「先頭以外のサイトはそもそも UI に現れないので、複数サイトを運用し
始めたときに気付きやすい」と書いてあったが、**一覧が全サイトを返す今それは偽**。
言えるのは次の 2 つで、**多サイトでの気付きやすさそのものは未検証**（多サイト構成の
実機確認をしていない）:

- 第 2 サイトの予約・録画は**一覧に出る**（「他サイトの予約が無い」ようには見えない）。
  予約は行の `site` を宛先に使うので詳細まで辿れる
  （`pages/reservations.test.tsx`「多サイトの予約一覧」で固定）。録画は複数サイトを
  構成しているときだけ行と詳細に `site` を出し、単一サイトではノイズになるので出さない
- 一方、**予約行から EPG に降りる導線は先頭サイトの番組表に着く**（容量バッジの
  `/programs?at=` は site を落とす）。エラーにも空表示にもならず、予約行に `site` を
  出してもいないので「別サイトの番組を見ている」ことは画面から分からない

既知の不足（多サイトを実際に運用するときに、切り替え UI の形と一緒に決める）:

- **予約一覧の行に `site` を出していない。** 同じ放送を 2 サイトで受けていると行を
  見分けられない
- **ルール条件のサービス選択肢は先頭サイト / 適用は全サイトを跨ぐ。** ルールは
  `sites` を送らない = 全サイトで評価される（issue #290）
- **容量超過の導線は判定を行の `site` で行うのに、遷移先が site を落とす**
  （issue #292）
- **番組表のグリッドは多サイトを畳めない。** 「予約済み」判定と容量超過の帯は
  現在サイトに絞る（上記）が、BS / CS は全国共通・地上波はサイトごとに別物なので、
  多サイト時に列をどう見せるか（サイトごとの帯・列の畳み方）は切り替え UI の形と
  一緒に決める
- **ブレーカーバナーの行の React key が `name` だけ**（`circuit_breakers` の PK は
  `(site, name)` なので多サイトで衝突する。issue #293）

経緯: サイトレジストリの API（`GET /api/sites`）と `<SiteGate>` は issue #184（M4-12）。
「先頭以外はそもそも見えない」という記述を、全サイトを返す一覧 API に合わせて上の形に
直したのは issue #218（`docs/frontend/search.md` から移設）。最初に書き直したときは
分類を「Rokuban の DB 由来 / mirakc 由来」の 2 段で切ったが、ブレーカー再開と予約詳細
（どちらも `/api/sites/{site}/...` を行 / URL の site で呼ぶ）が反例になり、`/rules` の
ように 1 画面で両側にまたがるものも落ちた --- 軸を「site の出所」に取り直したのが
上の表（同 issue のレビュー）。

## 生成クライアントの型を実行時の事実に合わせる

orval は OpenAPI に書いたエラーレスポンスも含めた `{status, data}` の判別可能
union を生成するが、`customInstance` は非 2xx で throw するのでフックの `data` に
届くのは常に成功バリアント。この差を `api/unwrap.ts` の 1 箇所で埋める
（status を実行時に確かめてから絞り込む）。

エラーレスポンスを OpenAPI から消して型を単純化する道は採らない。エラーの形は
契約の一部であり、生成物の差分で破壊的変更を検知したい。

**エラーの本文も UI まで運ぶ。** `customInstance` は非 2xx で throw するが、
当初は本文を捨てていた。`ApiError`（status + body）と `apiErrorMessage`（`unwrap` と
対になる失敗側の半分）を置き、**400 を黙って 0 件にしない**。典型は不正な正規表現
（Postgres の ARE をサーバーが検証して 400 を返す）で、メッセージを見せないと
ユーザーは「書き方が悪いのか該当なしなのか」を区別できない。

## リアルタイム通知 --- SSE + invalidateQueries パターン

mirakc と同じ「接続時に現在状態を再送し、以降差分」という設計に揃える。クライアントの再接続処理が対称的になる。

- SSE (`/api/events`) を配るのは api ではなく **notifier ロール**。notifier を複数レプリカにしても、各レプリカが Postgres の NOTIFY を購読して配るだけなので **Redis アダプタのような追加基盤は不要**
- notifier をロールとして分けたことで、api は SSE という長寿命接続を持たなくなり、サーバーレス（scale-to-zero）に本当に載せられるようになった（[overview.md](../overview.md)）
- レベルトリガーの「定期」の側は `lib/events.ts` が持つ。**接続断中の変更は再接続時（切断を観測した後の `open`）の invalidate で取り直し、接続が生きたまま個別の通知だけ落ちたケースはグループごとの定期 invalidate（前面タブのみ）で収束する。** `staleTime` は stale と判定する期限であって再取得を起こすタイマーではないので、これに頼ると古い表示が無期限に残る（グループの周期と対象は [api.md](../api.md) §SSE の表）
- **SSE トピックを持たないグループ（ストレージ残高）は、個別の通知という経路が最初から無い。** 収束するのは定期 invalidate と再接続時の全グループ invalidate（と mount / window focus）だけなので、周期は「通知が落ちたときの上限」ではなく「これが唯一の周期」として決める

通信設計の詳細は [api.md](../api.md) を参照。

## `<html lang>` は ja

UI が日本語なので `lang="en"` のままにしない。ブラウザのフォント選択と
禁則処理・行分割の挙動が変わる。

## PWA は入れない

ホーム画面追加は魅力的だが、go:embed と S3+CDN の immutable / no-cache 規約に
service worker を足すと配信経路の話が複雑になる。得るものと釣り合わない。
