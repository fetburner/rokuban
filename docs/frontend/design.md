# デザイン言語（副調整室の計器盤）

**この節は以後の UI PR のレビュー判定基準。** 新しい画面・コンポーネントを足すときは
ここを満たしているかで見る。

形（トークン名と実際の値）の権威は `web/src/index.css`。ここには判断（なぜ）だけを書く。
**合否は実ブラウザで測る**（`pnpm e2e:design`。下記「合否は画素で測る」）。

## テーゼは「副調整室の計器盤」

Rokuban が扱うのは放送波と有限のチューナーで、UI の仕事は
**いま何が電波に乗っていて、何が録れていて、何が足りないか**を一目で言うこと。
装飾で個性を出す画面ではない。基準にするのは副調整室（サブ）の計器盤 ---
地は徹底して無彩、色が点いていること自体が情報。

原点は 16px のファビコン（[branding.md](branding.md)）で成立している階調構成で、
それをそのままアプリの地に持ち上げている。

## 地は「イ」の 3 値

地の階調は**ファビコンの 3 値と同じ値**を使う。

| ファビコン | トークン |
|---|---|
| 輝線 = 白 | `--paper`（紙白） |
| 間隙 = 灰 | `--scanline`（走査線グレー） |
| 字 = 黒 | `--sumi`（墨） |

値そのものはここには書かない（`index.css` と `scripts/gen-favicon.mjs` に既に 2 度
書いてあり、3 つ目を作ると必ずどれかが古くなる）。

ライトは「白地に黒」（ファビコンそのもの）、ダークは「消灯した画面に輝線」
（役割を入れ替える。反転ではない）。3 値の間を埋める段（`--tone-*`）は、
3 値がちょうど 50 / 500 / 900 に一致する Tailwind zinc の ramp から採る ---
別の ramp を持ち込むと、3 値だけが浮いて中間段と噛み合わなくなる。

zinc はわずかに寒色（hue ≈ 286、chroma ≤ 0.016）で、これが「地は無彩、色は信号」を
成立させている: 地が寒色側に寄っているぶん、暖色の信号（タリーレッド・琥珀）だけが
色として立ち上がる。

**3 値の一致は `web/tests/design-tokens.test.ts` が両方のファイルを読んで検査する。**
同じ決定が 2 箇所（`index.css` と `scripts/gen-favicon.mjs`）に書いてあるので、
片方だけ動かすと黙って食い違う。

例外は 1 つだけ。**浮いた面（`--card` / `--popover`）はライトで純白**を使う ---
ポップオーバー（録画の絞り込み・チャンネル選択）はオーバーレイを持たないので、
地と同色だと輪郭が罫線と影しか無くなる。

## 色は信号のみ

**恒常的な装飾色を持たない。** チャンネル色・アバター色・ブランドアクセントは入れない。
色が点いている箇所は、そのとき何かを主張している箇所に限る。

| 信号 | トークン | 意味 | 形 |
|---|---|---|---|
| タリーレッド | `--tally` / `--tally-foreground` | いま電波に乗っている（録画中・現在時刻） | **塗りと線のみ**（点灯した札・playhead） |
| 琥珀 | `--warning` | 警告（チューナー不足・条件なしのルール・期間指定の副作用） | 文字 + 淡い地 |
| destructive | `--destructive` | 取り返しがつかない・壊れた（失敗・ドロップ・EPG から消失・削除操作） | 文字 + 淡い地 |
| ジャンル淡色 | （Tailwind の 50 / 950） | 番組の種別。読まずに帯の並びを掴むための補助 | セルの淡い地 |

**タリーは塗りと線にしか使わない。文字色にはしない。** 11px〜14px の赤い文字は
ダークの地に対して AA（4.5）に届かない。塗りにすれば「紙白の文字 / タリーの塗り」の
比で測れて、両テーマとも 4.5 を超える。この規律のおかげで「点灯している」という
比喩と読みやすさが同じ方向を向く。

**リストの「放送中」には色を使わない**（太さだけ）。チャンネル数ぶんの行が同時に
放送中になるので、赤くすると信号ではなく地になる。「いま」を主張するのは
番組表グリッドの線と札（画面に 1 本 / 1 枚しか出ない）。

`--tally` にだけ `--tally-foreground`（塗りの上に載る文字）を持たせ、`--warning` には
対の前景色を作っていない。琥珀は塗りに使わないので書き手がいない ---
使う人がいないトークンは足さない（CLAUDE.md 不変条件 11）。琥珀を塗りに使いたく
なったら、そのコードと同じ PR で `--warning-foreground` を足す。

**タリーレッドと destructive は色相が近い。区別は色ではなく形が担う。**
タリーは「点灯」なので塗り（`bg-tally` + 紙白の文字）、destructive は「壊れた」なので
文字と淡い地（`text-destructive` + `bg-destructive/10`）。同じ赤でも、
塗られているかどうかで「いま動いている」と「壊れた」が見分けられる。

この排他性のために外した色が 1 つある。**日付ストリップの「日 = 赤 / 土 = 青」は使わない。**
カレンダーの慣習ではあるが、赤が画面の中で 2 つの意味を持つと、
タリーが「いま電波に乗っている」を主張できなくなる。週末は濃さで立てる
（墨 = 週末 / 走査線グレー = 平日）。土と日のどちらかは文字自身が言うので、
色で区別する必要はない。

**沈黙は保証ではない。** 警告を出さないことは「大丈夫」を意味しない
（[data.md](../data.md) §6.5）。「競合なし」「収まります」を緑で出すことはしない ---
判定の盲点はすべて「警告を見逃す」方向に偏っている。緑の信号色を持たないのはこのため。

### コントラストは毎回測る

**数値はここに転記しない。** `pnpm e2e:design` が実画素から WCAG 比を計算して表で出し、
下限を割ったら落ちる。文字は 4.5、面と線は 3 が下限。

測る対象は「実際に出ている組み合わせ」で、**半透明の地は合成してから測る** ---
`text-warning` が乗るのは地ではなく `bg-warning/10` の上なので、地に対する比だけを
見ると 0.5〜0.7 ほど甘い数字が出る（最初の版はそれで「AA を満たす」と書いていた）。

下限を割ると分かっていて直さないものは、`design.mjs` の `knownGaps` に**理由込みで**
書く。合否には数えないが、実行するたびに「既知の不足」として出る。黙って下限を
下げる形は取らない。いまそこに載っているのは 1 件:

- **失敗バッジ（`text-destructive` / `bg-destructive/10`、ライト）。**
  destructive は shadcn 既定のままにする決定なので触っていない。明度を下げると
  タリーレッドと見分けが付かなくなるので、直すなら色相ごと動かす判断が要る
  （実測値は `e2e:design` の出力に出る）

`bg-muted` + `text-muted-foreground` の小さいバッジ（予約一覧の「ルール外」など）も
AA に届いていない。走査線グレーは 3 値の一方なので動かしていないが、**判定にも
載せていない** --- 数値をここに書くと守られない転記になるので、直すなら
`design.mjs` の判定に足して `knownGaps` に理由を書く形にする。

## トークン外の生の色値を書かない

コンポーネントが書いてよいのは**意味を持つトークン名**だけ
（`bg-background` / `text-muted-foreground` / `text-warning` / `bg-tally`）。
`bg-amber-700` のような Tailwind 標準パレットの直指定と、`#rrggbb` / `rgb()` /
`oklch()` の生値は書かない。**色の定義は `web/src/index.css` の 1 箇所に集める。**

```sh
cd web && pnpm check:colors
```

CI の lint job でも回る。除外は理由込みで `web/scripts/check-colors.mjs` に並べてある
（トークンの定義 / ジャンル淡色 / 映像のレターボックスとダイアログの幕の黒）。
**「テーマの色ではないもの」だけが除外の対象**で、ライト・ダークで変わってはいけない
黒（映像が来ていない領域・背後を沈める幕）がこれに当たる。

検査が**見ていない**書き方も同じファイルに書いてある（動的なクラス名の合成・CSS の
名前付き色・3 桁の 16 進・`public/` の資産）。「`check:colors` が通った」を
「色をトークン外に書いていない」と読み替えない。

濃さを変えたいときも**別の色を作らず、同じトークンの不透明度を下げる**
（容量超過の帯は琥珀の塗りを薄くし、罫線を濃く残す）。帯のためだけの琥珀を作ると、
琥珀が 2 つになった時点で「琥珀 = 警告」が言えなくなる。**不透明度の実際の値は
コンポーネント側が持つ**（ここに書くと、下限を割って直したときに追随し損ねる）。

## 数字は tabular-nums

時刻・尺・サイズ・ドロップ数・PID は縦に並ぶので、等幅数字にしないと桁が揃わず
「並べて比べる」という計器盤の唯一の仕事ができない。

**`html` に 1 度だけ当てて全域に効かせる。コンポーネント側で個別に指定しない。**
触るたびに指定を思い出す必要をなくすためで、`web/tests/font-tokens.test.ts` が
「コンポーネント側に `tabular-nums` の個別指定が残っていないこと」を検査する
（残っていると全域適用に統合した決定と矛盾するので、そこで落ちる）。フォントと
tabular-nums の実効性（どの書体が実際に等幅を作るか）は
[stack.md](stack.md)「フォントは英数字と和文で 2 書体を使い分ける」にある。

## 走査線は 3 箇所限定

走査線のモチーフ（縞）を使ってよいのは**空状態・読み込み中・ON AIR** の 3 箇所だけ。
全面に敷くとキッチュに転ぶ。ここが「地は無彩」との境界で、
走査線は色ではなく**質感**として現れる。

形は `web/src/index.css` の `.scanlines`（空状態・読み込み中）と
`.tally-scanlines`（ON AIR）の 2 ユーティリティ。周期 2px（輝線 1px + 間隙 1px）は
[branding.md](branding.md)「走査線は 3 値で描く」のファビコンと同じ設計を流用する。

**「読み込み中」が指すのは共通の `Skeleton` / `ListSkeleton`（components/page.tsx）
だけ。** `site-gate.tsx` の起動時「読み込み中…」のような、各画面が個別に持つ
`<p>読み込み中…</p>` 文言までは対象にしていない（アプリ起動時の全画面ローディング
を含め 8 箇所ほど残っている）。広げるかどうかは未決 --- 広げるならこのタスクの
延長ではなく、`Skeleton` を使う形に寄せるか個別に判断する

**ファビコンの 3 値をそのまま持ち込むと本文の AA を割る。** ファビコンは 16px の
1 文字で WCAG の対象ではないが、空状態・ON AIR は実際に読む文字が乗る。
「輝線・間隙・字が互いに異なる 3 値」という**構造**だけを流用し、縞 2 色の
具体的な値は本文の文字色（4.5 下限）に対して十分なコントラストが立つ段へ
選び直してある（`.scanlines` のコメント参照。値そのものはここに書かない ---
`index.css` が権威）。ON AIR は色は信号のみの例外としてタリーレッドの塗りを
使ってよい（上記「色は信号のみ」）。片方の縞にはタリーそのもの（録画中バッジと
同じ、AA を満たす組み合わせ）を使い、もう片方は**色相・彩度を変えずに明度だけ
落として**沈めてある --- 色相を変える手段（`color-mix(in oklch, ...)` を墨と
混ぜる等）は、oklch の補間が色相を極座標の最短弧で結ぶせいでタリーの色相から
外れた第 5 の信号色（マゼンタ寄り）を生みかねない。CSS Color 4 の相対カラー
構文（`oklch(from var(--tally) calc(l * ...) c h)`）で明度だけを操作すれば
色相・彩度は変数元と完全に同じ値のまま動かない。

**縞の 2 色（`--scan-gap` / `--scan-lit`）は「文字に対してコントラストが低い
側」を `--scan-gap` に割り当てる。「暗い側」ではない。** 空状態はライト・
ダークで字の明暗が入れ替わる（「地は『イ』の 3 値」）ので、不利になる縞も
入れ替わる --- ライトは字が暗いので明るい側（間隙）が不利、ダークは字が
明るいので明るい側（輝線相当）が不利になり、`--scan-gap` はダークでは
輝線側を指す。ON AIR は字（`--tally-foreground` = 紙白）が両テーマで変わらない
ので `--scan-gap` は常にタリーそのもの側を指す。

実装は縞の 2 色を `--scan-gap`（= `background-color`）と `--scan-lit`（=
`background-image` の `repeating-linear-gradient` が参照するカスタム
プロパティ）に分けてある。**`background-color` は `getComputedStyle` で
読めるが、`background-image` に直接書いた色は読めない** --- カスタム
プロパティに出しておけば `e2e:design` がどちらの縞も個別に読め、**両方**を
文字色との AA で判定できる。**「どちらが最悪ケースか」を決め打って片方だけ
測ってはいけない** --- そう決め打つと、決め打ちが外れたとき（あるいは
決め打ちが正しくても、測っていない側を文字と同じ色にする変異が入ったとき）に
判定がすり抜ける（「コントラストは毎回測る」の失敗事例と同じ形）。使う側は
文字色を必ず `text-foreground`（ON AIR は `text-tally-foreground`）にする。

アニメーションは付けていない。CRT の走査を模した動きを検討したが、
このアプリの他の状態色がどれも静止していることを理由に見送った。付けるなら
`prefers-reduced-motion: reduce` で静止させる。**走査線そのものの動きは
無いが、読み込み中（`Skeleton`）は走査線とは無関係に元から `animate-pulse`
（不透明度の明滅）を持っており、この PR ではそこに触れていない。**
`animate-pulse` は `prefers-reduced-motion` に対応していない（このタスクの
対象外。別タスク）。

3 箇所以外に走査線クラス（`scanlines` / `tally-scanlines`）が無いことは
`web/tests/scanline-usage.test.ts` が固定する（`scanlines` は `index.css`
定義 + `components/page.tsx`、`tally-scanlines` は `index.css` 定義 +
`pages/live.tsx` だけに閉じていることを見る。4 箇所目を足すと落ちる）。
手で確認するなら（`tally-scanlines` は文字列として `scanlines` を含むので、
ヒットしたファイルを目で見て 3 箇所に収まっているかを判断する）:

```sh
grep -rln --include='*.ts' --include='*.tsx' --include='*.css' 'scanlines' web/src | grep -v '\.test\.'
```

## 角は立てる

`--radius` は `0.25rem`。shadcn 既定の `0.625rem`（10px）は SaaS のカードの丸みで、
1 行 56px の密な一覧に対して過剰に柔らかい。計器のパネルとスイッチは角が立っている。
`--radius-*` の派生段（0.6〜2.6 倍）はこの値に追従する。

## 頻度 3 段

配置は実装順ではなく**触る頻度**で決める。

| 段 | 対象 | 置き場 |
|---|---|---|
| 一等地 | 番組・録画 | 最短の導線。モバイルは親指の届く位置 |
| 中間 | 予約・ライブ | 一等地の次 |
| 端 | 検索・ルール・破壊的操作 | 意図して探しに行く位置 |

単一世帯の運用なので、頻度の仮説は自分の行動で検証してよい。

**「端」に寄せる実装手段は overflow メニュー（`components/ui/dropdown-menu.tsx`。
`@base-ui/react` の `Menu` を shadcn の作法でラップした標準部品）。** ルール一覧の
削除（稀・破壊的）はこれに乗せ、検索で開く/編集という主操作とは同格に並べない。
新しい破壊的・稀な操作を行に足すときは、新しい overflow の作法を都度作らずこの
部品を再利用する。逆方向（頻度が高いのに埋もれている操作を「一等地」へ引き上げる）
の実装例は [recordings.md](recordings.md) の再生ボタン。

## 合否は画素で測る

**色は jsdom では測れない。** Tailwind のクラスは解決されないし、oklch も計算されない。
`pnpm test` が全部通っても、色については何の保証にもならない。判定手段は 2 つに分かれる。

| 手段 | 見るもの | CI |
|---|---|---|
| `pnpm e2e:design` | **実ブラウザの実画素**。主要画面 × ライト / ダーク × デスクトップ / モバイルのスクリーンショットと、状態色・地の無彩性・コントラストの機械判定 | 載せない |
| `pnpm check:colors` | トークン外の生の色値（実ブラウザ不要） | lint job |
| `pnpm test`（`tests/design-tokens.test.ts` ほか） | 実ブラウザ無しで文字列として言えることだけ ---「3 値がファビコンと一致」「地と字が 3 値を参照している」「信号色がライト・ダーク両方にある」「どのトークンのクラスが当たっているか」 | 未（既存の欠落） |

**変えた状態色は必ず `e2e:design` の判定に載せる。** 判定の外に 1 箇所でも置くと、
そこだけ既定値へ静かに戻っても全部緑のまま通る。いま載っているのは録画中バッジ・
失敗バッジ・チューナー不足バッジ・番組リストの時刻（色が付いていないこと）・
現在時刻の線と札・容量超過の帯・ルールの「条件なし」。

手順は [web/e2e/README.md](../../web/e2e/README.md) §デザイン。
**判定を足すときは、直す前の実装で実際に落ちることを確認する。**

`e2e/design.mjs` は API を `page.route` で丸ごと差し替えるので、mirakc も実チューナーも
DB も要らない。時刻も固定してあり、ショットの差分は実装の差分だけになる。

## ダークは実行時にはまだ到達できない

`.dark` を付ける手段（切り替え UI も `prefers-color-scheme` の同期も）が
アプリ側に無い。ダーク側のトークンは**定義してあり、`e2e/design.mjs` が
`.dark` を直接付けて撮っている**が、利用者がこの見た目に到達する経路はまだ無い。
到達手段を入れるかどうか（自動追従にするか切り替えを持つか）は未決。

## 経緯と失敗事例

- 頻度 3 段の「端」を overflow メニューで実装する形、および `dropdown-menu.tsx`
  の導入は M5-4（issue #227）。それまでルールの削除は編集フォームのフッタに
  保存・キャンセルと同格の `destructive` ボタンとして置かれていた
- `index.css` は長らく shadcn neutral の既定（全色 chroma 0、`--radius: 0.625rem`）
  のままだった。M1 の UI が意図的に素だった（[issue #22](https://github.com/fetburner/rokuban/issues/22)）
  ことの残り
- ダークの `--sidebar-primary` だけが shadcn 既定で青（`oklch(0.488 0.243 264.376)`）
  だった。誰も参照していなかったので気付かれていない
- `e2e/design.mjs` の最初の版は `getComputedStyle()` の戻り値を `rgb(...)` だと
  思って正規表現で読んでいた。**トークンが oklch なので Chromium は計算値も
  `oklch(0.56 0.215 27)` のまま返す**（canvas の `fillStyle` も同じ）ため、
  すべての判定が「色が読めない = null」で素通りした。1px 塗って `getImageData` で
  実画素を採る形に直してある
- コントラストを「文字 / **地**」で測って AA を満たしたことにしていた。実際に
  文字が乗るのは `bg-warning/10` のような淡い地の上で、そこでは 4.22 しか無かった。
  半透明を合成してから測る形にしたうえで、琥珀を一段暗くしている
- **その「合成してから測る」を入れた直後の版でも、当の琥珀バッジでは効いていなかった。**
  淡い地を持つのは外側の span、文字を持つのは内側の span で、locator が内側だけを
  掴んでいたため背景が透明になり、合成が恒等関数になっていた。**琥珀を暗くした修正を
  revert しても判定は緑のまま通った。** いまは「祖先を遡って最初に不透明な面に
  当たるまで重ねる」形にし、掴んだ要素の背景が透明なら（＝合成が効いていないなら）
  そのこと自体で落とす。**判定を足したことと、それが効いていることは別**
- 放送中の番組の時刻をタリーレッドにしていた。ダークで 4.17（塗りの上のカードなら
  3.71）まで落ちるうえ、チャンネル数ぶんの行が同時に赤くなって信号として機能して
  いなかった。色をやめて太さにし、赤は塗りと線だけに限った
- 容量超過の帯の罫線は、置き換え前も後もライトで地に対して 3:1 を割っていた
  （旧 1.51 / 置き換え直後 2.67）。判定を足して初めて分かった --- 見た目の印象では
  「淡い着色に留める」が守られているようにしか見えない
- ON AIR の走査線を最初に足したとき、輝線を `color-mix(in oklch, var(--tally)
  60%, var(--sumi) 40%)` で作っていた。**oklch の補間は色相を極座標の最短弧で
  結ぶ**ため、タリー（27°）から墨（286°）へ補間すると短い方の弧（27° →
  346.6°）を通り、結果がマゼンタ寄り（実測 `oklch(0.42 0.1314 346.554)`、
  `design.mjs` の `isRed()` に掛けると `r-b=33` で「タリーレッドでない」判定）
  になっていた。**「色は信号のみ」が固定した信号色のどれでもない、5 つ目の
  色相**が生まれていたことになる。CSS Color 4 の相対カラー構文
  （`oklch(from var(--tally) calc(l * ...) c h)`）で明度だけを操作する形に
  直した。**濃さを変えるときに墨・紙白のような別トークンと混ぜる手は、色相を
  持つ信号色（タリー・琥珀）には使えない** --- 混ぜてよいのは無彩同士のときだけ
- 走査線のコントラスト判定は最初、`background-color`（縞の片側。輝線は
  `background-image` に直接書いてあり `getComputedStyle` では読めない）だけを
  測り、それを「縞の暗い側 = 最悪ケース」と決め打っていた。**輝線を文字と
  同じ色にする変異**（グリフの半分が地に溶ける）を入れても `pnpm test` /
  `e2e:design` は全部緑のまま通った。加えて「暗い側が不利」という決め打ち
  自体もダークの空状態と ON AIR では偽だった（字が明るいテーマでは、明るい側
  の縞が不利になる）。縞の 2 色を `--scan-gap` / `--scan-lit` というカスタム
  プロパティに出し、`background-image` 側の色も `getComputedStyle` から読める
  形にしたうえで、**どちらが不利かを決め打たず両方を実測して両方に下限を
  掛ける**形に直した
- **予約一覧のチューナー不足バッジの色判定が、issue #233（バッジ自身が `<span>`
  から番組表への `Link`（`<a>`）に変わった変更）以降ずっと赤（exit 1）のまま
  だった。** 判定は `ul span` で淡い地を持つ「外側」を掴む前提のままで、外側が
  `<a>` になったことに追随していなかった --- `.filter({ hasText })` が `<a>`
  の子である 2 つの `<span>`（sr-only の文・見える側のラベル）しか拾えず、
  `label`（掴んだ要素の子孫を探す）が常に空になって `fg === null` で
  `ng.push(...)` していた。**「判定が赤いことに誰も気付かず数マイルストーン
  放置されていた」こと自体が失敗事例** --- `e2e/design.mjs` はローカル専用
  （CI に無い）ため、実際に手元で走らせて exit code を見るところまでやらないと
  この種の drift は検出できない。M8-3（issue #242）の実装確認で実際に
  `pnpm e2e:design` を走らせて見つけた（`ul a` に直して修正）
