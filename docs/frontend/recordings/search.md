## 録画検索は `/recordings` に同居する

録画の検索は録画一覧そのものの絞り込みなので、専用の別画面は作らず録画一覧に同居させる。EPG の番組検索とは条件モデルを共有せず、相互に流用する導線も作らない。

EPGStation にある「録画済みの検索」に対応する機能だが、EPG 検索の `/search`（[search.md](../search.md)）のような独立ルートは作らない。`/search` を独立ルートにした理由（「番組表は EPG を時間軸で眺める画面、検索は ruler と同じ条件コンパイラを叩く別の問いの画面」）は、録画には当てはまらない。録画一覧に検索専用の別画面を作ると、絞り込み結果と一覧が別画面になる。その結果、「絞り込んだ録画をそのまま操作（削除・復元・エンコード追加）する」という主用途が 2 画面に分裂する。

**`/search` と条件モデルを共有しない。** EPG 検索・ルール条件と、録画一覧 API（`GET /api/recordings`）の絞り込みは別のクエリである。フィールドの意味も重ならない。録画検索の状態と出自は録画の観測・出自で、`/search` にはそもそも無い次元である。あちらの条件をこちらに持ってくる導線（相互流用）も作らない。両者は別の問いに答えているためである。

<details><summary>根拠</summary>

- 条件モデルが別: `ProgramSearchRequest`、`internal/rulequery`、`GET /api/recordings`
- 録画検索にだけある次元: `status`、`source`

</details>

### 検索欄へ移るショートカット

録画一覧・シリーズ一覧・EPG 検索の各画面では、入力欄の外でキーを押すと検索欄へ移る。入力欄・テキストエリア・編集可能領域と IME 変換中は、文字入力を優先する。

押すキーは `/` で、対象は `/recordings`・`/series`・`/search` である。`/search` では最初のテキスト条件へ移る。

画面の移動はサイドバーで足りるため、`g` に続く頭文字は増やさない。覚える必要があり、一覧（`?`）も併せて作り保守する必要がある。

<details><summary>根拠</summary>

- ショートカットの実ブラウザ判定: `web/e2e/search-shortcut.mjs`

</details>

### 条件は URL に持つ。`lib/recording-search.ts` に純関数として集約する

絞り込み条件は URL に持ち、URL の検証・API クエリへの変換・条件チップの生成を純関数に集約する。チャンネルはサービスの合成 id で選び、site は別のクエリとして URL と API に載せる。

EPG 検索の下書きを扱うファイルとは、意図的に分離している。条件モデルを共有しないので、変換ロジックを共有する理由も無い。

<details><summary>根拠</summary>

- 集約する型と検証: `RecordingsPageSearch`（型）、`parseRecordingsSearch`（`validateSearch`）
- 集約する変換: `buildListRecordingsParams`（API クエリへの変換）
- 集約する条件チップ: `describeRecordingsFilters`（適用中の条件チップ）、`clearRecordingsFilters`
- 分離している EPG 検索の下書き: `lib/program-search.ts`

</details>

#### チャンネルと site

チャンネルはサービスの合成 id で選び、site は別のクエリとして URL と API に載せる。site をチャンネルの識別に混ぜない。

サービス番号は network をまたいで一意でないが、合成 id なら BS 101 と CS 101 を独立に選択・解除できる。**site を識別に混ぜると、「高松の録画を全部」がチャンネルの列挙でしか表せなくなる。** チャンネルの軸だけが、他の軸と違う意味論（3 つ組の選言）にもなる。条件は軸内が OR、軸間が AND である。

<details><summary>根拠</summary>

- チャンネルの識別と site の載せ方: `Service.id`、`?site=`
- 番号が network をまたいで一意でない: `serviceId`
- 他の軸と意味論が違う軸: `service`

</details>

#### ルールの絞り込み

ルールは絞り込みパネルから選び、選んだルールを URL と録画一覧 API に渡す。ルールが 1 件以上あるか URL でルールが決まっているときだけ節を出し、ルールが決まっているときは出自の手動と帰属なしを選べず、矛盾する URL もパース時に落とす。

候補は一覧の順に並べる。ルール名は一意でないので、同名の候補だけ `#<id>` を添える。適用中のチップは一覧から名前を解決し、`ルール: <名前>` と表示する。他のチップと同じく軸名を前置する。

一覧で名前を解決できないときは `ルール #N` と表示する。ルールを削除しても URL の値は残るので、選択欄にはその値を一時的な候補として足す。一覧に無い値だからと先頭の「問わない」へ戻さない。

ルールの節は、ルールが 1 件以上あるか、URL でルールが決まっているときだけ出す。新規インストールでルールが 0 件なら節ごと出さない。サイト節と同じ「機能しないコントロールは置かない」規律である。

ルールが決まっているときは、出自の「手動」「帰属なし」を選べないようにする。どのルールかが分かれば出自をさらに問う必要はなく、常に 0 件になる組み合わせを選べるまま残すより、条件を設定したのに 0 件になる理由を探させない方が明確だからである。出自が「ルール」は矛盾しないので選べる。

**矛盾するルールと手動の組み合わせは、URL のパース時点でも落とす。** パネルだけで塞ぐと、手編集や古い共有 URL では条件が残り、種別チップが active のまま disabled になる。

<details><summary>根拠</summary>

- 一覧名の解決と削除後の URL: `rules.name`、`recordings.rule_id`、`ON DELETE SET NULL`
- 削除後も残る URL: `?ruleId=N`
- URL/API の受け渡し: `ruleId`、`GET /api/recordings`、`source='rule'`、`source=manual`
- 矛盾条件の排除: `parseRecordingsSearch`、`updateRuleFilter`

</details>

#### サイトの絞り込みと site の表示

サイトの絞り込みと、録画行・詳細の site 表示は、関係する site が 2 件以上のときだけ出す。絞り込みの選択肢は、レジストリと現在の絞り込みの和集合から作り、レジストリから消えた site も解除できるようにする。

絞り込みの選択肢は、サイトのレジストリと、現在の URL の絞り込みにある site の和集合から作る。レジストリから消えた site が絞り込みに残っていても、見えて解除できるようにするためで、`/search` のサイトチップと同じ判定規律に揃える。**節自体は選択肢が 2 件以上のときだけ出す。** 単一サイト構成で "default" だけの節が常に表示されるのを避けるためである。

録画行と詳細の site は、サイトレジストリと録画が持つ site の和集合が 2 件以上のときに表示する。レジストリから消えた site の録画でも、拠点を識別できるようにするためである。録画一覧では無限スクロールで別 site の行を後から読み込んだ場合、既存行にも site が表示される。

<details><summary>根拠</summary>

- 選択肢の元になる URL の絞り込み: `?site=`

</details>

#### UI に出さない条件とチップの数え方

チャンネル種別と検索対象は UI に出さない。キーワードはチップにしない。配列の条件は値ごとに、スカラーの条件は次元ごとに 1 チップにする。

**チャンネル種別は UI に出さない。** 個々のサービスを選べるチャンネル選択の方が細かく絞れるので、種別だけの選択肢を並列に置く理由が無い。検索対象の指定も、UI 案に無い次元で、出しても検証できないコントロールを増やすだけなので出さない（「機能しないコントロールは置かない」の逆になる）。API のパラメータ自体は残るので、共有 URL に手で `qTarget=title` を足す使い方は塞がない。

キーワードはチップにしない。検索欄自体が値を表示しているので、消すのは入力欄の編集で足りる。配列の条件（ジャンル・チャンネル）は値ごとに 1 チップにして、個別に外せるようにする。スカラーの条件（状態・種別・期間・ルール）は次元ごとに 1 チップにする。期間のチップは md 未満でだけ出す（次節）。

<details><summary>根拠</summary>

- UI に出さない次元: `channelType`、`qTarget`
- 個々のサービスを選べるチャンネル選択: `<ChannelPicker>`（`Service.id`）
- 残る API パラメータ: `ListRecordingsParams`

</details>

### ツールバーと期間

ツールバーは検索・期間・絞り込み・並び順を 1 行に並べる。期間は録画を探す主な軸なので、絞り込みパネルの中に置かず、独立した操作にする。期間の区切りは、ブラウザのタイムゾーンによらず日本時間で明示して計算する。

ツールバーは `[検索][期間][絞り込み][並び順]` の 1 行にする。md 以上の 3 つは、今の選択をボタンに出す pop-up button（HIG）にする。期間のボタンは「2026 夏」「今週」、並び順は「新しい順」を出す。並び順は透明に重ねたネイティブの `<select>` が操作を受け、見た目だけを期間・絞り込みと揃える。

#### 期間の区切りと表示

期間の区切りは日本時間で明示して計算し、日付の終了日はその日を含める。期間のボタンとチップは、同じ関数で表示する。

クールの境目は放送の暦で決まり、ブラウザのタイムゾーンでは変わらない。クールは 1/4/7/10 月 1 日 0:00 JST から次の期の始まりまでである。URL と API の意味（`from` 以上・`to` 未満）は変えない。

**日付の終了日はその日を含む。** 6/30 を入れると `to` は 7/1 0:00 JST になる。「この時刻未満」を入力させると、6/30 まで含めたいときに 7/1 と打たせることになるためである。

期間のボタンとチップは、同じ表示関数で表示する。1 クールちょうどならその名前、上段の選択肢と一致すればその名前、それ以外は「8/10〜8/16」（終わりは含む最終日）にする。2 つの関数を持つと片方だけが直る。今年でない端には年を、0:00 JST でない端（古い共有 URL）には時刻を添え、表示から範囲を読み違えさせない。期間のチップは md 未満でだけ出す。md 以上はボタンが中身を表示しているので、二重になる。

上段とクールは押すと閉じ、日付は閉じない。上段とクールは 1 回の選択で範囲が決まる。日付は開始と終了の 2 欄を続けて入れるので、1 欄目で閉じると開き直させることになる。

週は月曜に始まる（ISO 8601 / JIS X 0301）。日曜始まりにすると、土曜と日曜の深夜帯が別の週に割れる。今週・今月は終わりを開く（`to` なし）ので、放送中・これからの録画も入り続ける。まだ始まっていない期は、録画が 1 件も無いことが確定しているので押せない。

検索・ルールの期間とは、部品も変換も共有しない。あちらは未来の番組の条件で、ルールでは `periodStartAt` / `periodEndAt` として保存される。「終了日を含む」をそちらへ波及させると、既存ルールの解釈が変わる。

<details><summary>根拠</summary>

- 日本時間での区切りの計算: `lib/recording-period.ts`
- ボタンとチップで共有する表示関数: `periodLabel`
- 共有しない検索・ルールの期間の部品: `condition-fields.tsx`

</details>

#### md 未満のツールバーとシート

md 未満では、検索欄と枠なしのアイコンボタン 3 つを 1 行に並べ、期間と絞り込みを下から出るシートで開く。md 以上は従来のポップオーバーを使う。

並び順まで文字で出すと 360〜430px で 2 行に折り返し、録画への到達が 1 行ぶん遠くなる。条件がかかっているボタンには右上に点を付ける。並び順は既定（先頭の選択肢）から外れているときに同じ点を付ける。アイコンからは今の並びが読めないが、「既定と違う」が分かれば押して確かめられる。期間・絞り込みのような別の印を、並び順だけに作らない。

シートは HIG の「狭い画面ではポップオーバーを避け、シートで出す」に従う。中身はシート内でスクロールさせる。シートとポップオーバーの切り替えは、1 つの部品にした。呼び出し元の期間と絞り込みは、どちらも「ツールバーのパネルを狭い幅でどう出すか」で変わるからである。

録画詳細の再生設定・チャプター一覧のシートとは共有しない。あちらは動画に重なるメニューで、プレイヤーの都合で変わる。角丸・セーフエリア・つまみの見た目だけを揃える。つまみは見た目だけで、引き下げて閉じる操作は持たない（再生設定のシートと同じ）。

<details><summary>根拠</summary>

- 並び順の既定: `options[0]`
- シートとポップオーバーを切り替える部品: `components/toolbar-panel.tsx`、`ToolbarPanel`
- 共有しない再生設定・チャプター一覧のシート: `popoverClass`

</details>

#### チャンネルとジャンルの選び方

絞り込みシートでは、チャンネルを同じシート内の一覧へ進んで選ぶ。ジャンルも同じく、md 未満ではシート内の別画面へ進み、絞り込みパネル（md 以上）ではチェック付きメニューに畳む。シートは重ねず、同時に表示するのは 1 枚だけにする。

絞り込みシートの「チャンネル　すべて ›」は、同じシート内でチャンネル一覧へ進める。見出し左の「‹ 絞り込み」で戻る。シートを重ねる案は採らない。複数シートの同時表示になり、HIG の「一度に表示するシートは 1 枚だけ」に反するためである。その場で展開する案も採らない。選択中のチャンネルが 0 局になった状態を破棄して全局へ戻す契機が無いためである。戻る操作で一覧を閉じることで、階層の移動と全局へ戻す判断を同じ操作にする。

番組表のように親の絞り込みシートが無い画面では、チャンネル選択自体を独立したシートで出す。`md` 以上は従来どおりポップオーバーにする。

ジャンルは選択肢が多いため、絞り込みパネルではチェック付きメニューに畳む。トリガーはチャンネル選択と同じ構造（節見出しの下に値だけを出し、シェブロンは値の直後）で、値は選択件数にする。選んだ名前はパネル外の「適用中」チップに出す。`md` 未満ではチャンネルと同じく、絞り込みシート内でジャンルの画面へ進む。判定基準は 1280×800・2 site の fixture で、絞り込みパネルとジャンルメニュー（通常候補のみ）がどちらも中でスクロールしないことである。実ブラウザで判定する。

大分類 12・13 は予備で、14 は番組付属情報の枠なので、通常の選択肢には出さない。URL や保存済みルールで指定されているコードは候補に残し、チップと選択状態に表示して外せるようにする。検索・ルール条件欄も候補を共有する。同じ条件を指定したまま解除できる必要があるためである。

<details><summary>根拠</summary>

- ジャンルメニューのスクロール判定: `web/e2e/recordings-rule-filter.mjs`

</details>

### シリーズ一覧も同じ条件を使う

シリーズ一覧は、録画一覧と同じ条件・同じ絞り込み UI を使う。条件の意味が同じなので新しい条件モデルは作らず、ごみ箱・並び順・エンコード状況の条件だけを落とす。

URL のパースは、録画一覧のパース結果から、棚が受けない次元を落とす形にする。落とすのはごみ箱・並び順・エンコード状況である。エンコード状況は録画 × ジョブの行で絞るので、棚の件数が膨らむ。作品を探す軸でもない。並び順は画面ごとに軸が違うので、絞り込み UI の外から子要素として渡す。

「録画 / シリーズ」の切り替えは、両方向で条件を引き継ぐ。シリーズへは棚が受けない次元を落として渡し、録画へはそのまま渡す（シリーズ側の条件は録画側の部分集合）。

<details><summary>根拠</summary>

- 共有する絞り込み UI: `RecordingFilters`
- シリーズ側のパースと次元の削除: `parseSeriesSearch`、`parseRecordingsSearch`、`toSeriesSearch`
- 落とす次元: `tab`、`order`、`encodeState`
- 子要素として渡す: `children`

</details>

### ごみ箱タブと検索条件は直交させる

タブ（ライブラリ / ごみ箱）は検索条件と直交する別の軸だが、リロードや共有で同じ表示を復元するため URL に持つ。

URL では `?tab=trash` で持ち、既定のライブラリは URL に書かない。履歴を汚さず共有 URL を短く保つためである。

録画一覧のページは、タブからごみ箱かどうかを導き、API クエリへの変換には検索条件とは別の引数で渡す。タブ切替は、検索条件を保持したまま履歴を置き換えて移動する。

<details><summary>根拠</summary>

- タブの導出と別引数での受け渡し: `pages/recordings.tsx`、`trash`、`buildListRecordingsParams`
- 履歴を置き換える移動: `replace`

</details>

## 一括操作は録画だけを編集モードで出す

一括操作は録画に限る。見終わった録画をごみ箱へ移すことと、ごみ箱からの復元・完全削除だけを、ヘッダー右端の「選択」から入る編集モードで行う。予約の一括取消は持たず、専用 API も作らず、既存の 1 件 API を並列に送る。

単一世帯で必要な一括操作は、この 2 つに限る。ルール変更後に不要になった予約は ruler が再評価で自動的に引っ込めるため、予約一覧の一括取消は持たない。手動予約とルール予約では取消・Undo の intent も異なり、同じ選択バーへ載せると操作の逆が一意に決まらない。

### 録画行の右クリックメニュー

細いポインタの通常表示では、録画行全体を右クリックの対象にして、独自のメニューを出す。選択モードと粗いポインタでは、独自メニューを出さない。

行全体を対象にするのは、全面リンクの外だけを対象にすると行を組み直す必要があるためである。メニュー先頭に「開く」「新しいタブで開く」「リンクをコピー」を置く。Shift+右クリックはブラウザのメニューへ渡す。選択モードと粗いポインタでは独自メニューを出さず、選択バーとタッチ端末のリンク操作を保つ。ごみ箱送りは、詳細画面と同じ Undo 付きトーストを使う。

### 編集モードの選択操作

一括操作は破壊的で頻度が低いため、常時 checkbox を並べず、ヘッダー右端の「選択」から編集モードへ入る。編集モード中だけ checkbox を描画し、全面行リンクを外して行クリックも選択トグルにする。

キーボード操作は次の通り。

- 一覧は 1 つの Tab 位置にし、↑ / ↓ で行を移る。Space で現在行を切り替える。
- Shift+↑ / ↓ と Shift+クリックは起点から現在行までを範囲選択にする。Finder と同じく、範囲は動かすたびに置き換わり、戻れば縮む。範囲外で個別に選んだ行は残す。
- 選択モードに入った後のレイアウトで、sticky ヘッダーの下端から固定選択バーの上端までに収まる最初の行を現在行と範囲の起点にする。checkbox でカードが伸びた後に対象を決めるので、選択バーの裏に隠れない。先頭行固定では、画面外へフォーカスが飛び最初の ↓ や Space が見えない行に作用する。
- 行ごとに Tab を止めず、矢印で移動できるようにする。checkbox は状態表示に残すが Tab 順から外し、Tab は DOM 順で次の要素へ進める。
- Cmd+A / Ctrl+A は読み込み済みの行だけを選び、Shift+Cmd+A / Shift+Ctrl+A は選択を解除する。Shift+Cmd+A が Mac Chrome のタブ検索に届くかは未検証なので、固定バーにも解除ボタンを置く。
- Esc で選択モードを終了する。選択モード外と入力欄では Cmd+A / Ctrl+A をブラウザの文字選択に任せる。

<details><summary>根拠</summary>

- 編集モードへ入る入口: `PageHeader`

</details>

### 選択バーと一括送信

一括操作の専用 API は作らず、既存の 1 件 API を選択した全件に並列で送る。

選択バーは「n 件を選択中」と表示し、全選択は「読み込み済みの n 件を選択」と明記する。無限スクロールでまだ取得していない録画は対象にしない。

並列送信は、全件の結果を待つ形で行う。成功分だけ一覧から外し、失敗分は選択したまま API の本文を error toast に出す。ごみ箱送りの toast は成功件数だけを数え、Undo は成功 ID だけを同じ方法で並列復元する。ごみ箱の完全削除は、選択件数を示す確認ダイアログで確認してから送信する。

<details><summary>根拠</summary>

- 全件の並列送信: `Promise.allSettled`
- 完全削除の確認: `AlertDialog`

</details>

### debounce と URL 同期で履歴を汚さない

キーワード入力は debounce を挟んでから、URL の条件に確定する。URL の書き込みは、キーワードもチップの個別解除も、常に履歴を置き換える形で行う。

1 文字ごと・操作ごとに URL を書き換えて、履歴を汚さないためである。絞り込み UI 自体は状態を持たず、debounce 用の下書きだけを例外とする。

<details><summary>根拠</summary>

- キーワード入力の debounce: `components/recording-filters.tsx`、`KeywordField`
- 状態を持たない絞り込み UI: `RecordingFilters`
- 履歴を置き換える書き込み: `replace`、`pages/recordings.tsx`

</details>

### TanStack Router の `validateSearch` は無効な値を「省略」しても消えない

検証関数が無効な値を戻り値から省略しても、元の値は消えない。無効な次元を落とすときは、キーを省略せず undefined を明示代入する。

録画検索の検証関数は、既定の非 strict モードで使われる。このモードでは、検証関数の戻り値を未検証の検索値に重ねる。実際のルートマッチと、リンク生成時の軽量マッチのどちらでもこの合成になる。戻り値からキーを省略すると、生の値が上書きされず残る。壊れた URL の `?status=bogus` がチップに出ることを実機で確認済みである。`undefined` を明示代入すれば、合成後の値を上書きできる。

`/live` の `service` と `/search` の `ruleId` も、この形に揃えてある。ルートの検索値を直接見るテストが固定している。

<details><summary>根拠</summary>

- 録画検索の検証関数: `parseRecordingsSearch`
- 未検証の検索値: `location.search`
- 通常のルートマッチの合成: `@tanstack/router-core` の `router.js`、`matchRoutesInternal`、`preMatchSearch`、`parentSearch`
- 実際の合成式: `preMatchSearch = { ...parentSearch, ...strictSearch }`
- リンク生成時の軽量マッチ: `matchRoutesLightweight`、`accumulatedSearch`、`Object.assign(accumulatedSearch, validateSearch(...))`
- 不正な値を上書きする形: `{ ...x, k: undefined }`
- 揃えてあるルートの定義と固定するテスト（`router.state.matches` の `search` を直接見る）: `routes.tsx`、`routes.test.tsx`

</details>

### 一覧は自前で組んだ `useInfiniteQuery`

録画一覧の無限クエリは自前で組む。生成されるのは単発のクエリだけで、無限クエリのフックが無いためである。キーは同じ条件のページを積むために、絞り込みと件数で作り、ページカーソルは含めない。

orval が生成するのは単発の `useQuery` ラッパーなので、録画一覧関数を自前の無限クエリに渡す。キーは同じ条件のページを積むためのもので、カーソルを含めるとページごとに別クエリになる。キーの先頭は `'/api/recordings'` のままにし、一覧の invalidate に前方一致を使える形にする。

進行方向の読み込み（番兵 + IntersectionObserver、失敗後はボタンへ落とす）は、番組一覧と同じ部品を再利用する。計測できない環境の判定にも、既存の判定関数を使う。録画一覧はグリッドのような座標系を持たないリストなので、仮想化はしていない。`limit` は API の既定と同じ値を明示して渡し、カーソルで継ぎ足す。

<details><summary>根拠</summary>

- 生成された一覧関数と query key: `listRecordings`、`getListRecordingsQueryKey`
- 無限クエリのライブラリ: `@tanstack/react-query`、`useInfiniteQuery`、`useQuery`
- クエリキーの構成: `queryKey`
- ページカーソルは query key に入れない: `before` / `beforeId`
- 前方一致で一覧を invalidate する: `RecordingActions`、`invalidateQueries({ queryKey: ['/api/recordings'] })`
- 再利用する部品: `pages/programs.tsx`、`lib/auto-load.ts`、`shouldAutoLoadNextPage`、`shouldShowLoadMoreButton`
- 計測できない環境の判定: `lib/list-virtualization.ts`、`domLayoutMeasurable`
- 明示して渡す件数: `pages/recordings.tsx`、`pageSize`

</details>

### 0 件の文言は条件の有無で分ける

録画一覧に「未検索」の状態は無いが、0 件の文言は条件の有無で分ける。条件があるときは「条件に一致する録画がありません」と条件をクリアする導線を出し、無いときだけ「録画がありません」と出す。取り違えると「まだ何も録れていない」と誤読させる。

ごみ箱タブでは、条件が無いときの文言を「ごみ箱は空です」にする。条件ゼロは全件が正しい状態なので、`/search` の「未検索と 0 件を別状態にする」規律は、ここには持ち込まない。

空状態の部品は `<div>` で包み、`<p>` は使わない。条件クリアのボタンを子に持つ呼び出し側があるためである。`<p>` の中にブロック要素（`<div>` / 別の `<p>`）を置くと無効な HTML になり、React が hydration エラーの警告を出す。

<details><summary>根拠</summary>

- 空状態の部品: `components/page.tsx`、`EmptyState`

</details>
