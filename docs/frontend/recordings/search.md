## 録画検索は `/recordings` に同居する

`/recordings`・`/series`・`/search` では、入力欄の外で `/` を押すと検索欄へ移る。入力欄・テキストエリア・編集可能領域と IME 変換中は文字入力を優先する。 `/search` では最初のテキスト条件へ移る（`web/e2e/search-shortcut.mjs`）。

画面の移動はサイドバーで足りるため、`g` に続く頭文字は増やさない。覚える必要があり、一覧（`?`）も併せて作り保守する必要がある。

EPGStation にある「録画済みの検索」に対応する機能だが、`/search`（EPG 検索。[search.md](../search.md)）とは**別ルートにしない**。録画検索は録画一覧そのものの絞り込みである。`/search` を独立ルートにした理由（「番組表は EPG を時間軸で眺める画面、検索は ruler と同じ条件コンパイラを叩く別の問いの画面」）は、録画には当てはまらない。録画一覧に検索専用の別画面を作ると、絞り込み結果と一覧が別画面になる。その結果、「絞り込んだ録画をそのまま操作（削除・復元・エンコード追加）する」という主用途が 2 画面に分裂する。

**`/search` と条件モデルを共有しない**。`ProgramSearchRequest`（`internal/rulequery` を通る EPG 検索・ルール条件）と `GET /api/recordings` の絞り込みは別のクエリである。フィールドの意味も重ならない。録画検索の `status` / `source` は録画の観測・出自で、 `/search` にはそもそも無い次元である。あちらの条件をこちらに持ってくる導線（相互流用）も作らない --- 両者は別の問いに答えている。

### 条件は URL に持つ。`lib/recording-search.ts` に純関数として集約する

`RecordingsPageSearch`（型）・`parseRecordingsSearch`（`validateSearch`）・`buildListRecordingsParams`（→ API クエリ）はすべてここに置く。`describeRecordingsFilters`（→ 適用中の条件チップ）・`clearRecordingsFilters` も同様である。`lib/program-search.ts`（`/search` の下書き）とは意図的に分離している --- 条件モデルを共有しないので、変換ロジックを共有する理由も無い。

- **チャンネルは `Service.id` で、site は `?site=` で URL と API に載せる。**`serviceId` は network をまたいで一意でないが、合成 id なら BS 101 と CS 101 を独立に選択・解除できる。**site を identity に混ぜない** --- 混ぜると「高松の録画を全部」がチャンネルの列挙でしか表せず、`service` だけが他の軸と違う意味論（3 つ組の選言）になる。軸内は OR、軸間は AND
- **ルールは絞り込みパネルから選ぶ。** 候補は一覧の順に並べ、選んだ `ruleId` を URL と録画一覧 API に渡す。`rules.name` は一意でないため、同名の候補だけ `#<id>` を添える。適用中のチップは一覧から名前を解決し、`ルール: <名前>` と表示する。他のチップと同じく軸名を前置する。
- **一覧で名前を解決できないときは `ルール #N` と表示する。** ルール削除後も `?ruleId=N` の URL は残るため、選択欄にはその値を一時的な候補として足す。一覧に無い値で先頭の「問わない」へ戻さない。
- ルール節はルールが 1 件以上あるか、`ruleId` が決まっているときだけ出す。新規インストールでルールが 0 件なら節ごと出さない（サイト節と同じ「機能しないコントロールは置かない」規律）。
- `ruleId` が決まっているとき、「手動」「帰属なし」は選べないようにする。どのルールかが分かれば出自をさらに問う必要がなく、常に 0 件になる組み合わせを選べるまま残すより、条件を設定したのに 0 件になる理由を探させない方が明確だからである。`source='rule'` は矛盾しないため選べる。
- **矛盾する `ruleId` と `source=manual` は URL のパース時点でも落とす。** パネルだけで塞ぐと、手編集や古い共有 URL では条件が残り、種別チップが active のまま disabled になる。

- 一覧名の解決と削除後の URL: `rules.name`、`recordings.rule_id`、`ON DELETE SET NULL`
- URL/API の受け渡し: `ruleId`、`GET /api/recordings`、`source='rule'`、`source=manual`
- 矛盾条件の排除: `parseRecordingsSearch`、`updateRuleFilter`

- **サイト絞り込みの選択肢は、レジストリと現在の `?site=` 絞り込みの和集合から作る。** レジストリから消えた site が絞り込みに残っていても見えて解除できるようにするためで、 `/search` のサイトチップと同じ判定規律に揃える。**節自体は選択肢が 2 件以上のときだけ出す** --- 単一サイト構成で "default" だけの節が常に表示されるのを避ける。
- **録画行と詳細の site は、サイトレジストリと録画が持つ site の和集合が 2 件以上のときに表示する。** レジストリから消えた site の録画でも拠点を識別できるようにするためである。録画一覧では無限スクロールで別 site の行を後から読み込んだ場合、既存行にも site が表示される。
- **チャンネル種別（`channelType`）・`qTarget` は UI に出さない**。チャンネルは個々のサービスを選べる `<ChannelPicker>`（`Service.id`）の方が細かく絞れる。種別だけの選択肢を並列に置く理由が無い。`qTarget` も UI 案に無い次元で、出しても検証できないコントロールを増やすだけ（「機能しないコントロールは置かない」の逆）。パラメータ自体は `ListRecordingsParams` に残るので、共有 URL に手で `qTarget=title` を足す使い方は塞がない
- **キーワードはチップにしない。** 検索欄自体が値を表示しているので、消すのは入力欄の編集で足りる。配列条件（ジャンル・チャンネル）は値ごとに 1 チップ（個別に外せる）、スカラー条件（状態・種別・期間・ルール）は次元ごとに 1 チップにする。期間のチップは md 未満でだけ出す（次節）

### ツールバーと期間

ツールバーは `[検索][期間][絞り込み][並び順]` の 1 行にする。期間は録画を探す主な軸なので、絞り込みパネルの中に置かず独立した操作にする。md 以上の 3 つは、今の選択をボタンに出す pop-up button（HIG）にする。期間のボタンは「2026 夏」「今週」、並び順は「新しい順」を出す。並び順は透明に重ねたネイティブの `<select>` が操作を受け、見た目だけを期間・絞り込みと揃える。

- **区切りは日本時間で明示して計算する**（`lib/recording-period.ts`）。クールの境目は放送の暦で決まり、ブラウザのタイムゾーンでは変わらない。クールは 1/4/7/10 月 1 日 0:00 JST から次の期の始まりまで。URL と API の意味（`from` 以上・`to` 未満）は変えない
- **日付の終了日はその日を含む。** 6/30 を入れると `to` は 7/1 0:00 JST になる。「この時刻未満」を入力させると、6/30 まで含めたいときに 7/1 と打たせることになる
- **期間ボタンとチップは同じ `periodLabel` で表示する。** 1 クールちょうどならその名前、上段の選択肢と一致すればその名前、それ以外は「8/10〜8/16」（終わりは含む最終日）。2 つの関数を持つと片方だけが直る。今年でない端には年を、0:00 JST でない端（古い共有 URL）には時刻を添え、表示から範囲を読み違えさせない
- **期間のチップは md 未満でだけ出す。** md 以上はボタンが中身を表示しているので二重になる
- **上段とクールは押すと閉じ、日付は閉じない。** 上段とクールは 1 回の選択で範囲が決まる。日付は開始と終了の 2 欄を続けて入れるので、1 欄目で閉じると開き直させることになる
- **週は月曜に始まる**（ISO 8601 / JIS X 0301）。日曜始まりにすると、土曜と日曜の深夜帯が別の週に割れる
- **今週・今月は終わりを開く**（`to` なし）。放送中・これからの録画も入り続ける
- **まだ始まっていない期は押せない。** 録画が 1 件も無いことが確定している

**検索・ルールの期間（`condition-fields.tsx`）とは部品も変換も共有しない。** あちらは未来の番組の条件で、ルールでは `periodStartAt` / `periodEndAt` として保存される。「終了日を含む」をそちらへ波及させると、既存ルールの解釈が変わる。

**md 未満は検索欄と枠なしのアイコンボタン 3 つ（44×44px）を 1 行に並べる。** 並び順まで文字で出すと 360〜430px で 2 行に折り返し、録画への到達が 1 行ぶん遠くなる。条件がかかっているボタンには右上に点を付ける。並び順は既定（`options[0]`）から外れているときに同じ点を付ける。アイコンからは今の並びが読めないが、「既定と違う」が分かれば押して確かめられる。期間・絞り込みのような別の印を並び順だけに作らない。

**md 未満では期間と絞り込みを下から出るシートで開く**（HIG「狭い画面ではポップオーバーを避け、シートで出す」）。上部につまみ、中央に見出し、右に「完了」を置く。高さは 85dvh まで、中身はシート内でスクロールさせる。md 以上は従来のポップオーバー。シートとポップオーバーの切り替えは `components/toolbar-panel.tsx` の `ToolbarPanel` に 1 つにした。呼び出し元の期間と絞り込みは、どちらも「ツールバーのパネルを狭い幅でどう出すか」で変わるからである。録画詳細の再生設定・チャプター一覧のシート（`popoverClass`）とは共有しない。あちらは動画に重なるメニューで、プレイヤーの都合で変わる。角丸・セーフエリア・つまみの見た目だけを揃える。つまみは見た目だけで、引き下げて閉じる操作は持たない（再生設定のシートと同じ）。

絞り込みシートの「チャンネル　すべて ›」は、同じシート内でチャンネル一覧へ進める。見出し左の「‹ 絞り込み」で戻る。シートを重ねると複数シートの同時表示になり、HIG の「一度に表示するシートは 1 枚だけ」に反する。その場で展開する方式には、選択中のチャンネルが 0 局になった状態を破棄して全局へ戻す契機が無い。戻る操作で一覧を閉じることで、階層の移動と全局へ戻す判断を同じ操作にする。

番組表のように親の絞り込みシートが無い画面では、チャンネル選択自体を独立したシートで出す。`md` 以上は従来どおりポップオーバーにする。

ジャンルは選択肢が多いため、絞り込みパネルではチェック付きメニューに畳む。トリガーはチャンネル選択と同じ構造（節見出しの下に値だけを出し、シェブロンは値の直後）で、値は選択件数にする。選んだ名前はパネル外の「適用中」チップに出す。`md` 未満ではチャンネルと同じく、絞り込みシート内でジャンルの画面へ進む。判定基準は 1280×800・2 site の fixture で、絞り込みパネルとジャンルメニュー（通常候補のみ）がどちらも中でスクロールしないこと。`web/e2e/recordings-rule-filter.mjs` が実ブラウザで判定する。

大分類 12・13 は予備で、14 は番組付属情報の枠なので、通常の選択肢には出さない。URL や保存済みルールで指定されているコードは候補に残し、チップと選択状態に表示して外せるようにする。検索・ルール条件欄も候補を共有する。同じ条件を指定したまま解除できる必要があるためである。

### シリーズ一覧も同じ条件を使う

`/series` は録画一覧と同じ条件・同じ絞り込み UI（`RecordingFilters`）を使う。条件の意味が同じなので、新しい条件モデルを作らない。URL のパースは `parseSeriesSearch` で、`parseRecordingsSearch` の結果から棚が受けない次元を落とす（`toSeriesSearch`）。落とすのはごみ箱（`tab`）・並び順（`order`）・エンコード状況（`encodeState`）である。エンコード状況は録画 × ジョブの行で絞るので、棚の件数が膨らむ。作品を探す軸でもない。並び順は画面ごとに軸が違うので、`RecordingFilters` の外から `children` で渡す。

「録画 / シリーズ」の切り替えは、両方向で条件を引き継ぐ。シリーズへは `toSeriesSearch` を通して渡し、録画へはそのまま渡す（シリーズ側の条件は録画側の部分集合）。

### ごみ箱タブと検索条件は直交させる

タブ（ライブラリ / ごみ箱）は条件と直交する別の軸だが、リロード・共有で同じ表示を復元するため URL の `?tab=trash` に持つ。既定のライブラリは URL に書かない。履歴を汚さず共有 URL を短く保つためである。

`pages/recordings.tsx` は `tab` から `trash` を導き、`buildListRecordingsParams` には検索条件とは別の引数で渡す。タブ切替は検索条件を保持したまま `replace` で navigate する。

## 一括操作は録画だけを編集モードで出す

単一世帯で必要な一括操作は、見終わった録画をごみ箱へ移すことと、ごみ箱からの復元・完全削除に限る。ルール変更後に不要になった予約は ruler が再評価で自動的に引っ込めるため、予約一覧の一括取消は持たない。手動予約とルール予約では取消・Undo の intent も異なり、同じ選択バーへ載せると操作の逆が一意に決まらない。

細いポインタの通常表示では録画行全体を右クリックの対象にする。全面リンクの外だけを対象にすると行を組み直す必要があるため、メニュー先頭に「開く」「新しいタブで開く」「リンクをコピー」を置く。Shift+右クリックはブラウザのメニューへ渡す。選択モードと粗いポインタでは独自メニューを出さず、選択バーとタッチ端末のリンク操作を保つ。ごみ箱送りは詳細画面と同じ Undo 付きトーストを使う。

一括操作は破壊的で頻度が低いため、常時 checkbox を並べず `PageHeader` 右端の「選択」から編集モードへ入る。編集モード中だけ checkbox を描画し、全面行リンクを外して行クリックも選択トグルにする。

- 一覧は `role=listbox` の 1 つの Tab 位置にし、↑ / ↓ で行を移る。Space で現在行を切り替える。
- Shift+↑ / ↓ と Shift+クリックは起点から現在行までを範囲選択にする。Finder と同じく、範囲は動かすたびに置き換わり、戻れば縮む。範囲外で個別に選んだ行は残す。
- 選択モードに入った後のレイアウトで、sticky ヘッダーの下端から固定選択バーの上端までに収まる最初の行を現在行と範囲の起点にする。checkbox でカードが伸びた後に対象を決めるので、選択バーの裏に隠れない。先頭行固定では、画面外へフォーカスが飛び最初の ↓ や Space が見えない行に作用する。
- 行ごとに Tab を止めず、矢印で移動できるようにする。16px checkbox は状態表示に残すが Tab 順から外し、Tab は DOM 順で次の要素へ進める。
- Cmd+A / Ctrl+A は読み込み済みの行だけを選び、Shift+Cmd+A / Shift+Ctrl+A は選択を解除する。Shift+Cmd+A が Mac Chrome のタブ検索に届くかは未検証なので、固定バーにも解除ボタンを置く。
- Esc で選択モードを終了する。選択モード外と入力欄では Cmd+A / Ctrl+A をブラウザの文字選択に任せる。

選択バーは「n 件を選択中」と表示し、全選択は「読み込み済みの n 件を選択」と明記する。無限スクロールでまだ取得していない録画は対象にしない。

一括操作専用 API は作らず、既存の 1 件 API を `Promise.allSettled` で全件に並列送信する。成功分だけ一覧から外し、失敗分は選択したまま API の本文を error toast に出す。ごみ箱送りの toast は成功件数だけを数え、Undo は成功 ID だけを同じ方法で並列復元する。ごみ箱の完全削除は、選択件数を示す `AlertDialog` で確認してから送信する。

### debounce と URL 同期で履歴を汚さない

キーワード入力は 300ms の debounce を挟んでから条件（URL）に確定する（`components/recording-filters.tsx` の `KeywordField`）。`RecordingFilters` 自体は状態を持たず、debounce 用の下書きだけを例外とする。条件の URL への書き込みは、debounce（キーワード）もチップの個別解除も常に `replace` で navigate する（`pages/recordings.tsx`）。1 文字ごと・操作ごとに URL を書き換えて履歴を汚さないためである。

### TanStack Router の `validateSearch` は無効な値を「省略」しても消えない

`parseRecordingsSearch` は既定の非 strict モードで使われる。このモードでは `validateSearch` の戻り値を未検証の `location.search` に重ねる。実際のルートマッチと、リンク生成時の軽量マッチのどちらでもこの合成になる。
- 戻り値からキーを省略すると、生の値が上書きされず残る。壊れた URL の `?status=bogus` がチップに出ることを実機で確認済みである。
- 無効な次元を落とすときはキーを省略せず `undefined` を明示代入する。これで合成後の値を上書きできる。

<details><summary>根拠</summary>

- 通常のルートマッチの合成: `@tanstack/router-core` の `router.js`、`matchRoutesInternal`、`preMatchSearch`、`parentSearch`
- 実際の合成式: `preMatchSearch = { ...parentSearch, ...strictSearch }`
- リンク生成時の軽量マッチ: `matchRoutesLightweight`、`accumulatedSearch`、`Object.assign(accumulatedSearch, validateSearch(...))`
- 不正な値を上書きする形: `{ ...x, k: undefined }`

</details>

`/live` の `service` と `/search` の `ruleId` はどちらもこの形に揃えてある（`routes.tsx`）。`routes.test.tsx` が `router.state.matches` の `search` を直接見て固定している。

### 一覧は自前で組んだ `useInfiniteQuery`

orval が生成するのは単発の `useQuery` ラッパーで、無限クエリのフックは生成しない。そのため録画一覧関数を自前の `useInfiniteQuery` に渡す。`queryKey` は絞り込みと limit で作り、ページカーソルは含めない。同じ条件のページを積むためのキーであり、カーソルを含めるとページごとに別クエリになる。キーの先頭は `'/api/recordings'` のままにし、一覧の invalidate に前方一致を使える形にする。

<details><summary>根拠</summary>

- 生成された一覧関数と query key: `listRecordings`、`getListRecordingsQueryKey`
- 無限クエリのライブラリ: `@tanstack/react-query`、`useInfiniteQuery`
- ページカーソルは query key に入れない: `before` / `beforeId`
- 前方一致で一覧を invalidate する: `RecordingActions`、`invalidateQueries({ queryKey: ['/api/recordings'] })`

</details>

進行方向の読み込み（番兵 + IntersectionObserver、失敗後はボタンへ落とす）は、`pages/programs.tsx` と同じ部品を再利用する。部品は `lib/auto-load.ts` の `shouldAutoLoadNextPage` / `shouldShowLoadMoreButton` である。計測できない環境の判定は `lib/list-virtualization.ts` の `domLayoutMeasurable` を使う。録画一覧はグリッドのような座標系を持たないリストなので仮想化はしていない。`limit` は API の既定と同じ値（`pages/recordings.tsx` の `pageSize`）を明示して渡し、カーソルで継ぎ足す。

### 0 件の文言は条件の有無で分ける

録画一覧に「未検索」の状態は無い（条件ゼロ = 全件が正しい。`/search` の「未検索と 0 件を別状態にする」規律はここには持ち込まない）。ただし 0 件の文言は分ける --- 条件があるとき「条件に一致する録画がありません」+ 条件をクリアする導線、条件が無いときだけ「録画がありません」（ごみ箱タブでは「ごみ箱は空です」）。取り違えると「まだ何も録れていない」と誤読させる。

`components/page.tsx` の `EmptyState` は `<p>` ではなく `<div>` で包む。条件クリアのボタンを子に持つ呼び出し側があるため --- `<p>` の中にブロック要素（`<div>` / 別の `<p>`）を置くと無効な HTML になり、React が hydration エラーの警告を出す。
