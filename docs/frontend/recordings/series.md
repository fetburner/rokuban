## 録画 → ルールの導線

`RecordingDetail` は `recording.ruleId` があるときだけ「ルール」セクションを出す（`ruleId` が無い手動予約由来の録画では**セクションごと出さない** --- 「機能しないコントロールは置かない」の既存規律）。

- **ルール名は一覧のキャッシュから解決する。** 単体取得エンドポイント（`GET /api/rules/{id}` / `useGetRule`）はあるが使わない。`RulesPage` が常に全件の一覧を読む設計に乗り、`/rules` を経由していればキャッシュを使う。まだ一覧を読んでいないときは詳細を開いて取得し、取得中は `#N` から名前へ差し替える。
- 同じ一覧に同名のルールが複数あるときは、名前に `#<id>` を添えて識別する。名前が重複していないときは補助ラベルを付けない。録画の帰属とリンク先はいずれも `ruleId` で決まるため、表示名の一意性制約は置かない。
- **一覧にまだ載っていない `ruleId` は一時的に `#N` と表示する**。ただしこれは「ルールが削除された」ケースではない。ルール削除後は `ON DELETE SET NULL` で `recordings.rule_id` が NULL になり、`Recording.ruleId` は省略される。その結果、「ルール」節も消える。一覧クエリが未解決または失敗している間、または新しいルールが一覧へ届く前だけ `#N` にする。
- ルール名または `#N` を `/search?ruleId=N` へのリンクにする。「このルールの録画で絞る」は `/recordings?ruleId=N` にする。前者は `RuleRow` のルール名リンクと同じ着地先（ルールの実質的な編集画面）へ、後者は同一ページ内の検索条件変更で、`parseRecordingsSearch` を通るので条件チップにもそのまま出る。

<details><summary>根拠</summary>

- 全件一覧をキャッシュし、ルール名を解決する: `useListRules`、`useListRules()`、`GET /api/rules/{id}`、`useGetRule`、`RulesPage`、`rules`
- 削除後はルール節を出さない: `recordings.rule_id` の FK、`ON DELETE SET NULL`、`Recording.ruleId`
- 未解決の `ruleId` は `#N` にする: `rules.find`、`query.data`、`undefined`。
- テスト: `recording-detail.test.tsx`「ルール一覧にまだ載っていない ruleId でも #N 表記に落ちて壊れない」
- ルール検索リンクと条件チップ: `RuleRow`、`parseRecordingsSearch`、`lib/recording-search.ts`

</details>

## シリーズ一覧（シリーズライブラリ）

`/series` は、生きている録画を実効シリーズ単位で眺める入口である。録画一覧のヘッダーにある「録画 / シリーズ」の 2 択からも移動できる。ごみ箱は録画一覧の内側に残し、シリーズ一覧には含めない。

- API の `value` をシリーズ名として大きく表示し、代表録画の生タイトルを補助表示する。`value` が `NULL` の棚は番組ハブを開けないので表示しない
- 再生できる件数（`playableCount`）と最新の放送開始時刻（`latestStartAt`）を表示する。録画中・取り込み待ち・失敗も総件数には含むため、棚の件数と見られる件数は異なりうる
- 代表録画のサムネイルを遅延読み込みし、失敗時はプレースホルダーを出す。カードとリストの切り替えは録画一覧と同じ `rokuban:recordings:view` に保存する
- 初期順は最新順で、件数順・名前順へ画面内で切り替えられる。並び順は URL に載せない
- 絞り込みは録画一覧と同じ条件を URL に持つ（[search.md](search.md) §条件は URL に持つ / §シリーズ一覧も同じ条件を使う）。サーバーはグループ化の前に、条件を録画 1 件ずつに当てる。件数・見られる件数・未視聴・最新の放送・代表は、条件に当たった回だけから出す。当たる回が 0 件の棚は出ない
- 期間は放送時期（番組開始時刻）で、制作時期ではない。再放送は放送した期に入る。放送のシリーズ記述子は地上波でほぼ付かず、元の制作時期は分からないからである
- 未視聴は、絞り込みの外にある録画の視聴済み印も読む。`site` で絞っても、別 site の録画で見た回は既読のままにする
- **キーワードは録画一覧と同じ `q` 1 つに寄せ、棚名専用の文字列絞り込みは置かない。** 同じ画面に意味の違う検索欄が 2 つあると、どちらへ入力するか分からなくなる。`q` は条件とともに URL に載り、表示を切り替えても引き継がれる。
- 自動キーはタイトルから導き、分類ルールの棚にはキーワードがタイトルに含まれる録画だけが入る。そのためタイトルの一部かルールのキーワードで棚を探せる。
- **表示中の棚名をそのまま入力しても見つかるとは限らない。** 棚名は NFKC で正規化する一方、検索語は全角英数字と全角空白だけを畳む。全角記号や半角カナを含む棚名は、タイトルの表記と一致しないことがある（「ラブライブ!スーパースター」と「ラブライブ！スーパースター」）。
- 分類ルールにだけあってタイトルに無い語では見つからない。`q` は説明文にも当たるため、名前を説明で触れただけの録画が別の棚として出ることもある。

<details><summary>根拠</summary>

- 検索語を正規化する実装: `normalize_search_text`
- 棚名の正規化と検索語の正規化の差: NFKC、全角英数字、全角空白、全角記号、半角カナ

</details>

- `label_rules` の `valueKey` と一致するシリーズには「手動」バッジを付ける。分類ルールの作成・編集・削除は、棚一覧の位置を保つため一覧の後ろに置いた `/series` のシリーズ分類セクションに集約する。分類結果が効く画面で管理し、予約を作る録画ルールとは効果の向きが違うことを混同させない
- カード・行全体のリンク先は正規化キーではなく `/recordings/{representativeId}/series`。キーの規則が変わっても番組ハブの宛先を失わない

## シリーズの導線（番組ハブと次のエピソード）

録画から `/recordings/$id/series` を開くと、番組ハブは次の 3 ブロックを出す。シリーズの同一性は [docs/data/series.md](../../data/series.md) §8 が持つ。

- **identity と操作は並び順に依存しない**: 最新録画・最新話・サムネイル・最新日時・「毎回録画中」の判定・「自動: X」は、エピソードの並び順とは別に取った新しい順の 1 ページ目（50 件）から導く。古い順に切り替えても主ボタンは動かない（新しい順の表示中は同じクエリキーなので取得を共有する）。**限界（未検証）**: ルール由来か・「自動: X」の判定はこの 1 ページ目でしか効かず、それより古い回だけがルール由来なら「毎回録画する」が出る。同じ値を指す分類ルールが複数あるとき、キーワードの初期値は評価順（`priority DESC, id ASC`）の先頭で近似する。どのルールが勝つかは録画ごとの当たり判定で決まり、クライアントは持たない
- **identity**: 最新録画のサムネイルと `Recording.series` の実効シリーズを出す。サムネイルの枠は、worker が SAR を補正して生成する画像に合わせた 16:9 とする。比率は録画一覧と同じにする。 `/series` と同じく、対応する `label_rules.value_key` があれば「手動」バッジを付ける。手動棚では読み込み済みエピソードの `Recording.seriesKey`（`recordings.series_key`）を「自動: X（ほか N）」として補助表示する。これは画面に読み込んだ範囲の値だけで、棚全体の統計ではない。`seriesKey` は一覧と詳細の同じ録画行から返し、URL や絞り込みの軸には使わない
- **操作**: 再生できる録画のうち最も新しい回へ「最新話を再生」を置く。録画中や失敗した最新行は飛ばして、再生できる回へリンクする。「続きから」は出さない。エピソードの `ruleId` が現在の録画ルールに解決できれば`ルール「名前」で毎回録画中` から `/search?ruleId=N` へ進む。解決できなければ「毎回録画する」から `/search?cond=...` を開き、名前のキーワードと起点の `networkId/serviceId` を条件に入れる。検索結果を確認してから利用者がルールを作る流れにする
- **エピソード**: `GET /api/recordings?seriesOf=<id>&order=desc|asc` の録画を、録画一覧と共有する `RecordingRow` で出す。録画中・失敗・取り込み待ちの状態はその行のバッジで表示し、古い順／新しい順の切り替えは API の `order` に反映する。「次回」は `GET /api/recordings/{id}/upcoming` から取り、 `(networkId, serviceId, startAt)` で 1 行にまとめて site をチップで出す

overflow の「分類を直す（割る・指定する）」は `/series` と同じ `LabelRuleForm` を開き、棚の軸 `key=series` と現在の実効シリーズを初期値にする。自動キーは題名の NFKC 正規化を通る一方、検索条件の照合には別の正規化があるため、「毎回録画する」で自動キーをそのまま使うと一部の題名を拾えない場合がある。サービス条件は必ず付けるので、同名番組を別チャンネルへ広げない。

ハブの宛先は導出キーではなく録画 id にする。戻るボタンは履歴を使い、直接開いた場合は起点の詳細へ戻る。起点の単体 GET が purge 済みで 404 のときは、一覧と次回に残る行からハブを開き、戻り先を `/recordings` にする。単体 GET の 5xx は purge と見なさずエラーを出す。一覧も次回も空なら、存在しない id と区別できないため「録画が見つかりません」とする。

実ブラウザでは `pnpm e2e:design` がデスクトップと 400px 幅の番組ハブを撮り、3 つの塊の順序、塗りの主ボタンが 1 つであること、overflow メニューの収まりを確認する。

## 番組ハブの宛先と次のエピソード

- **ハブの宛先は録画 id**。`/series/<正規化キー>` や `?series=<値>` にしない --- 規則を変えた時点で 404 ではなく 0 件で黙って壊れる
- **`Recording.series` が null の録画には導線を出さない**（ハブも「次回」も 0 件になる）。`RecordingDetail` はこの 1 条件だけを見て、タイトル行のシリーズ名のリンクと棚を出す
- 「次回」の予約状態は**結合しない**。予約一覧を別に引いて突き合わせるのは番組リストと同じ判断（[api/rest.md](../../api/rest.md)「予約状態は番組と結合しない」）
- クエリキーの先頭は「次回」が `programsQueryKeyPrefix`、一覧が `recordingsQueryKeyPrefix`。**分類ルールを足した直後に開いているハブが SSE で更新される**のは、`recordings` トピックが両方の接頭辞を invalidate するためである（`lib/events.ts`）
- **「次のエピソード」は再生できる行に限る**（`sizeBytes` があるか `encodedAssets` が空でない）。同じシリーズの中で起点より後、`program_start_at` が最も早い回を選ぶ。同じ時刻の候補が複数あれば起点と同じ site を優先し、次に id の小さい方（`lib/series.ts` の `nextEpisode`。詳細パネルが使う。置き場は[detail.md](detail.md) §次のエピソードとシリーズ）。開始時刻がずれて supersede されなかった failed 行を指すと、押した先の再生が 404 になる
- 探索は `?seriesOf=<id>&order=asc&from=<起点の startAt>`。再生できない行が起点の後に 49 件以上続くとページからはみ出し、「次のエピソード」が出ない（既知の限界）。話数は持たないので、重複排除を切ったルールでは再放送が「次」になりうる（既知の限界）
