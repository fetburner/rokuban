> [recordings.md](../recordings.md) のルール・シリーズ導線。索引から辿る

## 録画 → ルールの導線

録画詳細は、録画にルールの帰属があるときだけ「ルール」セクションを出す。ルール名は、全件のルール一覧のキャッシュから解決する。

手動予約由来の録画にはルールの帰属が無いので、セクションごと出さない。「機能しないコントロールは置かない」の既存規律である。

<details><summary>根拠</summary>

- 詳細の画面とルールの帰属: `RecordingDetail`、`recording.ruleId`、`ruleId`

</details>

### ルール名の解決

ルール名は全件の一覧のキャッシュから解決する。単体取得のエンドポイントはあるが使わない。

`GET /api/rules/{id}` はあるが使わない。ルールのページが常に全件の一覧を読む設計に乗り、`/rules` を経由していればキャッシュを使う。まだ一覧を読んでいないときは詳細を開いて取得し、取得中は `#N` から名前へ差し替える。

同じ一覧に同名のルールが複数あるときは、名前に `#<id>` を添えて識別する。名前が重複していないときは補助ラベルを付けない。録画の帰属とリンク先はいずれも `ruleId` で決まるため、表示名の一意性制約は置かない。

<details><summary>根拠</summary>

- 全件一覧をキャッシュし、ルール名を解決する: `useListRules`、`useListRules()`、`rules`、`RulesPage`
- 単体取得を使わない: `useGetRule`
- 録画の帰属とリンク先を決める値: `ruleId`

</details>

### 一覧に未掲載のルールの表示

一覧にまだ載っていないルールの識別子は、一時的に番号だけの形で表示する。一覧クエリが未解決または失敗している間、または新しいルールが一覧へ届く前だけである。

この番号は `#N` の形で出す。

この表示は、ルールが削除されたときのものではない。ルール削除後は、外部キーの `ON DELETE SET NULL` で録画のルール帰属が NULL になり、API はルール識別子を省略する。その結果、「ルール」節も消える。

<details><summary>根拠</summary>

- 削除後はルール節を出さない: `recordings.rule_id` の FK、`ON DELETE SET NULL`、`Recording.ruleId`
- 未解決の識別子を `#N` にする: `rules.find`、`query.data`、`undefined`
- テスト: `recording-detail.test.tsx`「ルール一覧にまだ載っていない ruleId でも #N 表記に落ちて壊れない」

</details>

### 検索へのリンク

ルール名または番号表示は、検索画面のルール絞り込みへのリンクにする。「このルールの録画で絞る」は、録画一覧の条件変更にする。

リンク先は、ルール名または `#N` が `/search?ruleId=N`、「このルールの録画で絞る」が `/recordings?ruleId=N` である。

前者は、ルールの一覧の行にあるルール名リンクと同じ着地先（ルールの実質的な編集画面）へ進む。後者は同一ページ内の検索条件変更で、録画一覧の検索条件の解釈を通るので、条件チップにもそのまま出る。

<details><summary>根拠</summary>

- ルール名リンクの着地先: `RuleRow`
- 検索条件の解釈と条件チップ: `parseRecordingsSearch`、`lib/recording-search.ts`

</details>

## シリーズ一覧（シリーズライブラリ）

シリーズ一覧は、生きている録画を実効シリーズ単位で眺める入口である。録画一覧のヘッダーの「録画 / シリーズ」の 2 択からも移動できる。ごみ箱は録画一覧の内側に残し、シリーズ一覧には含めない。

シリーズ一覧は `/series` で開く。

### 棚の表示

各棚は、シリーズ名・代表録画のサムネイル・再生できる件数・最新の放送開始時刻を出す。カードや行の全体が、代表録画の番組ハブへのリンクである。

API が返すシリーズの値をシリーズ名として大きく表示し、代表録画の生タイトルを補助表示する。値が NULL の棚は番組ハブを開けないので表示しない。

再生できる件数と最新の放送開始時刻を表示する。録画中・取り込み待ち・失敗も総件数には含むため、棚の件数と見られる件数は異なりうる。代表録画のサムネイルは遅延読み込みし、失敗時はプレースホルダーを出す。カードとリストの切り替えは、録画一覧と同じ保存先に保存する。

カード・行全体のリンク先は `/recordings/{representativeId}/series` である。正規化キーは宛先に使わない。キーの規則が変わっても、番組ハブの宛先を失わないためである。

<details><summary>根拠</summary>

- シリーズ名の値と、値が NULL の棚: `value`、`NULL`
- 再生できる件数と最新の放送開始時刻: `playableCount`、`latestStartAt`

</details>

### 並び順と絞り込み

初期順は最新順で、件数順・名前順へ画面内で切り替えられる。並び順は URL に載せない。絞り込みの条件は録画一覧と同じで、URL に持つ。

絞り込みの条件の持ち方は [search.md](search.md) §条件は URL に持つ / §シリーズ一覧も同じ条件を使う にある。サーバーはグループ化の前に、条件を録画 1 件ずつに当てる。件数・見られる件数・未視聴・最新の放送・代表は、条件に当たった回だけから出す。当たる回が 0 件の棚は出ない。

期間は放送時期（番組開始時刻）で、制作時期ではない。再放送は放送した期に入る。放送のシリーズ記述子は地上波でほぼ付かず、元の制作時期は分からないからである。

未視聴は、絞り込みの外にある録画の視聴済み印も読む。サイトで絞っても、別サイトの録画で見た回は既読のままにする。

<details><summary>根拠</summary>

- サイトによる絞り込み: `site`

</details>

### キーワード検索

キーワードは録画一覧と同じ検索語 1 つに寄せ、棚名専用の文字列絞り込みは置かない。同じ画面に意味の違う検索欄が 2 つあると、どちらへ入力するか分からなくなるためである。

検索語は `q` で、条件とともに URL に載り、表示を切り替えても引き継がれる。自動キーはタイトルから導き、分類ルールの棚にはキーワードがタイトルに含まれる録画だけが入る。そのため、タイトルの一部かルールのキーワードで棚を探せる。

表示中の棚名をそのまま入力しても見つかるとは限らない。棚名は NFKC で正規化する一方、検索語は全角英数字と全角空白だけを畳む。全角記号や半角カナを含む棚名は、タイトルの表記と一致しないことがある（「ラブライブ!スーパースター」と「ラブライブ！スーパースター」）。

分類ルールにだけあってタイトルに無い語では見つからない。`q` は説明文にも当たるため、名前を説明で触れただけの録画が別の棚として出ることもある。

<details><summary>根拠</summary>

- 検索語を正規化する実装: `normalize_search_text`
- 棚名の正規化と検索語の正規化の差: NFKC、全角英数字、全角空白、全角記号、半角カナ

</details>

### 分類ルールと手動バッジ

分類ルールの値と一致するシリーズには、「手動」バッジを付ける。分類ルールの作成・編集・削除は、シリーズ一覧の後ろに置いた分類セクションに集約する。

セクションを一覧の後ろに置くのは、棚一覧の位置を保つためである。分類結果が効く画面で管理し、予約を作る録画ルールとは効果の向きが違うことを混同させない。

<details><summary>根拠</summary>

- 分類ルールの値の照合: `label_rules`、`valueKey`

</details>

## シリーズの導線（番組ハブと次のエピソード）

録画から番組ハブを開くと、シリーズの顔・操作・エピソード一覧の 3 つの塊を出す。最新録画や操作の判定は、エピソードの並び順とは別に取った新しい順の 1 ページ目から導く。

番組ハブは `/recordings/$id/series` で開く。シリーズの同一性は [docs/data/series.md](../../data/series.md) §8 が持つ。

### 並び順に依存しない導出

最新録画・最新話・サムネイル・最新日時・「毎回録画中」の判定・「自動: X」は、エピソードの並び順とは別に取った、新しい順の 1 ページ目（50 件）から導く。古い順に切り替えても主ボタンは動かない。

新しい順の表示中は同じクエリキーなので、取得を共有する。

限界（未検証）: ルール由来かどうかと「自動: X」の判定は、この 1 ページ目でしか効かない。それより古い回だけがルール由来なら、「毎回録画する」が出る。

同じ値を指す分類ルールが複数あるとき、キーワードの初期値は評価順（優先度の降順、同点は id の昇順）の先頭で近似する。どのルールが勝つかは録画ごとの当たり判定で決まり、クライアントは持たない。

<details><summary>根拠</summary>

- 評価順: `priority DESC, id ASC`

</details>

### シリーズの顔

最新録画のサムネイルと実効シリーズを出し、対応する分類ルールがあれば「手動」バッジを付ける。

サムネイルの枠は、worker が SAR を補正して生成する画像に合わせた 16:9 とする。比率は録画一覧と同じにする。`/series` と同じく、対応する分類ルールの値があれば「手動」バッジを付ける。

手動棚では、読み込み済みエピソードの自動キーを「自動: X（ほか N）」として補助表示する。これは画面に読み込んだ範囲の値だけで、棚全体の統計ではない。自動キーは一覧と詳細の同じ録画行から返し、URL や絞り込みの軸には使わない。

<details><summary>根拠</summary>

- 実効シリーズ: `Recording.series`
- 分類ルールの値: `label_rules.value_key`
- 自動キー: `Recording.seriesKey`、`seriesKey`、`recordings.series_key`

</details>

### 操作

主ボタンは、再生できる録画のうち最も新しい回への「最新話を再生」である。録画中や失敗した最新行は飛ばして、再生できる回へリンクする。「続きから」は出さない。

エピソードのルールの帰属が現在の録画ルールに解決できれば、`ルール「名前」で毎回録画中` から `/search?ruleId=N` へ進む。解決できなければ「毎回録画する」から `/search?cond=...` を開き、名前のキーワードと起点のネットワーク・サービスを条件に入れる。検索結果を確認してから、利用者がルールを作る流れにする。

<details><summary>根拠</summary>

- 起点のネットワーク・サービス: `networkId/serviceId`
- ルールの帰属: `ruleId`

</details>

### 分類を直す操作

overflow の「分類を直す（割る・指定する）」は、シリーズ一覧と同じ分類ルールのフォームを開き、棚の軸とシリーズを初期値にする。

棚の軸は `key=series`、シリーズは現在の実効シリーズである。自動キーは題名の NFKC 正規化を通る一方、検索条件の照合には別の正規化があるため、「毎回録画する」で自動キーをそのまま使うと一部の題名を拾えない場合がある。サービス条件は必ず付けるので、同名番組を別チャンネルへ広げない。

<details><summary>根拠</summary>

- シリーズ一覧と同じフォーム: `LabelRuleForm`
- 棚の軸の初期値: `key=series`

</details>

### エピソード

エピソードは、シリーズに属する録画を、録画一覧と共有する行の部品で出す。録画中・失敗・取り込み待ちの状態は、その行のバッジで表示する。

録画は `GET /api/recordings?seriesOf=<id>&order=desc|asc` で取る。古い順／新しい順の切り替えは、API の `order` に反映する。「次回」は `GET /api/recordings/{id}/upcoming` から取り、同じ放送の組で 1 行にまとめて、site をチップで出す。

<details><summary>根拠</summary>

- 録画一覧と共有する行の部品: `RecordingRow`
- 次回を 1 行にまとめる組: `(networkId, serviceId, startAt)`

</details>

### 戻り先と purge 済みの起点

ハブの宛先は、導出キーを使わず録画 id にする。戻るボタンは履歴を使い、直接開いた場合は起点の詳細へ戻る。

起点の単体 GET が purge 済みで 404 のときは、一覧と次回に残る行からハブを開き、戻り先を `/recordings` にする。単体 GET の 5xx は purge と見なさずエラーを出す。一覧も次回も空なら、存在しない id と区別できないため「録画が見つかりません」とする。

### 実ブラウザでの確認

実ブラウザでは、デスクトップと 400px 幅の番組ハブを撮り、3 つの塊の順序、塗りの主ボタンが 1 つであること、overflow メニューの収まりを確認する。

実行は `pnpm e2e:design` である。

## 番組ハブの宛先と次のエピソード

番組ハブの宛先は録画の id で決め、シリーズの導出キーは URL に置かない。次のエピソードは、再生できる行の中から、起点より後で最も早く放送された回を選ぶ。

`/series/<正規化キー>` や `?series=<値>` の形にしない。規則を変えた時点で、404 にならず 0 件になって壊れるためである。

シリーズが null の録画には導線を出さない（ハブも「次回」も 0 件になる）。録画詳細はこの 1 条件だけを見て、タイトル行のシリーズ名のリンクと棚を出す。

「次回」の予約状態は結合しない。予約一覧を別に引いて突き合わせるのは番組リストと同じ判断である（[api/rest.md](../../api/rest.md)「予約状態は番組と結合しない」）。

分類ルールを足した直後に、開いているハブが SSE で更新されるのは、録画のトピックが「次回」と一覧の両方のクエリキーの接頭辞を invalidate するためである。

次のエピソードは再生できる行に限る。同じシリーズの中で起点より後、番組開始時刻が最も早い回を選ぶ。同じ時刻の候補が複数あれば起点と同じ site を優先し、次に id の小さい方を選ぶ。詳細パネルがこの選び方を使い、置き場は [detail.md](detail.md) §次のエピソードとシリーズにある。開始時刻がずれて supersede されなかった failed 行を指すと、押した先の再生が 404 になるため、再生できる行に限る。

探索は `?seriesOf=<id>&order=asc&from=<起点の startAt>` で行う。再生できない行が起点の後に 49 件以上続くとページからはみ出し、「次のエピソード」が出ない（既知の限界）。話数は持たないので、重複排除を切ったルールでは再放送が「次」になりうる（既知の限界）。

<details><summary>根拠</summary>

- シリーズが null: `Recording.series`、`RecordingDetail`
- クエリキーの接頭辞: `programsQueryKeyPrefix`、`recordingsQueryKeyPrefix`、`lib/events.ts`、`recordings`
- 再生できる行の条件: `sizeBytes`、`encodedAssets`
- 番組開始時刻: `program_start_at`
- 次のエピソードの選び方: `lib/series.ts` の `nextEpisode`

</details>
