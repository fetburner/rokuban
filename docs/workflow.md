# 開発ワークフロー（タスク分解・docs 保守・並行作業）

CLAUDE.md から退避した規律。**タスク分解・docs の大きな編集・複数エージェントでの並行作業をするときだけ読む。** 通常の実装タスクは CLAUDE.md（と担当サブ issue）だけで足りる。

## タスク分解と issue

**タスク分解を頼まれたら、マイルストーンごとにエピック 1 本 + サブ issue に分ける。** 形式は `.github/ISSUE_TEMPLATE/` の 2 つのテンプレート（`epic` / `sub-issue`）に従う。既存の issue を読んで形式を真似る必要はない。

```console
$ gh issue create --template epic --title 'M5 タスク分解: ...'
$ gh issue create --template sub-issue --title 'M5-1 ...' --label area:worker
```

- **サブ issue は自己完結させる。** 分割の目的は「実装する人が余計な文書を読まずに済むこと」であって、進捗管理ではない。**エピックや他のサブ issue を読まないと実装できないサブ issue は分割が失敗している。** エピックの「着手前の前提」で決めた共通事項は、参照させずに必要な行を転記する
- **「読む文書」は節名まで絞る。** 挙げなかった文書は開かせない。不変条件は番号で参照してよい（CLAUDE.md は毎セッション読まれるため）
- **「触るファイルの目安」を書く。** 並行して進めるときの衝突を防ぐ。`openapi.yaml` を触るタスクは明示する（下記「並行作業」のボトルネック）
- 本文の先頭に `親: #<エピック番号>` を書く。GitHub ネイティブの parent/sub-issue 機能（`gh issue create --parent`）は使わない —— 本文だけ読んでも親が分かれば足りる
- **ラベルは `epic` と `area:*` の 2 系統。** `area:*` は `internal/` のパッケージ境界（複数パッケージにまたがる area は許容する。詳細はテンプレートのコメント参照）に対応させる。現在の一覧は `gh label list` で見る（ここには列挙しない。パッケージ構成が変わるとここが腐るため）。`lane:*`（並行ワークストリーム）は導入しない —— エピックの「段階切り」表とサブ issue の「並列」節で足りている

## ドキュメントと issue の保守

資料マップ・タスクマップ（CLAUDE.md）は**読む量を減らす**ための仕組みで、それが効くのは中身が最新である限りにおいてである。

**実装と同時に更新する。** 実装が docs を追い越したらその PR で直す（別タスクにしない）。古い記述は、古いと分かるまで信じられてしまうぶん、無いより悪い。

**終わったら close する。** 完了したタスク・直したバグはその場で close し、「何がどう解決したか」「どの回帰テストが守っているか」を issue 側に残す。巨大な issue は、残っている項目だけをサブ issue に切り出して親を close する。

**close したものへのポインタを索引に残さない。** 「〜は完了した」「〜は close 済み」という報告を資料マップ・タスクマップ・docs の索引に書くと、**読んだ人がその issue を見に行ってしまう**。索引に載せるのは「これから読む必要があるもの」だけにする。完了の事実は、それが変えたコードと docs 自身が示している。完了済みマイルストーンの手順書・チェックリストの類は残さず削除する（git 履歴が記録になる）。

**足す前に「これを読まないと判断を誤る人がいるか」を問う。** docs も issue も価値は「必要な節だけを 1 回で読めること」であって量ではない。同じことを docs と issue の両方に書かない。

### 残す文章の種類

docs が持つのは**現行の規則と、その「なぜ」**だけである。出自（誰がいつ何を変えたか）は git と GitHub が持っている。docs が代わりに持つべきなのは、次に同じ列・同じ JOIN・同じキューを足そうとしたときに、**まだやりがちな形とそれが壊すもの**だけ。

| 残す（判断の直後に 1〜2 文） | 消す |
|---|---|
| 現行の規則と、その「なぜ」 | issue 番号・タスク番号・マイグレーション番号 |
| **今でも先に浮かぶ案**が壊すもの | 長い戦史（当時の列名・遷移の再現・どの PR が何を移したか） |
| 未解決の穴（本文に「未解決: …」の 1 行） | もう誘惑にならない却下案（今のスタックでは先に浮かばないもの）と、その比較表 |

- **docs に issue 番号・タスク番号・マイグレーション番号を書かない。** 番号を読まないと意味が通らない文は、番号ではなく理由そのものを書き直す。未解決の穴は本文に「未解決: …」とだけ書き、追跡番号は open issue 側に置く。例外は CLAUDE.md のタスクマップだけ —— あれは出自ではなく「これから読む open issue への入口」である
- **末尾に「経緯と失敗事例」節を作らない。** 人間は飛ばせるが、ファイルを丸ごと読む LLM は飛ばせない。残す失敗の形は判断の直後に 1〜2 文で置き、繰り返し出てくる族だけ [invariants.md](invariants.md) に集める。**退避用の `history.md` も作らない** —— 移すと読むコストがファイルごと残るだけで、消したことにならない
- **短くするために、まだやりがちな失敗の形まで落とさない。** 「`effective.skip` が同期を決める」は残す。「当時 `state` 列が…」は消す
- **1 段落に主張を 4 つ以上乗せない。** 表か番号付きの短文に割る
- **正典の再掲は一言 + リンクにする。** 不変条件・site スコープ・レベルトリガー・コミット = DB 行を、各ファイルで半段落ずつ再説明しない

### 分割 doc の形

- 大きい doc は「**索引 + 分割本文**」にする。索引には節 → ファイルの表と「読む順の目安」を置く（型は [docs/recording.md](recording.md)）。**節番号・節名は分割前のまま保つ** —— コード・他 doc からの参照が節名で書かれているため、索引の表から引ければリンクは壊れない
- 分割ファイルの先頭に breadcrumb を 1 行置く（例: `> recording.md §3 の一部。索引から辿る`）
- **仕様が先、理由はその直後。** 各ファイルは「現在の形 → その形である理由（1〜2 文）」の順に書く。理由の中に、まだやりがちな案が壊すものを 1〜2 文で畳み込む。過去の実装・却下案の記述を末尾に溜めない（上記「残す文章の種類」）
- **形（パス・パラメータ・スキーマ・設定キー）の権威は生成元に置き、docs には判断（なぜ）だけを書く。** REST の形は `openapi.yaml`、設定キーの網羅は `config.example.yml`、マイグレーションの一覧は `internal/db/migrations/` が権威。docs に書き写すと片方だけ直って静かにずれる

## 並行作業（複数エージェント）

**契約を先に書いてコミットしてから並列に投げる。** テーブル・クエリ・パッケージ境界・メトリクスを先に固定すれば複数本が競合なしに走る。

- **`openapi.yaml` はボトルネック。** 触るのは 1 本に限定する（description だけの狭い例外は可）
- **クエリファイルは新規に切る。** 既存の `reservations.sql` 等を複数が触ると取り合いになる
- **git が競合と見なさない意味的な競合がある。** `sqlc.embed(r)` が別ブランチで削除した列を含んでいて、行としては衝突しないのでマージは成功し、その後ビルドが落ちた実例がある。テストフィクスチャの生 SQL も同様
- **「触るファイルが重ならない」は並列可の条件として不十分。** 一方が**制約を厳しくする**（NOT NULL / CHECK / 一意索引）側で、他方が**同じ表に行を作る**（テストフィクスチャの生 SQL を含む）側なら、ファイルが重ならなくてもマージ後に落ちる。**片方をマージしてから他方をリベースして CI を通す。**（実例: 制約を厳しくする側と同じ表に行を作る側が、それぞれのブランチで CI 緑・衝突行も無くマージが成功し、main が赤くなった）
- **マージ後に必ず生成物を再生成してフルテストを回す**（`sqlc generate` / `go generate ./internal/api/` / `go test ./...`）。マージが通ったことは何の保証にもならない。再生成漏れ自体は CI の `generated-diff` ジョブが落とすので、ここで手で見るのは**再生成した結果でテストが落ちる**意味的な競合の方
- **ローカルのフルテストが緑でも CI を確認する。** CI にしかない条件（コア数・Postgres の構成・`docker` ジョブ・`-timeout`）が拾う失敗はローカルには出ない。実例: 並行 Export の一貫性テストが 2 コアの CI でだけ「レース窓を踏めなかった」で落ちた（競合ゴルーチンの飢餓。閾値を下げるのではなく、条件を満たすまで回す形に直した）
- エージェントの報告は検証してから信じる。実際に「docs に古い記述がある」という報告が grep すると存在しなかったし、指示範囲外の妥当な修正（分離が生んだ新経路の取りこぼし）を見つけてきたこともある
- **PR を開く前に、別のエージェントに「このテストは何を壊せば落ちるか」だけを見せるパスを 1 回挟む。** レビュー往復 1 回より安い。7 本の PR で数えた必須指摘は、2/3 が「テストが退行を検出しない」か「コメントが測っていないことを断言している」のどちらかで、いずれもこのパスで出る種類だった
