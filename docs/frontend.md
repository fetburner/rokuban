# フロントエンド

## 前提条件

go:embed で単一バイナリに同梱するため、成果物は**静的ファイル一式**である必要がある。SSR サーバーを要求するフレームワーク（Next.js 標準構成、Nuxt SSR、Remix）は自動的に除外される。自宅内 or 認証の内側で動く管理 UI なので SSR の動機（SEO・初回表示）も元々ない。

## 採用スタック

| カテゴリ | 採用技術 |
|---|---|
| ビルド + フレームワーク | Vite + React + TypeScript |
| 状態管理・ルーティング・仮想化 | TanStack Query / Router / Virtual |
| API クライアント生成 | orval（OpenAPI → 型付きクライアント + TanStack Query フック） |
| スタイリング + UI コンポーネント | Tailwind + shadcn/ui |
| 動画再生 | hls.js |

## 決め手

### 1. SSE との組み合わせがバックエンドの思想と対称になる

バックエンドは「NOTIFY はヒント、真実はテーブル再読」のレベルトリガー設計（参照: [data.md](data.md)）。フロントも同じ形にできる:

- SSE イベントは該当クエリの `invalidateQueries` に徹する
- 真実は常に REST から再取得
- SSE の取りこぼしは stale-time 経過後の再取得で自然回復

プッシュデータを信頼して手元状態を書き換える設計（Socket.IO 時代の EPGStation）より壊れ方が大幅に単純になる。

### 2. OpenAPI ファーストとの接続

orval で `useRecordings()` のような型付きフックまで生成物にできる。CI に組み込み、契約の破壊的変更は生成物の差分として検知する（参照: [api.md](api.md) の REST API）。

### 3. 番組表グリッドのエコシステム

番組表グリッドはこのアプリ最大の UI 課題（数十チャンネル x 24 時間の巨大な仮想スクロール面）。TanStack Virtual なり canvas なり、この規模の実装例とライブラリの厚みは React が頭一つ抜けている。

Vue 3 / Svelte 5 でも成立する領域であり、決定打はエコシステムの厚み。

## UI の構造（M1-7 で確定）

### リストを第一級に置く。グリッドはその上に足す

EPGStation はグリッドが主でリストが従なので、モバイルでは常にグリッドの窮屈な
縮小版か単局表示になる。番組表は本質的にデスクトップ形状（2 次元 × 数十チャンネル ×
24 時間）なので、この構造だとモバイル体験が構造的に犠牲になる。

Rokuban は**リストをモバイルの妥協物ではなく第一級のビューとして設計する**。
グリッド（M2）は `lg` 以上でのみ出し、モバイルは常にリストのままにする。

グリッドの価値は「見やすさ」ではなく**同時性を空間に符号化すること**であり、
このドメインでは同時性がチューナー本数というハード制約に直結する
（判定の設計は [data.md](data.md) §6.5 / [issue #21](https://github.com/fetburner/rokuban/issues/21)）。

#### 実装で決めたこと（M2-9）

座標系は `web/src/lib/epg-grid.ts` の純関数（React 非依存）、グリッド本体は
`web/src/components/program-grid.tsx`。

- **セルの高さに下限を設けない。** 5 分番組は 5 分ぶんの高さ（10px）になる。見やすさの
  ために下限を入れると同時性の符号化が崩れ、グリッドの存在理由そのものが失われる
- **仮想化はライブラリを入れず自前。** issue #5 / #24 は TanStack Virtual を名指ししているが、
  縦軸は連続量で番組セルは目盛りをまたぐ「区間」なので、行の並びを前提とする仮想化
  ライブラリの模型に乗らない。可視判定は純関数 2 つ（`visibleTimeWindow` /
  `visibleColumnRange`）に落ちるので、依存を増やすより検証しやすい
- **未計測（DOM 計測が 0）なら全部描く**方向に倒す。jsdom のように計測できない環境で
  「空のグリッドなのにテストが通る」（CLAUDE.md の「非同期の空虚な成功」の変種）を
  構造的に防ぐ
- **出し分けは `matchMedia`（JS）で行い、CSS で隠さない。** グリッドが自前のクエリ
  （全サービス × 24h）と仮想化を持つため。`view` の選択は画面幅で捨てないので、
  狭くするとリストへ倒れ、広げるとグリッドに戻る
- **容量超過の帯は `ProgramGrid` の `overlay` prop で受ける。** 番組セルより上・ヘッダより
  下の「全チャンネル縦断の層」（`pointer-events-none`。帯がクリックを飲むと予約操作が
  壊れる）で、`spanToPx(axis, from, to)` を呼べば番組セルと同じ座標に必ず乗る。
  現在時刻インジケータが最初の利用者
- **グリッドの窓は 24 時間を 1 回で取得**する（リストのような窓の積み上げにしない ---
  積み途中が「番組がない時間帯」と見分けられない）
- **セルの中に操作を置かない。** 選択した番組を既存の `ProgramRow` としてグリッドの上に
  出すので、予約・取消・詳細展開・重なり警告がリストと同一実装になる
- 列は「窓内に番組があるサービス」だけ。順序は種別 → リモコン番号 → serviceId の全順序。
  **サービス取得の失敗はグリッドではエラー扱い**（列が構造なので、列 0 本を
  「番組がない」と区別できない）
- ジャンル色は**補助**。意味の本体は `aria-label` のラベルで、知らないジャンルは
  「その他」に丸めない（ARIB の本物の「その他」= コード 15 と、分類できなかったことを
  区別する）。色は Tailwind 標準パレットの 50 / 950 に限定し、未知は既存トークンへ戻す

**未検証**: 「全サービス × 24 時間でスクロールが落ちない」は jsdom で計測できないため
実ブラウザで確認していない（縦横とも間引く実装は入っている）。受け入れは実機で行う。
セル間の矢印キー移動も未実装（グリッド領域の focus とスクロールまで）。
リストでは重なりが見えないため、グリッドとは別に画面幅に依存しない伝達手段が必要
（後述「容量超過は番組ではなく区間に描く」）。

### ナビゲーション: モバイル = ボトムタブ / デスクトップ = サイドバー

ルート定義は 1 つで、レイアウトのみブレークポイントで切り替える。

ボトムタブは画面下端に密着させず `env(safe-area-inset-bottom)` + 最低 8px を空ける。

- **iOS のホームインジケータ**と重なると最下段が押せない。実害が大きい
- **Android のジェスチャーナビ**は下端からの上スワイプがホームなので、
  スクロール中に指が滑ると誤爆する

`index.html` の viewport に `viewport-fit=cover` が必要（無いと `env()` が 0 になる）。
高さは `--bottom-nav-height` として CSS 変数に持ち、本文の下パディングと共有する。

**ブラウザのビューポートはシステムナビゲーションバーの下には入らない**ので、
Web ページのボトムバーが Android の戻る/ホームボタンと重なることはない。
懸念は上記 2 点だけで、いずれもパディングで解決する。

### M2 のグリッドで横スワイプによるナビゲーションを使わない

Android のジェスチャーナビは左右端からの横スワイプが「戻る」なので、
グリッドの横パンと確実に喧嘩する。

### 番組リスト: 時間順フラット + 日付・サービス絞り込み

- 「今」起点の時間順フラットリスト。sticky 日付ヘッダで日付境界を示す
- **日付チップ**（今 + 8 日分）で先の日付へ跳べる。無限スクロールだけだと
  8 日先に到達するのに「さらに読み込む」を 30 回押すことになる
- **サービスチップ**は時間窓内に番組があるサービスだけ出す
  （[issue #17](https://github.com/fetburner/rokuban/issues/17) の S3）。
  マルチ編成のないサブサービスは番組を持たないので自動的に消える
- sticky な小見出しの `top` はハードコードしない。`PageHeader` が
  `ResizeObserver` で実測して `--page-header-height` を親要素に書き出す
  （フィルタ行の増減や文字サイズでずれる）

### 段階的開示

行は「時刻 / タイトル / サービス」だけ。説明の続きと出演者・映像音声属性は
展開時に `GET /api/programs/{id}` で取る（[api.md](api.md) の「EPG の読み取り」）。

### 予約はワンタップ + トーストから取消

確認ダイアログを挟まない。M1 は全予約が manual（overrides のみ）なので確認する
内容が実質ない。誤タップは 2 つの手段で緩和する。

- 予約ボタンは行右端の固定幅に置き、行本体（詳細展開）のタップ領域と分離する。
  最小 44px を確保する
- 実行直後にトーストで「予約しました [取消]」を出す。確認より速く、かつ取り返しがつく

**楽観的更新はしない。** SSE と REST 再取得で確定させる（レベルトリガー）。
操作中の行だけを pending にする（mutation の `isPending` を全行に渡すと、
1 件予約する間にリスト全行のボタンが無効化される）。

### 予約詳細は base / overrides を 1 画面に統一する

`base`（ruler が書く）と `overrides`（api が書く）は同形の jsonb なので、
ルール由来予約と手動予約を同じ画面で扱える。EPGStation は編集画面が分裂しているが、
その形を最初から避ける。

**機能しないコントロールは置かない。** `encodeProfiles` / `keepOriginal` は
エンコード worker と削除エンジンが M3 なので、値の表示のみでマイルストーンを併記する。
M1 では全体が読み取り専用（reconciler が予約オプションの差分を反映しないため、
編集できても mirakc に伝わらない。[issue #19](https://github.com/fetburner/rokuban/issues/19)）。

### 容量超過は番組ではなく区間に描く（M2）

チューナー不足の表示は**番組への着色ではなく区間の帯**にする。番組を着色すると「この番組が負ける」という勝敗の主張になるが、決めるのは mirakc であり、Rokuban から見えない消費者（EPGStation の並走・ライブ視聴・EPG 収集）がいるので予測できない。判定と根拠は [データ層](data.md) §6.5。

- **グリッド（`lg` 以上）**: 超過区間を全チャンネル縦断の帯で着色する。区間は結合済みで返るので描く帯は少ない
- **リスト・予約一覧・モバイル**: 同じ文言のバッジ。グリッドが出ないモバイルでも情報が届く（画面幅に依存しない伝達手段が別に必要、という #21 の要件）
- **文言は「この予約は競合しています」ではなく「この時間帯はチューナーが不足しています」。** 主張できるのは下界（超過している）だけで、収まることは保証できない。不足本数と詰まった種別まで出せるので「BS が 1 本不足」と具体的に書く

### ドロップ統計はバッジ + 展開

録画一覧に drop / error / scrambled を色付きバッジで出す。**0 のものは出さない**ので
正常な録画ではバッジが 1 つも出ない。PID 別内訳は行を展開して見せ、
モバイルで表を横スクロールさせない。

M2-13 で展開表に**種別**列が付いた（映像 / 音声 / PAT 等）。PID 数値だけの統計では
「映像が壊れたのか EIT が数回落ちただけか」を区別できず運用判断に使えないため
（[録画エンジン](recording.md) §1「例外の境界」）。分類できなかった PID は
種別を空にして PID 数値だけ出す — 分類の失敗で統計そのものを隠さない。

### 予約が録られない理由を出す（M2-6）

`skip` が立っている予約はバッジで示し、重複排除の判定根拠があれば
「重複（録画 #id, 類似度 0.83）」まで出す。**これが M2-6 の受け入れ条件**である
（[録画エンジン](recording.md) §3.1「なぜスキップされたかを説明可能にする」）。

`skip` は列ではなく `base` + `overrides` + `program_intents.action` からの導出値なので、
API が解決済みの boolean を返す（クライアントで jsonb を合成させない）。
`action = 'record'` が重複判定に勝ったケースでは根拠を残したまま `skip = false` になるため、
「重複と判定したが録る」と表示できる。

### 生成クライアントの型を実行時の事実に合わせる

orval は OpenAPI に書いたエラーレスポンスも含めた `{status, data}` の判別可能
union を生成するが、`customInstance` は非 2xx で throw するのでフックの `data` に
届くのは常に成功バリアント。この差を `api/unwrap.ts` の 1 箇所で埋める
（status を実行時に確かめてから絞り込む）。

エラーレスポンスを OpenAPI から消して型を単純化する道は採らない。エラーの形は
契約の一部であり、生成物の差分で破壊的変更を検知したい。

**エラーの本文も UI まで運ぶ**（M2-11）。`customInstance` は非 2xx で throw するが、
当初は本文を捨てていた。`ApiError`（status + body）と `apiErrorMessage`（`unwrap` と
対になる失敗側の半分）を置き、**400 を黙って 0 件にしない**。典型は不正な正規表現
（Postgres の ARE をサーバーが検証して 400 を返す）で、メッセージを見せないと
ユーザーは「書き方が悪いのか該当なしなのか」を区別できない。

### 検索は独立ルート `/search`（M2-11）

番組表は EPG を時間軸で眺める画面、検索は **ruler と同じ条件コンパイラ
（`internal/rulequery`）を叩く「ルールの条件を試す画面」**で、関心事が違う。
「検索 API と ruler 経路の programId 集合が一致する」ことは M2-2 のテストで
担保されているので、ここで当たりを確認してからルールにできる。

- **未検索と 0 件を構造的に別の状態として扱う**（`isIdle` と `success && 空`）。
  文言が入れ替わらないようにする
- 結果は **programId 昇順**（API の契約）で時刻順ではないため、番組表のような
  sticky 日付ヘッダは使わず行に日時を出す
- **「問わない」次元はリクエストのキーごと落とす**（`null` を明示しない）。
  不変条件 10（意味を持たない行を作らない）の精神をリクエストにも適用する
- **フォームで止めるのは「送るとサーバーが壊れる」ものと「黙って嘘の絞り込みに
  なる」ものだけ。** 矛盾した範囲（下限 > 上限）は 0 件が正しい答えなので検証しない。
  曜日ビットが 0 のときだけ止めるのは、`rulequery` が範囲外エラーを返し API が
  400 に変換しないため 500 になるという実装上の理由
- **サイトの選択肢は置かない。** サイトレジストリを返す API が無く現状単一サイトなので、
  置いても意味のある選択ができない（「機能しないコントロールは置かない」）
- ジャンルの未知コード（12 / 13 の予備）は数値のまま出す。「その他」に丸めると
  ARIB の本物の「その他」（15）と区別できない（`lib/genre.ts` と同じ規律）

### 容量超過の帯とバッジ（M2-10 の UI）

`web/src/lib/capacity.ts` に交差判定と文言の純関数、`components/capacity-band.tsx` が
グリッドの `overlay` に渡る帯、`components/capacity-shortfall-badge.tsx` が予約一覧の
バッジ。座標は必ず `spanToPx` を通す（番組セルと同じ関数を通すことが「帯とセルが
同じ時刻で同じ位置に来る」ことの保証）。

- **肯定的な文言を一切持たない。** 「競合なし」「収まります」は出さない。区間が
  返らないときは何も言わない（沈黙は保証ではない。[データ層](data.md) §6.5）
- **複数区間に跨る予約では種別を合併せず、最も不足の大きい区間を採る。** 合併すると
  「どの区間でも成り立っていない主張」になる
- 見える文言は短く（「チューナー不足（BS が 1 本）」）、読み上げ用の文を `sr-only` に
  置いて見える側を `aria-hidden` にする（二重読みを避ける）
- 鮮度は SSE の `reservations` トピックと予約 mutation 後の invalidate に相乗りさせる
  （容量超過は予約集合の導出値なので専用トピックを作らない）
- **交差判定は予約自身の `site` と突き合わせる。** `Reservation` は `site` を返す
  （当初返していなかったため UI に単一サイト前提の定数を置いていたが、`#24` の
  レビューで API に足した）。クライアントに定数を持たせないのは、他サイトの不足を
  自分の不足として出す形で静かに壊れるのを避けるため。フィクスチャが全部 `default`
  だと定数を書いた実装でもテストが通ってしまうので、**`default` 以外のサイトの予約に
  自サイトの不足を当てるケース**を置いてある
- **skip / orphaned の予約にもバッジが出る。** サーバーの需要計算はこれらを除外して
  いる（= その予約は超過の原因ではない）ので、区間の性質としては真だが因果の誤読を
  招きうる。フィルタするかは未決

### ファビコンは白黒テレビに映る「イ」

高柳健次郎が 1926 年にブラウン管へ映した日本初のテレビ映像が「イ」だった
（いろは順の最初の文字。ABC の A に相当）。プロダクト名とは関係しないが、
放送そのものの起点を指す図像として使う。

構図は[元画像](https://dndi.jp/20-tani/images/09110901.jpg)に寄せる。

- **白地に黒**。被写体は雲母板に墨で書いた文字なので、画面が明るく字が暗い
- **枠は黒い四角だけ**。ダイヤルやスピーカーグリルは入れない
- **走査線を縞として描く**。元画像は輝線の間隔が広く、縞に見える

字形は Noto Sans JP Black。元画像の毛筆の字体を再現しようとしたが、筆の形を
自作すると細部（入筆の押さえ、二画目の運筆）が原典から外れる。既存の書体を
使う方が確実。

**明朝は使えない。**「イ」の二画目は止めだが、明朝は縦画が下へ向かって細り
末端が尖る。ゴシックは縦画が等幅で末端が平らに止まる。Black を選んだのは
16px での可読性で、Bold では縦画が灰色に沈む。

### 走査線は 3 値で描く（白黒 2 値だと字が消える）

輝線と間隙を白黒 1:1 にして黒い字を乗せると、**字が間隙と融合して読めなくなる**。
元画像がそう見えないのは、字の上を走査線が暗く通っていて字自体が中間の灰だから。

そこで灰の割り当て先を入れ替える。**輝線 = 白、間隙 = 灰、字 = 黒**の 3 値にすると、
字がどの階調とも衝突せずに読める。元画像（輝線 = 白、間隙 = 暗、字 = 灰）の
階調構成を保ったまま、小さいサイズで効く方に灰を移した形。

走査領域の境界は偶数座標に取り、周期 2（輝線 1 + 間隙 1）にする。32px 描画では
輝線が 1px で画素境界に乗る。16px では 0.5px になって縞は溶けるが、
明るい画面として残るので字は読める。

### ファビコンはスクリプトで生成する

`<text>` を使わずパスで持つ。ファビコンの SVG はレンダリング環境のフォントに
依存するため、文字要素だと字形と太さがプラットフォームで揃わない。ヒラギノは
Apple のプラットフォームにしか無い。

`web/scripts/gen-favicon.mjs` が枠・走査線・字形の配置を組んで
`public/favicon.svg` を吐く。字形はフォントをラスタライズして potrace で
トレースした輪郭を定数で持っており、再生成の手順はスクリプト先頭のコメントにある。
`favicon.svg` は生成物なので直接編集しない。

**輪郭を同梱するので、書体は再配布が許諾されているものから選ぶ。** Noto Sans JP は
SIL OFL 1.1（Copyright 2014-2021 Adobe）で、著作権表示を生成される SVG の
コメントに入れている。ヒラギノで作った版もあったが、Apple のシステムフォントには
輪郭を同梱する権利がないため使えない。

依存全体のライセンス表示は別途必要
（[issue #22](https://github.com/fetburner/rokuban/issues/22) の論点 5）。

ラスタ版（`favicon.ico` / `apple-touch-icon.png`）は npm 依存にない外部ツール
（rsvg-convert / ImageMagick）で作るため自動化していない。

フォールバックも置く。`rel="icon"` の SVG は Safari 16 未満で無視されるので
`favicon.ico`（16/32）を `alternate icon` として併記し、
`apple-touch-icon.png`（180）も置く。PWA は入れないが iOS の
「ホーム画面に追加」はマニフェストなしでも使われ、指定がないと画面の
スクリーンショットが使われてしまう。

`public/` に置いたファイルは Vite が `dist/` 直下に出すので、go:embed 経路と
S3 経路の両方に自動で乗る。

### `<html lang>` は ja

UI が日本語なので `lang="en"` のままにしない。ブラウザのフォント選択と
禁則処理・行分割の挙動が変わる。

### PWA は入れない（M1 時点）

ホーム画面追加は魅力的だが、go:embed と S3+CDN の immutable / no-cache 規約に
service worker を足すと配信経路の話が複雑になる。得るものと釣り合わない。

## リアルタイム通知 --- SSE + invalidateQueries パターン

mirakc と同じ「接続時に現在状態を再送し、以降差分」という設計に揃える。クライアントの再接続処理が対称的になる。

### アーキテクチャ上の利点

- SSE (`/api/events`) を配るのは api ではなく **notifier ロール**（issue #24 M2-19）。notifier を複数レプリカにしても、各レプリカが Postgres の NOTIFY を購読して配るだけなので **Redis アダプタのような追加基盤は不要**
- notifier をロールとして分けたことで、api は SSE という長寿命接続を持たなくなり、サーバーレス（scale-to-zero）に本当に載せられるようになった（[overview.md](overview.md)）
- レベルトリガーにより、SSE 接続断中の変更も stale-time 経過後の REST 再取得で自然回復する

通信設計の詳細は [api.md](api.md) を参照。

## アセット配信 --- go:embed / S3+CDN 両対応

同一の `dist/` を (a) go:embed で同梱、(b) S3 バケットに同期、の両方に使う。フロントのコードとビルドは両モードで完全に同一。

### 両立のための規約

| 規約 | 詳細 |
|---|---|
| SPA フォールバック | 両モードで用意。Go 側は catch-all、S3 側は CloudFront Function rewrite 等 |
| API パス | 常に相対パス `/api/*` を叩く。S3 配信時は CDN のパスベースルーティングで `/api/*` をバックエンド origin へ振り分ける（CORS 不要、実行時コンフィグ注入不要） |
| SSE の振り分け | `/api/events` だけは `/api/*` の中でも例外で、**api（scale-to-zero）ではなく notifier（常駐）へ**ルーティングする。CDN のパスルーティングで最長一致的に `/api/events` を先に notifier origin へ、残りの `/api/*` を api origin へ振り分ける。タイムアウト・キャッシュ無効化の設定も必要。CDN を迂回して notifier に直接繋ぐ選択肢も残す |
| キャッシュ規約 | ハッシュ付きアセット（`assets/*`）は `Cache-Control: immutable`、**それ以外はすべて no-cache**。go:embed モードでも同じヘッダを付けて挙動を揃える |
| 後方互換 | UI と API のデプロイタイミングはずれ得るため API は後方互換を保つ。破壊的変更は OpenAPI 生成クライアントの差分として CI で検知 |

### ハッシュを持たないファイルに no-cache を付け忘れない

`index.html` だけでなく `public/` 由来のファイル（`favicon.svg` / `favicon.ico` /
`apple-touch-icon.png`）もハッシュを持たない。内容が変わってもパスが変わらないので、
キャッシュ指定を落とすと差し替えが伝わらない。

埋め込んだ FS の `ModTime` はゼロ値なので `http.ServeContent` は `Last-Modified`
も `ETag` も出せない。`Cache-Control` がなければ検証子もないので、ブラウザの
ヒューリスティックキャッシュに委ねることになる。**ファビコンを差し替えたのに
古いものが出続ける**形で効く。

そのため `assets/*` 以外は一律 no-cache にする。

### 配信経路の整理

go:embed 配信でハッシュ付きアセット immutable + それ以外 no-cache のヘッダーを正しく付ければ十分。本気の配信最適化は S3+CDN 経路の仕事であり、ここに nginx キャッシュを挟むと配信経路が 3 つになるため行わない（参照: [api.md](api.md) のメディア配信）。

## ライブ視聴 --- EPGStation 水準のシンプルな UI

リッチな視聴体験（ハードウェアトランスコード、低遅延、コメント連携）は KonomiTV が既に高水準で解決しており、そこに張り合わない。同じ mirakc を共有すれば KonomiTV との共存も可能（チューナーは優先度調停で録画が勝つ）。

Rokuban 自体のライブ視聴は「チャンネル一覧から選んでブラウザ再生、画質切り替え程度」で良い。

### 実装方式

- **mirakc `/api/services/{id}/stream` → ffmpeg → HLS** の薄いパイプ。セグメントはローカルスクラッチに書き、api が配信
- `streamer` ロールが担当。リアルタイムに mirakc からの帯域を張り続けるため、分散モードではエッジ寄りに配置する（エンコードジョブと違いレイテンシ・帯域制約がある）

### セッション管理

- **ライブ視聴セッションは意図的に in-memory**。落ちたらクライアント再接続で済む使い捨て状態であり、「すべての状態を Postgres に」の原則の明示的な例外（参照: [overview.md](overview.md) の crash-only 設計原則）
- 「クライアントがいなくなったら ffmpeg を止める」idle GC が必要。セグメント要求がアプリを通ることで last-access の更新がタダで手に入る（参照: [api.md](api.md) のライブ HLS 配信）
