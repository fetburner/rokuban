### 録画中の temp を読む方式の測定

録画中のファイルへの追記は、別ノードから見えるまで最大で約 55 秒かかった。start_time を引いて換算した相対 seek（以下、補正相対 seek）は、実録画の原本で ±1 frame に収まった。製品の seek 引数は、クラスタの原本を含むすべての入力と起動位置で 0 frame だった。

古い音声 PES は、先頭の音声 PES だけが映像より古い PTS を持つ原本である。PTS wrap は、PTS が 33 bit で折り返す原本である。

エピックの方式では、録画中の番組は ingest が追記している temp を FFmpeg の入力にし、セグメントを録画時刻上の固定格子にそろえる。現行の追っかけ再生は、[playback.md](playback.md) の「録画中の追っかけ再生」のとおり mirakc を Range で読む方式のままである。測定から決めた終わらせ方は、[playback.md](playback.md) の「伸びる temp の終わらせ方」にある。この節は、合成入力での先行測定と、実クラスタ（運用中の media PVC、FFmpeg 7.1.5）での測定をまとめる。

合成入力の先行測定では、FFmpeg 9.0.2 を使った。合成入力は 160×90・25 fps・MPEG-2・GOP 2 秒（50 frame）・B-frame なしである。出力は libx264 の lossless にし、出力セグメントの先頭フレームを入力のフレームと framehash で照合した。入力の種類と回数は各表に書く。

#### 時間軸を録画時刻の格子にそろえる引数

起動位置が違っても、セグメント n の出力 PTS が n·D+C（C は全起動で同じ定数）になる引数を決めた。入力は format の start_time を基準にした相対の seek に pre-roll を付けて読み、フレームの選別と PTS の付け替えをフィルタで行う。この seek を補正相対 seek と呼ぶ。

製品の `SegmentManager` は、この式ではなく後述の「製品の seek 引数の測定」の引数を使う。この節の式は、時刻の基準を比べるための測定である。

記号は次のとおりである。V は映像の最初の PTS、S は format の start_time で、どちらも `ffprobe` で読んで 90 kHz の整数にする。k は起動するセグメント番号、D はセグメントの秒、P は pre-roll の秒である。例の P90 は P を 90 kHz の整数にした値である。

```sh
# V90 = 映像の最初の PTS、S90 = format の start_time、P90 = pre-roll（0.5 秒なら 45000）。いずれも秒 × 90000 の整数
T90=$((V90 + k*D*90000)); K90=$((k*D*90000))
SS=$(awk -v t=$((T90 - P90 - S90)) 'BEGIN{printf "%.6f", t/90000}')
ffmpeg -copyts -ss "$SS" -i "$INPUT" -map 0:v:0 -an -fps_mode passthrough \
  -vf "select=gte(pts\,$T90),setpts=PTS-$T90+$K90" \
  -c:v libx264 -preset ultrafast -qp 0 -pix_fmt yuv420p \
  -g 50 -keyint_min 50 -sc_threshold 0 -bf 0 \
  -force_key_frames "expr:gte(t,$((k*D))+n_forced*$D)" \
  -f hls -hls_time $D -hls_list_size 0 -start_number $k -hls_flags temp_file \
  -hls_segment_filename 'seg%03d.ts' index.m3u8
```

判定は 2 つである。出力セグメントの先頭フレームは `ffmpeg -i seg -map 0:v:0 -f framehash -hash md5 -` の最初の行を、入力全体の同じ出力の何行目かに照合する。出力 PTS は `ffprobe -select_streams v:0 -show_packets -show_entries packet=pts` の最初の値を使う。

引数ごとの理由は次のとおりである。

- `-copyts` を付けて、フィルタの式を入力の PTS だけで決める。出力の PTS が入力の start_time の扱いに左右されなくなる
- フレームの選別は `trim` ではなく `select` で行う。`trim` は T を含む 1 フレームを残すので、29.97 fps の実録画では T より 555 tick（約 6 ms）早いフレームが先頭に来た
- `-seek_timestamp 1` は使わない。format の start_time が 0 でない入力では、次の「相対 seek と絶対 seek の比較」のとおり出力が空になった

この 2 つの理由を、29.97 fps の放送 TS（後述の A / B）で測り直した。offset 10.36 秒、P=2 秒、n=0〜6、各 1 回で、基準は 90 kHz の framehash、FFmpeg は 9.0.2 である。φ は、最初の復号 frame が V から数えた 3003 tick の格子からずれている tick 数で、放送 TS は φ=0 である。V を s tick 引いて φ=s を作った。

| 式（A / B） | φ=0 | φ=609 | φ=1500 |
|---|---|---|---|
| 補正相対 + `select` | 全て 0 | n=5,6 が +1 | 全て 0 |
| 補正相対 + `trim=start=T` | `select` と同じ | `select` と同じ | `select` と同じ |
| `-copyts -seek_timestamp 1` の絶対 seek | 出力が空 | 出力が空 | 出力が空 |
| 同 + `-noaccurate_seek` | +12 / +6 frame | n=5,6 が +13 / +7、他は +12 / +6 | +13 / +7 frame |

`trim` は `select` と同じ誤差で、T より 555 tick 早い frame は再現しなかった。再現しなかった理由は特定していない。当時の入力は手元の実録画 2 本で、今回の放送 TS とは入力も条件も同じではない。絶対 seek は、`-noaccurate_seek` が無いと出力が空（0 segment、exit 0）になり、再現した。付けると出力は出るが、フィルタも pre-roll も無いので先頭 frame は keyframe に着地して大きくずれる。製品はこの seek に `trim` を足して使うので、製品の結果は後述の節にある。

合成入力 3 種で、k=3 と k=5 の 2 回ずつ変換した結果は次のとおりである。P は 2 秒、`-copyts` ありで、各行 1 回の測定である。

| 入力 | format の start_time / V | 起動 k | 出力セグメント n | 先頭フレームの誤差 | 出力 PTS − n·D |
|---|---|---:|---|---:|---:|
| 古い音声 PES（映像を 5,400 秒進め、別音声を 0 秒に置く） | 0 / 5,400.010022 秒 | 3 | 3〜14（12 本） | 全て 0 frame | 全て 1.400 秒 |
| 同上 | 同上 | 5 | 5〜14（10 本） | 全て 0 frame | 全て 1.400 秒 |
| PTS wrap（映像のみ、PTS が 2^33 をまたぐ） | −13.717689 / −13.717689 秒 | 3 | 3〜14（12 本） | 全て 0 frame | 全て 1.400 秒 |
| 同上 | 同上 | 5 | 5〜14（10 本） | 全て 0 frame | 全て 1.400 秒 |
| 50,000 秒（映像のみ、PTS が 2^32 tick を超える） | 50,000 / 50,000 秒 | 3 | 3〜14（12 本） | 全て 0 frame | 全て 1.400 秒 |
| 同上 | 同上 | 5 | 5〜14（10 本） | 全て 0 frame | 全て 1.400 秒 |

3 種とも、k=3 と k=5 の両方が出した n=5〜14 の出力 PTS は一致した。C は 1.400 秒だった。1.400 秒になる理由は調べていないが、入力と起動位置によらず同じだった。

29.97 fps の実録画では、frame 周期が 2 秒の格子に割り切れないので、出力 PTS − n·D は frame 周期（約 33 ms）に収まる範囲で動く。手元の実録画 2 本（後述）の先頭 420 frame を、320×180 の通常画質で同じ引数に通した。k=3 と k=5 の重なる n=5〜9 の出力 PTS は一致し、n·D との差は 1.406〜1.422 秒で、n が 1 増えるごとに 2 ms 増えた。実録画では出力セグメントの内容の照合までは行っていない。

#### pre-roll の長さ

pre-roll P は入力の GOP の長さ以上にする。seek は要求位置の後ろの keyframe に着くことがあり、その keyframe が T より後ろだと、先頭フレームが格子から外れる。

外れても FFmpeg はエラーにせず、別のフレームから出力する。GOP が 3 秒（75 frame）の合成入力で、古い音声 PES と PTS wrap の 2 種を各 1 回変換した結果は次のとおりである。2 種の結果は同じだった。誤差は先頭セグメントの先頭フレームで、全セグメントが 0 frame になったものを 0 と書く。

| P | k=1 | k=2 | k=4 |
|---:|---:|---:|---:|
| 0 秒 | +25 frame | +50 frame | +25 frame |
| 1 秒 | +25 frame | 0 | +25 frame |
| 2 秒 | 0 | 0 | 0 |
| 3 秒 | 0 | 0 | 0 |

GOP 2 秒の合成入力では、格子の位置がすべて keyframe なので、P=0 でも 0 frame になった。P=0 が通るのは、この偶然によるものである。実録画 2 本では、k=3 と k=5 の先頭フレームを入力の先頭フレームと照合した。P=0 は 4 回とも外れ、P=0.5・1・2 秒は 12 回とも一致した。

#### 相対 seek と絶対 seek の比較

録画の先頭からの秒をそのまま seek に渡すと、基準が format の start_time になり、映像の開始とずれる。絶対 seek は目標より後ろの keyframe に着く。seek 位置を映像の PTS から start_time を引いた値に換算し、pre-roll とフレーム選別のフィルタを使う前節の方法だけが 0 frame になった。

古い音声 PES の合成入力で、offset 10.36 秒（格子上にない位置）を要求した結果は次のとおりである。誤差は、出力セグメント n の先頭フレームの、期待した入力フレームとの差で、全セグメントで同じ値だった。`-copyts` なし / ありの順に書く。各 1 回の測定で、古い音声 PES は format の start_time が 0 秒、V が 5,400.010022 秒である。

| 入力 | `-ss 10.36`（相対） | `-seek_timestamp 1` の絶対 seek | pre-roll 2 秒 + `select` |
|---|---:|---:|---:|
| 古い音声 PES（出力 15 / 9 / 10 本） | −259 / −259 frame | +41 / +41 frame | 0 frame（`-copyts` あり） |
| PTS wrap（出力 4 / 4 / 5 本） | +41 / +41 frame | +41 / +41 frame | 0 frame（`-copyts` あり） |

古い音声 PES の相対 seek は、`-ss 10.36` が入力の PTS 10.36 秒を指し、映像の開始（5,400 秒）より前なので、映像の先頭フレームに丸められた。先頭の音声 PES だけが古い実録画で、原本 VOD の `-ss` が全部先頭に丸められた事例と同じ形である。`-copyts` の有無では選ばれるフレームは変わらなかった。

絶対 seek は、`-copyts` を付けると start_time が大きい入力で出力が空になった。映像のみ 30 秒（GOP 50、B-frame なし）の合成入力で、`-seek_timestamp 1 -ss <start_time + 10.36>` の出力フレーム数を数えた（FFmpeg 9.0.2、各 1 回）。start_time が 5,400 秒と 50,000 秒の入力は、`-copyts` なしで 450、ありで 0 だった。start_time が 0.04 秒の入力は、なし・ありとも 450 だった。wrap（start_time −13.717689 秒）は、なしで 450、ありで 408 だった。この wrap の 408 は相対の `-ss 10.36` でも同じで、理由は調べていない。

実録画 2 本（start_time は約 43,588 秒と約 5,793 秒）でも、`-copyts` ありの絶対 seek は 0 frame だった。同じ実録画に `-ss 6` を渡すと start_time + 6 秒から出た。FFmpeg の文書にない挙動で理由は説明できていないので、`-seek_timestamp` に頼らない。

#### 製品の seek 引数の測定

製品の seek 引数を採る。クラスタの原本 2 本と放送 TS・合成入力のすべてで、起動位置によらず先頭フレームの誤差が 0 frame だった。

製品の `SegmentManager` は、`-copyts -seek_timestamp 1 -noaccurate_seek` の絶対秒で読む。`trim=start=T` の後、最初のフレームだけを T に置き、残りは元の PTS から T を引く。エンコーダの time base は 90 kHz、`-fps_mode:v passthrough` である。

以前の引数（`setpts=PTS-STARTPTS`、既定のエンコーダ time base）では、同じ番号のセグメントの先頭が起動位置で 1 frame 変わった。29.97 fps では最初のフレームが T の 0〜1 frame 後ろにあり、その差が起動位置で変わる。`-force_key_frames` の格子と、frame rate の time base への丸めが、その差に引きずられた。PTS wrap の原本では、k=51 が 0、k=52・53 が −1 で、同じ n が食い違った。下の表は以前の引数での測定である。

測定のテストは、環境変数で入力を渡したときだけ走る opt-in である。`SegmentManager` で実 FFmpeg 9.0.2 を動かし、出力は QP=0 の無損失で縮小しない。各セグメントの先頭フレームの framehash を、入力の復号 frame 列に照合する。期待 frame は、入力の復号 frame の PTS が V + n·D 以上になる最初のものである。hash が入力内で一意でなければ失敗にする。

基準 frame の PTS は `-enc_time_base:v 1/90000` で 90 kHz にそろえる。付けないと、framehash の PTS は frame rate の time base に丸められる（25 fps の合成入力で `#tb 0: 1/25` を測定）。丸めの端数は最大で 1 frame 分になる。最初の実行では、丸めたまま比較して合成入力の全セグメントが −1 frame になり、そろえると全て 0 になった。クラスタ上の `seek.py` の基準 PTS も同じ丸めを含んでいたので、runner は直した。古い音声 PES の原本は位相の端数が 0 で影響を受けないが、PTS wrap の原本など他の表への影響は測っていない。

各行は、k から 5 本のセグメントを各 1 回ずつ取った結果である。P は製品の既定の 2 秒である。位相 φ は、テストの環境変数で V から tick 数を引いて作る（φ は前節の定義）。

| 入力 | 起動 k | 先頭フレームの誤差 |
|---|---|---|
| 古い音声 PES の合成入力（25 fps、V は約 5,400 秒、start_time 0） | 3 / 5 / 8 | 15 本とも 0 frame |
| PTS wrap の合成入力（25 fps、V は境界の約 10 秒前） | 3 / 5 / 8 | 15 本とも 0 frame |
| 放送 TS A（1440×1080 インターレース MPEG-2、29.97 fps、音声 2 本、約 99 MB）、φ=0 | 3 / 4 / 5 / 6 | 20 本とも 0 frame |
| 同 A、φ=609 | 3 / 4 / 5 / 6 | 20 本とも 0 frame |
| 同 A、φ=1500 | 3 / 4 / 5 / 6 | 17 本が 0 frame、k=5 の n=9 と k=6 の n=9,10 が +1 frame |
| 放送 TS B（同じ形式、音声 1 本、約 98 MB）、φ=0 | 3 / 4 / 5 / 6 | 20 本とも 0 frame |
| 同 B、φ=609 | 3 / 4 / 5 / 6 | 20 本とも 0 frame |
| 同 B、φ=1500 | 3 / 4 / 5 / 6 | 17 本が 0 frame、k=5 の n=9 と k=6 の n=9,10 が +1 frame |

PTS wrap の合成入力では、k=3 の変換が境界をまたぎ、n=5 以降の先頭は境界の後にある。放送 TS の 2 本は、自宅の mirakc が配信中の放送を 50 秒だけ読んだ TS である。録画ではなく、先頭の音声 PES は古くない。mirakc の録画一覧には内容のある録画が無かった。放送 TS では、同じ n を複数の k で取った組（n=6 は k=3〜6 の 4 通りなど）の誤差が、全ての φ で一致した。n は 10 までしか取っておらず、それより大きい n で誤差が増えるかは測っていない。

いまの引数では、許容 0 frame で次のとおりだった。クラスタの原本は、運用中の media PVC を読み取り専用でマウントした測定用の Pod で、FFmpeg 7.1.5 を使って測った。

| 入力 | 起動 k | 先頭フレームの誤差 |
|---|---|---|
| 古い音声 PES の原本 | 3 / 4 / 5 | 18 本とも 0 frame（以前の引数では全て −1） |
| PTS wrap の原本（境界をまたぐ） | 51 / 52 / 53 | 18 本とも 0 frame（以前の引数では k=51 が 0、k=52・53 が −1） |
| 放送 TS A、φ=609 / 1500 | 3 / 5 / 6 | 12 本ずつ全て 0 frame |
| 古い音声 PES の合成入力 | 3 / 5 / 6 | 12 本とも 0 frame |

`trim` を `select` に替えても、原点だけを T に固定しても、相対 seek にしても、以前の食い違いは変わらなかった。食い違いを消したのは、最初のフレームを T に置くことと、90 kHz の time base の 2 つで、どちらか片方を外すと回帰テストが落ちる。

評価したのは映像の先頭フレームだけで、音声は見ていない。

#### 伸びている入力の追従

伸びている入力は、前節の引数に追従と読み待ちの時間切れの指定を足せば、途中から読み続けられる。書き手が生きている間にセグメントが公開され、先頭フレームの誤差は 0、出力 PTS は格子どおりだった。

24 秒の合成入力（古い音声 PES と PTS wrap）を、同じバイト列のまま実時間で書き足して測った。書き手は 188 byte の倍数ずつ、バッファなしで一定の速さで追記する。読み手は書き手の開始 8 秒後に k=2・P=2 秒で起動し、`-follow 1 -rw_timeout 2000000` を付けた。ホストの一時ディレクトリでの測定で、PVC 上の挙動は示さない。

入力ごとに 5 回、計 10 回の結果は同じ傾向だった。出力は n=2〜11 の 10 本で、そのうち 9 本は書き手が生きている間に公開された。最初のセグメントは読み手の起動の 0.08〜0.13 秒後に公開された。全セグメントの先頭フレームの誤差は 0 frame、出力 PTS − n·D は 1.400 秒で、全セグメントのフレーム数の合計は期待どおり 500 だった。読み手は書き手の終了の 1.99〜2.01 秒後に exit 0 で終わった。

#### 録画が終わったときの止め方

入力の読み待ちの時間切れで、FFmpeg が正常終了することは確かめた。ただし、終了コードを録画完了の判定に使えない。SIGINT で止めると、停止は早まらず末尾フレームが欠けた。

[FFmpeg の文書](https://ffmpeg.org/ffmpeg-protocols.html#file)の file プロトコルの `follow` には、終わらせるには `rw_timeout` か割り込みコールバックが要ると書いてある。SIGINT が読み待ちを中断するとは書かれていないので、契約として頼れない。測定でも SIGINT は不利だった。

| 終わらせ方 | 回数 | 終了コード | 書き手の終了から終了まで | 全フレーム数（期待 500） |
|---|---:|---:|---:|---:|
| 時間切れ（rw_timeout 2 秒） | 10 | 0 | 1,993〜2,005 ms | 500（末尾フレームも一致） |
| SIGINT（書き手の終了直後に送る。rw_timeout 10 秒） | 10 | 255 | 9,986〜10,006 ms | 498（末尾 2 フレームが欠けた） |

どちらも古い音声 PES と PTS wrap を各 5 回、前節の引数で測った。SIGINT は待機中の読みを早く終わらせず、実質 `rw_timeout` の時間切れまで待った。しかも出力の末尾 2 フレームを失った。先行の測定（ホストの一時ファイル、4 回）では、書き手の終了直後に送った SIGINT が 60〜9,999 ms と揺れた。

時間切れは、書き手の停止が `rw_timeout` より長いと、録画の途中でも exit 0 で終わる。書き手を実時間の 14〜19 秒の間（5 秒間）止めて `rw_timeout` を 2 秒にした 2 回では、どちらも exit 0 で、出力は 249 frame（期待は 500）で終わった。終了コード 0 は録画の終了を意味しない。

したがって、時間切れを採るなら、`rw_timeout` は書き手が止まる最長の時間より長くし、録画が終わったかどうかは FFmpeg の終了の外で判定する必要がある。書き手が止まる最長の時間には、`--once` の Pod が入れ替わる 4 分 slice の境目が含まれる。下の PVC 測定では `rw_timeout` に 10 秒と 90 秒を試したが、有限回の観測から停止時間の上限は保証できない。

#### 実録画の母集団と時刻の基準

古い音声 PES を持つ原本でも、補正相対 seek にすると、先頭 frame の誤差は ±1 frame に収まった。

実クラスタの測定の runner と集計結果は `scripts/playback-measure/` にある。合成入力の先行測定の runner はリポジトリに無い。

2026-10-26 に、運用中の media PVC にある `.m2ts` 原本を列挙した。対象は 51 本で、全件の `ffprobe` による開始時刻と duration の取得が成功した。MP4 は TS 原本の母集団に含めない。FFmpeg は配備イメージと同じ 7.1.5、実行 UID/GID は 65534 である。

古い音声 PES の原本が 1 本見つかった。最初の video packet の PTS は 8125285560 tick だった。第 2 音声の最初の PTS は 7639495330 tick だった。その音声の次の packet は 8125524130 tick に戻っていた。format の start_time は第 2 音声の古い値になり、映像との差は 5,397.669222 秒だった。

同じ原本で offset 10.36 秒を要求し、次の表を得た。D=2 秒、出力は 320×180 の lossless H.264、各組 420 frame、各 1 回である。入力先頭の 900 frame を同じ縮小処理で framehash にし、出力の各 segment の先頭 frame を照合した。照合対象の hash はすべて入力内で一意だった。

期待 frame は、入力の復号 frame の PTS が `V + offset + n·D` 以上になる最初のものとした。先頭 packet は復号できず、最初の復号 frame は V より 39,648 tick 後だった。packet 数や出力 PTS から frame 番号を推定せず、入力の復号 frame 列で判定した。

| n | 相対 / copyts 無し | 相対 / あり | 絶対 / 無し | 補正相対 + copyts |
|---:|---:|---:|---:|---:|
| 0 | −298 | −298 | +2 | 0 |
| 1 | −298 | −298 | +2 | 0 |
| 2 | −298 | −298 | +2 | 0 |
| 3 | −298 | −298 | +2 | 0 |
| 4 | −298 | −298 | +2 | 0 |
| 5 | −297 | −297 | +3 | +1 |
| 6 | −297 | −297 | +3 | +1 |

値は frame 単位の誤差である。絶対 seek + copyts は 60 秒で打ち切り、復号できる出力 segment は 0 本だった（timeout の exit 124）。合成入力で出力のフレーム数が 0 になった結果とは違い、こちらは timeout で打ち切った結果である。補正相対は前節の式で P=2 秒とし、`select` と `setpts` を使った。この原本の 7 segment は ±1 frame に収まった。

n=5,6 の +1 は、seek の着地ではなく、測定用の出力側の keyframe の位置で決まっていた。この原本の最初の復号 frame は V + 39,648 tick で、39,648 mod 3,003 = 609 である。基準 PTS の丸めは、この位相では端数が 0 なので原因ではない。放送 TS A / B の V から 609 tick を引いて同じ位相にし、同じ式（補正相対 + `select` + `-force_key_frames expr:gte(t,n_forced*2)`）を流した。2 本とも n=0〜4 が 0、n=5,6 が +1 になり、この表と同じ形になった。φ=0 と φ=1500 では全て 0 だった。

`-force_key_frames` の閾値を `n_forced*2-0.034` に下げ、`-hls_time` を 1.9 秒にすると、放送 TS A（φ=609）は n=1〜4 が −1、n=5,6 が 0 になった。誤差は出力側の keyframe の置き方で動く。`-enc_time_base:v 1/90000` を出力に付けても +1 は変わらず、keyframe の式の時刻がどう丸まるかは特定していない。クラスタの原本をこの観点で測り直すことは未実施である。

#### 実録画の PTS wrap

実録画で PTS wrap が見つかった。境界後への seek は、補正相対 seek とフレーム選別で誤差が 0 frame だった。

51 本の映像の開始時刻と duration から、33 bit の境界をまたぐ候補を 4 本得た。候補全件を packet 走査したわけではない。そのうち、映像の開始 PTS が 8,580,400,148 tick の 1 本を `ffprobe -show_packets` で確認した。

`-correct_ts_overflow 0` で先頭から読むと、PTS が 8589931670 から 81 tick に折り返す隣接 packet があった。既定の補正ありでは、境界前後の区間で 449 packet を読み、8589400139〜8590745483 tick だった。以降の V と目標時刻は、FFmpeg が補正した連続時間軸で扱い、要求時刻だけを 33 bit で折り返さない。

この原本の offset 108 秒（境界の後）で同じ比較をした。基準の framehash は先頭 3,900 frame、各組の出力は 420 frame、各 1 回である。入力の hash の一意性も確認した。

| n | 相対 / copyts 無し | 相対 / あり | 絶対 / 無し | 補正相対 + copyts |
|---:|---:|---:|---:|---:|
| 0 | −7 | −7 | +8 | 0 |
| 1 | −7 | −7 | +8 | 0 |
| 2 | −7 | −7 | +8 | 0 |
| 3 | −7 | −7 | +8 | 0 |
| 4 | −7 | −7 | +8 | 0 |
| 5 | −7 | −7 | +8 | 0 |
| 6 | −7 | −7 | +8 | 0 |

絶対 seek + copyts は、こちらも 60 秒の timeout（exit 124）で打ち切り、有効な segment は 0 本だった。補正相対は P=2 秒で、7 segment すべて 0 frame だった。これは境界後への seek の確認で、原本全体の連続変換や音声の継ぎ目を保証しない。

#### PVC の追記の遅れ

別ノードから追記を読めるまでの遅れは、2 回の試行で中央値が約 23 秒、最大が約 55 秒だった。4 分後の書き手の交代でもファイルを引き継げた。

運用中の media PVC そのものを使い、別ノードに書き手と読み手を置いた。StorageClass は `ds420plus-kagawa`、RWX、NFS 4.1 である。両ノードは amd64 で、書き手は read-write、読み手は read-only のマウントを使った。`noac` や `actimeo=0` は指定していない。

280 秒の合成 TS を、188 byte 境界の 31,208 byte ずつ、500 ms 間隔で 560 回追記した。書き手のビットレートは 500 kbit/s で、実放送の 17〜24 Mbps より低い。書き手は ingest と同じ `O_RDWR|O_APPEND` と排他 flock を使い、slice の終わりだけ Sync/Close した。実際の ingest や DB は動かさず、専用ディレクトリのファイルで再現した。

読み手は 20 ms 間隔で path の stat、開いたままの fd の fstat、同じ fd の ReadAt を記録した。遅れは各 Write の完了から、対応する累積サイズを初めて観測した時点までである。fstat の時刻は、その直後の read が返った時刻で近似した。read はサイズの観測だけでなく全バイトを hash に流し、入力と SHA-256 が一致することを確認した。

時計は測定の前後に Pod 間 HTTP を各 30 往復させて校正した。最小 RTT は 5.26 / 5.08 ms、推定時計差は +0.61 / −0.06 ms だった。表の遅れはその平均で補正した観測値で、polling と I/O の所要時間を含む。ミリ秒以下の精度や、時計が途中で step しなかったことは保証しない。

| 観測 | 回数 | 中央値 | 最大 |
|---|---:|---:|---:|
| path stat | 560 | 22.710 秒 | 54.401 秒 |
| persistent fd の fstat | 560 | 23.080 秒 | 54.700 秒 |
| persistent fd の read | 560 | 23.181 秒 | 54.700 秒 |

上の表は、最初の書き手を 4 分動かし、別の準備済み Pod が同じファイルを追記した試行である。準備済み Pod だけでは起動待ちを測れないため、別ファイルで、4 分で終了する Job の完了後に次の Job を作る試行を加えた。実際の Pod 起動を含む。

| 試行 | 最後の Write から次の Write まで（Close から） | 次の slice の最初の追記が見えるまで（stat / read） | read の増分が無い最長区間 | 560 回の遅れの最大（stat / read） |
|---|---|---|---:|---|
| 準備済み Pod | 1.630 秒（1.117 秒） | 10.053 / 10.230 秒 | 51.315 秒 | 54.401 / 54.700 秒 |
| Job 交代 | 5.957 秒（5.438 秒） | 31.602 / 31.910 秒 | 51.385 秒 | 54.028 / 54.337 秒 |

Job 交代の遅れの中央値は、stat が 23.217 秒、read が 23.644 秒だった。全バイトの SHA-256 は一致した。時計校正の最小 RTT は前後で 7.69 / 5.78 ms だった。

この値は 1 つの StorageClass とノード対、書き手 500 kbit/s の観測である。media PVC が読めなかった先行の timeout 記録を、遅れの標本には含めない。NFS の属性 cache が原因という切り分けはしておらず、マウント設定の変更も試していない。

#### PVC 上での FFmpeg の追従と終了

10 秒の読み待ちでは、FFmpeg は録画の途中で空の出力のまま正常終了した。90 秒待つ設定では、途中から末尾までの全フレームが有限ファイル版と一致した。

同じ伸長ファイルを別ノードの FFmpeg 7.1.5 で読んだ。`-follow 1 -rw_timeout 10000000` と途中からの seek を指定した 1 回では、書き手が動いている間に exit 0 になった。出力は 0 byte の TS 1 本と ENDLIST 付き playlist だった。読み手の起動から終了までは 40.736 秒だった。

次に `-rw_timeout 90000000 -skip_estimate_duration_from_pts 1` を指定した。V=129600、k=3、D=2 秒、P=2 秒で、前節の補正相対 seek と `select` を使った。起動は書き手の最初の追記から約 151 秒後で、既存部分を読み終わってから追記を待った。

137 segment が生成され、write 完了前にも segment が公開された。有限ファイル版の入力から framehash を取り、6 秒から末尾までの 6,841 frame が出力とすべて一致した。先頭だけでなく末尾 frame も一致し、入力バイト列の一致とは別に確認した。

n=3 / 5 / 120 / 139 の segment の最初の映像 PTS は、それぞれ 666000 / 1026000 / 21726000 / 25146000 tick だった。`n·D + 1.400 秒` と一致した。FFmpeg は書き手の Close の 98.505 秒後に exit 0 で終了し、ENDLIST が付いた。PVC で追記が見えるまでの遅れもあるため、Close からちょうど 90 秒後に終わるわけではない。

変換中には packet の duration が 0 という警告が出た。全フレームの内容一致は確認したが、音声、字幕、ブラウザ再生はこの測定に含めない。90 秒の指定と duration 推定を省く指定を別々には比較していないため、成功を片方だけの効果とはしない。

#### 未解決の項目

この節の方式を採るために、次が残っている。

- 未検証: NFS の hard mount で read 自体が止まる障害では、`rw_timeout` は効かない可能性がある。`rw_timeout` は、末尾で読み直すループを切るものだからである
- 未検証: SIGSTOP（先読みの停止、キャッシュ満杯での停止）の間の時間が `rw_timeout` に数えられ、SIGCONT の直後に exit 0 になる可能性がある。先読みで止まるのはデータがあるときなので、起きる頻度は低い見込みである
- 未解決: 放送 TS 全般の最大 GOP 長に対する pre-roll の十分性。P=2 秒は比較した実録画の要求位置でのみ確認した
- 未解決: 音声と字幕。映像だけを変換して測ったので、第 2 音声の継ぎ目も測っていない
